# UI 设计与实现交接

先读当前需求和现有界面，再选择设计方法。设计必须支持用户完成真实任务，并能落到项目已有的组件、状态和代码上。

## 选择材料

- **产品界面、后台、桌面应用、现有页面改造：** 读 [产品 UI 工作流](references/product-ui.md)。
- **营销页、下载页、活动页、等待名单：** 读 [完整落地页设计](references/landing-page-guide.md)，保留其需求采集、版式选择、转化文案、逐节构建和完整视觉系统。
- **Figma 文件：** 使用当前宿主提供的 Figma 能力；若已安装，可交给 `dev-figma-design`。本技能不要求安装它，也不以不存在的工具代替实际操作。

完整策略、文案、视觉数值与验收规则均在本技能内。应用顺序如下：

1. 用户明确要求和项目已采用的设计系统优先。本地指南的字体、色板、Tailwind 数值和动效作为新设计的默认方案；记录覆盖理由，不强制迁移框架或整站换肤。
2. 营销页的主 CTA、社会证明、FAQ、tagline reveal 适用于营销目标，不添加到业务表单、设置页或仪表盘中。
3. 本技能独立提供所需规则。缺少外部工具时完成本地设计与交接，准确说明尚未实际编辑的外部文件。
4. 真实产品的价格、客户、评价和统计只用用户资料或可核验来源；缺失就保留标明用途的占位，不能编造。
5. 说明行为和视觉约束，按任务选择合适的实现与验证方法，并依据约束验收。

## 从需求进入

复用当前 `.agents/wtadev/changes/<date-slug>/spec.md` 或项目等价需求文档。读取与当前页面相关的内容即可：用户、要完成的任务、入口、核心动作、数据、例外、完成信号与明确不做的事情。

先查现有路由、组件、样式变量、图标库和相邻页面。能从代码、截图或已有需求得到的答案不要重新问。只澄清会改变信息架构、核心交互或范围的问题；其余采用可撤销的合理假设并标明。

营销页按本地指南 A 部分收集主张、受众、主要行动、流量来源、异议和可用证明。一次补齐必要缺口，不用设计问题阻塞已经明确的实现。

## 形成最小可用的设计规格

通常在当前变更的 `design.md` 中写明：

- 关键使用路径，以及每个页面/区域的作用。
- 复用的组件与 token 的代码位置；确需新增的差异。
- 加载、空、失败、校验、禁用、成功等实际会遇到的状态。
- 键盘、窄屏和文本变长时的行为；项目需要时补充主题模式。
- 可观察的验收点与需要用户提供的真实素材。

需要新文档时可用 [设计记录模板](assets/design.md)，按实际删去无关栏目。小改动可直接写在 spec 的验收段，不为了流程创建文件。持久设计事实尽量引用真实组件和 token 文件，避免维护第二份数值表。

## 构建、检查、交接

先做关键区域或一条完整使用路径，实际渲染后检查，再扩展其他区域。采用逐节迭代的方法，避免每次反馈重建整页。

验收要落到运行结果：适用视口截图、键盘操作、表单错误、长内容、数据状态和真实链接。营销页还检查 CTA、元数据、分享图、footer 链接与 390px 布局。只报告实际检查过的范围；不能把静态代码阅读说成视觉通过。

将必要截图、设计决策与实现入口附到当前变更；共享约定稳定后再把短说明及代码链接写入 `.agents/wtadev/notes/`，已有文档以真实路径引用。交付可继续实现的规格和已经验证的结果，并明确遗留素材或交互缺口。

## 原型探索

布局或逻辑仍不确定、需要比较方案时，读[原型方法](references/prototype.md)，按问题选择完整的 UI 或逻辑分支。原型回答一个具体问题，不自动变成生产交付。
