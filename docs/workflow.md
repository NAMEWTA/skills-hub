# 开发流程与衔接

## 目标

从任意来源的需求出发，把目标、规格、垂直切片、实现、UI、审查、部署与知识沉淀连起来。每一步有自己的用途与输出，但不建立必须逐关通过的状态机。

先决定要交付的行为及边界，再选择适合的开发与验证方法。规格可以是一段话，不等于长 PRD。行为契约稳定时可以采用 TDD 的红、绿、重构短循环；探索性任务可以先做可丢弃原型；状态与并发风险高时结合状态图和形式化分析。无论采用哪一种，都核实最终代码、实际制品与真实运行结果。

## 日常入口与完整方法

第一次使用可运行 `dev-setup`，记录真实可用的模型角色、工具和长任务偏好；已经配置好的环境直接沿用。跨阶段任务用 `dev-workflow` 加目标和验收；已有明确阶段时直接选择对应入口，例如已有规格实施用 `dev-build`。`dev-help` 包含完整本地指南、场景配方和能力选择，独立安装也能查阅。

总入口携带 23 个完整流程，包括调查、缺陷、性能优化、单指标迭代、运行与轨迹取证、新功能、重构、原型、视觉对齐、技能编写、盲测评估、PR 跟进、验证落地、自主运行、跨日协调、独立 PR 队列、堆叠 PR 队列、任务接手、安全暂停、多阶段计划、工作树清理和创建 PR。采用哪一条取决于用户目标，步骤与原则按需读入；没有复杂状态引擎或准入网关。

24 条完整工程原则、委派角色和注释审查方法随相关技能保存。角色含义来自任务职责；多模型仅在工具确实支持时使用，没有并行能力就如实串行，不伪造独立复核。

## 一次需求怎样推进

| 阶段 | 消除的不确定性 | 最小有用产物 |
| --- | --- | --- |
| Intake | 多个来源究竟要求改变什么 | 有来源的目标、当前事实、范围与非目标 |
| Grill | 哪些产品决定仍不清楚 | 已解决决定与真正剩余的问题 |
| Spec | 什么行为才算正确 | 可观察验收、边界和实施约束 |
| Architecture / UI | 什么结构或体验支持这些行为 | 必要的取舍、接口/所有权、交互与设计约束 |
| Plan | 怎样逐步交付而非横向铺半成品 | 垂直切片、真实依赖、验收与负责人 |
| Build / Debug | 实际实现能否满足行为 | 可运行改动、根因修复与当前版本证据 |
| Review | 是否符合规格且工程上可维护 | 有证据的缺陷、修复结果或残余风险 |
| Deploy | 指定环境是否真正运行此版本 | 当前制品、实际入口、业务验证与发布记录 |
| Archive | 哪些认识能帮助下一次开发 | 更新后的少量长期知识与干净的历史记录 |

`dev-workflow` 选择需要的阶段。只安装 `dev-build` 也能按已有规格实施；其他技能的名字是可选协作提示。工具缺失时按实际能力完成可做部分并说明缺口，不伪装调用成功。

## 按问题组合小技能

| 需要解决的问题 | 可以插入的能力 | 与主流程的衔接 |
| --- | --- | --- |
| 工作进行中需要快速知道目前发生了什么 | `dev-status` | 对照最新代码和执行记录给简报；回答状态问题后继续原目标，除非用户明确暂停 |
| 多次重复工作希望形成自己的稳定方法 | `dev-personalize` | 只分析允许访问的历史，把真正重复的偏好写入项目技能，不把一次纠正提升为普遍规则 |
| 要求或方案有表达、假设和深度上的缺口 | `dev-sharpen` | 澄清前或架构审查时使用；改写请求本身不等于启动开发 |
| 不理解过去为何这样设计 | `dev-why` | 在学习、重构和删改历史约束前查找理由，并区分证据和推断 |
| 多项工作真正独立，或需要比较不同实现 | `dev-parallel` | 先明确范围、评分与隔离方式，再集成；没有并行工具就如实串行 |
| 用户指定测试先行，或当前实现已选择 TDD | `dev-tdd` | 每个垂直切片内逐个红、绿、重构；已有正确行为补测试不自动进入实现循环 |
| 已有或明确需要 TLA+ 模型，要展示检查结果 | `dev-statechart` | 运行 TLC，生成规则标记和最短反例，回到代码重放；普通讲解图由当前学习或设计任务直接完成 |
| 关键不变量、并发或恢复属性值得更严格分析 | `dev-formal-verify` | 从明确属性建模，检查反例，回到真实实现验证，并持续防止模型漂移 |
| 已知错误反复出现，单靠提醒不足 | `dev-guardrails` | 修复后选择准确的类型、接口、lint 或构建约束；归档记录理由与例外 |
| 需要证明真实入口和副作用可用 | `dev-verify` | 实施、审查与发布时驱动真实对象，必要时建立项目专用验证方法 |
| 优化需要量化比较，或要判断指标是否可信 | `dev-benchmark` | 固定负载、版本和测量条件，运行比较；预算取自本项目目标 |
| 需要让文档、PR 与交接表达准确易读 | `dev-writing` | 根据读者任务选择文档类型，解释行为、取舍和证据，减少空泛措辞 |

结构约束、经验验证与形式化分析互相补充。模型检查覆盖的是声明的模型与属性，定理证明也受所证明命题和前提限制，有界检查则受边界限制；任何一种都不能替人判断规范是否表达了正确需求。需要明确写出实际执行了什么、未检查什么，并把反例和结论映射回真实代码。

这些能力产生的项目资料统一以 `.agents/wtadev/` 为根目录。模型和可重复验证代码放在项目现有源码或验证位置；本次图、轨迹、测量与检查记录放在 `.agents/wtadev/changes/<日期-主题>/`；只有仍影响未来决策的假设、约束、术语和错误模式进入 `.agents/wtadev/notes/`。部署资料进入 `deploy/`，历史过程进入 `archive/`，项目配置进入 `project/`。不会为此引入 Agent 工作流状态引擎。

## Issue 自动化怎样接入

普通 Issue、聊天或日志是输入来源，由 `dev-intake` 整理，功能缺陷交 `dev-debug`，性能目标交 `dev-benchmark`。

`dev-issue-setup` 将报告来源、问题追踪器、仓库路由、可信身份、UI 控制与触发器分别配置；聊天、工单、邮件、监控告警与手工材料按实际可用适配器接入；没有后台能力时交付真实可用的手动方法或配置，不把文件写好说成自动化已启用。`dev-issue-triage` 读取已有证据、追踪原因、去重和分流，不在该阶段复现或修复。`dev-issue-fix` 在可信分诊和控制条件齐备后查已有修复，按本次目标仅复现、仅验证已有补丁，或执行授权内修复并以同路径证据交付草稿 PR。

可信标记是任务路由依据，不是给 Issue 正文提升权限。发消息、创建平台自动化、发布或合并都遵守本次已经明确的目标与范围；已经授权的动作无需重复确认。证据、失败重试和交接沿用 change 目录，长期有效的配置理由进入 notes，环境运行方法进入 deploy。

## 相似请求怎样区分

| 请求中的主要目标 | 主入口 |
| --- | --- |
| 按已有规格实施 | `dev-build` |
| 从想法持续推进到上线，或恢复阶段不明的任务 | `dev-workflow` |
| 深化待执行请求与验收证据 | `dev-sharpen` |
| 查当前机制并讲清楚 | `dev-learn` |
| 独立查当时的设计理由 | `dev-why` |
| 复述理解中的目标 / 把上一条解释讲通俗 | `dev-intake` / `dev-learn` |
| 功能不正确 / 性能指标需要改善 | `dev-debug` / `dev-benchmark` |
| 项目知识收尾 / 个人方式 / 结构防错 | `dev-archive` / `dev-personalize` / `dev-guardrails` |
| 进展简报或报告视频 / 构建可操作的状态应用 | `dev-status` / `dev-build` |
| 普通流程图 / TLA+ 结果图 / 属性检查与模型维护 | 当前学习或设计任务 / `dev-statechart` / `dev-formal-verify` |

完整任务复用同一规格、基线和记录。通用决策审计由 workflow 的决策证据方法负责，性能技能只负责其测量范围。UI 的设计系统、语义 token 与组件规范统一在 `dev-ui-design`，无需 Figma。

## 一个贯通示例

用户说：“账户页面增加邀请成员，参考这张截图，上线到预发。”

**接收。** 将聊天、截图与可能的 Issue 记录为同一需求来源。查看当前“账户”的代码概念和界面：它可能是个人账号，也可能是组织租户。不能仅因中文近似就把两个模型合并。

**澄清。** 从代码回答已有角色、邀请接口和存储位置。向用户询问无法从代码决定的产品规则，例如是否允许无账号邮箱接收邀请、哪个角色可邀请；如果早已决定则直接沿用。

**规格。** 写清发起邀请、接收邀请、重复/过期/权限不足的行为与成功条件。需求目标与当前代码分开表述。UI 补充空态、加载、错误、成功反馈、键盘操作和窄屏行为。不会因为参考源偏营销页就给后台强加 Hero 与 CTA。

**架构与切片。** 确认身份与组织归属边界，优先复用现有能力。第一片跑通一个合法邀请的完整链路；后续增加幂等、防滥用、状态展示等独立可验收场景。不能把“先写所有表，再写全部接口，最后做全部页面”当作垂直切片。

**实施和审查。** 按契约和风险选择测试先行、实现后验证或二者结合，并验证完整场景。审查一条线看规格是否完整实现，另一条线看接口、状态所有权、错误处理和复杂度。缺陷根据真实证据修复；不用修改规格来隐藏未满足的要求。

**部署。** 核对预发目标、精确制品、环境配置及数据迁移。执行后从实际入口验证邀请流程，记录实际版本。生产未授权就不发布生产；用户明确授权预发后不再重复询问每个可逆准备步骤。

**归档。** “账户”在本项目中确实指组织租户的，写入带范围和代码引用的 glossary；若与个人账号不同，显式保留边界。邀请状态持久化的取舍若会影响未来开发，写 ADR。一次临时重试留在发布记录，只有可能复发的原因才进入 errors。核对并修正旧导读中已移动的文件引用。

## 不同规模和来源

- **两行文案修正**：简短规格、修改、实际界面检查；不强制架构文档、分片和 ADR。
- **已有完整 Issue/spec**：核实版本和当前实现，直接进入计划或实施；不重新采访已解决的问题。
- **陌生项目二次开发**：先沿用户目标运行 `dev-learn`，建立相关垂直链路，再做变化；不默认通读全仓。
- **行为保持型重构**：记录需保持的不变量，必要时按调用链分波迁移；大范围机械替换可用脚本，不强求每片新增用户功能。
- **生产缺陷**：先定位和控制影响，在授权内修复或恢复；补齐可复用错误经验，不把紧急工作变成表单流程。
- **仅设计或调研**：以可评估的设计或有证据的解释为终点，不擅自部署。

## 中断、并行和变更

长期任务在 `.agents/wtadev/changes/<日期-主题>/` 保留规格、最新进展、当前分支/制品、证据与下一步。恢复时重新核对代码和用户最新指令；旧进度不是当前事实。

只在真正独立的文件或研究范围上并行，分配所有权并由主代理集成。不要并发写同一全局索引。子代理报告不是验收本身，集成后的制品仍需验证。

新增要求如果修正既有意图，就更新对应规格并找出受影响切片；如果是独立后续任务，单独记录来源和范围。保留被替代决定的理由，不积累互相矛盾的多个“最终版”。

需求来源与监控初始化的完整边界见[报告来源与监控配置](issue-sources.md)。`dev-setup` 负责宿主与模型角色，`dev-issue-setup` 负责来源接入和实际触发；文件配置完成不等于监控已经启用。
