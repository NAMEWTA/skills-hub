# 知识、记忆与归档

## 项目记忆保存什么

这套机制使用可版本管理的 Markdown 和代码引用。它不要求向量数据库、专用记忆服务、JSON 状态文件或复杂 schema。未来增加检索索引时，索引应能从这些资料重新构建，不成为新的事实来源。

有价值的记忆是下一次接手时不容易仅从代码恢复、却会影响决定的内容：业务术语、用户真实意图、约束的来源、架构取舍、反例、错误经验和模块入口。函数实现、完整文件清单、一次性聊天过程通常不值得重复保存。

## 资料分区

按技能领域存放项目资料：开发领域在 `.agents/dev/`，系统维护领域在 `.agents/system/`，以后新增领域按 `.agents/<domain>/` 扩展。以下路径均相对于目标项目根目录。技能安装与配套许可分别位于 `.agents/skills/` 和 `.agents/skills-hub-licenses/`。项目根目录的 `AGENTS.md` 继续作为宿主可发现的导航入口，分别指向各领域的真实知识位置。

| 类型 | 位置 | 更新方式 |
| --- | --- | --- |
| 当前任务 | `.agents/dev/changes/<日期-主题>/` | 随任务更新实际进展，完成后归档 |
| 简短入口 | `AGENTS.md`、`.agents/dev/notes/index.md` | 指向有关主题和条件，不复制全部知识 |
| 术语 | `.agents/dev/notes/glossary.md` | 核实同义词、边界、关系及代码映射 |
| 背景 | `.agents/dev/notes/context/` | 记录非显而易见的约束与由来，事实变化时更新 |
| 决策 | `.agents/dev/notes/decisions/` | 保留为什么、替代方案和后果；真正反转时建后继 |
| 错误经验 | `.agents/dev/notes/errors/` | 保留复发识别、根因证据、修复与恢复条件 |
| 学习导读 | `.agents/dev/notes/learning/` | 指出完整用例、入口、边界和二次开发位置 |
| 部署现状 | `.agents/dev/deploy/<环境>/runbook.md` | 核对当前实际环境后更新 |
| 历史发布 | `.agents/dev/deploy/<环境>/releases/` | 保存当时事实，不能当当前环境说明 |
| 历史归档 | `.agents/dev/archive/changes/`、`.agents/dev/archive/notes/` | 明确历史用途，修复迁移造成的引用 |
| 项目配置 | `.agents/dev/project/` | 保存项目专用的非秘密配置、自动化功能图和分流规则 |
| 角色配置 | `.agents/dev/context/model-roles.md` | 按当前可用工具、模型和用户选择更新 |
| 系统维护 | `.agents/system/<主机标识>/` | 记录对应主机的实际操作与验证，秘密只留安全引用 |

只有出现真实内容才建对应目录。已有 `docs/adr`、`docs/architecture` 或运维手册时，在 `.agents/dev/notes/` 的有关主题或入口记录其真实路径，引用有效内容；不复制一套重复正文。用户明确指定其他资料位置时遵循该要求，并在导航中记录。

从旧结构 `.agents/wtadev/` 迁移时，将其中 `system/<主机标识>/` 迁入 `.agents/system/<主机标识>/`，其余开发领域的 changes、notes、deploy、archive、project、context 分别迁入 `.agents/dev/`。按相同职责保留子目录和原文，逐项处理目标位置冲突，并修复 `AGENTS.md`、主题索引、文档入链及代码引用。后续写入对应领域根目录，不同时维护两份现行资料。具体安全迁移顺序见[领域持久化与迁移](persistence-roots.md)。技能安装器只更新技能包，不自动搬动使用者项目中的记录。

## 证据优先级不等于“代码永远正确”

当前源码、配置和运行结果证明**系统现在是什么**。用户明确决定和有效规格说明**系统应当变成什么**。发现不一致时分辨是实现缺陷、文档过期还是目标已变化，不能用旧实现否定新需求。

运行事实带上环境、版本和时间；一个本地函数存在不证明生产已部署。长期文档中的引用尽量使用相对路径、关键符号、调用入口和适用范围。必要时保留核对提交来复现当时判断。行号可辅助定位，但不是稳定语义标识。

“最近核对”只在实际检查后更新。未读到代码或拿不到环境时标注待核验，不把日期刷新当成知识变新。

## 轻量术语关系

术语表是给人和 Agent 共用的导航，不要求本体语言或图数据库。例如在一个假设项目中：

| 项 | 示例说明 |
| --- | --- |
| 规范名 | 用户账号 |
| 用户叫法 | 用户账户、账号；仅在个人身份语境下等价 |
| 代码映射 | `UserAccount` 类型、账号创建服务和身份存储入口 |
| 不等价概念 | `Credential` 是登录凭据；`Organization` 是组织；不能合并 |
| 关系 | 账号拥有凭据；账号通过成员关系加入组织 |
| 证据与核对 | 实际项目路径、符号、有效需求及核对版本 |

这些代码名字只是示例，实际使用必须换成已读到的真实符号。先确认语义，再统一词汇；发现同一个词在不同领域含义不同，就记录作用域，不强行选一个全局含义。

## 每次归档做什么

1. 核对需求实际交付结果、最新代码与部署记录。区分已实现、已验证、已上线和未完成，不能把关闭文件夹当作完成。
2. 从本次工作挑出会影响以后决定的知识，找到已有的主题所有者。已有知识就更新，不再创建同义副本。
3. 逐项处理事实过期、真实决定反转、完整替代和部分替代。修复过期路径；决定反转建立带关系的新记录；部分替代保留仍生效的约束。
4. 完整合并前保留旧记录中独有的动机、替代方案、代价、负面保证、未覆盖风险与重新引入条件。不能只说“Git 有历史”就删掉仍重要的理由。
5. 移动或删除后检查所有入链、常用入口、术语映射和导读；更新当前文档指向现行主题，历史引用注明历史用途。
6. 把已结束的过程资料归档；把最新的代码导航、决策与经验留在当前知识里。简要报告保留、合并、更新、归档或删除了什么及原因。

归档依据是**未来决策价值**。内容旧、文件长、数量多都不是单独的删除理由。小 UI 调整和机械日志通常可删除或留在工作历史；短短一段安全边界也可能必须长期保留。

## 为什么不像复杂状态系统

目录表达职责，Markdown 表达事实和理由，Git 表达版本变化。没有任务编译器、准入网关、固定 lifecycle 枚举、哈希封印或必须按顺序生成的一组 JSON。

现行事实跟着代码变化，重要决定保留取舍，完整与部分替代分开判断。知识按需要自然增长，不要求双语三件套或机械门禁。`index.md` 只是少量常用入口，不是所有文件都要登记的全局索引。

## 学习与记忆形成循环

`dev-learn` 选择一个真实用例，贯通入口、处理、数据/状态、返回结果、失败和恢复。导读解释业务意图、边界和修改入口，详细实现直接引用源码。无法从代码证明的设计动机明确标为推断，不替历史作者编理由。

后续需求使用这些导航快速定位；实现改变边界或文件时同步更新；交付后 `dev-archive` 整理新经验并清理冲突。这样积累的是更准确的项目理解，而不是越来越长的上下文。

## 凭据

部署资料保存账号用途、配置键与秘密的真实保管位置。密码、token、私钥或含认证信息的连接串不进入普通项目知识。安全存储使用项目已有密钥系统或受限未跟踪配置，不能凭空写一个 URI 就声称已保管。
