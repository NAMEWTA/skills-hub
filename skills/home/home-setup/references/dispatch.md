# 派遣方式与 Home team

## 初始化与后续维护

1. 显式建立 Home 或补初始化时，读取现有偏好和被引用的方式、team。独立确定一个默认派遣方式和一个默认 team。有效的旧选择优先保留，除非用户明确切换。仅安装、普通登记、查询或执行一次任务不隐式初始化。
2. 用户说「初始化时用某方式派遣」等同指定该方式为默认。只登记若干可选方式、未选默认且无有效旧默认时，确认当前会话是否公开可用于交付项目任务的原生 Agent 派遣能力。可确认时创建 `context/dispatch/native.md`，使用模板的「当前宿主原生」类型。文件保存随当前宿主解析的规则；每次执行重新确认入口。无法确认或存在互不等价的原生方式且无明确选择时，报告缺项，询问一种实际方式，保留已完成的登记和 team。初始化不启动 Agent，不通过搜索 PATH 选择其他工具。
3. 有适用的现有默认 team 或明确选择时直接引用。首次未指定则建立 `context/team/default.md`，只配置一个项目负责人角色，各 CLI、模型和推理覆盖留空，由实际派遣能力选定的执行入口使用自身默认。遇同名的非等价用户文档时选一个未占用的稳定名称，保留原文。初始化角色不等于派发任务或创建固定并发数量。
4. 新增方式或 team 时使用独立、可辨认的单段名称，复用已存在的权威文件。默认位置用小写字母、数字和连字符，检查同名、大小写冲突及实际路径；拒绝父目录跳转、链接和目标目录逃逸。替换当前默认时先确认新链接可读。移除某项前检查默认、方式与 team 的关联和当前任务引用；优先给当前有效偏好改用用户选定的目标，历史引用保留真实身份。
5. 旧配置中已有明确默认派遣约定时，把它原地规范为独立方式或在方式文件中引用其既有规则，保持原来的 CLI、角色、模型和推理意图。旧默认 team 仍指向原 team。移到独立方式时将原 team 的派遣定义替换为指针，避免重复维护；如用户在已有有效根指令维护对应选择，保留该唯一权威并引用。只迁移本次实际选用或已要求保存的内容，不扫描旧文件并合并偏好。对失效、歧义或冲突的显式默认先核实，不当作从未设置。
6. `context/preferences.md` 用「默认派遣方式」「默认 Home team」两个小节各保存一条相对链接。「按派遣方式选 team」只列用户明确保存的关联，每个方式一个指针。写入前读基线，先保存并核对目标文档，再合并偏好，最后回读路径、唯一性和范围。安装更新、查询和临时覆盖都不改偏好。

## 选择与核验

1. 先选方式：本次明确指定 → Home 默认派遣方式。未迁移的旧 Home 在没有独立默认时，沿用仍适用的旧明确派遣约定；缺项时提示补初始化或只指定本次方式。
2. 再选 team：本次明确指定 → 已选方式关联的 team → Home 默认 team。多个 team 不合并。旧 Home 只有一次性派遣方式时，沿适用的旧团队约定和实际工具默认；普通任务不新建默认配置。
3. 在选定 team 中，按精确 repo ID 匹配「项目执行者覆盖」。每个项目只允许一条覆盖；只有有值的单元格覆盖项目负责人角色既有设置。然后应用本次关于该项目的 CLI、模型和推理要求。未指定的字段省略工具覆盖，模型与推理分别按真实接口核对，不能把示例名字或 `auto` 拼成实参。原生派遣方式和 team 指定的 CLI 不兼容时报告差异，由用户决定替代方式或 team；记录曾使用的组合不自动授权回退。
4. 用户说「记住使用方式 X 默认用 team Y」时更新偏好关联，两个文档保持独立。用户说「以后派 A 用某 CLI 或模型」时只更新指定 team 的 A 行，未点名时更新 Home 默认 team；若未建立默认 team，交初始化处理真实缺项。用户只说这一次时沿用现行偏好。核对 repo ID 用登记或 `home-route`，不按相似名称推断。

这些选择对应 Home 到目标项目的直接派遣。项目负责人进入实际 checkout 后，后续执行与派遣取决于项目当地有效规则。选择和兼容性以本次会话能力、已选入口的实际参数和绑定结果为准；保存选项不代表执行过或模型已生效。
