# 功能开发

**负责人统筹设计、规划、审查与验证。** 适合分工时委派实现；单人或能力受限时自行实现，并在完成后独立核对规格和证据。

1. 阅读受影响子系统，追踪真实入口、数据流、状态所有权、外部依赖与输出。
2. 针对有重要取舍的部分探索结构不同的设计，记录选择理由；简单改动使用已清楚的结构。
3. 按下列四个维度安排分工；不适用的维度可以省略或写明原因，无需固定任务状态：
   - **阻塞性前置步骤。** 在扇出之前完成门禁。
   - **独立工作流。** 不重叠的文件、服务或层可以并行；共享写入必须串行。
   - **共享可变状态。** 默认拆分目标，避免多个写入者覆盖同一事实。只有真实不变量要求时才串行。
   - **最小安全拆分。** 如果一个执行者最好，说明原因。
4. 有可用子智能体且范围可隔离时委派代码编写，提供明确范围：文件路径、命名的数据形态及组织结构、规格与成功标准。在写逻辑前确定恰当的数据表达：真实状态转换可集中表示，重复分支可用表或注册表，重复形状假设可用类型化领域模型；只采用问题实际需要的结构。如果实现存在多种有效形态，例如错误处理、抽象层或验证结构，先形成候选，再独立核对各自得失。不能再派生的执行者直接负责差异，并把实现与审查分开，不等待不存在的嵌套能力。注释解释非显然意图与不变量，避免复述代码。做精准修改；对既有代码重新核对当前内容后再改。共享原语的改进覆盖全部消费者，并逐一验证。按已有授权在可验证边界提交。
5. 在匹配的界面上验证。“无结论”或在错误界面验证都不算通过，必须指出。
6. 变基为有序的小提交。后续改动堆叠进行。
   每个单元按已选开发方式建立行为证据并完成实现，检查实际结果；有提交授权时保存有意义的检查点。
7. 设计有争议时，交付前从反例、调用者负担、数据边界和失败路径审查选择。
8. 按用户要求交付本地结果、提交或 PR。PR 正文包含问题、变更、行为证据与风险；未获发布授权时保留本地交付，不自动外发。

代码耦合工作（一个功能、一次迁移）交给单一负责人，检查点直接放在其任务中。负责人在阻塞阶段结束后自行扇出。父级扇出用于产出独立成果的切片（审计、跨子系统调查、竞争性实验）。在阶段边界重写检查点。创建新的负责人，不要串联中断。

**回复：** 构建了什么、选择了什么及原因、吞吐检查点、开放决策。设计替代方案用表格。

按行为规格选择开发顺序；契约明确时可用 TDD 的红、绿、重构短循环，探索性部分可先做原型，最终验证完整功能与边界。
