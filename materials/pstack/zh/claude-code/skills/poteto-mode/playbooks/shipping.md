### 交付

**你负责落地内容。逐个独立验证 PR，只落地从根部连续验证通过的部分，随后别碰堆叠。**

1. **确定托管工具，落地前逐个独立验证 PR。** 默认 GitHub CLI（`gh`）。若 `command -v origin` 成功且 Origin 能解析仓库，所有 PR 操作用 `origin pr`。否则继续 `gh` 并记录回退。永远不要求 Graphite（`gt`）。每 PR 一位验证者，均为 Cursor 云智能体，用匹配控制技能，例如 `cursor-team-kit` 的 `control-ui` 或 `control-cli`，按用户方式运行改动，对照父项与头提交，在 PR 报告 `PASS`、`PASS+NOTES`、`FAIL`。只有未写代码的智能体裁决才算，因为作者检查的是自己想构建什么。绿色 CI 和机器人批准都不是裁决，因为两者都没按用户方式运行改动。
2. **只落地从底部开始连续验证通过的部分。** 从最低未合并 PR 向上走，到第一个没有 `PASS` 或 `PASS+NOTES` 的停止。它下方就是本轮范围，最高项是上限。已验证 PR 若位于未验证项之上必须等，因为无法不带下方代码落地。某分支既不包含也不需要下方代码时，可以移到主干独立落地，但先要新裁决，因为旧裁决运行时下方有那些代码，主干却没有。
3. **再次检查裁决仍描述当前代码。** 裁决覆盖补丁，链式变基会让上方每个 PR 变成新 SHA，而不让任何检查失败。信任旧裁决前，比较裁决 SHA 与当前头的 `git patch-id`。补丁只在测试、文档、lint 配置上有差异时，如果通道运行的内容在两 SHA 构建相同、只差噪声，其结果可延续。噪声指裁决 SHA 自己两次构建也出现的差异，或嵌入的提交 SHA。报告每种噪声和文件，让读者能检查判断。变化本身仍需新检查和审查，因为旧裁决没看过。没有构建产物的通道，如开发服务器，无法证明这一点，应重跑；其他漂移也重新验证。
4. **自下而上，一次一个 PR。** 始终合并本轮最低未合并项，用 `origin pr merge <pr>` 或 `gh pr merge <pr> --squash`。Origin 普通命令也会合并所指定 PR 下面全部项；GitHub 中基础仍是父分支的 PR 会合入父分支，而非主干。回读结果，使用 `origin pr view <pr>` 或 `gh pr view <pr> --json state,mergedAt,baseRefName`，因为命令可能只进入合并队列却报告成功，申请自动合并也不算合并。真正落地 PR 显示已合并，基础是主干而非父分支。只有裁决覆盖当前头时才启用 `--auto`，因为它会落地任何就绪的头。一次合并落地后，把原来以该已合并分支为基础的 PR 改为主干，使用 `origin pr edit <pr> --base <trunk>` 或 `gh pr edit <pr> --base <trunk>`；把其补丁移到合并结果，使用 `--force-with-lease` 推送。裁决覆盖补丁，不覆盖提交，第 3 步 patch-id 规则决定裁决是否存活。检查通过且裁决存活后合并。
5. **落地期间别动堆叠。** 第 4 步移动下一 PR 是唯一允许的分支或基础变更，因为合并会落地当时分支与基础上的任何内容，不论是否有裁决。GitHub 上在 `/loop` 下用 `playbooks/babysit.md` 的队列观察器（`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>`）观察，直到上限报告 `COMPLETE`。Origin 上每次 `origin pr checks <pr> --watch` 返回后，用 `origin pr view <pr> --checks` 重读当前 PR，直到上限显示已合并。父项合并后基础移至主干是预期，不是要修的损坏。合并停滞时，修改前先查原因。
6. **到上限停止。** 扩展范围需要新裁决，因此要新一轮从第 1 步开始。

**回复：** 已验证范围与上限，每个 PR 裁决及给出者，落地内容和确认方式，以及下一缺口需要什么。
