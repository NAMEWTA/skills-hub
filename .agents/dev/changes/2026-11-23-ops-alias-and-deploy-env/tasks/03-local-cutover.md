# 03 在现有 ops 工作根完成一次本地切换

规格：让现有 `D:/Document/code/ops` 同时采用新主机别名规则和 DBX 本地凭据规则，不触发真实部署。当前存在 `.agents/ops/registry/thillers.md`、`.agents/ops/projects/dbx/deployment.md` 和 `.agents/ops/projects/dbx/env.md`。文件名搜索确认 DBX 的部署文档与一份旧 run 汇总引用 `thillers.md`。该工作根目前不是 Git 仓库。

交付：主机的唯一现行登记是 `registry/01.md`。DBX 部署文档引用新登记并说明下一次已授权部署将登录资料写到现有 `env.md`。旧 run 保留原事实，`env.md` 不因升级被覆盖。

直接依赖：[01](01-registry-alias.md) 的按名登记、解析和安全替换规则；[02](02-deploy-env.md) 的项目显式选用和部署写入规则。两个产物在隔离根可用后才执行同一工作根切换，避免 DBX 部署说明与实际安装规则不一致。

边界：一位实施负责人串行更新项目部署说明和 registry；不同时改动现场主机或服务。仅在进入已授权实施后写真实工作根。本地切换不包含 Git 提交、推送、npm 发布或触发真实 DBX 部署。

## 实施要点

1. 在隔离工作根先按包的真实入口验证组合场景。检查 `D:/Document/code/ops` 的现行入口、`01.md` 目标是否空闲及 `thillers.md` 的引用。使用源码安装器按需预览更新已安装 ops 包；保留业务文件和原有技能选择。不为采用此规则在 ops 工作根安装整个 dev 领域。DBX 当前项目部署入口如果不使用 `dev-deploy`，就在其实际 `deployment.md` 写明同一契约，由现有部署流程调用，而不是新建发布器。
2. 保留原主机登记的稳定 ID 和已核验事实，直接将 `thillers.md` 重命名为 `01.md`，修复 `deployment.md` 及其他仍使用旧路径的现行资料。若 `01.md` 已被另一资源占用或旧登记身份不能唯一确认，则不强行覆盖。旧 run 仍保留当时使用的身份和路径，查询按当时的稳定资源 ID，不批量改写历史，也不保留旧别名映射文件。
3. 在 `deployment.md` 指定 `env.md` 是 DBX 的登录资料写入位置。原样保留现有 `env.md`，不在迁移时读取凭据值作为取证、不重置任何账号、不追填未知值。下一次获授权的 DBX 部署再按实际环境和账号更新该文件。
4. 重开任务上下文验证 `01` 和 DBX 文档的路径可解析，比较安装前后 `env.md` 是否保持不变，报告结果但不输出文件值。若迁移写入失败，恢复原文件名及本次改动的现行链接；若技能升级导致问题，使用安装器备份恢复选中的技能及相关托管导航。不要因路径迁移失败触发部署或连接。

## 验收

- [x] 隔离根的整合场景从新会话查询 `01`，再由 DBX 部署入口使用同一已核验目标。用假值演练部署同步，只有指定项目的 `env.md` 含这些值；记录和发布材料可回查结果但不含值。
- [x] 在真实工作根仅做本地核对：`01.md` 存在、`thillers.md` 不再是现行登记、`deployment.md` 两条路径都有效、真实 `env.md` 字节不变，旧 run 身份快照不变。没有部署、远端登录或凭据输出。
