### 多阶段或多 PR 计划

**你负责计划，不负责代码。计划是一份由负责人逐项执行、操作人按证据审计的检查清单。** 计划就是交付物。不要实现。

1. 如果改动只有一两个文件，方案也很明显，则跳过计划。说明这一点并停止。
2. 写计划前，按 `playbooks/prototype.md` 用原型解决未定问题。只有无法通过运行作出判断的产品或偏好决定，才询问操作者。
3. 编写计划文件。开头说明将发生什么变化、按合入顺序排列的 PR ID，以及依赖图；依赖图应说明哪些 PR 独立且从 trunk 分支、哪些等待哪些，以及各自可以修改的文件。之后每个 PR 一节。一个 PR 对应一项改动，并有自己的证据（参见 **sequence-verifiable-units** 原则技能）。每节用复选框列出依赖、编辑的文件、构建的单项改动、可见结果和验证。
4. 仅有测试不足以构成验证。只有 unit、live 和 perf 三类复选框全部勾选，PR 才算完成验证。每项 live 检查都要以具体场景和通过条件操作真实界面或入口。perf 检查写明指标、探针、首先测量的 trunk 基线，以及判定失败的数字。改变交互的 PR 在合并前等待操作者审阅。
5. 交回计划路径并停止。只有操作者明确发出开始指令后，才执行计划。

**回复：** 计划路径、PR ID 及其依赖关系和需要审阅才能合入的集合，以及仍未得到证明的部分。
