# 维护已有运行环境

交付明确对象、实际动作、影响范围、维护结果和消费者验证。维护对象从服务器与共享资源出发，不能只看到发起请求的一个项目。

## 确定范围

读取实际运维工作根 .agents/ops/AGENTS.md 与相关维护手册，沿用当前 run。需要补身份、同机服务或共享消费者时调用 ops-inventory；检查现状时调用 ops-inspect。

按[维护方法](references/maintenance-method.md)核对实际动作、已有授权、维护窗口、冗余、冲突和恢复条件。授权范围内持续完成，不把每步变成新审批；实质目标或影响扩大时先完成可做准备，再说明缺口。

## 选择维护方法

- OS/内核维护、主机重启：读[主机维护](references/host-maintenance.md)，审查实际包集合及所有已知运行对象。
- 证书、日志、备份和容量：读[现有服务维护](references/service-maintenance.md)，限定具体对象和既有运行契约。
- 急需恢复故障服务：交 ops-recover，携带已有证据和同一 run；不复制恢复方法。

所有现场操作和记录通过 ops-execute 的方法完成。维护报告正文作为原 run 的步骤由单一写入者保存；没有记录能力时不先变更现场后补账。

## 维持职责边界

按真实效果检查入口，而非脚本名字。OS 包计划中出现 PostgreSQL、Redis、Nginx 等项目组成服务的版本变化，应交其项目/共享服务部署责任方，不能夹在“系统更新”中执行。

新增部署、持久扩容、制品切换、永久路由/配置变化和应用 migration 都不属于本技能。不安装其他 domain，也不要求它们增加运维支持。没有明确计划或用户要求时，不建立定时维护或无人值守任务。

按[维护计划与结果](assets/maintenance-plan.md)记录真正发生的动作、逐目标结果和未完成事项。完整资料见[方法索引](references/method-index.md)及[边界示例](references/examples.md)。
