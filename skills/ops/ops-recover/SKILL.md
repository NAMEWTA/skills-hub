# 恢复已有服务运行

交付当前运行结果、实际恢复动作、逐目标与消费者验证，以及数据影响和剩余未知。服务恢复、故障缓解和根因确认分别说明。

## 先核对恢复对象

读取实际运维工作根的 .agents/ops/AGENTS.md、现行项目运行手册和原 run。通过 ops-inventory 确认稳定服务/实例/资源、项目环境、共享消费者和已知未知对象。

沿用 ops-execute 的执行与记录方法，先核实已有任务和现场再决定动作；断线或超时不证明前次未执行。缺少必要方法、身份、授权或记录能力时，完成准备和已有证据分析，明确缺口。

## 选择恢复分支

- 启动、停止、同版本重启、多服务就绪或恢复性重建：按[运行恢复](references/runtime-recovery.md)核对当前制品、有效配置、挂载和启动副作用。
- 备份/快照数据恢复：按[数据恢复](references/data-recovery.md)核对恢复点、损失窗口、数据范围、当前版本/schema 兼容性及验证。
- 原因仍不清晰或恢复后再次失败：携带证据返回 ops-diagnose。
- 需要切制品、回退发布配置、改变持久拓扑、升级应用/中间件或 migration：交项目自己的流程，不内部调用其他领域。

相同 tag 不代表相同制品；PID、容器 ID 变化也不自动代表发布。是否属于恢复依据实际状态变化判断，不依据 restart/repair/recover 的名称。

## 执行并证明结果

已有多服务系统的启动顺序使用项目已经验证的运行先决条件与就绪规则；依赖图只展示关系，不自动生成启动算法。共享服务只执行一次恢复，再分别验证相关消费者。

通过 ops-execute 保留步骤、任务引用和逐目标结果。若前置步骤失败、任务结果未知或实际作用跨越部署边界，停止尚未开始的相关变更，先核实；不要自动重试全部步骤。

按[恢复计划与结果](assets/recovery-plan.md)保存同一 run 下的业务正文。明确已恢复、仍失败、未开始与未知；没有检查原业务路径时不能宣布完整项目恢复。完整示例见[资料索引](references/method-index.md)及[场景与反例](references/examples.md)。
