# 个人工程方式

交付一份能改变后续行为、范围明确且可由用户审查的技能。先区分用户当前明确选择、反复观察到的习惯和仅一次发生的现象，当前明确要求优先。

## 主流程

按 [完整偏好提炼方法](references/derive-preferences.md) 检查已有技能、限定证据范围、归纳重复模式、补齐真实意图、起草并迭代。

更新已有技能时只处理上次有效版本之后的证据，保留未被新要求否定的规则。没有历史访问条件时，从当前对话与用户提供材料完成可用草稿，不编造习惯，也不为“找全历史”扩大访问范围。

输出位置沿用用户指定源仓库。新技能使用 `skills/dev/dev-<标识>-mode/` 等领域前缀结构，安装后为 `.agents/skills/dev-<标识>-mode/`。不写插件缓存，不自动安装为个人全局技能。

## 选择正确的改进方式

| 目标 | 本地完整方法 |

| 了解这些方法如何组合 | [完整工作方式演进指南](references/evolve-workflow.md) |

## 持久化与交付

用 [偏好证据模板](assets/preference-evidence.md) 留下必要来源、范围和冲突判断。需要保存时，新增分析记录统一写入 `.agents/wtadev/changes/<日期-主题>/preference-evidence.md`，已有资料按真实位置引用；生成的技能仍保存在前述技能源目录。通常保存简短指针和结论，不复制完整会话；不要保存密码、令牌、无关个人事实或原始私密聊天。

技能正文只放稳定、非默认、会改变决定的约定。项目当前状态、临时进度与具体业务事实留在项目资料中，引用代码或真实证据。规则应能说明何时适用、做什么，以及必要例外。

使用 [清晰写作规范](references/clear-writing.md) 逐句收紧。用户已要求修订或创建时完成该范围的文件工作；只要求分析时交付可审查草稿。提交、推送和 PR 沿用用户已授权方式，不额外加固定审批或强制 PR。
