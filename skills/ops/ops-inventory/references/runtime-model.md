## 最小实体

模型用于解释已有运行事实，不要求数据库、图数据库、CMDB 服务或自动扫描器。小清单用 Markdown 表格即可；现有平台已有权威对象时保存引用和必要快照。

| 实体 | 稳定身份与必要含义 | 不能混同的内容 |
| --- | --- | --- |
| Project | 项目 ID、用户识别的系统名称、维护归属、现有资料引用 | 一个项目可能跨多个代码仓库，也可能无源码仓库 |
| ProjectEnvironment | 项目 ID 与明确环境构成唯一范围 | shop/prod 与 shop/staging 不共享默认目标 |
| Service | 服务 ID、用途/类型、运行与发布责任引用、健康定义位置 | 逻辑服务不等于一个进程或一个项目 |
| ProjectService | 项目环境与服务的使用关系、角色、必要性、消费范围、项目验证入口 | 同一个服务可由多个项目使用；使用关系不复制服务身份 |
| ServiceInstance | 稳定实例 ID、服务 ID、环境、运行定位、资源引用 | PID、容器 ID、Pod UID 是观测，不是长期 ID |
| Resource | 服务器、VM、集群、托管实例等稳定资源 ID、类型、连接引用 | IP、SSH alias、显示名是定位线索，不单独证明身份 |
| ServiceDependency | 有向的消费者→提供者、关系类型、实际作用范围、证据 | 业务依赖、共享资源和启动先决条件不是同一关系 |
| Observation | 被观察对象、时间、来源、实际版本/运行状态/短期标识 | 观测有有效时间，不能当永久期望配置 |

ProjectService 的消费范围可为 PostgreSQL 的 database/schema、Redis 的已确认键前缀或逻辑库、消息队列的 vhost/topic、代理中的既有路由。只记录实际核实的边界；不能因逻辑隔离就断言进程重启不会影响其他消费者。

依赖可先登记到逻辑服务，只有证据支持时才进一步定位到具体实例。支持多实例服务和托管服务：没有可见服务器不等于没有依赖。直接共机仅描述资源竞争，不自动添加业务依赖边。

## 稳定身份

1. 优先采用已有云资源 ID、资产系统 ID、集群 UID/namespace/workload 名称或项目明确的稳定运行单元。
2. 本地服务器尚无权威编号时，在 ops 中生成稳定、无秘密的资源 ID，并保存已核验的硬件/虚拟机身份线索。`hostname`、IP、SSH alias 或 OS 的 machine-id 单独都不足以避免克隆/替换歧义，交叉核对来源。
3. systemd 实例可按资源 ID 与明确 unit 定位；Compose 实例按运行范围、项目、服务和副本位置定位。不能只用容器显示名跨服务器合并。
4. Kubernetes 的 workload 是稳定运行定位之一，Pod UID 和调度节点作为有时间的观测。托管服务使用供应商资源身份及区域/账号范围，连接信息仅留引用。
5. 同一实例同部署重启产生新 PID/容器 ID，追加新观测。若出现扩缩容、实例替换或重新发布，先核对真实部署语义，由项目负责变更；ops 只记录新旧事实及明确的承接关系。
6. 机器替换但复用 IP 或别名时建立新资源身份，旧 run 仍指向旧资源快照。主别名的登记、定位和替换见[主机别名](host-alias.md)。

没有足够证据唯一定位时保留候选和冲突。不要猜一个看起来最像的生产目标。

## 来源与时间

每项关键事实至少能回答“来自哪里、何时看到、属于哪种结论”。可让一组同批采集的表行引用同一证据段，不为每个单元格复制完整日志。

| 事实种类 | 例子 | 如何使用 |
| --- | --- | --- |
| 声明 | 项目配置说 API 使用 pg-main/shop | 说明预期或约定；仍核对当前生效版本 |
| 观测 | 某时刻 unit 的 PID、制品摘要、连接端点 | 只证明该时刻和采集覆盖内的现场 |
| 推断 | 同时异常可能来自共享代理 | 写出支持/反对证据与未知，不提升为成员关系或根因 |
| 未知 | 进程可见但项目资料没有归属 | 保留对象和下一步核验方式，不接管、不停止 |

关系保留来源引用、核验时间、有效范围，变化时说明何时失效或替换。旧 run 里的当时快照保持原样，不能用今天的项目成员关系改写过去的影响结论。声明与观测冲突时记录两个来源、版本和时间；继续使用现场描述“现在”，把差异交给原文档 owner，不写回其他领域。

原始配置可能包含密码、令牌、认证 URL 或业务数据。只保存定位、字段名、脱敏摘录和受控证据引用，不全量复制环境变量、连接串或容器配置。

## 关系与一致性

登记或更新时检查真正影响查询正确性的项目：

- ID 在自己的命名范围内唯一，所有被引用对象存在或明确标为外部/未知。
- 项目环境明确；相同服务名、同一仓库名不会跨环境自动合并。
- 一个共享 service 与其真实 instance 只保存一份；每个消费者通过 ProjectService 或明确依赖引用它。
- ProjectService 写明“项目组成”或“外部依赖”等角色，必要性来自用户/现有资料，不由模型猜测。
- ServiceDependency 的方向有含义，循环境、租户与逻辑消费范围核对。环路标出来，不自动删除边或生成拓扑排序操作。
- 运行位置可以是多层引用，如托管服务→平台资源、workload→集群，临时节点位置单独标观测。
- 未知对象、过期来源、访问失败和未扫描范围在结果里可见；清单行数不是覆盖率。

## 保存位置

新资料按实际需要存 `.agents/ops/registry/`。明确主别名的单主机登记按[主机别名](host-alias.md)拆文件；关系清单可用单一 `runtime.md`，规模扩大后可按项目、服务或资源拆文件并维护导航，不复制别名映射。它们是事实文件，不是执行计划或工作流定义。已有权威清单保持原位置，ops 只保存引用及自己的观测。

更新当前视图时由当前负责人串行整合已核验事实；并行采集者先把独立证据回到同一任务，不同时覆盖相同清单。先保存运维 run 中的当时证据，再更新现行视图。`ops-execute` 拥有 run 写入与并发记录方法，`ops-history` 查询旧事实；本技能不建立另一份操作流水。
