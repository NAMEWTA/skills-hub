### 持续指标优化

**你负责指标与实验完整性。监督、审查，把尝试委派出去。** 适用于围绕目标持续迭代改进一个可测量对象。一次性修复属于缺陷或性能问题，这里是循环。

核心纪律：一次改动、一次测量、保留或回滚。绝不叠加未验证改动，不凭读代码宣称收益，遵循 **prove-it-works**。

1. 选指标前先理解负载和架构。对目标运行 **how**，指出能影响结果的真实负载维度，如数据量、历史、状态、并发，选择复现用户抱怨的场景。没有场景能复现，就修复现，不开始优化。之后固定一个指标、改善方向和可检查停止判据；判据结合目标与最低尝试次数，避免早期偶然收益结束执行，例如“至少比基线好 50%，且至少 10 轮”。用户给数字就用，否则协商。
2. 构建测量驱动、证明敏感性，再冻结，遵循 **build-the-lever**。运行对比真实负载，确认目标场景复现症状、简单场景按预期区分。驱动无法区分就修改负载或指标。冻结前用 **benchmark-checklist** 审核，让它输出错误数与完成工作量。冻结后，一条可重复命令产出指标，足够采样排除噪声，如 N 次中位数而非单次。任何修改前记录基线指标和回归门禁，即必须继续通过的测试的一次绿色运行。
3. 用 **show-me-your-work** 建决策日志。`decision.tsv` 每次尝试一行，列为 ID、假设、改动、之前、之后、变化、测试、裁决（保留或回滚）、备注。每次尝试前读，放代码树之外或 git 忽略位置。
4. 每个假设基于第 1 步架构模型，点名具体机制，如“把 X 移出启动路径，因为它阻塞首次绘制”，而非“试着缓存点什么”。性能指标按性能问题手册（`playbooks/perf-issue.md`）第 2 步口诀排列假设，只借顺序，不借该步停止规则。
5. 循环，每轮一个假设：
   - 给使用已配置 hillclimb 模型（默认 `grok-4.7-xhigh-fast`）的子智能体窄范围改动。按“子智能体”一节选择推理级别和快速或标准速度。监督、审差异，不亲自输入代码，遵循 **guard-the-context-window**。多个独立假设活跃时，并行派出，各有工作树，遵循 **separate-before-serializing-shared-state**。
   - 用冻结驱动测量前后并运行回归门禁。
   - 只有指标改善越过噪声且门禁保持绿色才接受，否则完整回滚。“也许有用”的微调不保留。
   - 每个接受修复一个提交，只暂存自己改的文件（`git add <files>`，不用 `-A`）。保留或回滚都记一行。
   每轮在下一轮前以检查结束，遵循 **sequence-verifiable-units**。无人值守时只借自主执行（`playbooks/autonomous-run.md`）唤醒机制，不借停止规则。
6. 突破首个平台期。停滞或连续多次拒绝时，换类别、组合差一点成功的尝试、重读源码、或尝试更激进方案，再判断优化已尽。正确性与简单性高于数字。破坏行为的收益回滚，数字不变的简化保留，遵循 **laziness-protocol**。
7. 判据达成，或剩余想法收益微小不值得成本时停止。不放宽判据来达成，不在还有便宜未尝试假设时退出。卡住时明确报告，不空转。
8. 执行 **Opening a PR**，按接受顺序堆叠提交。

**回复：** 指标与目标、基线到最终值及百分比变化、轮次（保留与回滚）、每个接受修复一行、`decision.tsv` 路径，以及若继续最值得试的想法。
