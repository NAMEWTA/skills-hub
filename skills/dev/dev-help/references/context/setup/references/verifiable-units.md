# 按可验证单元排列工作

把工作排成一串小单元，每个单元结束于可检查的状态；当前单元没有通过，就不前进。

**原因：** 在产生问题的单元中发现破坏，定位成本很低。整批完成后才发现，问题会被埋住，而且你已经在破损的基础上继续构建。把这些单元排成审查者能够重放的交付顺序，便能将“相信我”变成“看规格、实现与证据如何对应”。

**执行。** 在全量修改、迁移或任何一串相似编辑中，开始下一项前先验证当前改动。每个单元都有一个前后对照：已知正常状态、一次改动、执行检查，然后继续。先核实本次基线与用户工作，必要时在隔离分支整合主干；不能为整理基线覆盖未提交内容。工具批量实施改动时，逐单元检查几乎不额外花成本；仍然执行它。

**交付。** 按能够证明工作的顺序排列提交和 PR。典型形状是先用失败复现或测试展示问题，再提交解决它的实现；也可以先明确规格与可观察验收、完成实现后取得行为证据。选择能讲清本次改变且符合仓库检查规则的顺序，不强求将失败测试作为可独立落地主干的提交。其他叙事顺序包括先删减再重塑、先采集基线再处理、先搭骨架再加功能。每个提交都可独立落地，整个顺序读起来是一段论证。

它补充 **真实证据** 工程原则，由后者保证每次检查真实；也补充 **构建验证工具** 工程原则，由后者降低逐单元检查成本。
