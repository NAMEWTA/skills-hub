# 修改代码之前先理解它

编辑自己不理解的代码，会让隐蔽的回归问题进入交付；这对智能体和你都一样。智能体通常以两种方式失败：误解你的要求，或缺少正确完成工作的背景。[目标复述](goal-restatement.md)与[学习流程](learning-workflow.md)处理第一种，本页处理第二种。

学习任务以 `机制探索` 和 `讲清楚` 为主：前者解释当前代码做什么，后者按用户背景组织说明。历史理由影响理解时使用 `原因调查`；接手前缺少背景时使用 `回忆上下文`。这些完整方法都留在本包，围绕同一次学习复用证据。

## 从只读调查开始

学习当前机制时，可以要求只读调查，并区分已知事实与待查假设。若目标是复现故障并证实根因，以 `dev-debug` 为主，例如：

```text
使用 dev-debug 调查为什么后台任务每隔几个小时就超时。告诉我已知事实、用了什么数据，以及你认为最合理的假设。先不要修改代码。
```

这类只读调查可以使用本包[调查手册](investigation.md)：运行 `机制探索`，在动机问题上加入 `原因调查`，返回有引用的解释。面对方案选择时，它返回建议和权衡表。追问“用了什么数据”会让智能体区分证据与猜测。只读请求的发现指向修复时，交付证据和下一步；已有明确修复授权的任务沿同一目标继续。

## 用 `机制探索` 追踪行为

```text
机制探索 我们怎样对通知去重？查找订阅者时是否存在 n+1？
```

提出你真正想问的问题。[`机制探索`](module-exploration.md) 阅读代码，像资深工程师带你接手子系统那样回答，讲清运行流程、关键类型和不明显的部分。大型子系统先派出两到四位只读探索者。范围狭窄的问题则直接阅读并解释。

## 讲解需要历史理由时

独立历史调查以 `dev-why` 为主；教学中需要同类证据时，使用本包的完整 `原因调查`，例如：

```text
原因调查 为什么重试上限设为五次？理由现在仍然成立吗？
```

[`原因调查`](decision-investigation.md) 从源码管理开始，然后并行查询 MCP 提供的各类证据，例如工单跟踪器、长文档、团队聊天、可观测性、错误追踪和分析数据。报告为每项内容提供引用，区分直接证据与推断，记录薄弱时说“看起来”。空结果也会报告，因为“没有人记录原因”本身也是答案。

两种方法可以自然组合。怀疑历史能够解释眼前混乱时，“先调查原因，再追踪当前机制”是一个好提示。

## 用 `讲清楚` 真正理解

```text
讲清楚 给我讲清这个 PR 如何改变重试。说服我它修复的是原因，而非症状。
```

[`讲清楚`](teaching.md) 用于摘要不足以让你理解的时候。它运行 `机制探索` 和 `原因调查`，小改动也许只需要其中一个，然后把发现组织成朴素说明，逐张图建立理解。“说服我”这种表达值得复用，它让解释成为可以检验的论证，而非导览。

它也适用于智能体自己的选择：

```text
讲清楚 给我讲清为什么你这样实现，而没有使用队列。你做了什么取舍，为什么？
```

教学对智能体和你都有帮助。必须解释工作的智能体需要读代码，并为每个主张提供证据，而非自信地说完就继续。

## 接手前缺少主题背景时

行动前恢复主题背景以 `dev-workflow` 为主，供人阅读的进展回顾以 `dev-status` 为主。本包保留完整背景方法，供学习任务确实依赖此前工作时使用：

```text
回忆上下文 帮我回顾上周导出功能的进展
```

[`回忆上下文`](context-recall.md) 挖掘你自己的近期聊天，以及共享记录，例如工单、之前的修复和仍在触发的错误，返回当前状态与下一步的简报。旧聊天保存着新智能体缺少的背景，因此在旧主题上开始新工作时，先加载它，再交付新输入：

```text
回忆上下文 回顾我昨天关于虚拟列表的工作，然后读这份缺陷报告。
```

如果要恢复一条指定聊天，使用下方的会话接续手册，而非 `回忆上下文`。

## 用户同时要求继续开发时

另一个智能体，或上周的你，留下了进行中的分支时，接续任务由 `dev-workflow` 负责；只有已具备实施条件的切片可以直接交给 `dev-build`。单独安装本技能时仍可使用本包完整手册：

```text
使用本技能 接手这个分支。读决策日志，弄清哪些已经完成，然后接着做。不要重做已完成的工作。
```

[会话接续手册](session-resume.md) 把先前轨迹作为恢复起点，并用当前代码与实际状态核对。它重建分支状态与决定，指出恢复点，并对照原始目标验证继承的主张，而非从头推导一遍。

**误区：** 不要因为“智能体反正会读代码”而跳过本页的方法。没有追踪形成的模型就开始编辑，往往会在第一个看起来合理的位置修补症状。先做 `机制探索`，比再修第二个缺陷便宜。
