# 架构布局修复

实际视觉审阅发现多条纠缠路由后，使用本参考。成功的机器回执不能决定构图是否合格。基于现有候选文件工作，保留所有必需组件、关系、标签、证据、边界和节点尺寸。

<a id="choose-the-repair-scope"></a>

## 选择修复范围

如果主链和次要链路已经清晰可读，局部修复孤立缺陷。如果主链受阻、多条路由纠缠，或局部修复把缺陷转移到了另一条路由，就在一次编辑中重新排布相连场景。保留全部语义和用户固定的几何；agent 生成的位置和路由控制可以改变。移动节点后，删除过时的自动生成路由覆盖，让自动路由使用新的摆放。

回执中的 `directCorridorBlockers` 若存在，会指出某条边对齐端点之间的节点。这是几何证据，不能证明该边是主路径，也不是新的校验失败。先追踪阅读者真正的主路径。当列出的障碍节点打断该路径时，应重新摆放相连的一组节点，而不是再加一条绕路。

<a id="one-coherent-repair"></a>

## 一次连贯的修复

1. 在 JSON 中追踪受影响的关系及其端点。选坐标之前，先把阅读者的主路径写成现有边的有序列表，再识别共享状态和真实反馈环。主路径中每一对相邻节点都必须存在当前要解释的关系；其他组件放在真实所属者旁的分支上。如果精简回执和截图未揭示所需路由或标签几何，只运行一次 `validate architecture <candidate.json> --layout-json --repo-root <root>`；只有不含仓库证据的设计才能省略 `--repo-root`。不要反复猜测途经点坐标。
2. 按阅读顺序摆放主路径中实际连接的相邻节点。将共享状态放在其读者／写者之间，必要时使用相邻行，避免某个写者的线条跨越整个执行区域。按真实边顺序，将反馈环围绕一个开放矩形布置，其他消费者放在其所属者旁。例如，若边是 `client → API → dispatcher → worker → collector → runner → dispatcher`，将前四个放在上排，collector 放在 worker 下方，runner 放在 dispatcher 下方：返回即可使用下排和一条短的向上边。这只演示邻接关系，不是可复制的图或坐标集；只能使用候选文件中存在的关系。保留每条边及其实际方向。
3. 新布局保留自动端点。只有分支或返回需要特定通道时才约束端口侧；检查该通道与每条受影响关系的关系，包括存储分支。如果该局部约束引入新冲突，就返回相连布局的调整，不要循环尝试端口侧组合。详细 `via` 或标签坐标只用于剩余的实测缺陷。将外部执行者放在解析后的边界矩形及其内边距之外；不把某节点列入 `wraps`，并不能在视觉上将其排除。内部关系和标签应留在共享边界内，除非越界本身表达真实事实；不要仅为避开其他路由而暗示一次外部跳转。
4. `composition/label-gap` 报告测得的最小值时，应扩大该净空，或把相连的一组节点移动到另一条可读行。完整标签要留在自身路由旁；把它移到远处空白处并没有修复关系。压缩无用空隙，同时保留测得的标签空间和先前字号。让主要交互和所有必需节点在默认桌面视图中保持可读；不要以巨大空白画布、微小文字，或没有语义理由的折返链条来交换更少交叉。

编辑后运行一次完整 `finalize`，然后对成功产物运行 `visual-check`，检查其桌面截图。替换已经审阅过的产物时，按照[交付契约](delivery-contract.md#a-new-candidate-at-an-existing-output-path)，为两个命令共同使用一个新的 `--out-dir`。追踪主路径、每条次要链路以及所有受影响的箭头和标签。可以进行有界的第二次修复，以处理仍存在的具体缺陷。如果仍未达到视觉验收，保留候选文件并报告具体缺口；不要将其算作成功修复，也不要继续盲目改变坐标。
