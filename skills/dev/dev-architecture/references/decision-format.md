# ADR 格式

ADR 存放在 `.agents/wtadev/notes/decisions/`，采用顺序编号：`0001-slug.md`、`0002-slug.md`，以此类推。

延迟创建 `.agents/wtadev/notes/decisions/` 目录：只有需要第一份 ADR 时才创建。

## 模板

```md
# {决定的简短标题}

{1—3 句话：背景是什么、决定了什么，以及为什么。}
```

仅此即可。ADR 可以只有一段。价值在于记录**曾经做过这个决定**和**原因**，而不在于填满各节。

## 可选部分

仅在确有价值时添加。多数 ADR 都不需要。

- **有效性或替代关系**：重新讨论时用普通 Markdown 说明“已采纳”“已失效”或“被某决定取代”；无需固定 frontmatter 枚举。
- **考虑过的选项**：只有被拒绝的其他选项值得记住时才写。
- **后果**：只有需要明确非显然的下游影响时才写。

## 编号

扫描 `.agents/wtadev/notes/decisions/` 中已有的最大编号，加一。

## 何时建议 ADR

以下三项必须全部成立：

1. **难以逆转**：以后改变主意的成本显著。
2. **缺少背景就难以理解**：未来读者看到代码会问“为什么偏偏这样做？”
3. **真实取舍的结果**：确实有其他可行选择，而选择当前方案有具体理由。

如果决定易于逆转，就跳过：到时候直接改回来。如果并不令人意外，没人会追问原因。如果没有真正可选的方案，除“做了显而易见的事”外也没什么可记。

### 哪些决定符合条件

- **架构形态。** “使用单体仓库。”“写模型采用事件溯源，读模型投影到 Postgres。”
- **上下文间集成模式。** “订购与计费通过领域事件通信，不使用同步 HTTP。”
- **带来锁定的技术选择。** 数据库、消息总线、认证提供方、部署目标。并非每个库，只包括替换可能需要一个季度的选择。
- **边界和范围决定。** “客户数据由客户上下文拥有，其他上下文只能通过 ID 引用。”明确不做什么与做什么同样有价值。
- **有意偏离显而易见的路线。** “因为 X，手写 SQL 而不使用 ORM。”任何合理读者会默认采用相反方案的决定。这能防止后来的工程师把有意为之的设计“修复”掉。
- **代码中看不到的约束。** “合规要求导致不能使用 AWS。”“合作方 API 合同要求响应时间低于 200ms。”
- **被拒绝原因并不显然的备选方案。** 如果考虑过 GraphQL，因细微理由选择 REST，就记下来；否则半年后又会有人提议 GraphQL。

未同时满足正式 ADR 的三项条件，但仍有长期价值的背景和约束，统一保存到 `.agents/wtadev/notes/context/`，按真实位置引用已有背景；错误与恢复方法进 `errors/`，术语进 `glossary.md`。不因未达到 ADR 门槛删除有效知识，也不强制迁移项目已有记录。
