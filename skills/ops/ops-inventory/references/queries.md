# 双向查询与影响分析

查询首先明确“看现在”还是“看某次运维当时”。现在使用带来源和时间的现行关系；历史影响读取当时 run 的快照，历史查询方法归 `ops-history`。

## 从服务器看项目

1. 通过稳定 resource ID 定位目标，列本次已观测和权威资料声明的实例，分别标状态与时间。
2. 用 instance→service 找到逻辑服务，再由 ProjectService 反查明确使用该服务的项目环境。共享服务可返回多个项目，不复制实例。
3. 单独展示共机而无已证实业务关联的对象、未知对象与未覆盖范围。
4. 需要影响分析时再沿明确的消费者→提供者关系反查上游消费者，保留每条路径的证据、环境和逻辑消费范围。直接使用与间接受影响分栏，不把所有连通服务都变成项目成员。
5. 输出服务器、实例、逻辑服务、项目环境、关系/消费范围、来源时间；对仍有其他就绪实例的服务说明现有证据，不在未验证流量和容量时承诺零影响。

## 从项目看服务组成

1. 精确定位项目环境，读取 ProjectService 的组成/依赖角色、必要性和项目验证入口。
2. 将服务关联到该环境下的真实实例，再关联到服务器、集群或托管资源。未知位置保留未知，不因没有 SSH 主机就遗漏托管依赖。
3. 展示 service 的当前版本观察、运行状态证据、共享消费者以及有向依赖；健康结论交 `ops-inspect`。
4. 区分“已声明但当前未见”“实际运行但无归属”和“资料与现场不符”。项目定义不完整时不能报告完整覆盖。
5. 一份系统项目可能涉及入口、web、API、worker、数据库、缓存、消息队列等多层。HTTP 端口响应只证明一个已观察路径。

## 从共享服务看影响

先核对操作的实际粒度。例如 PostgreSQL 实例重启涉及全部数据库消费者；只读检查某 schema 的结果不自动扩大到全部实例。Redis 的逻辑库/键前缀不能把进程级故障隔离掉。

列直接 ProjectService 消费者和明确依赖它的其他服务，再按证据回到受影响项目环境。只对真实依赖边进行有界反向遍历；保留已访问 ID 以识别环路，列出关系证据过期或缺失的断点。环路与未知不靠猜测填平。

输出建议复验的消费者路径，使用现有健康定义。一个服务被两个项目引用，只产生一个共享对象操作目标；各项目的消费验证可以各有结果。是否允许变更、如何协调唯一执行者归任务 owner 和 `ops-execute`。

## 维护前的影响材料

| 内容 | 必须说明 |
| --- | --- |
| 直接操作对象 | 稳定 ID、实际运行定位、操作粒度 |
| 共机范围 | 所有已知实例、未知对象、扫描覆盖 |
| 共享影响 | 直接消费者、间接证据路径、环境和消费范围 |
| 冗余条件 | 已核验的其他实例、流量/容量条件及未知 |
| 恢复验证 | 需要复验的服务与项目路径，现有方法入口 |
| 权限边界 | 本次授权允许什么；影响范围不等于写入授权 |

影响分析不是启动顺序生成器。业务依赖不一定是启动硬前提；循环依赖、重试和就绪策略必须由现有运行手册或现场证据确认。计划性维护交 `ops-maintain`，运行恢复交 `ops-recover`，不自动升级中间件或修改永久拓扑。

## 反例

- 两个不同项目在同一服务器，不能因此互为业务依赖；维护一个 unit 不等于维护整机。
- 两环境都有名为 redis 的服务，不以名字合并；先看环境、资源与实际端点身份。
- 发现 API 连接了数据库，不据此得出全部表/schema 权限，也不认定该数据库专属于 API 项目。
- 一个项目查不到某服务实例，不能把服务从项目定义中静默删除；可能是访问、部署或观测缺口。
- 今天新增的消费者不能自动写回昨天 run 的“当时影响”，可以追加后续发现及时间。
