# 基于仓库证据的创作

当任意类型的图表需要解释真实仓库时，使用本参考。职责、调用、边界和持久化均以源代码为准。当请求涉及的含义得到覆盖，并且每条断言的事实都有源代码证据支持时，图表才算完整。

<a id="explore-on-demand"></a>

## 按需探索

1. **固定身份。** 在目标仓库中记录 `git rev-parse HEAD`、`git remote get-url origin` 和 `git status --short`。记录 origin 或将其写入候选文件前，移除 HTTP(S) userinfo（包括用户名、密码和 token）。保留传输方式、端口、路径和 `.git` 后缀；不要把内部 SSH origin 改写成 HTTPS。在 `meta.repository` 中固定不含凭据的 URL 和四十字符的 revision。对于 SSH origin、不受支持的代码托管平台、刻意仅保留本地源链接的情况，或 HTTPS URL 只用来标识仓库身份的本地 fixture，使用 `link_mode: "local-only"`，并保留 URL 与 revision。Web 链接要求来源为受支持的 GitHub、Gitee 或 GitLab HTTPS origin；GitHub、Gitee、gitlab.com，以及声明了 `provider: "gitlab"` 的自托管 GitLab 主机，都会与同一主机上的 SSH origin 匹配。如果工作树有未提交修改，在回复中说明变更路径；候选结构没有对应字段。仓库证据按固定 revision 中已经提交的字节校验，而不是按工作树编辑校验：对引用到的任何变更路径，应在该 revision 的干净检出中检查。不要把未提交的字节当作 `HEAD` 的证据；`local-only` 也不会为这些字节记录可验证快照。

2. **映射相关切片。** 使用项目指令、清单、入口、注册点与部署配置定位候选运行单元。阅读与请求相关的入口、配置和模块。沿着导入与调用位置追踪，直到请求中的职责抵达实际输入、输出或副作用。阅读一小块相互关联的代码，而不是为了找到方便使用的标签而扫描整个仓库。

3. **追踪归属。** 从调用位置实际观察到的执行者、操作和目标推导运行时与 I/O 关系；部署和信任关系则使用对应配置或强制执行证据。区分请求操作的控制器、执行操作的运行时，以及接收字节的存储。对文件或数据库的边，源代码必须标识真实读者或写者；“维护任务”这样的职责描述不能证明直接 I/O。阅读时，将这些事实与源码位置一起保留，不另建规划产物。按照[组成与含义](authoring-defaults.md#composition-and-meaning)决定哪些区别需要独立节点；发现一个实现角色，不代表自动将其加入概览。配置的 provider、注入的 adapter、本地 stub 和持久服务是不同的主张；只标注源代码支持的那个。

4. **阅读时记录证据。** 为每个组件和有意义的关系保留精确的仓库相对路径，以及首尾均包含的行号范围。跟踪实际分支、重试、回退和错误处理。某个函数虽然导出或已配置，但普通路径从不调用它，那么它是可选能力，不是必需的运行时边。对于权威状态变更或控制归属的主张，应追踪到实际写入或执行位置，以及允许执行的条件；仅看到上游调用者不足以证明这些条件。

5. **明确不确定性。** 将尚未解决的问题写在其影响的主张旁边，例如“这里调用了 `writeFile`；持久性未知”。通过阅读下一段相关源码解决问题，或将它保留为明确的未知。绝不要把标签、包描述或配置值转化为尚未观察到的服务或行为。

当请求中的每个职责、关系和边界都获得源代码支持，并且剩余未知不会改变覆盖范围时，停止探索。没有必须凑够的节点、边、引用、视图、卡片或边界数量。不要仅为了表示完成而增加总结步骤。

已知彼此独立的相关文件时，批量读取。阅读带原始行号的源码摘录（例如 `nl -ba <file> | sed -n '40,90p'`）。从显示出的源码复制引用起止行号；摘录抵达 EOF 时，也要使用实际最后一行。每一次额外读取都应回答一个会改变图表的未解决问题。复用本任务中已经验证的简洁事实及其源码范围；跨修订时，重新核查受影响的入口、配置、依赖和证据。

<a id="evidence-by-diagram-type"></a>

## 各图表类型的证据

只有主要元素携带 `sources`，每个最多三个范围：Architecture 组件，Workflow、Dataflow 和 Tree 节点，Sequence 参与者，Lifecycle 状态，ERD 实体，Class 类型，Timeline 事件，以及 Waterfall 跨度。关系、消息、数据流和状态转换都不携带 `sources`：将调用、写入或转换位置引用到拥有该动作的元素上（调用者、写入者、被离开的状态），更多证据保存在说明或卡片中。文件夹节点引用自己的 README 或入口文件；否则引用定义或运行它的文件。Timeline 事件引用固定 revision 中记录它的文件，例如 changelog 条目，并从该历史中的 tag 或 commit 取得时间；如果记录只有日期，则使用当地时间中午。不能引用该历史之外的 tag 或 commit。在卡片中说明采用了哪一种时间来源。没有记录追踪数据的 Waterfall 使用 `meta.evidence: "illustrative"`，并始终将时长标注为示意；不要仅为了计时而运行项目。

<a id="choose-an-example-by-structure"></a>

## 根据结构选择示例

加载示例内容之前，先依据请求和源码检查已经需要的仓库元数据，从[类型路由](../SKILL.md#type-router)选择主要示例。该选择应融入已有读取批次，无需额外消息、命令或全仓库扫描。对于混合或不明确的任务，在普通检查逐步揭示职责与入口时使用这些信息，并保留它们的真实角色。当某项必需能力仍没有得到解释时，再阅读另一个示例。示例传授结构而不是事实：库项目不必因此获得文件系统节点；已经完成的展示案例也仍须遵守首稿使用自动路由的规则。

<a id="author-from-evidence"></a>

## 从证据创作

使用该模式完整的 JSON 结构，包括仓库身份、组件和连接；每个基于仓库的组件都需要支持它的源代码引用，而边界或卡片仅在确实回答阅读者问题时添加。先让自动路由和自动 viewBox 尺寸计算发挥作用。保持主路径可读，将异常路径放在其所属者旁边；当源代码表现为独立职责时，将文件系统存储置于控制边界之外。

现有示例传授字段结构，不提供事实或任意可用的值。它不能授权新的边界类型、长说明、viewBox 尺寸或路由控制。无论所选示例是否已经包含某字段，都应查阅具体模式的 schema 与 `schemas/common.schema.json`，并采用 schema 的枚举、长度、标识符和仓库规则。Architecture 的边界当前使用 `kind: "region"` 或 `kind: "security-group"`；源引用使用 `path`、`line` 和可选的 `end_line`。

基于仓库的组件需要简洁、真实的 `sources` 引用。汇总文件系统 I/O 时保留控制归属：读写文件的代码拥有该动作，纯内存转换则接收并返回值。此事实检查不要求为每个辅助函数单独建立概览节点。以现有示例学习合法字段结构，再将所有标识符、措辞、源码路径和主张替换为已经检查的仓库事实。
