# 架构理由模板

通常一页足够。只保留能帮助实施与未来理解的内容，不要求每项设计都形成永久 ADR。

```markdown
# <设计名称>

## 问题
<当前需求，现有系统中使设计不明显的约束>

## 调用者体验
<先写两个真实用法：输入、调用、返回、错误；再推导结构>

## 推荐形状
<数据与状态所有权、模块职责、接口、不变量、边界解析位置>
<公开接口隐藏了哪些复杂度，哪些仍必须由调用者知道>

## 候选比较与选择
- <方案 A>：<结构特征、调用者代价、为何选或不选>
- <方案 B>：<真正不同的结构、调用者代价、为何选或不选>
- 选择：<以哪个为基础，吸收了哪些部分，舍弃了什么>

## 接受的代价
- 接受 <代价>，换取 <具体收益>。

## 验证与实施
<规格完成后要验证的行为和边界>
<第一项完整实现单元>

## 尚未解决
<真正需要决定或调查的问题；无则省略>

## 代码与来源
<路径、符号、观察日期 / 提交、相关决定或探针结果>
```

## 何时提升为 ADR

仅在三个条件同时成立时写 ADR：

1. 改变决定的成本明显。
2. 后来的读者若缺少背景，会不理解为什么这样做。
3. 当时确有不同方案，并作了具体取舍。

ADR 解释为什么以及何时重新评估；代码引用解释目前在哪里实现。日常实现细节不要复制成一套会滞后的架构百科。
