# CI 不稳定失败诊断

只在任务是调查已有概率性测试或 CI 失败时使用本流程。保留请求的读写范围：诊断不授权修复、重跑工作流或修改 CI 配置。

## 固定证据

记录仓库、工作流、任务、提交 SHA、runner 标签、时间戳、准确失败测试或命令，以及首个稳定失败特征。基础设施消息与测试输出分开。

比较多次失败和通过的运行。优先同一 SHA 的运行；无法做到时，验证比较的提交之间，相关测试和 CI 配置完全相同。一次重跑通过不能证明基础设施故障，一次超时也不能证明产品竞态。

使用 Actions 日志和元数据，确认失败是否在同一主机或资源命名空间上重叠。保留支持结论的运行链接，而不是粘贴大量日志。

## 分类失败

依据记录的证据分类，而非依据最终修复：

- **主机资源碰撞：** 同一端口、套接字、数据库、可预测路径、缓存或外部命名空间，被独立进程或任务获取。
- **生命周期不完整：** 子进程、worker、流、服务器或回调达到静止状态前，拆除就返回；后续输出或修改出现在另一测试中。
- **进程全局污染：** 结果依赖测试顺序，或泄漏的 `process.env`、`cwd`、假计时器、全局对象、模拟、语言区域或模块状态。
- **负载敏感同步：** 用 sleep、轮询间隔或假定的事件循环轮次代替可观察的就绪或完成。
- **平台或入口路径不匹配：** 失败稳定地跟随某操作系统、shell、文件系统规则、源码／构建模式或可执行入口。Windows 与 POSIX 主机的时间戳精度、环境变量名大小写、句柄释放时机和权限语义都不同，所以 macOS 通过不能说明 Windows 通道如何。
- **产品并发缺陷：** 测试控制了自己的资源，通过显式重叠确定性复现，暴露交付行为中的竞态。
- **外部提供者瞬态失败：** 失败归真实 API 或网络边界负责，且符合其已记录的重试策略。
- **Runner 基础设施：** 检出、依赖下载、磁盘、主机进程或 runner 服务独立于测试命令失败。归入此类前，要求直接 runner 证据。自托管池没有主机指标时说明这一点，依据日志实际包含的信息分类：即使无法检查主机，一个池上无关分支重复同一特征，也构成共享主机争用的证据。

证据支持多个独立事实时，分别报告。不要将超时、信号、退出码和断言合并为一个推断结果。

## 复现最小相关拓扑

从负责测试的文件或聚焦测试名开始。只提高到首个能复现该特征的并发拓扑：

1. 一个测试进程；
2. 并发测试或文件；
3. 多个独立 Vitest 进程；
4. 使用配置 worker 数量的负责仓库门禁；
5. 共享涉事主机资源的独立任务或 runner 进程。

匹配实际 Vitest 配置、环境调节项、源码／构建模式及平台。不要为制造另一种失败而降低生产超时或增加随机负载。

失败特征属于当前主机无法运行的平台时，阶梯止于最后可达层。记录限制，不拿另一平台的通过运行替代；随后把 CI 用作复现，每次运行只修改一个疑似拥有者，使结果仍可归因。

疑似竞态时，在争用转换处用屏障替代概率性时序。疑似主机碰撞时，证明同时获取同一标识符，或证明原子唯一分配消除了冲突。

## 在拥有者处修复

获准实施时，修复分配资源、发布就绪、修改全局状态或负责拆除的组件。不要用快照规范化器、重试包装、更宽超时、全局串行设置或更弱断言隐藏失败。

稳定夹具数据与活跃资源分配分开。录制的 URL 可以保持稳定，由夹具把其传输映射到操作系统分配的端口；稳定预期路径可以继续用于断言，而不成为共享可写目录。

## 结束调查

满足以下条件，证据才完整：

- 原始失败特征已有证据支持的分类；
- 最小相关拓扑可复现，或外部证据充分且复现限制明确；
- 获准的修复在负对照或修复前状态失败，在同一拓扑的修复后状态通过；
- 资源拥有者要求的任何并发进程、恢复或静止拆除证明通过；
- 其余 Actions 检查按观察状态报告为通过、等待、跳过或失败。

不要一直运行到测试碰巧通过，就把结果称为稳定。选定证据已确立结论后停止，或报告阻止分类的缺失事实。
