**软件工厂**是一套代理系统，将工单、PR 和日程转化为已合并代码，部署在用户选择的远程基础设施上。本技能提供设计它的语言。讨论或白板设计工厂时，只使用这些术语；用户使用_避免_列表中的词时，指出规范术语。

## 任务与运行

**任务（Task）**：
工厂执行的一类工作，定义一次、运行多次：审查、探索、实现、棘轮迁移。任务可以处理工单、PR 或整个代码库。
_避免_：job、workflow、action

**触发器（Trigger）**：
启动一次运行的事件：工单跟踪器或 Git 托管平台中的变更、编排器中的时钟，或另一次运行。

**运行（Run）**：
一个任务在一个运行器上的一次执行，从触发到结束，作为黑盒看待。运行通过编排器逻辑直接触发后续运行，或通过修改工单跟踪器、Git 托管平台间接触发。运行永不等待人类：它结束，人类稍后对工单跟踪器或 Git 托管平台的变更触发新运行。
_避免_：session

**运行器（Runner）**：
运行执行所在的一次性机器。即使机器本身长期存在，上面也没有任何内容在运行后保留：运行对之前运行的唯一记忆是工单跟踪器、Git 托管平台和编排器。
_避免_：server、host、box、compute、sandbox

## 服务

**工单跟踪器（Ticket tracker）**：
保存工单的位置，也是工厂面向人类的接口：人类通过提交工单安排工作，在评论中与代理交流，对工单的修改会触发运行。
_避免_：issue tracker、ticket manager、project board

**工单来源（Ticket source）**：
工厂外任何向工单跟踪器创建工单的事物：反馈按钮、监控器、错误跟踪器、收件箱。
_避免_：data source、trigger source、intake

**Git 托管平台（Git host）**：
保存分支、PR 和审查的位置。
_避免_：code host、forge、repo

**编排器（Orchestrator）**：
接收触发器、在运行器上启动运行、记录哪些运行排队中/执行中/已完成的部分。
_避免_：dispatcher、scheduler、control plane

**可观测性平台（Observability platform）**：
运行器发送日志、追踪和状态的位置，让人类能看到每次运行内部发生了什么。可选：承担运行器或编排器位置的产品往往已经展示足够信息。运行不会直接依据其内容决策，除非某个东西先将其写入工单跟踪器或 Git 托管平台。
_避免_：observability、logs、monitoring、dashboard

## 设计工厂

设计有两半：**服务**，每项是由某产品填补的位置；以及**任务**，其运行推动工作在服务间流转。

从用户问题出发，而不是从工厂出发：未分诊工单、等待自动审查的 PR、迁移到更严格自动检查、无人阅读的缺陷。当用户提出问题或不知道要构建什么时，读取 [EXAMPLE-TASKS.md](EXAMPLE-TASKS.md)，了解解决常见问题的任务。

### 慢慢起步

每个触发器都是加速器。没有刹车的加速器会成为垃圾内容大炮。三种刹车是：

- **自动检查**：每次运行都必须通过的确定性门禁（类型、lint、测试）。
- **自动审查**：一次独立运行，在没有先入之见的情况下，依据代码库标准及工单（如有）阅读差异。
- **人类审查**：合并前由人类阅读 PR；捕获的问题转化为新自动检查和更精准的自动审查。

每次只添加一个自动触发器，起初节流（每十份缺陷报告处理一份、每天触发一次时钟），每个 PR 都有人类审查。随着刹车赢得信任逐渐放开节流，并把每条运行循环限制为少数几次尝试，再交给人类。

### 填补每个位置

每个服务是一个位置。一个产品可填补多个位置，一台服务器可托管多个服务。三种设计并列如下：

| 服务 | 全部使用 GitHub | Linear 工单 | 自有跟踪器 |
| --- | --- | --- | --- |
| 工单跟踪器 | GitHub Issues | Linear | 自有应用 |
| 工单来源 | 反馈按钮 | 反馈按钮、监控器 | 反馈按钮、监控器 |
| Git 托管平台 | GitHub | GitHub | GitHub |
| 编排器 | GitHub Actions | 自有服务器 + 数据库 | 自有应用 |
| 运行器 | Actions 运行器 | Actions、E2B、Daytona 或 VPS | 自有应用或沙箱 |
| 可观测性平台 | 无：Actions 运行页面足够 | LLM 追踪平台 | 自有应用 |

用户为某位置选择产品时，先读取相应调研建立方向感，再自行研究当前选项；每份调研按类型分组选项，并列出决定该位置的问题：

- [TICKET-TRACKERS.md](TICKET-TRACKERS.md)
- [GIT-HOSTS.md](GIT-HOSTS.md)
- [RUNNERS.md](RUNNERS.md)
- [OBSERVABILITY-PLATFORMS.md](OBSERVABILITY-PLATFORMS.md)

购买服务，构建任务：任务承载用户的设计，服务是通用的。优先采用现成工单跟踪器：它健壮、人们已熟悉，也便于接纳外部用户。

### 质询每个任务

对每个任务回答：

1. 什么触发它？
2. 它做什么，读写哪些服务？
3. 接下来触发什么？
4. 人类从哪里重新参与？
5. 如何防止两次运行做同一份工作？

对每个工单来源回答：如何防止它重复提交同一张工单？

只有每个位置都指明产品（可观测性平台也可有意选无）、每个任务和工单来源都回答全部问题，设计才算完成。
