# 派遣方式与 Home team

## 初始化与后续维护

1. 显式建立 Home 或补初始化时，读取现有偏好和被引用的方式、team。独立确定一个默认派遣方式和一个默认 team。沿用有效旧选择，采用用户明确指定的新值。只询问尚待确定的默认设置，两项都已确定时直接保存。
2. 用户说「初始化时用某方式派遣」等同指定该方式为默认。缺少默认方式时，展示有依据的可选入口并请用户选择。当前会话已确认提供可派发项目任务的原生入口时，可以建议「当前宿主原生」。用户确认后按模板保存为 `context/dispatch/native.md`，每次执行重新确认入口。无法核实其他入口时请用户提供准确技能或工具名。已有明确选择和已完成的登记按各自范围保存，派遣方式待定时标明具体缺项。能力核查从用户选择和现有入口出发。初始化以配置回读为验收，实际任务由派遣流程启动。
3. 缺少默认 team 时，建议每个项目安排一位项目负责人，CLI、模型与推理强度沿用执行入口的默认值。由用户确认建议或指定所需配置后，再保存 `context/team/default.md` 或引用已有 team。只填写用户给定的覆盖值。遇同名的非等价用户文档时选一个未占用的稳定名称，保留原文。
4. 新增方式或 team 时使用独立、可辨认的单段名称，复用已存在的权威文件。默认位置用小写字母、数字和连字符，检查同名、大小写冲突及实际路径；拒绝父目录跳转、链接和目标目录逃逸。按[派遣方式模板](../assets/dispatch.md)记录所选入口。替换当前默认时先确认新链接可读。移除某项前检查默认、方式与 team 的关联和当前任务引用；优先给当前有效偏好改用用户选定的目标，历史引用保留真实身份。
5. 旧配置中已有明确默认派遣约定时，把它原地规范为独立方式或在方式文件中引用其既有规则，保持原来的 CLI、角色、模型和推理意图。旧默认 team 仍指向原 team。移到独立方式时将原 team 的派遣定义替换为指针，避免重复维护；如用户在已有有效根指令维护对应选择，保留该唯一权威并引用。只迁移本次实际选用或已要求保存的内容，不扫描旧文件并合并偏好。对失效、歧义或冲突的显式默认先核实，不当作从未设置。
6. `context/preferences.md` 为每项已确认的默认设置保存一条相对链接，分别放在「默认派遣方式」和「默认 Home team」小节。「按派遣方式选 team」只列用户明确保存的关联，每个方式一个指针。写入前读基线，先保存并核对目标文档，再合并偏好，最后回读路径、唯一性和范围。安装更新、查询和临时覆盖都不改偏好。

## 选择与核验

1. 先选方式：本次明确指定 → Home 默认派遣方式。未迁移的旧 Home 在没有独立默认时，沿用仍适用的旧明确派遣约定；缺项时提示补初始化或只指定本次方式。
2. 再选 team：本次明确指定 → 已选方式关联的 team → Home 默认 team。多个 team 不合并。旧 Home 只有一次性派遣方式时，沿适用的旧团队约定和实际工具默认；普通任务不新建默认配置。
3. 在选定 team 中，按精确 repo ID 匹配「项目执行者覆盖」。每个项目只允许一条覆盖；只有有值的单元格覆盖项目负责人角色既有设置。然后应用本次关于该项目的 CLI、模型和推理要求。未指定的字段省略工具覆盖，模型与推理分别按真实接口核对，不能把示例名字或 `auto` 拼成实参。原生派遣方式和 team 指定的 CLI 不兼容时报告差异，由用户决定替代方式或 team；记录曾使用的组合不自动授权回退。
4. 用户说「记住使用方式 X 默认用 team Y」时更新偏好关联，两个文档保持独立。用户说「以后派 A 用某 CLI 或模型」时只更新指定 team 的 A 行，未点名时更新 Home 默认 team；若未建立默认 team，交初始化处理真实缺项。用户只说这一次时沿用现行偏好。核对 repo ID 用登记或 `home-route`，不按相似名称推断。

这些选择对应 Home 到目标项目的直接派遣。项目负责人进入实际 checkout 后，后续执行与派遣取决于项目当地有效规则。选择和兼容性以本次会话能力、已选入口的实际参数和绑定结果为准；保存选项不代表执行过或模型已生效。
