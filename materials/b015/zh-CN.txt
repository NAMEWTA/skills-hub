### 多阶段或多 PR 计划

**你负责计划，不负责代码。计划是一份由负责人逐项执行、操作人按证据审计的检查清单。** 计划就是交付物。不要实现。

1. 如果改动只有一两个文件，方案也很明显，则跳过计划。说明这一点并停止。
2. 写作前先用原型解决开放问题。每个问题都运行 `playbooks/prototype.md`。保留分支、SHA 和截图，放进附录 A。只有任何运行都无法解决的产品或偏好问题才询问操作人。给出选项（**never-block-on-the-human** 原则技能）。
3. 通过子智能体探索，使用 `subagent_type: "poteto-agent"`，并按“子智能体”一节指定模型（**guard-the-context-window** 原则技能）。按任务为每个子智能体选择推理级别及快速或标准速度。每个子智能体返回文件指针、约定、测试命令和入口点，不内嵌整段内容。
4. 把下方骨架复制进计划文件，填完每个占位符。除非操作人指定路径，否则写入智能体存储的 `docs/`。保留每个标题和子块，并维持下列顺序。每个 PR 一节。一个 PR 就是一个拥有独立证据的改动（**sequence-verifiable-units** 原则技能）。在**如何阅读**中指出执行手册。运行可能合并时选 `playbooks/autopilot-full.md`。由操作人落地 PR 时选 `playbooks/autopilot-stack.md`。持续项目选 `playbooks/orchestrate.md`。
5. 完整遵循 `/technical-writing` 写作，再运行 `/unslop`。正文采用单一 Diátaxis 模式，即操作指南。附录容纳解释与参考。每个标题陈述任务或发现。不用长破折号，不在句中使用冒号。
6. 运行 `node pstack/skills/poteto-mode/scripts/check-plan.mjs <plan.md>`，修复它输出的每一行（**encode-lessons-in-structure** 原则技能）。
7. 交还。发布计划路径和脚本输出，然后停止。只有操作人明确发出开始指令后，才按计划指定的执行手册开始执行。

**验证。** 仅有测试不足以完成验证。只有单元、实际运行和性能各项都勾选后，PR 才算验证完成（**prove-it-works** 原则技能）。这句话就是验证规则，每个验证块都以它开头。实际运行块是必需的。按 **swarm** 技能，十条通道在 PR 头提交上通过对应控制技能驱动真实界面，使用 `swarm workers` 模型（默认 `grok-4.7-xhigh-fast`）。每条通道是一项，包含具体场景、保存的截图和通过判据。其中一条是**对照主干的回归通道。** 它在主干和头提交上运行同一个关键场景。若主干没有此功能，通道记录这一事实，并以差异新增的行为及用户等待的最终状态为门禁，不编造主干结果。性能门禁是双侧的：主干与头提交都必须产出指定指标。若主干没有此功能，还要隔离差异新增的工作，为该工作和用户等待的端到端状态设置绝对预算。不要对不相同的场景宣称比率。性能块要写清指标、交错执行的探针、先测量的主干基线，以及带有失败数值的规则。改变交互的 PR 设有审查门禁：合并前，操作人在聊天中用截图和视频审查。未改变任何交互的 PR 写 `**审查门禁。** 无。<PR id> 没有审查门禁。`，其下不放复选框。

**控制技能。** 按界面选择。浏览器、Electron 和 Web UI 使用 `cursor-team-kit` 的 `control-ui`。CLI 和 TUI 使用 `cursor-team-kit` 的 `control-cli`。原生移动端使用仓库中已有的模拟器驱动技能。触及两个界面的 PR 在两者都安排通道。没有控制技能的界面作为风险放入附录 C，其实际运行块仍需说明各通道如何驱动它。
