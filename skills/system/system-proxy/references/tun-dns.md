# TUN 与 DNS 接管

TUN 是网络入口机制；真正经过哪条路，还取决于操作系统路由、接口、策略、地址族和应用解析行为。配置 `enable: true` 只表示请求启用，不是已经接管的证据。

## 拆开六件事

1. 应用是否使用系统 resolver、自己的 DoH/DoT、代理远端解析，或缓存答案。
2. 查询发往哪个系统接口和 DNS 地址。
3. 包是否实际进入 TUN。
4. 内核 `dns-hijack` 是否覆盖该协议、目标与端口。
5. 内核选择哪一个 resolver，以及 resolver 连接使用哪条代理链。
6. 业务目标最终按哪条规则走到哪个节点，或是否 DIRECT。

只验证第 5 项不能证明第 1 至 4 项，只看到 fake-ip 也不能证明全部应用接管。

## 关键配置的判断

| 配置或现象 | 实际需要的证据 |
| --- | --- |
| 自动路由 | 系统路由表与真实目标连接，不能只看开关 |
| `strict-route` | 当前平台和内核支持语义，既有 VPN、局域网与远程管理是否仍可达 |
| UDP 53 劫持 | 一次原生 UDP DNS 查询实际进入内核 |
| TCP 53 劫持 | TCP DNS 单独验证，不能用 UDP 成功代替 |
| 同网段路由器 DNS | 发往路由器的查询是否走物理直连路由，不能假定 TUN 接到所有 LAN 包 |
| IPv6 | 原生路由、DNS 服务器和业务请求分别检查 |
| 浏览器 DoH / 系统 DoT | 不属于普通 53 端口劫持范围，独立验证 |
| stack / MTU | 保留可用基线，只在明确兼容或传输证据支持时调整 |

macOS 与 Windows 的局域网 DNS 路由和接口优先级可能与 Linux 不同。使用[平台 DNS](platform-dns.md)核对现场，不从另一系统复制网络设置。

## 启动与异常路径

节点域名解析、resolver 主机名解析、订阅/provider 刷新可能在隧道建立前发生。画清依赖，避免“要启动代理先解析节点、要解析节点先启动代理”的循环。严格不允许引导直连时，必须有可用且身份正确的节点入口；不得用旧 IP 替换域名来假装消除依赖。

客户端退出、节点失败、睡眠唤醒和网络切换后，路由可能恢复为直连。TUN 本身不是断线阻断机制。若用户要求受保护流量不能旁路，需要适用系统的独立隔离策略与实际验证，并保留节点访问、必要引导、DHCP、局域网管理、远程救援及回滚。

不在唯一远程管理链路上贸然测试断网。没有明确测试窗口时，记录异常路径未验证，不报告“绝不泄漏”。
