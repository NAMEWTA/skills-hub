# 在既有部署内恢复运行

## 目录

1. 界定期望恢复状态
2. 核验真实前提与副作用
3. 确定有限动作和停止条件
4. 现有 systemd / Compose 入口
5. 共享服务与多服务系统
6. 中断、失败和复验

## 1. 明确要恢复到什么状态

记录用户期望、当前症状、环境、稳定实例/服务/资源及完成条件。恢复目标是已有声明与当前制品范围内的运行状态，不是由本技能产生另一套期望部署配置。

“恢复到昨天”可能指昨天数据、昨天版本或昨天健康状态；先根据已有材料确定含义。未明确数据损失、制品或环境时可以调查和准备，但不能猜测生产写操作。

读取现有 run 与后端任务，确认是否已执行、仍在执行、部分执行或结果未知。由 ops-execute 核实真实现场后再决定继续、补充检查或重试；不要一进入技能就再次 restart。

## 2. 核对恢复前提

| 项目 | 必须取得的证据 |
| --- | --- |
| 对象身份 | 稳定服务/实例/资源、项目环境、SSH/平台入口和实际运行定位 |
| 制品 | 现有二进制/镜像的实际身份；声明 tag 与 image ID/digest 分开 |
| 有效配置 | 当前实际加载的配置身份、来源、启动时会读取的文件；秘密仅保留引用 |
| 数据 | 当前 schema/存储版本、挂载、逻辑范围、持久性与写入状态 |
| 启动副作用 | ExecStartPre/启动脚本/entrypoint、拉取策略、迁移、自动修复和外部调用 |
| 依赖与就绪 | 已验证运行先决条件、共享消费者、冗余与每一步的实际就绪规则 |
| 权限与冲突 | 已有授权覆盖的动作和影响、唯一执行者、现有后端冲突控制 |
| 记录与验证 | 同一 run、真实任务引用、原失败路径及预期观察窗口 |

只核对服务显示版本不够。若启动会解析浮动 tag、执行 migration、拉取新制品或读取已经改变的部署配置，不能按普通同版本恢复执行。

脚本名为 restart.sh 或 repair 不提供任何领域保证。检查真实命令及其被调用内容；无法核实时报告缺口。可以分离的纯运行步骤按授权完成，发布部分形成项目交接。

## 3. 选择最小且足够的动作

优先使用项目既有、已核验的运行配方，说明为什么适用于当前症状。没有适用配方时先调查与准备，不把一串通用命令当成验证过的恢复方法。

允许的候选包括：启动已经停止的现有 unit/container；在同制品/配置前提下重启；按既有运行方法临时摘流和恢复原流量；在既有资源与声明范围内经核验的恢复性重建。停止动作只有在用户目标及恢复方法明确需要时才执行。

不新增部署、持久资源或副本，不更改声明拓扑、制品、项目配置或 schema。重建临时运行单元也必须能证明其身份、制品、配置、挂载与范围仍属于原有部署；不能只因为名字没变就认定相同。

把动作、对象、先决条件、停止条件、实际任务 ID 获取方式和验证交给 ops-execute。一次授权不自动扩展到别的项目、整台主机或共享数据损失。

## 4. 使用真实运行入口

以下是已存在工具的命令入口示例，不是自动执行脚本。由 ops-execute 在核验身份与范围后调用，不拼接不可信文本为 shell 命令。

### systemd

| 情形 | 示例入口 | 前提与验证 |
| --- | --- | --- |
| 现有停止单元恢复 | systemctl start shop-worker.service | unit 定义、ExecStartPre/ExecStart 与数据前提已核实 |
| 同部署重启 | systemctl restart shop-worker.service | 不会顺带更新制品、配置或迁移；影响与授权明确 |
| 方法要求的停止 | systemctl stop shop-worker.service | 明确为什么需要停止、数据/任务影响和下一步 |
| 查看实际状态 | systemctl show shop-worker.service --property=ActiveState,SubState,MainPID,ExecMainStatus,NRestarts | MainPID 是新观测，不重写稳定实例身份 |
| 查询恢复窗口日志 | journalctl --unit=shop-worker.service --since=已核验时间 --no-pager --output=short-iso | 日志筛选与脱敏；查询截断如实说明 |

start/restart 退出为零可能只说明请求被接受或启动作业完成；还需服务就绪、原失败路径和消费者结果。unit 执行了新路径、共享配置变了或重启时自动迁移，均不能掩饰为同版本恢复。

### Compose / 容器

先核对实际连接端点、Compose 项目名、服务、全部配置来源及当前容器的 image ID、挂载和数据状态。

| 情形 | 示例入口 | 前提与验证 |
| --- | --- | --- |
| 已存在停止容器 | docker start 已核验容器ID | 容器仍对应同一稳定实例；entrypoint 副作用已检查 |
| 已有服务的同部署重启 | docker compose --project-name shop --file /srv/shop/compose.yaml restart --no-deps worker | 当前工具支持该参数；目标配置/项目身份核实；不连带依赖 |
| 实际运行状态 | docker inspect --format '{{json .State}}' 已核验容器ID | Health 不存在不代表健康，检查真实就绪 |
| 实际镜像身份 | docker inspect --format '{{.Image}}' 已核验容器ID | 与恢复前身份对照；tag 相同不够 |
| 项目当前单元 | docker compose --project-name shop --file /srv/shop/compose.yaml ps --all --format json | 保留逐实例结果，不只看总退出码 |

默认不使用 compose up、pull、build、down 或 volume 删除作为运行恢复。若现有手册确实需要恢复性重建，先逐项证明原制品在本地且身份固定、无构建/拉取、当前声明配置未变、挂载/资源/规模不变、无 migration，并核对真实工具版本与参数；任何一项无法证明就形成项目事项，而不是尝试后再分类。

不把“删除后重建看看”作为通用排查步骤。既有数据卷缺失时尤其不能创建空卷并宣布恢复。

## 5. 共享对象与多服务系统

共享服务只登记一份实际身份，由唯一执行者负责恢复；各项目负责提供其消费范围与验证要求，不能每个项目各重启一次同一 Redis/数据库。

一个系统需要多个服务协作启动时，使用已经验证过的运行先决条件和就绪规则。依赖、共机、项目成员和启动约束不同；不能对依赖图简单拓扑排序就生成停止/启动计划。循环依赖与未知前提明确报告。

每一步满足其真实就绪条件后再决定是否继续。前一步失败或结果未知时，不自动推进依赖它的步骤。独立且已授权的其他目标是否继续，由现有运行方法、冲突与影响决定，不把整个系统当跨机事务。

临时摘流只使用已核验的既有运行能力，并记录原状态及恢复条件。改变永久路由、发布比例、持久拓扑或自动化配置交项目处理。

## 6. 处理未知、失败与复验

连接断开或本地进程退出不证明远端停止，也不证明操作没发生。保存已知任务引用和时间，按 ops-execute 的中断核实方法查询原任务与现场，再决定下一次 attempt。记录保存失败不成为重放恢复命令的理由。

逐目标报告执行状态、现场结果和记录状态。成功的目标不能掩盖失败或未知目标；任务退出失败前也可能已经改变现场。

复验至少覆盖恢复目标本身、原失败路径和已知共享消费者。按实际方法的就绪/恢复窗口进行有限观察，不无限轮询。无法验证某消费者则写明缺口。

服务已恢复但原因未明时返回 ops-diagnose 或保留明确后续；稳定方法需要沉淀时交 ops-runbook。不要把这次恢复自动写成普遍修复规则。
