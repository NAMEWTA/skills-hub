# `.agents/dev/changes/2026-11-19-execution-receipts/plan.md`

## 执行回执实施计划

让 #4 Agent CLI 对一次执行给出可按原身份查证的回执，让 #5 Tasks 在重启、模块暂停或评论写入失败后，仍能把问题、进度和结果送达原任务。交付判据是同一执行意图至多启动一次，同一回执的每项业务效果至多应用一次，未查明的执行保持可追查。

依据为离线提供的 `agent.md`「启动、断线与持久化」及工作区操作表，以及 `automation.md`「用户可以做什么」「并发与失败的外部语义」「界面、权限与数据范围」。本计划只覆盖与回执闭环有关的入口和行为。

**接续点。** 计划已拆分，实施与运行验证待开始。先做 01。实施时核对当前分支的 Core 查账入口、Agent CLI 执行及仲裁入口、Tasks 条件写与恢复入口，以及到点派遣和人工派遣的调用路径。离线资料未提供源码、可运行命令或原型确认正文，下面的接口和夹具为拟议产物。涉及界面呈现时，实施者从两份规格各自引用的 `prototype-review.md` 核对确认版本、状态及对应原型源码。该核对只影响相关界面实现和体验验收。

## 01 固定回执契约，让两端可独立验证

**负责人和依赖。** 共享契约负责人唯一维护回执合同、示例及符合性夹具。无前置切片。

**交付。** 提供按原身份查询、读取可重交回执、确认持久接收的行为契约，以及同一批可供生产端和消费端使用的样例。以下为拟议的合同语义，字段拼写和存放位置在核对现有实现后确定。

- 区分执行意图、运行、会话、回执和时间线消息的稳定身份。受理前冻结 Vault、机器、来源及适用的 `taskId`、Space 配置 revision、目标、cwd 与执行参数。绑定建立后关联 `runId`、`sessionId`。请求与回答关联具体 `requestId`、版本和 `replyId`。目标与导航代次限制视图更新。定时、人工与回复来源保留自身身份，并可追溯到实际接受的执行意图。
- 分别表达本地记录、进程创建、attach 可见、Agent 受理、业务结果。另有明确拒绝、待资源、待核实和进程丢失等事实。退出、attach 和业务结果可独立出现。权威查询结果须区分已知事实与无法确认。相同身份和相同内容可重交，身份相同但内容冲突时显式报错。
- 接收确认表示消费端已持久记录该回执及其待应用工作。评论写入状态单独持久化。生产端仅在收到持久确认后结束该回执的重交责任。传输投递保留重复与乱序的可能，由消费端按稳定身份去重并按因果关系处理。适用的任务、运行、会话和 Vault 绑定均须校验。

**独立验收。** 提供可执行的符合性夹具和预期结果，覆盖正常里程碑、重复和乱序、同键异内容、确认丢失、跨 Vault 或错绑定、权威状态未知、问题及结果。用参考发送器和接收器验证样例可重放，确认丢失后仍可用同一回执身份重交。明确消费端可开工的产物为合同、样例及预期结果，真实 Core 实现留给 02。

## 02 在 Agent CLI 产生、保存并重交权威回执

**负责人和依赖。** #4 Agent CLI 负责人维护 resolver、执行与对账适配、回执持久记录及工作区运行反馈。依赖 01 的合同与夹具。Core 接口若需调整，由本切片负责落地，运行权威事实仍由 Core 提供。

**交付。** 手动启动与 #5 派遣使用同一 resolver 和执行入口。先持久写入冻结意图，再在原身份下请求启动，记录权威里程碑及业务事件并持续提供对账。接收端暂停或确认丢失时保留未确认回执，恢复后按原身份重交。进程创建与持久回执之间中断时，先用原身份查询 Core。查不到权威状态时显示待核实，保留适用的任务、实例和资源占用。失联只改变连接事实。Core keep 恢复为替代 shell 时，记录原 Agent 丢失，禁止重放原 argv 或向替代 shell 发送旧输入。

**独立验收。**

- 通过实际工作区入口启动，在 Core 已创建进程后丢弃 run 响应。双击或同身份重试后只观察到一个进程，查账返回原运行。两次独立新建各有一个进程。切 Space 或关闭目标后，迟到回执只定位原目标或显示目标过期，仍能在所属 Space 查找已产生的进程。
- 使用 01 的模拟接收器，分别在首次接收前暂停、持久接收后丢确认、生产端重启三处注入故障。恢复后观察原回执身份、绑定和内容一致。查账不明时界面保持待核实。模拟替代 shell 后检查启动记录及输入，确认没有重放。
- 通过真实 provider adapter 分别观察 attach、受理、正常退出及明确业务结果。仅有退出、静默或终端最后一行时，查询仍无业务成功事实。注入假秘密，检查回执、诊断、导出和重启记录均无明文。

## 03 在 Tasks 持久消费回执并补投原任务

**负责人和依赖。** #5 Tasks 负责人维护持久接收与去重、Task/Run 投影、问题和结果 delivery、Markdown 评论条件写。依赖 01 的合同与夹具。使用参考发送器独立开发与验收，可与 02 并行。

**交付。** 围绕单 Vault 单 Engine 的 Markdown/JSON 文件事实，在持久记录中按回执身份保存已接收事实与待应用效果，再确认接收。SQLite 可从文件重建。对任务时间线使用稳定 `messageId`，条件写冲突后重读，按原消息身份补投。在评论已写但投递标记未写的窗口，恢复时先查原消息是否已存在。依赖前序事实的回执先持久保存，前序补齐后再应用。状态依据因果事实推进，迟到回执不得让已知状态倒退。

首次明确受理本轮输入后，原任务进入进行中并追加一次系统评论。待资源和启动里程碑只更新运行详情。问题、有效回答、待核实及结果按原绑定落到时间线。回复和补充先持久保存，再走共享输入仲裁。同键同内容返回原结果，并发换键无法抢答同一 `requestId/version`。普通问题的回答可驱动同会话新轮并记 `parentRunId`，原生 deferred 仅在能力支持时恢复原 run/request。已关闭任务可补历史结果，后续输入要求明确重开。任务删除后保留送达失败诊断。

**独立验收。**

- 用 01 夹具重放乱序、重复和错绑定回执。比较 Run 事实、唯一 `messageId`、任务文件字节及看板。确认启动阶段保持未开始，受理后只推进一次，只追加一次系统评论，运行退出或结果投递后的完成状态仍由用户控制。
- 分别在任务持久接收后、评论条件写失败时、评论成功但投递标记尚未落盘时中断或重启。恢复后只补原 delivery，时间线恰有一条相应消息，参考发送器收到同一确认。区段外字节、讨论评论和已有任务格式保持原样。
- 经详情提交并发回复和补充，核对版本、绑定、忙时待发送和发送未知。关闭后补结果，删除后记录目标已消失。切 Vault 后旧回执无新 Vault 写入，损坏记录显式报错且冻结相关领取。只读 Vault 或临时目录在派遣和回复产生副作用前拒绝，Agent CLI 暂停期间输入保存在 Tasks，恢复后按原身份尝试发送。

## 04 通过真实任务和工作区完成联合验收

**负责人和依赖。** 联验负责人维护真实入口接线与联验场景。开工准备可用 01 的样例。正式联验依赖 02 的真实启动、查询与重交能力，以及 03 的真实接收、投递与恢复能力，两端先各自产出独立验证证据。

在同一候选版本、隔离测试 Vault 和 Core 中，使用实际应用、Engine 和真实 CLI 验证以下场景。故障注入只控制中断时点和传输，业务事实从真实入口取得。

| 场景 | 操作与通过判据 |
| --- | --- |
| 定时派遣与受理 | 保存计划次日运行的 Agent 任务，在规则时区推进到 availableAt，触发真实规则入口，并让人工派遣与重复规则发生竞争。保存及到点前进程数为零。竞争后仅一份有效运行，后到来源可查已有接受或排除理由。受理后只出现一次状态推进和系统评论，后台会话归原 Space 且不抢焦点，可从原任务前往现场。 |
| 问题、回答与结果 | 在原任务看见 provider 问题并回答。人为制造 busy 和确认丢失，核对待发送、待核实及对账后的状态。覆盖普通问题新轮及支持 deferred 的真实 provider 恢复原请求。只有 blocked 信号时可前往现场处理。最后在原任务只看到一次有意义的结果，详细输出仍在现场。 |
| 四个故障窗口 | 逐次在进程创建后丢 run 响应、回执持久接收后丢确认、结果持久化后拒绝评论条件写、评论提交后丢投递标记。各场景重启受影响模块后对照身份和进程数。通过条件为无重复启动或输入，最终只补原结果，系统评论及结果消息各一份。若暂时没有权威证据，待核实和相关占用持续到对账。 |
| 暂停、失联与生命周期 | 分别暂停 Tasks 和 Agent CLI，检查前者保留重交回执、后者保留待发送输入。切 Vault、关闭 pane、断线、恢复到替代 shell，再检查旧回调隔离、真实退出或丢失事实、任务业务状态及输入记录。已关闭任务可补收结果，已删除任务保留失败诊断，原运行无重启。 |
| 恢复、权限及回归 | 在新测试 Vault 备份恢复包含待投递结果的文件事实，重建索引后核对原绑定及一次性补投。损坏或错绑定时显式报告并冻结相关领取。核对内部回执在全局外露关闭时正常收取，外部创建任务不会获得执行权，假秘密不出现在任务、诊断或导出。在主干与候选版本重走手动新建和普通讨论，记录既有行为及可见差异。 |

联合覆盖对应 `agent.md` 的 A05–08、C10 及启动回执、失联与生命周期条款，以及 `automation.md` 的 A01–03、A05–07、B05、C01–04、C07–08 和持久送达条款。01 证明合同可互操作，02 证明执行事实可找回，03 证明任务效果可恢复，04 证明真实入口形成闭环。

## 接线、证据与完成边界

01 就绪后可并行推进 02 和 03，各自维护模块持久格式与隔离测试数据。共享合同及夹具变更由 01 负责人统一合入。04 负责人统一协调共享注册点、启动配方、格式切换和联验数据。在同一整合边界迁移本次涉及的真实调用者并清理旧回执路径，保全真实旧数据、外部历史和存活进程。中间接线状态以切片证据记录，整体交付以候选版本联验为准。

实施时使用仓库实际运行入口，把预期证据记录在本变更目录 `evidence/<切片>/<场景>/`。每个场景记录候选提交、环境与 CLI/provider 版本、操作和故障点、脱敏的身份与事件顺序、进程数、文件或时间线观测及判定。可见交互保存截图，按已核实的原型状态、主题和视口对照。夹具通过只证明本端合同。若真实 provider、原型版本或权威 Core 查询能力缺失，记录受影响场景及尚缺证据，其余场景继续验证。
