### 性能问题

**你负责测量叙述。规划、审查、核验数字。** 每个修复关联一次测量，不用读源码替代测量。

1. 用匹配控制技能捕获基线轨迹。用 **benchmark-checklist** 审核基线和之后每个数字。
2. 追踪代码，为假设提供依据。在实际运行前，不要断言性能上限。
   按顺序尝试性能口诀，先便宜的：
   1. 不做它。停止结果无人使用的工作，不只是让它更便宜。
   2. 做，但别再做一次。
   3. 少做。
   4. 晚点做。
   5. 在用户没看时做。
   6. 并发做。
   7. 更便宜地做。

   较早口诀达到目标就停止。
3. 根据追踪结果规划修复。如果跨越函数边界，先运行 `architect`。将实现委派给使用已配置 perf-issue 模型的子代理（默认 `claude-opus-5-5-xhigh-fast`）。按照 Subagents 部分，为每个子代理选择适合任务的推理级别。审查 diff。捕获修复后的 trace。
   按 **sequence-verifiable-units**，每次尝试验证后再试下一次。
4. 解析比较产物，如 JSON 转 sqlite、差异比较。“无结论”或错误界面不是通过，必须指出。
5. PR 引用测量。
6. 执行 **Opening a PR**。

要围绕指标持续改进而非一次性修复，使用持续指标优化（`playbooks/hillclimb.md`）。

**回复：** 基线数字、修复后数字、变化、产物路径。
