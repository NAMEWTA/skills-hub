# 邮件模块总体路线与关键风险

先用一个普通 IMAP 账号跑通「添加账号 → 从联系人打开邮件 → 离线保存回复 → 重启后续写并查询投递结果」的完整路径。尽早验证邮件定位、Vault 隔离和 SMTP 回执丢失，再扩展多账号、OAuth 和外部入口。Mail 作为独立工作台模块，Inbox 继续承接快速捕获。

## 总体路线

| 阶段 | 用户可见结果 | 关键依赖与取舍 |
| --- | --- | --- |
| 1. 跑通单账号收读 | 测试连接、选择 INBOX，从联系人打开邮件，离线仍可读缓存。正文就绪且实际可见后才标读。 | 首条路径确立 Vault 与账号代隔离、本地消息 ID 到远端来源的映射，以及统一的只读约束。先验证 IMAP 主路径。 |
| 2. 跑通草稿与投递恢复 | 从原账号回复或转发，离线保存草稿和受管附件，重启后续编，并在发件箱查询每位收件人的结果。 | 回复和转发依赖首阶段的来源账号与消息契约。草稿持久化和投递故障验证可提前推进。首次接通真实 SMTP 前，先验证同一草稿版本的并发提交、部分接受和回执丢失。 |
| 3. 扩展多账号与提供商 | 补齐 18 个预设及自定义、Google 和 Microsoft 授权、跨账号联系人聚合与缓存搜索。界面显示实际同步路径、回退范围和修复入口。 | OAuth 授权可与草稿并行推进。Gmail、Graph 接入依赖消息来源与同步契约，真实验收需要已注册的 Huhu 客户端和测试邮箱。搜索结果与通知共用定位能力。 |
| 4. 接通管理与外部入口 | 完成同步设置、账号删除预览、整 Vault 恢复和 S6b 新格式邮件子集恢复。工作台、CLI、MCP 共用能力契约，AI 默认关闭。 | 恢复依赖草稿、附件和投递记录的持久语义。CLI/MCP 的目录、能力选择与传输由 #6 提供，Mail 负责统一校验和处理。AI 依赖明确的内容选择和目的服务展示，可独立推进。 |

收件附件基线限元数据。远端备份和 SMTP 成功后的远端 Sent APPEND 仍属规格列出的缺口。恢复范围采用 Huhu 新格式。

## 关键风险

| 风险 | 应守住的边界 |
| --- | --- |
| **SMTP 回执丢失导致重复投递** | 同一草稿版本的并发提交指向同一业务操作，逐收件人记录明确接受与可证明未提交。可能已接受时保留「结果未知」及核对入口。断线、重启和恢复备份的故障验证应观察到 SMTP 提交次数没有增加。在途发送与删号的交互以 `design.md` 为准。 |
| **切 Vault、删号或只读时仍发生副作用** | 在统一处理入口约束持久写入、发送、远端标记和导入提交。切 Vault、停用或删号后，迟到响应不能写回缓存或触发通知。Mail 认证独立于 Safe，密钥暂不可用时仍可读取已有缓存和草稿。 |
| **同步或定位错误造成漏信、错读、错标** | IMAP 核对 UIDVALIDITY，STORE 后确认 FLAGS。Gmail history 和 Graph delta 在分页成功后推进游标，游标失效时重扫受影响范围。Graph 的 `Mail.ReadBasic` 权限不足以读取正文和附件，Gmail/Graph 的基线本地标读明确返回 `remoteSynced:false`。 |
| **聚合、渲染或外部入口泄露私有数据** | 同账号内按可靠 Message-ID 归并，保留缺 ID 的独立来源，聚合全部符合条件的本地历史后再分页。Bcc 仅在相应私有发件记录可见。正文默认零外部资源请求，CLI/MCP 大附件只接受受限句柄或流，AI 经用户选择内容并看到目的服务后才传输。 |
| **维护与恢复丢失唯一副本** | 草稿、受管附件、投递记录和本地标记随新格式恢复。缺字节附件标为待重绑，新机默认重新认证。验证清缓存、重建 FTS、Git 同步和恢复后，唯一副本仍可找回，投递操作仍可查询。 |

功能验收需要真实邮箱验证协议与权限、受控故障验证投递与恢复，以及桌面和 Web 对照确认版原型验证交互。此路线依据提供的 `mail.md`，阶段顺序为规划建议。现有 `plan.md`、`design.md`、原型确认范围及 Issue 验收清单仍需在对应阶段复核。
