# 架构布局修复

实际视觉审阅发现多条纠缠路由后，使用本参考。成功的机器回执不能决定构图是否合格。基于现有候选文件工作，保留所有必需组件、关系、标签、证据、边界和节点尺寸。

<a id="choose-the-repair-scope"></a>

## 选择修复范围

如果主链和次要链路已经清晰可读，局部修复孤立缺陷。如果主链受阻、多条路由纠缠，或局部修复把缺陷转移到了另一条路由，就在一次编辑中重新排布相连场景。保留全部语义和用户固定的几何；agent 生成的位置和路由控制可以改变。移动节点后，删除过时的自动生成路由覆盖，让自动路由使用新的摆放。

回执中的 `directCorridorBlockers` 若存在，会指出某条边对齐端点之间的节点。这是几何证据，不能证明该边是主路径，也不是新的校验失败。先追踪阅读者真正的主路径。当列出的障碍节点打断该路径时，应重新摆放相连的一组节点，而不是再加一条绕路。

对于自动排列的图，`validate architecture <candidate.json> --layout-json` 会显示渲染器选定的位置。实际图片出现问题时，可用这些位置定位受影响分支。auto 模式下提供 `pos` 会固定该组件，其他组件仍可移动。

<a id="one-coherent-repair"></a>

## 一次连贯的修复

1. 在 JSON 中追踪受影响关系及其端点。选择坐标前，先把读者的主要路径写成由现有边构成的有序列表，再识别共享状态与真实反馈环。主要路径上每对相邻组件都必须存在所要解释的关系；其他组件放到其实际所属对象旁的分支上。如果简短回执和截图无法显示所需路由或标签几何信息，运行一次 `validate architecture <candidate.json> --layout-json --repo-root <root>`；只有不包含仓库证据的设计才省略 `--repo-root`。不要反复猜测途经点坐标。
2. 按阅读顺序放置这些相连的主路径邻居。把共享状态放在其读取方/写入方之间，必要时放在相邻行，避免某个写入方必须用一条线横跨整个执行区。按真实边的顺序，把反馈环围绕一个开放矩形排列，其他消费者放在其所属对象旁。例如，若边为 `client → API → dispatcher → worker → collector → runner → dispatcher`，就把前四个放在上行，collector 放在 worker 下方，runner 放在 dispatcher 下方：返回路径便可沿下行，再用短向上边完成。这是在说明相邻关系，不是让你复制图或坐标；只能使用候选中实际存在的关系。保留每条边及其真实方向。
3. 新布局继续使用自动端点。多个对等组件与同一组件交换请求和回复时，尝试把每对繁忙交互放到该组件的不同侧。中继放在其本地端点外侧，为平行箭头及标签留出空间。如果标签挤在一起，尝试在外侧轨道设置相对标签偏移，并沿标签追踪回其箭头。绝对标签位置或显式直线路由可能阻止自动端口展开。只有分支或返回需要特定通道时才约束某一侧；对所有受影响关系检查该通道，包括存储分支。如果局部约束引入新冲突，应回到连通布局，而不是循环尝试侧面组合。只有剩余的实测缺陷才使用详细 `via` 或标签坐标。外部参与者应位于已解析边界矩形及其内边距之外；不把节点列入 `wraps` 并不能在视觉上排除它。内部关系及其标签应留在共享边界内，除非跨越边界表达了真实事实；不能仅为避开另一条路由而暗示外部一跳。
4. 当 `composition/label-gap` 报告实测最小间距时，扩大净空，或把相连分组移到另一条可读行。完整标签必须留在自己的路由旁；放到远处空白区不能修复该关系。在保留实测标签空间和之前文字大小的前提下，压缩未使用间隙。使主要交互和所有必需节点在默认桌面视图中可读；不要用大幅空白画布、微小文字，或没有语义原因的折返链条来换取更少交叉。

编辑后运行一次完整 `finalize`，然后对成功产物运行 `visual-check`，检查其桌面截图。替换已经审阅过的产物时，按照[交付契约](delivery-contract.md#a-new-candidate-at-an-existing-output-path)，为两个命令共同使用一个新的 `--out-dir`。追踪主路径、每条次要链路以及所有受影响的箭头和标签。可以进行有界的第二次修复，以处理仍存在的具体缺陷。如果仍未达到视觉验收，保留候选文件并报告具体缺口；不要将其算作成功修复，也不要继续盲目改变坐标。
