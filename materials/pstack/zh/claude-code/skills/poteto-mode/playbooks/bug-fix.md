### 缺陷修复

**你负责本任务。规划、审查、验证。** 把调查和修复委派给子智能体，自己主导。按“子智能体”一节为任务选择推理级别和快速或标准速度。

保持科学。每行交付代码都追溯到运行证据。“也许有用”的双保险是假设，不是修复，不交付。证据反驳假设时，回滚它促成的改动。只交付证据支持的最小变化。

1. 通过控制技能在匹配界面亲自复现，见不可妥协项，即使调试或观测协议让你请用户复现。只有给出明确具体理由，说明控制界面无法触及目标，且已驱动到能力边界后，才询问用户。不能直接复现时，合成触发条件、收紧条件或加入观测，直到触发。
2. 二分定位原因。形成候选假设，再逐项排除直到仅剩一个。先用 `how` 理解受影响子系统，用 **why** 查回归历史。每轮选能切掉最多剩余问题空间的分割，获取运行证据并排除。程序状态不清时加观测或日志，运行中读它，不猜。长期或顽固排查用 Cursor `/loop` 推进。步骤 3 的 architect/interrogate 扇出前，先用运行证据确认剩余的*机制*。
3. 规划修复。跨函数边界时先 `architect`。用已配置缺陷修复模型，默认 `grok-4.7-xhigh-fast`，给子智能体具体范围并委派实现。
4. 在同一界面验证。原始复现现在通过。“无结论”或错误界面不算通过，必须指出。单元测试显示分支行为，不能证明缺陷不存在。
5. 安排提交，让失败复现先于修复进入 git 历史。缺陷有便宜本地测试路径时，按 **tdd** 技能执行失败测试先行节奏；测试昂贵、集成复杂或不明确时跳过。
   这是 **sequence-verifiable-units** 原则技能的标准形态：失败测试在前，修复在上。
6. 执行 **Opening a PR**。

**回复：** 什么坏了、根因、修复、如何验证。原样粘贴先失败后通过的复现输出。
