# 仪表盘设计

本技能提炼自 127 个已经交付的仪表盘界面、该领域的经典著作与研究（Stephen Few、Edward Tufte、Cole Nussbaumer Knaflic、Cleveland & McGill、Nielsen Norman Group）、X 上近期优秀设计师的作品（2026 年 11 月）、两份完整拆解，以及实际重设计经历：下列每条规则都曾在真实项目中被违反、在截图上暴露问题，随后得到修复。来源：[references/sources.md](references/sources.md)。

仪表盘应让读者**第一眼就能从一个屏幕得到一个问题的答案**（“学校今天情况正常吗？”“业务是否在增长，增长由什么推动？”），指出需要关注的事项，并让相关操作触手可及。每个元素要么回答问题，要么提示异常，要么让出空间。

## 核心关键词

- **第一眼（First glance）**：无需悬停，读者在 3 秒内获得的信息。首先围绕这一瞬间设计。
- **监测（Monitor）**：读者的顺序是「概览 → 需要关注之处 → 进一步查看 → 行动」。异常应一眼可见，操作就在异常旁边。
- **克制（Quiet）**：没有异常时保持平静。正常数据用灰色和一个代表数据实体的色相；亮色或暖色仅留给需要关注的内容。
- **少文字（Wordless）**：屏幕上只放名称、数字、单位、一到两个词的对比基准，以及紧凑的数值事实（“CPL 24 902 · CTR 1.8%”）；所有解释都放在工具提示里。除工具提示及空状态外，不放完整句子。
- **真实（Honest）**：同一个数字在所有位置一致，估算值明确标记，不夸大小基数的变化。
- **目标紧邻数值（Goal beside the number）**：有目标的指标应在同一张卡片展示当前值、目标和剩余差距（刻度条、简短文字）。

这些关键词背后的感知原理（视觉编码优先级、配色规则、刻度、子弹图和可访问性）：[references/perception.md](references/perception.md)。

## 构建或重新设计

1. **明确问题。** 写出本屏幕要回答的唯一问题、回答它的 3–6 个数字、用数值表达的异常规则（“最近 3 天中有 2 天 CPL 高于目标的 1.2 倍”“出勤率低于 85%”），以及每个异常对应的操作。在制作任何界面之前，建立能触发全部异常的固定测试数据，并先写出预期答案（qa.md → Known totals）。**完成条件**：四份清单、固定数据和预期答案均已具备。
2. **为每个数字选择表示形式。** 根据视觉编码优先级（perception.md）：数量用位置或长度，仅对网格数据用热力图，与目标比较用子弹图，历史变化用迷你趋势图。**完成条件**：每个数字都有一种表现形式和一句理由。
3. **安排视觉层级。** 页头（标题、日期范围、筛选器）→ KPI 卡片 → 主视图（直接给出答案；监测场景应放展示异常的网格或列表）→ 细分项 → 详情列表。最重要的内容放左上角；一行卡片的信息量相近；监测屏的 KPI 和异常视图应在首屏内。宽度、网格与手机布局见 [references/layout.md](references/layout.md)。**完成条件**：视线有唯一明确的路径，没有半空的卡片。
4. **先定义设计 Token，再做组件。** 参见 [references/tokens.md](references/tokens.md)。**完成条件**：界面中的每种颜色都来自同时具有亮色、暗色取值的 Token。
5. **按组件模式逐个实现。** 使用 [references/components.md](references/components.md)，适用时复用 [references/snippets.md](references/snippets.md)（Web）或 [references/swiftui.md](references/swiftui.md)（SwiftUI、Swift Charts）的代码。片段使用 React + Tailwind；纯 HTML 应在相同 Token 基础上将类名转换为 CSS。**完成条件**：每个组件都符合相应模式，或在页面文件顶部的简短注释块说明偏离原因。
6. **设计全部状态。** 包括加载中、数据过时（请求新数据时仍展示旧数据）、错误、空状态、数据量极小和示例数据（components.md → States）。**完成条件**：每个面板都实际检查过每种状态。
7. **执行 QA。** Web 端使用 [references/qa.md](references/qa.md)（三种宽度），原生端使用 swiftui.md → QA pass（设备尺寸、最大的 Dynamic Type、深色模式和 Reduce Motion）。先检查已知总数，再检查文字与视觉显著性，最后查看截图。**完成条件**：数值相符、完整句子数量为零、第一眼聚焦异常，而且实际查看的截图通过每项检查。

## 评审（“这是好的设计吗？”）

先查看实际屏幕（截图或运行页面），再按以下顺序回答：

1. **结论**：用一句直白的话判断（例如“有所改进，但还不够好”）。
2. **做得好的地方**：给出 2–4 个具体点。
3. **按危害排序的问题**：真实性（数字不一致、误导性的增减幅或趋势图）→ 显著性（视线是否落在需要操作的地方，还是异常恰好最不显眼？）→ 层级（什么领头，什么争夺注意）→ 文字（应改成图形或工具提示的句子）→ 组件异味（qa.md 的问题清单）→ 细节打磨。每个问题都指出元素、读者看见的效果以及修复方式。
4. 提议一次性修复；提交代码之前先查看截图。

每次评审都先查找真实性问题；同一个问题给出两个不同答案，再好看的屏幕也不合格。真实却像报告一样堆满数字下方的句子和“洞察”行的页面，同样不通过少文字检查。此类失败与修复的完整案例见 [references/case-study-school-dashboard.md](references/case-study-school-dashboard.md)。

## 始终适用的规则

- **颜色跟随数据实体**：人员或流量使用一个色相，资金使用一个色相；暖色只用于异常；红色仅标记基数有意义时的不利变化。越接近问题，强度越高；不要因为“好”而加深颜色。未选中的卡片、前一周期与次要数据系列用灰色。红绿不能成为唯一的信息载体。
- **对比背景**：每个醒目数字都要用一种基准回答“相对什么而言”：前一周期（比较相同已过去时长）、目标、正常区间或历史。
- **数字**：使用等宽数字，在列中右对齐；精度取决于决策需要（卡片写 5.2M，工具提示给精确值）；坐标轴使用紧凑刻度（1k、$4k）；低于 0.1% 显示 `<0.1%`；没有数据用 `—`，绝不伪造 $0 或 0%。
- **周期比较**：上一周期使用灰色或虚线；未结束的周期用虚线绘制。基数小于约 5 时，用灰色显示“原来是 1”，不要使用刺眼的红色 −100%。涨跌颜色遵循业务含义：成本、CPL、流失率等越低越好的指标应反转红绿；支出、数量等中性指标保持灰色。
- **只说一次**：同一数字出现两次时必须一致，而且只作为一次主要结论强调。
- **在数据本身标记关注事项**：异常在它出现的位置直接标注（暖色热力图单元格、红色标签），操作紧邻该标记，而不是另写一句重复说明。
- **选中态**：柔和的带色填充，加一圈淡淡的边框。
- **占比条**：在列表行底部沿边缘放 3 px 的细圆角轨道。
- **控件定制且克制**：日期使用弹出日历；手机导航用菜单网格；分段标签缩窄而不是横向滚动。
- **信息密度**：14 px 基础字号、16 px 图标、1 / 1.2 / 1.5 的描边粗细，优先中等字重而非半粗体（[tokens.md](references/tokens.md)）。
- **宽度随屏幕增长**：仪表盘在更宽的屏幕上增加列数，而不是让一条窄内容列悬浮在大片空白里。

## 默认风格（House style）

平静、精致、少文字。浅灰页面、带柔和边框的白色卡片；胶囊形工具栏（日期范围、筛选，以及带绿点的“已更新”标签）；KPI 卡片包括标签、单色小图标方块、大数字和带一个词基准的涨跌值；带实色端帽的浅色条；胶囊形热力图单元格；分段占比条；字母头像；仅显示一个大数字的深色工具提示。一个蓝色强调色（#3e63dd），再加资金绿色；支持亮色和暗色。**项目自有设计系统优先于这个默认风格，用户明确的喜好又优先于前两者**——在工作开头记录并遵循。
