# 恢复场景与反例

示例名称用于解释判断，不是实际生产操作记录。

## 同版本 worker 退出

worker unit 退出，现行制品摘要、配置身份和数据/schema 契约均未变，启动脚本不拉取制品或运行 migration。已有运行手册允许重启并规定队列恢复验证。

按同一 run 记录启动前状态，通过 ops-execute 重启，验证 unit 就绪和原队列消费；新 PID 作为观测，稳定实例 ID 保持。恢复不自动证明退出原因已找到。

## 相同 tag 已对应不同制品

当前声明 tag 为 stable，但本地 image ID 与上次不同，启动脚本还会 pull。无法证明同部署恢复，先保存差异并交项目流程；不能因 tag 字符串一致就执行。

## 名为 repair 的脚本

脚本包含拉新镜像、替换 compose 配置和 migrate。它属于项目发布/迁移路径。若已有纯运行恢复入口可以满足当前授权目标，核实后使用；否则形成交接，不以脚本名放行。

## 多项目共享 Redis

shop 和 billing 共用 redis-main。只指定一个执行者恢复该实际实例，再分别验证两项目的消费路径。shop 恢复而 billing 仍失败，汇总为部分恢复；不得为了 billing 再让另一个 Agent 无条件重启 Redis。

## 数据恢复需要旧 schema

备份来自旧 schema，当前应用需要新 schema；恢复配方要求换旧应用后做转换。这是项目协同任务，ops 交付备份证据、当前状态和数据影响，不擅自切版。

## SSH 断开但任务可能已经完成

恢复请求发送后连接断开。先查询已有任务与现场，不重复发送。现场健康但后端结果无法确认时，执行状态与现场状态分别保留，不用当前健康编造原任务成功。
