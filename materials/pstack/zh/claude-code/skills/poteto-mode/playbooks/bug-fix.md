### 缺陷修复

**你对本任务负责。制定计划、审查、验证。** 将调查和修复委派给子代理，自己保持主导。按照 Subagents 部分，为每个子代理选择适合任务的推理级别。

保持科学。每行交付代码都追溯到运行证据。“也许有用”的双保险是假设，不是修复，不交付。证据反驳假设时，回滚它促成的改动。只交付证据支持的最小变化。

1. 通过控制技能在匹配界面亲自复现，见不可妥协项，即使调试或观测协议让你请用户复现。只有给出明确具体理由，说明控制界面无法触及目标，且已驱动到能力边界后，才询问用户。不能直接复现时，合成触发条件、收紧条件或加入观测，直到触发。
2. 对原因进行二分排查。形成候选假设，再逐个排除，直到只剩一个。以受影响子系统的追踪结果和 **why** 技能提供的回归历史为假设起点。每一轮选择能最大限度缩小剩余问题空间的分割方式，获取运行时证据并排除假设。当程序状态不明确时，加入插桩或日志，在代码运行时阅读结果。不要猜测。对于漫长或顽固的排查，使用 Cursor 的 `/loop` 命令持续推进。在第 3 步的 `architect` 或 `interrogate` 并行展开之前，用运行时证据确认最后留下的*机制*。
3. 规划修复。如果跨越函数边界，先运行 `architect`。将实现委派给使用已配置 bug-fix 模型的子代理（默认 `claude-opus-5-5-xhigh-fast`），并给出明确范围。
4. 在同一界面验证。原始复现现在通过。“无结论”或错误界面不算通过，必须指出。单元测试显示分支行为，不能证明缺陷不存在。
5. 安排提交，让失败复现先于修复进入 git 历史。缺陷有便宜本地测试路径时，按 **tdd** 技能执行失败测试先行节奏；测试昂贵、集成复杂或不明确时跳过。
   这是 **sequence-verifiable-units** 原则技能的标准形态：失败测试在前，修复在上。
6. 执行 **Opening a PR**。

**回复：** 什么坏了、根因、修复、如何验证。原样粘贴先失败后通过的复现输出。
