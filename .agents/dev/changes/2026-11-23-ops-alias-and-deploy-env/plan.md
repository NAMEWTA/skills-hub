# ops 主机别名与 DBX 部署登录资料实施计划

目标：在 `D:/Document/code/ops` 可以直接说「检查 `01`」，由 `.agents/ops/registry/01.md` 定位主机。DBX 每次获授权部署时，已经掌握且实际使用的登录资料直接以明文写入 `.agents/ops/projects/dbx/env.md`，打开即可查看和复制。

交付点：源码规则与隔离验收通过、真实运维工作根完成本地切换。首次真实部署、凭据同步、Git 推送和 npm 发布不在本次范围。

## 共用契约

| 对象 | 文件与职责 |
| --- | --- |
| 主机的现行别名 | `registry/<别名>.md` 的路径是别名本身。改别名直接重命名并更新现行链接，不留旧文件或第二份映射。同一主机只换主机名、IP 或连接方式而仍称作 `01` 时，直接替换 `01.md` 的相关内容。 |
| 主机的真实身份 | `resource_id` 存在登记正文及 run 的当时快照中。改名不改身份；整机替换使用新 ID，只有明确承接旧别名才替换该路径。现行登记不改写历史。 |
| DBX 部署入口 | `.agents/ops/projects/dbx/deployment.md` 保留部署步骤和路径引用。由项目自己的部署流程更新登录资料，不把部署动作转交 `ops`。 |
| DBX 登录资料 | `.agents/ops/projects/dbx/env.md` 是用户指定的明文查阅位置。按环境和用途更新同一条目，保留原有说明及其他环境。部署记录和运行日志不重复保存值。 |

现状依据：源码基线为 `3880371`。当前[登记模型](../../../../skills/ops/ops-inventory/references/runtime-model.md)允许按资源拆文件，但未定义用户别名路径。[部署凭据方法](../../../../skills/dev/dev-deploy/references/secrets-recovery.md)允许用户指定的受限本地配置，但不区分作为凭据文件的 `env.md` 与普通 Markdown。实际工作根已有 `thillers.md`、`deployment.md`、`env.md`；搜索到现行部署文档和一份旧 run 汇总提及旧登记名。本轮未读取真实凭据值。

## 整体验收

1. 在源码根使用 Node.js 22.14+ 执行 `npm run check`、`npm run check:full` 和 `npm run check:package`。检查技能入口、引用、生成导航、安装升级和打包。源码示例与制品不得包含真实 DBX 文件或凭据。
2. 在临时运维根使用[源码安装入口](../../../../docs/usage/installation.md)安装受影响的技能。从新会话登记 `01`、按别名查询、改连接定位、改别名。再用 DBX 隔离场景演练首次部署、重复部署、部分失败和回滚，用合成值核对目标文件与非目标文件。记录宿主实际读取的入口和文件，静态检查不能代替此步骤。
3. 联验通过后，在真实工作根只做本地切换与核对。`registry/01.md` 成为唯一现行登记，DBX 部署文档指向有效的新路径及现有 `env.md`，`env.md` 内容和旧 run 的身份事实不变。不连接主机，不部署，不改变账号。首次真实凭据写入只能在后续已授权部署中验证。
