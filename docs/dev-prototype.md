# 可交互原型与可视化意图确认

`dev-prototype` 把已收敛的需求转为可操作 HTML，让用户体验并确认具体效果。已确认原型规定其覆盖范围内的布局和交互，规格说明业务规则与其他约束，任务安排实现。完整执行方法见[技能入口](../skills/dev/dev-prototype/SKILL.md)。

## 在开发流程中的分工

| 技能 | 负责的问题 |
| --- | --- |
| `dev-intake` | 整理来源、事实、目标、范围、已有决定和缺口 |
| `dev-grill` | 按依赖解决尚未确定的产品取舍，沿用调用方的决定记录 |
| `dev-spec` | 哪些行为、边界和结果必须成立 |
| `dev-ui-design` | 如何沿用项目组件、token、布局和交互规范 |
| `dev-prototype` | 用户实际操作后，是否确认这就是期望效果 |
| `dev-plan`、`dev-build` | 按确认版本拆任务并实现真实能力 |
| `dev-review`、`dev-verify` | 产品是否与同版本原型及业务契约一致 |
| `dev-handoff`、`dev-archive` | 保留入口、完整资源、确认范围和证据 |

涉及新增或实质改变的页面、导航、交互，先把已收敛的需求做成完整原型，实际走查并取得用户对适用范围的确认，再实施依赖该体验决定的部分。已有计划可以继续完善，但任务描述不能覆盖确认原型。已有同内容、同范围的有效确认直接复用，其他已授权工作继续。

纯文案小修、无可见变化的内部维护不要求制作 UI。用户要直观理解 API、CLI 或后台行为时，可以用 HTML 演示输入、状态和结果，并标明模拟边界。

## 怎样使用

```text
使用 dev-prototype，完整读取这个需求的规格和设计。
沿用项目的布局、组件、配色、密度和交互习惯，生成可操作的 HTML。
把创建、修改、取消、失败、恢复和完成结果连起来，让我体验并确认。
后续实施与验收使用这个具体版本及其确认范围。
```

已有原型时，补齐未覆盖的需求和旅程，保留已有认可，说明本轮变化。仍有明确的未知问题时，选择探索分支，例如比较两种详情呈现方式。探索分支保留界面变体、逻辑演练和轻量比选方法；已经定案的任务不重新强制生成多个候选，探索结论也不代替完整体验确认。

### 安装和 TUI

在目标项目根目录更新整个 dev 领域，让调用者与方法一起生效：

```sh
npx @namewta/skills-hub@latest install --domain dev --dry-run
npx @namewta/skills-hub@latest install --domain dev
```

部分安装至少一起更新旧方法所在包与原型入口：

```sh
npx @namewta/skills-hub@latest install --skill dev-build dev-prototype
```

安装器不自动安装兄弟依赖，还应更新实际使用的规格、设计、计划、审查和交接等调用者。运行 `npx @namewta/skills-hub@latest` 进入 TUI，可搜索 `dev-prototype`、原型或可视化，并与其他分组混选。源码安装使用 `node /path/to/skills-hub/install.mjs` 及相同参数。

更新旧 `dev-build` 时，迁出的四份原型方法随整包替换移出运行目录，备份保留旧包。已有项目原型和确认记录保持原位置，详见[原型入口迁移](installation.md#开发原型入口迁移)。

## 交付、确认和内容版本

默认产物位于同一需求的 `.agents/dev/changes/<日期-主题>/`，已有有效位置可继续沿用：

| 位置 | 用途 |
| --- | --- |
| `prototype/index.html` | 用户体验入口，简单场景可以自包含 |
| `prototype/` 内的 CSS、JS、图片和字体 | 完整体验资源，复杂场景可由项目工具链导出 |
| `prototype-review.md` | 需求覆盖、风格依据、实际走查、用户反馈、确认版本和缺口 |
| 现有规格、设计、计划、任务、验证与交接文件 | 就近引用同版本、同场景的源码，说明规则与实施安排 |

交付可打开的 HTML 及完整资源，需要服务时给出可靠启动命令。关键操作必须改变前端模拟状态，列表、详情、计数和反馈保持一致；失败与重试保留上下文，并提供自由操作、必要的引导演练和确定性重置。外部能力使用明确的本地模拟，不发送真实邮件、不收费、不操作生产数据或服务器。

生成完成、浏览器走查通过和用户确认分别记录。只有用户针对实际版本和范围的明确认可才构成确认；自然语言反馈即可，不增加指定句式或审批系统。Agent 自检、自己点击按钮、用户沉默、文字方案认可和一般开发授权都不能代签。部分认可只覆盖已经展示并确认的范围。

固定提交或可恢复快照必须包含 HTML 及全部依赖资源。可使用包内工具计算和复核目录内容：

```text
node .agents/skills/dev-prototype/scripts/fingerprint.mjs .agents/dev/changes/<日期-主题>/prototype
node .agents/skills/dev-prototype/scripts/fingerprint.mjs .agents/dev/changes/<日期-主题>/prototype --expect <64位SHA256>
```

工具只用 Node 标准库，按排序后的相对路径和文件内容计算 SHA-256。文件增删、修改和改名改变摘要，目录移动与修改时间不影响摘要。目录中须有 `.html` 或 `.htm` 文件，工具拒绝空目录、符号链接和特殊文件，全程只读。

指纹只用于识别内容变化。Git 或快照仍须保留旧资源，确认记录和命令输出放在原型目录之外，目录外或远程依赖另行固定并说明。资源改变后定位影响，保留旧确认，更新引用并对齐受影响范围；只更换摘要不能沿用旧版本的确认。

## 实施怎样对照

用户最新明确决定优先。已确认原型规定覆盖范围内的可见效果，规格继续约束业务、安全、权限、数据一致性、性能和未在 HTML 中表达的规则。发现冲突或原型缺陷时说明并修正，不复制已知错误，也不把模拟成功当作生产能力通过。

说明文档按章节定位真实 HTML 节点、CSS 选择器或 token、JS 函数或事件，以及对应场景。单文件 HTML 中的 style 和 script 同样可以引用。正式产品在同页面、同状态、同视口、同主题下对照，生产技术栈可以调整，已确认体验不能被任务清单或实现方便性改写。

随包[采购申请示例](../skills/dev/dev-prototype/references/design-evidence-example.md)演示筛选、选择、dialog、焦点、失败重试和响应式的源码定位。它用于学习证据引用，不是项目默认视觉模板或已经获用户确认的完整需求原型。

## 验证边界

在可用浏览器中走通适用的用户旅程、异常恢复和键盘焦点行为，记录页面、状态、视口、主题及实际结果。结构检查只能核对资源和引用，模拟状态检查只能说明对应逻辑；两者不能代替浏览器观察、真实用户反馈或生产接口验证。

缺少浏览器时交付可检查产物并写明未验证范围。复核只针对变化、矛盾和剩余风险，已有有效确认与证据继续使用。完整资源、确认范围和恢复入口随同一需求交接与归档。
