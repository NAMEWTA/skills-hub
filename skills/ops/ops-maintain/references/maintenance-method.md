# 计划性维护方法

## 1. 把请求落到实际对象

明确这次维护要改变的运行状态、可观察完成条件、环境、稳定目标和实际维护入口。服务器、服务、实例及逻辑数据范围分别列出。

从运维根、现行手册和已有任务读取授权与限制。用户已经明确的窗口、范围与动作持续有效。若只要求“看看今晚维护影响谁”，交付影响分析，不自动执行维护。

由 ops-execute 建立或接续主 run。缺少记录方法、目标身份或必要权限时完成能做的材料核对和计划，不自行创建无记录执行路径。

## 2. 核对实际效果与领域边界

检查维护入口的真实操作、参数、引用文件、依赖任务及可能启动的服务。名称含 maintain、repair、restart 或 check 都不保证只做运维。

下列情况交项目自己的部署/开发流程：应用或中间件版本变化；拉取、构建或切换制品；修改项目部署配置、永久拓扑或规模；执行 schema migration；新增服务或持久资源。

主机 OS/内核维护可以属于本次运维，但不能把安装在同机的项目服务升级自动视为 OS 更新。先审查实际包集合、依赖变化、安装脚本和服务重启影响，不能只看命令上的包名。

## 3. 分析影响与冲突

通过 ops-inventory 核验直接对象、同机无关服务、共享资源消费者与未知资产。记录影响范围不自动扩大操作权限。

| 操作范围 | 至少核对的影响 |
| --- | --- |
| 单个 unit/实例 | 本实例、所属服务、真实消费者及仍可用的其他实例 |
| 共享代理/缓存/数据库 | 所有已知消费者、逻辑范围与完整实例影响的区别 |
| 主机包维护/重启 | 主机全部已知运行对象、挂载、启动服务和未知覆盖 |
| 备份/清理 | 具体数据源、对象路径、读写负载、保留要求和恢复依赖 |

确认现有任务、维护窗口、可用容量、冗余、就绪条件和回退/停止方案。只有实际验证的冗余才能支持逐机操作；“有两个副本”不足以证明可安全停其中一个。

按实际资源协调并发，复用已有后端锁与维护机制。并行取证可以独立进行；同一共享资源的变更由唯一执行者负责。本地写锁不等于跨控制端互斥。

## 4. 准备有限动作和验证

列出实际要执行的动作、先决条件、影响、预期结果、停止条件和每一步的验证。已授权的准备与可逆验证持续进行；只在真正缺少目标、权限或影响超出范围时停下。

基线来自真实现场与项目规则。维护前保存必要版本、资源定位、当前健康、任务引用与恢复材料；不把秘密写进报告。备份任务是否成功和备份是否可恢复分别核验。

dry-run/模拟只在工具实际支持时使用，其可能访问外部服务、锁表或触发插件。模拟结果不自动证明真实执行无副作用，实际包集合或配置发生变化后要重新核对。

## 5. 通过既有工具执行

向 ops-execute 传入核验目标、动作、真实入口、已有授权、验证和停止条件。单一写入者将实际步骤、后端任务 ID、逐目标结果和异常保存到同一 run。

只执行准备好的对象范围。新的警告、待重启服务、依赖变更或未知资产可能改变影响范围：先判断其真实含义，不自动接受工具的“全部处理”默认值。

多目标维护保留已成功、失败、未开始和未知的分别结果。不因为一个目标失败就自动撤销其他目标，也不把多机操作宣称事务。

## 6. 验证现场而非命令

复核实际版本/状态、原服务就绪、相关消费者和维护目标。系统命令成功不证明业务恢复；主机可 SSH 不证明数据库和异步任务正常。

比较维护前后同一口径，并说明观察窗口。任务中断、连接断开或记录保存失败时使用 ops-execute 的核实方法，先检查原任务和现场，不盲目重试。需要恢复现有运行状态时交 ops-recover，仍沿用原 run。

## 7. 交付与后续

明确实际完成的动作、各目标现场状态、记录状态、覆盖缺口和未完成事项。发现需要项目发布时形成普通项目交接，引用原 owner 的资料而不改写它。

只有用户要求或既有计划授权才配置定时维护。重复工作有稳定证据且需要沉淀时交 ops-runbook；一次维护成功不自动成为所有项目的通用规则。
