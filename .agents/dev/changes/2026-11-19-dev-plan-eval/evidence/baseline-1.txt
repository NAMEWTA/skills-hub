# 邮件模块总体路线与关键风险

## 总体路线

先用一个普通 IMAP 账号打通「连接 → 同步 → 阅读 → 离线重开」的完整路径，同时尽早验证 SMTP 在响应丢失时的行为。前者确立邮件来源和 Vault 隔离规则，后者决定发件箱怎样记录和恢复投递结果。

| 顺序 | 可演示结果 | 关键依赖 |
| --- | --- | --- |
| 1. 接通并阅读一个邮箱 | 从独立「邮件」模块测试连接、选择 INBOX、保存账号并打开邮件。断网重开仍能读缓存。正文就绪且进入视口后才触发独立标读，IMAP 经服务器确认后才显示远端同步成功。 | 从本段确立本地消息 ID 到远端来源的映射、Vault 与账号生命周期、只读限制，以及工作台调用的 Mail handler。 |
| 2. 扩展多账号与定位 | 补齐 18 个预设和自定义、Google/Microsoft 授权及各实际同步路径。用户能按公开参与者浏览往来，从跨账号搜索或通知定位原邮件，并看到实际同步路径和修复入口。同步周期设置可观察到调度变化。 | OAuth 和协议分支沿用第 1 段的账号与来源契约。聚合、搜索和定位可先用模拟缓存并行推进。 |
| 3. 写信与查投递结果 | 从来源账号回复或转发，离线保存富文本草稿和受管附件。恢复联网后发送，重启仍能查到逐收件人的投递结果。 | 回复与转发依赖第 1 段的来源契约。草稿可与第 2 段并行，发送交付取决于并发提交和故障恢复验证。 |
| 4. 恢复、开放能力与整体验收 | 用 Huhu 新格式验证整 Vault 恢复与 S6b 邮件子集预检和提交。CLI/MCP 经 #6 接入同一套能力，干净安装默认关闭。AI 默认关闭，由用户选中内容并确认目的服务后调用。 | 恢复需消费稳定的草稿、附件和投递记录。AI 可先用模拟内容验证，外部入口验收依赖 #6 的目录、能力开关和传输。 |

## 关键风险

- **重复投递。** 工作台、CLI 和 MCP 对同一草稿版本并发提交时，应查到同一业务操作。只有 SMTP 明确接受才能记为已接受，部分接受按收件人记录。用接受后响应丢失、部分接受和进程重启验证：结果未知时提供核对入口，仅可证明未提交的收件人可常规重试，重启和恢复均不触发投递。稳定 Message-ID 用于关联。
- **串账号、错取正文或错标读。** 正文和标记须按本地 ID 回到实际协议来源。用切 Vault 后迟到响应、IMAP UIDVALIDITY 变化、Gmail/Graph 分页中断及游标失效验证隔离和补偿。Gmail/Graph 基线标读返回 `remoteSynced:false`，旧同步须保留用户刚做的本地标记。
- **授权成功但邮箱权限不足。** 用真实 Google、Microsoft 测试邮箱分别验证授权、正文能力和失败后的修复路径。明确区分 Outlook IMAP 与 Graph，核对 Graph 的 audience 和 scope，仅有 `Mail.ReadBasic` 时明确呈现正文及附件能力限制。凭据替换失败应保有旧配置，连接恢复须维持 TLS 和证书校验。
- **泄露私有内容或绕过入口限制。** 用多账号、多目录和密送样本验证同账号副本归并、全历史先聚合再分页，以及 Bcc 只出现在相应私有发件记录。阅读器默认零外部资源请求。工作台、后台和 CLI/MCP 共同验证只读限制、插件停用及跨 Vault 隔离，AI 单独验证选区与目的服务确认。
- **恢复后丢失唯一副本。** 用缺附件字节、缺凭据和含未知投递结果的备份演练恢复。核对草稿、发件记录和本地标记可恢复，缺字节附件可重绑，新机凭据可重新配置。清缓存、重建 FTS 和 Git 同步均须保留唯一数据副本。账号删除涉及在途发送的部分，以 `design.md` 中的契约为实施前提。

最终验收由 Mail 整合负责人按 M-01 至 M-08、来源操作清单及映射收口。真实邮箱证明协议能力，受控故障证明发送与恢复边界，桌面和 Web 按有效确认的原型版本核对实际交互。本路线依据所给 `mail.md` 拟定，代码基线、既有切片、来源快照及原型确认范围仍待实施前核对。
