# Mail 离线草稿、附件恢复与投递实施计划

**目标。** 用户可断网续写并恢复草稿，可恢复受管附件或重新绑定缺失字节，并能在重启后从发件箱查明每位收件人的 SMTP 提交结果。只有能够证明未提交的收件人可进入常规重试。

**接续点。** 规划完成，尚无实现或运行证据。本会话进入开发时，从 01 开始。先核对现有计划和切片编号，再定位写信浮层、统一能力 handler、Vault 持久化和现有验证入口。沿用已有任务标识，本文编号仅用于当前计划的依赖导航。

**交付边界。** 本轮交付计划正文。后续实施按桌面、Web 和已开放的 CLI/MCP 能力采证。当前规划及原型场景使用模拟账号、邮件、附件和投递结果。

**依据。** 使用 `dev-plan` 的垂直切片方法。行为依据为本会话提供的 `mail.md`，重点是 M-06、M-07、「网络事实、发送与持久数据」和相关账号约束。实施时核对 `design.md` 的在途发送与账号删除约定、已有 `plan.md` 的关闭条件，以及 `source.md` 的 §8.2、§10 验收与来源映射。本轮材料给出了这些引用，具体内容、代码路径、运行命令和原型确认范围均待核实。

## 01 离线关闭后恢复草稿

**交付与依赖。** 无前置切片。负责写信浮层的保存、重开、续编和显式丢弃，贯穿桌面/Web、草稿 handler 与 Vault 持久化。向 02 提供草稿及附件引用的持久化契约，向 03 提供草稿版本与账号归属。

- [ ] 断网或 Mail 密钥暂不可用时，在可写 Vault 写入富文本、链接、发件人、To/Cc/Bcc 和主题。关闭后重启，打开同一草稿并核对字段。修改正文或收件人后保存，得到新版本。
- [ ] 注入保存失败，再关闭有内容的编辑器。编辑器保留输入并显示可恢复错误，旧持久版本仍可打开。恢复写入后可重新保存，显式丢弃按确认的交互生效。
- [ ] 从只读 Vault 打开已有草稿。通过工作台和已开放的外部能力尝试保存或丢弃，均返回只读拒绝，原 Vault 字节保持一致。切 Vault、停用插件或关闭时，迟到响应无法写入新 Vault 或覆盖当前编辑状态。

## 02 重开与恢复受管附件

**交付与依赖。** 消费 01 的草稿及附件引用契约。负责附件导入、去重、移除、字节持久化、缺失提示和重绑，为 03 提供可读取、可校验的附件快照。Mail 子集包的预检与提交沿用 S6b。

- [ ] 通过写信入口添加同一附件两次，按确认的规则去重。保存后移走原始文件、退出并重启，核对保留附件的字节摘要。移除一个引用后，其他仍引用该附件的草稿或历史可以继续读取。
- [ ] 注入写入中断或缺失字节，重开草稿。界面列出待重绑项，附件名与可用字节状态清楚可辨。完成重绑并重启后可读取字节。鉴于重绑可改变实际发送内容，实施时核实其对草稿版本及历史附件引用的影响。
- [ ] 通过已开放的附件能力传入受限句柄并流式导入大附件。无效句柄、跨 Vault 句柄和任意 Engine 主机路径均被拒绝，失败时草稿仍可打开。
- [ ] 使用模拟恢复数据分别验证字节齐全和缺失两种草稿。与 S6b 联验时，让新版 Mail 子集包在目标 Vault 预检后提交，确认完整附件可读、缺字节附件待重绑、只读目标拒绝提交。整 Vault 包按规格恢复到新空目录。S6b 的包提交实现只阻塞这条联验。

## 03 提交一个草稿版本并查询回执

**交付与依赖。** 消费 01 的版本与归属契约，以及 02 的可校验附件快照契约。负责统一提交 handler、业务操作身份、SMTP 尝试、逐收件人事实的持久化和最小回执查询。04 消费本项的操作、尝试与收件人查询契约。

- [ ] 同一 Vault 内，通过工作台双击并用已开放的 CLI/MCP 并发提交同一草稿版本。对有效提交，所有入口返回同一业务操作，受控 SMTP 只观察到一次初始提交。重启后查询仍得到同一操作与历史。编辑正文或收件人后显式提交新版本，生成独立业务操作。
- [ ] 在 SMTP 副作用前持久化操作、不可变发送快照和尝试信息。受控 SMTP 明确接受后才记录对应收件人为已接受。对单封含多个收件人的邮件，分别验证收件人阶段拒绝和邮件数据阶段的最终响应。SMTP 接受仅表明服务器接受提交。
- [ ] 在可证明尚未提交处断开、在服务器可能已接受但客户端未收到最终响应处断开，以及收到接受响应但结果未持久化时终止进程。重启后，分别查到可证未提交或结果未知。无法证明的情况保持未知，同一操作内已落盘的确定结果仍可查询。
- [ ] 对只读 Vault、接收专用账号、缺附件字节和不可用认证逐项提交。入口返回具体阻断原因，模拟 SMTP 观察到零次提交。工作台与已开放的 CLI/MCP 使用同一能力约束，且插件停用后拒绝调用。复核账号删除与在途发送按 `design.md` 处理。

## 04 从发件箱核对部分成功、未知与重试

**交付与依赖。** 消费 03 的稳定查询、逐收件人结果和尝试契约。负责发件箱选择恢复、续编入口、每次投递明细、核对入口、常规重试和本地记录删除。稳定契约与模拟回执足以开始界面开发，真实投递实现用于最终联验。

- [ ] 让受控 SMTP 接受 A、拒绝 B，发件箱显示部分成功及逐收件人依据。修复 B 的问题后发起常规重试，SMTP 信封仅含 B。历史保留两次尝试。并发触发同一重试时，只创建一次实际尝试。
- [ ] 让服务器可能已接受 A，但客户端未获得确定回执，同时保留 B 的未提交证据。发件箱明确显示 A 为「结果未知」并提供核对入口。常规重试只包含 B。稳定 Message-ID 用于关联，单凭它无法确认唯一投递。
- [ ] 对未知操作分别关闭界面、触发超时、重启、恢复备份和重连。发件记录可查询，新增 SMTP 提交次数为零。清缓存、重建 FTS 和 Git 同步同样产生零次提交，并保留唯一的本地草稿、附件及发件记录。
- [ ] 重开发件箱恢复选择，可打开投递明细或续编对应草稿。本机发件记录与服务器 Drafts/Sent 分别显示。仅密送邮件可从发件箱查看，Bcc 只出现在对应的私有发件记录。删除本地记录后，服务器邮箱和其他账号数据保持一致。同一草稿版本再次提交时仍遵守 03 的业务操作身份约束。

## 顺序与实施边界

01 是首个实施切片。草稿版本和附件引用稳定后，02 和 03 可分别推进附件恢复与发送快照的实现。03 的投递联验需要 02 的附件字节读取能力。03 的查询契约与回执样例就绪后，04 可先验证各状态和操作，最终接入真实 handler。

01 负责草稿版本规则，02 负责附件引用与字节生命周期，03 负责投递记录、尝试身份和结果判定，04 负责发件箱操作与整合验收。共享 schema、迁移顺序和能力注册由本会话实施者统一更新，桌面、Web、CLI/MCP 消费同一 handler。实施时先核对现有注册点及 #6 已交付的传输能力。外部工具关闭时复验工作台仍可用。

实现前核对 `prototype/index.html` 与 `prototype-review.md`，记录实际版本或指纹、用户确认范围，以及写信关闭失败、附件待重绑、发件箱部分成功、未知结果和窄屏操作对应的源码位置。确认缺口只限制依赖该体验决定的界面部分，持久化、投递契约与故障测试可继续。优先从现有设计核实未知结果核对入口、本地删除后的操作查询语义，以及重绑是否改变发送快照。若资料仍有会改变用户行为的分歧，仅暂停对应实现。

## 整合验收与证据

由 04 负责串联场景。在隔离 Vault 中断网写信并挂载附件，重启后续编。恢复模拟备份并重绑缺失附件，再通过实际入口提交。分别注入部分接受与结果未知，重启后核对发件箱及已开放的外部查询入口，显式重试可证未提交的收件人。对照 SMTP 收件人与提交记录、持久化回执和界面状态，确认收件人集合、尝试次数与每次结果一致，并确认重启和恢复期间的提交次数为零。

实施时按切片记录工作树或提交、Vault 模式、测试输入、故障位置、操作入口及可观察结果。拟将投递记录和桌面/Web 截图放在本计划目录下的 `evidence/<切片>/<场景>/`。界面在确认版原型对应的状态、主题和视口核对。项目级关闭所需的真实邮箱证据按已有计划另行采集，模拟 SMTP 证据用于证明受控故障与提交次数。

本轮已按所给规格核对切片覆盖与阻塞关系。仓库基线、原型版本、已有任务编号及运行证据待开发时核实。本轮无实际文件写入。
