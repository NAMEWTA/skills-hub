# 分诊参考：部署与发布（深入完整示例）

> 本文件展示了**积累一季度事件后**的参考是什么样子；
> 你的版本起初会更薄（本目录其他参考展示了中等形态），
> 并随着 `lessons.md` 条目成熟后通过 PR 融入而增长。
> 下文全部是工具包 webshop-CI 场景中的虚构示例内容，使用时替换。
> 底部提炼规则部分是其*结构*值得逐字复刻的地方——
> 等你的真实事件付出过代价后，各类别来之不易的教训就放在那里。

## 症状

- 部署卡住：流水线显示“进行中”，远超平常窗口
- 部署后回归：发布刚完成，错误率/延迟就发生变化
- 部署通知沉默：部署流安静了，但变更显然还在落地
  （或反过来——部署停了，却没人被告知）
- 配置“自己恢复了”：手工修复几小时内消失
- 逐步发布异常：金丝雀正常但全量阶段异常，或卡在两个步骤之间

## 首轮检查（按顺序；时间线已能解释症状时停止）

1. **时间线优先。** 从 `deploys` 流和 `flags` 变更历史中取得
   异常开始前 2h 内的所有变化：部署、功能开关放量、配置模板变化、
   基础设施发布。症状开始的那一分钟，是整个事件中区分力最强的事实；
   阅读任何讨论串前，先从指标确定它。
   `(sources: {{deploys}}, {{flags}}, {{metrics}})`
2. **部署流水线本身健康吗？** 区分“我们的改动坏了”和“部署机制坏了”：
   查看部署系统自身的错误率和队列，不只看自己的服务。
   `(query: {{metrics}} → deploy.pipeline.state, deploy.queue.age)`
3. **接收端看到了什么？** 对任何“甲不再和乙通信”的症状
   （webhook、通知、回调），先读取乙的访问日志中甲的调用，
   再为甲提出理论。完全没有记录，与有记录但报错，是不同事件；
   最常见的发现是一个实际身份出乎所有人意料的 403
   （见后文完整调查）。
   `(query: {{logs}} → receiver access log, filtered to the sender's path)`
4. **手工修复消失检查。** 若人的手动缓解消失了，检查部署自动化
   是否把模板重新应用到手工改动之上。自动化撤销手动缓解是一种
   反复出现、值得单独检查的原因，不应只作脚注；它意味着
   *持久*修复必须进入模板，手工路径只能争取时间。
   `(sources: {{deploys}} — template apply events around the vanish time)`
5. **认真读一次失败。** 从日志存储读取一个有代表性的失败部署的
   完整日志，而不只是摘要行。部署“失败”经常是准入/策略拒绝
   或配额错误，却伪装成代码问题。

## 关联表

| 如果看到 | 同时 | 通常意味着 | 那么 |
|---|---|---|---|
| 部署“成功”，但下游通知从未触发 | 之前所有“端到端”测试都在发送方下游注入数据 | 你从未真正测试发送方，应将整条流水线视为尚未从真正入口验证 | 在信任任何组件前，先从真实入口测试 *（出现 1 次：INC-142；代价是 3 次错误的“已验证”声明）* |
| 接收端对“权限正确”的调用返回 403 | 调用者经过代理或身份模拟跳转认证 | 接收端看到的是最后一跳的身份，而非最初发起方；应问“实际到达的是哪个主体”，而非“我配置了什么” | 取得接收端认证日志，读取实际身份；为该主体修正授权，并限定到它需要的那一条路径 *（出现 1 次：INC-142）* |
| 手工配置修复几小时内消失 | 部署自动化通过模板管理该配置 | 自动化把模板重新应用到手工改动之上 | 将修复纳入模板；说明手工路径只能撑到下次 apply *（出现 2 次：INC-137、INC-151）* |
| 证据说了不可能的事（“已经合并的修复不在文件中”） | 你通过缓存、contents API 或搜索工具读取 | 先怀疑测量工具，再怀疑系统：缓存会给旧数据，一些搜索工具会悄悄跳过被误判为二进制的文件 | 固定到提交 SHA 读取；排除检测工具的特殊行为后重跑搜索 *（出现 2 次：INC-142、INC-155）* |
| 部署队列已排空，但监控图每次部署后都变平 | 指标为每个 pod 输出一条序列，某消费者读取第一条 | 消费者读的是已死亡 pod 最后几分钟的数据，而非实时系统 | 在查询处跨序列聚合（max/sum），绝不按序号访问序列列表 *（出现 1 次：INC-149）* |
| 部署后回归，但部署差异看起来无关 | 同一窗口内推进了功能开关放量 | 原因是开关而非部署；两种变更流必须一起读，否则都不算读过 | 责怪部署前，先检查窗口内 `flags` 历史 *（出现 2 次：INC-133、INC-146）* |
| 发布卡在金丝雀与全量之间 | 放量关卡读的指标不再输出（不是指标变红） | 关卡在缺失数据时采取关闭行为，等待一个不会再来的信号 | 修复信号，或让人明确决定该步骤；绝不把“没有数据”当成“健康” *（出现 1 次，未验证：INC-158）* |
| 全部部署停止，部署系统健康 | 窗口内有组织级策略/准入变更 | 执行约束层拒绝了过去允许的操作，失效时采取关闭行为 | 读取所指策略的准入日志，附精确拒绝行转交策略负责人 *（出现 1 次：INC-144）* |
| “重试部署”修好了它 | 其他什么都没变 | 这是竞争条件或依赖短暂波动，不是修复，它还会回来 | 在 lessons.md 中记为未解决，并记下重试；重试成功是证据，不是解决 *（出现 3 次：INC-135、INC-140、INC-153）* |
| “导致问题”的部署发生在指标变化之后 | 开始时间来自讨论串，而非数据 | 人的记忆把开始时间记错了，应重新从指标确定 | 从指标首次异常的那一分钟重新建立时间线 *（出现 2 次：INC-139、INC-146）* |

## 一次完整的长调查（日志体）

产生了上述一半条目的事件——INC-142，“部署状态 webhook 沉默了”。
保留在这里是因为，即使具体内容不同，调查的*形态*也会再次出现。

**症状。** 宣布部署的频道在 {{a Tuesday}} 安静下来；
部署本身仍在落地。第六天才被人注意到
（“这个流为什么这么安静？”）——没有为通知流沉默设置告警。

**纸面检查——所有本应让它工作的条件，都已验证 ✅：**

| 检查 | 结果 |
|---|---|
| 部署系统配置模板中存在 webhook URL | ✅ |
| 接收端端点在线（整周可用性图平稳绿灯） | ✅ |
| 接收端认证配置列出了部署系统的服务账户 | ✅ |
| 上次模板应用成功 | ✅ |

纸面全部绿灯，实际观测到的送达为零。这张表是典型信号：
当全部是 ✅ 而事情仍不工作时，停止反复核对配置，
去看实际到达了什么。

**第一个令人警醒的发现。** “端到端测试里工作正常”——
但之前所有 e2e 测试都在发送方*下游*注入载荷
（“模拟 webhook 会发送的内容”），因为在测试中触发真实部署不方便。
发送方从来没有被执行过。讨论串中三次独立的“已验证 ✅”声明，
都追溯到绕过唯一故障组件的测试。

**证据弯路。** 调查中途，代码搜索说部署修订里的文件“没有”
webhook 发送调用——这不可能，模板历史里明明有。
搜索工具悄悄跳过了该文件（误判为二进制）；
固定 SHA 的读取显示该调用一直都在。一个小时耗在了测量工具上，
而不是系统上。

**根因。** 接收端访问日志——本应在第一天作为第 3 步完成的检查——
显示调用一直在到达，只是都被 403 拒绝。部署系统经转发代理认证，
接收端看到的是*代理的*服务身份，而非部署系统身份。
授权列的是发起方，实际到达的主体却从未获得授权。
修复方法是授权代理身份，并刻意限定到那一个 webhook 路径；
窄范围是一项安全决定，不是图省事。

**验证——通过同一个入口。** 不是授权的单元测试：
从真实入口触发一次真实部署，端到端观察直到通知进入频道。
随后添加一个通知流沉默的初始告警（部署持续落地而通知超过 24h 沉默），
使下一次回归由规则捕获，而不是靠某个人无聊时发现。

## 建议功能开关逐步回调（解决模式——由人执行）

若建议的修复是“把 {{flag}} 放量往回调”，建议是一份**计划**，
不是动作：当前百分比、目标百分比、步长、每步保持时间、
每次保持时观察的一个指标，以及中止标准
（“第一步后 10 min 内，结账错误率仍未回到 2% 以下 →
停止并呼叫负责人”）。Claude 可以通过 `flags` 绑定读取功能开关
状态与变更历史——开关变化和部署一样，是时间线事件——
绝不自行触碰开关（CLAUDE.md 规则 1）。
人执行每一步后，针对指定指标进行有界的三次检查观察
（triage 第 9 步）。

## 升级处理

- 全部部署阻塞，或回归正在伤害用户 → 按 `ONCALL.md`
  属于需呼叫值班人员的级别
- 一个服务的部署卡住且有绕行方法 → 工作时间通知服务负责人
- 授权/配置修复的预期恢复窗口：合并后约 30 min；
  模板修复则是一个应用周期。若超过窗口，假设就错了——
  回到首轮检查，把接收端日志列为需要调查的证据。

## 这个类别教会我们的规则（付出过代价的那些）

- **e2e 测试必须从生产流量使用的同一个入口进入流水线。**
  如果不能触发真实发送方，把它写成已知覆盖缺口，
  而不是绿色勾选。
- **问“实际到达的是哪个主体”，绝不要问“我配置了什么”。**
  经代理链到达的身份，以接收端日志为准。
- **用发现故障的同一套工具验证修复。**
  换一种工具验证，证明的是另一件事。
- 当证据说了不可能的事情时，**先怀疑测量工具，再怀疑系统**。
- **执行约束层失效时关闭，信息增强层失效时放行**；
  采取关闭行为的层常会产生链中最有误导性的错误，
  所以要指明退化的是哪个依赖。
- **自动化会把它的模板重新应用到手动修复上。**
  手工缓解争取时间，只有模板版本才是持久的真实配置。
