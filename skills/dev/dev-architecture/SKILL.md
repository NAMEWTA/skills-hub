# 架构与接口设计

结合 Matt Pocock 的 **deep modules** 与 pstack `architect`：先理解现有系统，再从调用者的使用方式反推接口，让复杂度留在有明确所有者的模块内部。

## 理解实际运行路径

读取相关代码、既有词汇表、架构决定和运行证据，串起输入、状态变化、外部边界与结果。只知道文件名不等于理解模块。

改动所有权或分层前，查清现有设计的理由；无法证实的历史原因标为未知。区分“现在如此”与“必须继续如此”。纯绿地需求仍要明确外部集成约束。

只加载相关模块；不要为了画全景图而遍历无关代码。需要解释给用户时，可用 `dev-learn`，未安装也照样从源码完成这一步。

## 先写调用，再写形状

先写两个真实使用例子：调用者提供什么、调用什么、获得什么，以及错误如何表达。由它们推出类型、签名、数据流和职责边界。

**模块**是具有接口和实现的单元，尺度可以是函数、包或跨层功能。**接口**包括调用方必须知道的不变量、顺序、错误、配置与代价，不只是一段类型声明。**深度**衡量少量接口承载多少真实行为，不以代码行数衡量。

让一个模块拥有一组相关知识与状态。边界外解析外部数据、适配协议；边界内依靠明确类型和不变量。只有真实变化需要多个实现时才引入替换接口；不要为假想未来搭空壳。

## 比较不同结构

存在重要取舍时设计至少两种结构上不同的候选，例如：

- 把完整行为集中在一个小接口后。
- 以最常见调用者为中心，让默认用法简单。
- 在确实存在外部依赖时使用适配接口，把领域逻辑与传输隔开。

可以用独立代理给出候选，也可以自行比较；不依赖特定模型、工具或固定代理数量。明显的一行修改无需展开架构竞赛。

比较每种方案的调用者负担、复杂度隐藏、状态所有权、修改集中程度、验证入口和真实成本。阅读 [设计检查与依赖策略](references/design-review.md) 筛查浅模块、泄漏的协议类型、共享写入者和手工同步列表。

推荐一项方案并解释具体得失，不只给菜单。不要为了折中把不同方案的复杂度全部合并。

## 形成可实施的设计

使用 [架构理由模板](references/rationale-template.md)。小改动写在规格或计划中；有足够独立内容时再建 `.agents/changes/<YYYY-MM-DD-slug>/design.md`。复用项目既有布局。

可以在文档中展示签名或伪代码；只有实施确实需要时才创建代码骨架，未实现骨架不是已完成交付。规格确定后按 SDD 实现，再针对行为与边界验证；禁止 TDD。

实施偏离设计时先判断：遗漏了需求、原设计错误，还是实现超出范围。出现多处同形绕行、类型逃生口、调用者必须理解内部规则，重新审视整体形状，不无限加补丁。必要时舍弃旧草图，从新证据重新设计。

只有同时符合“难以逆转、缺背景会令人困惑、存在真实取舍”的决定才值得 ADR。默认 `.agents/notes/decisions/`，记录理由、替代方案及代码指针；普通实现细节留在代码里。

输出最终调用方式、模块形状、选择理由、明确的风险和第一步实施。用户已授权实施时继续，只有明确要求先看设计时停在设计产物。
