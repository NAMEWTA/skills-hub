# 项目协作规则与批次接续验证

使用隔离 Git 项目安装本次技能。夹具有三个 Change，分别将公共响应的 `foo` 改为 `bar`、更新消费者、修正贡献指南错字。批次要求用实际 API 验证消费者，并核对文档改动。

| 场景 | 观察结果 |
| --- | --- |
| 无角色配置，直接给出批次 | Pi 读取安装后的 `dev-program` 和规格，给出 API 与文档可独立开始、消费端实现等待契约、联调等待可运行版本。项目中未生成角色文件。 |
| 用户要在同一个工作区逐项完成 | Pi 按安装后的 `dev-parallel` 给出 API、消费者、文档的可行顺序和验收方法，保留了文档独立这一事实。 |
| 只保存两个规则组 | Pi 通过 `dev-setup` 将“发布复核”和“文案走查”写入已有角色文件。回读确认两组均可选，原有 `inherit-parent`、`medium` 与项目自定义样本标识保留。 |
| 将“发布复核”设为默认 | 新会话从批次和项目文件识别移除 `foo` 触发兼容性复核，明确缺少绑定候选版本的独立评审。 |
| 本次点名“文案走查” | 将安装后的技能、成员规格及项目配置作为输入交给只读 Codex。回复沿用本次选择、保留真实 API 联验条件，并把选择带入接续记录。 |
| 新会话从批次记录恢复 | 在隔离副本中保留项目默认“发布复核”，在批次中记录当次选择“文案走查”。没有历史会话的 Pi 从文件恢复了批次选择，同时沿用已有兼容性样本和跨 Change 验收条件。 |
| 清除项目默认 | 实际回读角色文件确认默认选择已清除，两个规则组、原角色表与自定义段落均保留。 |

上述场景验证技能读取、配置写入和交付条件判断。没有实际发布公共 API 或取得真实发布评审。此前从 Change 清单进入真实 Codex Goal 并跨会话完成样例开发的结果见[批次验证](../2026-11-18-dev-program/verification.md)。
