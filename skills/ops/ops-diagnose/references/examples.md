# 运行调查示例

以下都是方法演示，不是生产验证记录。

## 两项目同时异常

shop/prod 与 billing/prod 都在 08:10 出现缓存超时。清单显示它们使用同一 redis-main，但另一个 billing 导出任务的错误始于 07:40。

将缓存异常关联到同一调查，分别保留各项目的原失败路径；导出错误另行调查。共享服务的恢复只由一个执行者负责。Redis 恢复后 shop 成功而 billing 仍超时，结果是部分恢复；不能把共享服务就绪等同所有消费者恢复。

## 所有配置都对，实际调用失败

API 配置中有访问地址和声明身份，接收端健康检查正常，调用仍被拒绝。先读取接收端该路径与窗口的实际访问/认证记录：若出现代理身份的 403，就用实际到达身份检查授权关系。

输出候选机制和证据；不自行扩大权限。若需要修改项目访问配置，形成交接。验证必须再次经过原调用入口，只测试接收端本地健康不能证明链路修复。

## 不能拿后发生的变化解释起因

用户说“刚重启后坏了”，讨论时间 10:05，重启记录 10:02，指标表明 09:58 已开始失败。先修正时间线，重启可能是一次失败的缓解，不是起因。随后查 09:58 前的共享依赖与资源证据。

## 断线与根因未明

恢复任务已被后端接受，连接随后断开。调查记录写结果未知，交 ops-execute 先核实原任务和现场；不能直接重试。连接恢复后服务正常，只证明当前运行结果，不证明第一次命令是否完整结束或根因已消除。
