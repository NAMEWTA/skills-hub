# 只读检查方法

## 1. 确定这次需要证明什么

把请求改写成可观察问题：例如“shop/prod 的页面、API、worker 及共享 Redis 消费链在最近十五分钟是否正常”。同时保留用户原话，不用自定的全机体检代替它。

明确目标的稳定 ID、环境、控制端工作目录、真实连接入口、时间窗口与时区。项目没有源码仓库也可检查；既有运维清单与运行平台是有效来源。需要补身份或项目服务关系时只调用 ops-inventory 的当前分支。

从已有材料读取服务就绪规则、业务基线、SLO、备份频率、证书身份和维护窗口。没有这些约定时先收集观测，分别标记“没有异常证据”和“尚无足够验收口径”。

## 2. 先取得记录与能力

由 ops-execute 创建或接续同一 run，在第一次现场查询前记录目标、动作、来源与授权范围。检查连接目标、查询权限和可用工具；已配置的 SSH、指标平台、云 API 等按实际能力使用。

“只读”按真实作用判断。某些健康端点会产生业务写入，数据库 EXPLAIN ANALYZE 会运行查询，远端脚本可能清理缓存，诊断包可能重启服务。先查实际行为；不确定时选择无副作用查询或报告限制。普通查询造成访问日志等常规副作用应如实理解，不假称绝对零影响。

输出只选择必要字段。凭据、完整环境变量、数据库连接串、会话令牌和业务正文不进入通用报告。原始日志只在已有受控位置查询；以时间、请求关联 ID、查询语句和必要脱敏摘录保存证据。

## 3. 按目标选择检查层

| 层 | 读取内容 | 需要区分 |
| --- | --- | --- |
| 服务器 | 时钟、运行时长、CPU/内存、磁盘空间与 inode、压力、网络错误 | 一次高值与持续饱和；容量与使用趋势；主机健康与应用健康 |
| 运行单元 | 进程/容器状态、退出原因、重启次数、就绪、当前制品与挂载 | 运行中与就绪；短期 PID/容器 ID 与稳定实例身份 |
| 服务 | 错误、延迟、吞吐、依赖连接、队列积压、数据库/缓存可用性 | 无流量与零错误；单实例健康与服务整体可用 |
| 项目 | 已核验组成服务、共享依赖、实际请求和异步消费路径 | 入口可访问与完整业务链成功；自身失败与共享依赖影响 |
| 运行保障 | TLS 身份/有效期、最近备份时间与成功证据、恢复演练引用 | 文件存在与备份完整；备份成功与实际可恢复 |
| 漂移 | 现场版本/摘要、配置身份、拓扑观测与权威资料的差异 | 声明、观测、推断与未知；旧文档与本次采集 |

检查服务依赖时使用经核验的关系及真实消费范围。数据库连接成功不能证明全部逻辑库可用；缓存 PING 成功不能证明队列消费；代理 200 不能证明后端全部路由。

## 4. 保持观测可比较

每项重要观测都带：来源入口、查询与过滤条件、开始/结束时间、采集时间、单位、聚合口径、覆盖目标和完成状态。

比较前确认时区、时间桶、采样、标签、重启前后实例身份及版本一致。多实例指标按语义选择 sum、max、分位数或逐实例展示，不读取序列列表的第一项当成整个服务。没有数据先检查采集器、权限、时序延迟和目标标签，不能填成零或健康。

历史窗口不足、查询超时、分页未完成、只访问一个副本，都必须说明覆盖限制。“没有找到错误”只有在实际完成相应窗口/范围查询时才能作为反证。

## 5. 形成有分寸的判断

- **正常：** 指定目标与窗口内，必要检查完成，符合实际约定的健康条件。
- **未发现异常：** 已完成的观测未见异常，但缺少充分基线或部分业务证明。
- **发现异常：** 观测与既有规则不符，或原失败路径确实失败；附证据。
- **数据缺失：** 指标/日志/身份未取得，说明原因与影响。
- **检查失败：** 工具、连接、权限或查询本身失败；不直接等同目标故障。
- **覆盖不完整：** 只完成部分目标、时间段或链路，保留逐目标差异。

项目级汇总取决于必需服务、冗余与真实消费路径，不机械按“多数绿色”计算。未知项目归属保持未知，观察到无归属服务不授权停止或清理。

## 6. 交付与后续

保存报告、证据入口和逐目标结果到同一 run，由 ops-execute 的记录方法保持单一写入者。只读与无变化也留下轻量记录，不创建空模板集合。

故障调查交 ops-diagnose；用户已经授权同范围排查时继续，不重复询问。需要维护或恢复时明确实际动作与边界并进入相应 owner。发现版本或声明配置漂移只报告事实及来源，不替项目改配置或切版。

检查完成说明已验证的范围、时间、新鲜度和仍未知事项；不要把命令退出码为零作为项目健康证据。
