# 发现与核验

## 1. 明确问题与可见范围

确认运维工作根、项目/环境或资源线索、需要回答的问题、已授权的只读范围和现有来源。不为一次服务器查询列出全公司的全部账号。登记清单与取得现场操作权限是不同事实。

先调用 `ops-execute` 建立或接续同一 run；初次登记可以无远端目标。材料不足时先分析已经提供的内容，明确缺少身份或记录能力，不先扫描再补账。

## 2. 读取现有权威资料

优先沿已知入口读取已有资产清单、Ansible inventory、云资源查询结果、项目运行手册和现行配置。区分资源声明、已生效部署与历史版本，保留实际来源路径和时间。其他领域文档只读引用，不要求其增加字段或 ops 接收器。

对每个来源记录能回答的范围：哪个账号、环境、主机组、集群或项目，更新频率/最后核验时间，哪些对象它本来就看不到。不存在的资料如实列缺口，不生成假项目填满模板。

## 3. 在明确目标采集运行事实

使用已有连接和工具，Agent 默认留在控制端。SSH host key、连接身份与目标资源的核验沿用既有机制，不关闭验证、不采集秘密、不要求每台机器安装 Agent。

以下是选择检查时的真实命令入口，需以已核验目标替换参数并由当前工具按独立参数传递；不是批量执行脚本。记录前先检查输出是否包含秘密。

| 需要的事实 | 既有入口与观察点 | 限制 |
| --- | --- | --- |
| 主机身份线索 | `hostnamectl` 的静态名称及已有资产系统/云实例 ID | 名称和 machine-id 单独不证明唯一身份，不全量输出秘密 metadata |
| systemd 运行单元 | `systemctl list-units --type=service --all --no-pager`；对明确 unit 取 `Id`、`FragmentPath`、`ActiveState`、`SubState`、`MainPID` | 列表可能包含无关服务；保留未知，不逐个自动重启；unit 文本可能含秘密 |
| 容器与 Compose 定位 | `docker ps --all --no-trunc` 的有限字段；对明确容器取运行 ID、镜像 ID、Compose project/service 标签 | 不全量复制 `docker inspect` 的环境变量；标签只能辅助定位，不能证明项目业务归属 |
| Kubernetes 位置 | 已授权 namespace 内的 workload UID、Pod UID、节点、owner reference 与 service 选择关系 | 只查指定 context/namespace；节点位置是观测，不永久绑定 |
| 托管中间件 | 既有云 API/控制台资源 ID、区域、运行端点引用和状态 | 不向更多账号扩扫；端点本身不能证明所有消费者 |
| 使用关系 | 已生效配置中具体依赖目标、已知项目文档与受控连接证据 | 一次连接不是完整依赖；不为了发现业务关系额外读取数据内容 |

确有必要读取额外配置时限定文件/字段。先从文档和配置确认逻辑服务，再将实例与资源位置对齐。`ps`、端口和连接信息只能补证，不以任意字符串匹配替代身份。

## 4. 对照并登记

按 [运行关系模型](runtime-model.md) 区分四类结果：已匹配、声明但未观测、观测但未知归属、来源冲突。一次连接失败不能把资源判成已退役；一次进程缺失也不代表配置已删除。

先核验稳定身份，再登记 service 和 instance；用 ProjectService 说明项目使用，再添加已有证据支持的有向依赖。共享服务只记录一份实例，消费范围分别保存在项目使用关系中。

向同一 run 附上采集时间、范围、实际工具入口及脱敏证据，才更新现行 registry。对候选关系记录“待核实”，不要把猜测存成无条件事实。

## 5. 返回当前任务所需的结果

按 [双向查询](queries.md) 交付机器/项目视图和影响范围。说明未知对象、过期数据、访问失败、未覆盖环境以及后续可以取得的证据。

本技能的完成结果是可核验的对象与关系，不宣布部署成功或服务健康，也不通过“发现”启动、停止、删除或接管未知对象。需要健康、诊断或恢复时交给对应 ops 技能，沿用同一 run 和既有授权。
