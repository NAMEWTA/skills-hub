### 多阶段或多 PR 计划

**你负责计划，不负责代码。计划是一份由负责人逐项执行、操作人按证据审计的检查清单。** 用户只要求计划时，计划就是交付物；已经授权实施时，计划完成后继续执行。

1. 如果改动只有一两个文件，方案也很明显，则跳过独立计划文档。只要求方案时说明结论；已要求实施时直接按简短规格继续。
2. 写作前先用原型解决需要实验的开放问题。相关问题运行 `prototype.md`。保留分支、SHA 和截图，放进附录 A。只有任何运行都无法解决的产品或偏好问题才询问操作人。给出选项（**授权内持续执行** 工程原则）。
3. 有独立探索方向和可用代理工具时，按实际并发与模型能力分配工作；没有工具或任务很小就顺序探索。每份结果返回文件指针、约定、检查命令与入口，不内嵌大块源码。需要推理级别或速度参数时，以当前工具真实支持的配置为准。
4. 把下方骨架复制进计划文件，只填写本次适用项，删除无关占位符。新增计划统一写入 `.agents/wtadev/changes/<日期-主题>/plan.md`。保留必要的任务、证据、依赖、风险与交付部分，不强制空章节。每个 PR 一节。一个 PR 就是一个拥有独立证据的改动（**可验证单元** 工程原则）。在**如何阅读**中指出执行手册。运行可能合并时选 `autonomous-queue.md`。由操作人落地 PR 时选 `autopilot-stack.md`。持续项目选 `program-coordination.md`。
5. 完整遵循 本地技术写作检查 写作，再运行 本包清晰写作方法。正文采用单一 Diátaxis 模式，即操作指南。附录容纳解释与参考。每个标题陈述任务或发现。不用长破折号，不在句中使用冒号。
6. 检查计划中每个占位符、依赖、可观察结果、验证命令、实际运行与性能适用性；若项目已有计划检查器则运行，并修复实际问题（**结构化经验** 工程原则）。
7. 交还。报告计划路径和实际检查结果。若当前仅授权计划，交付计划后停止；已授权实施时按计划继续，不重复等待开始口令。

**验证。** 仅有测试不足以完成验证。只有适用的单元、实际运行和性能检查都有证据，其他项有具体不适用理由时，PR 才算验证完成（**真实证据** 工程原则）。这句话就是验证规则，每个验证块都以它开头。实际运行块是必需的。无行为变化时写具体不适用理由；单元或性能检查仅在变更有对应风险或项目门禁要求时适用，不为低影响文案修改编造测试。按 **并行验证** 技能，按风险选取独立通道在 PR 头提交上通过对应控制技能驱动真实界面，使用当前可用的独立验证能力，默认继承当前会话模型。每条通道是一项，包含具体场景、保存的截图和通过判据。其中一条是**对照主干的回归通道。** 它在主干和头提交上运行同一个关键场景。若主干没有此功能，通道记录这一事实，并以差异新增的行为及用户等待的最终状态为门禁，不编造主干结果。性能门禁是双侧的：主干与头提交都必须产出指定指标。若主干没有此功能，还要隔离差异新增的工作，为该工作和用户等待的端到端状态设置绝对预算。不要对不相同的场景宣称比率。性能块要写清指标、交错执行的探针、先测量的主干基线，以及带有失败数值的规则。用户或项目明确要求时，改变交互的 PR 设置审查门禁：合并前，操作人在聊天中用截图和视频审查。未改变任何交互的 PR 写 `**审查门禁。** 无。<PR id> 没有审查门禁。`，其下不放复选框。

**控制技能。** 按界面选择。浏览器、Electron 和 Web UI 使用 `当前可用工具集` 的 `界面控制工具`。CLI 和 TUI 使用 `当前可用工具集` 的 `终端控制工具`。原生移动端使用仓库中已有的模拟器驱动技能。触及两个界面的 PR 在两者都安排通道。没有控制技能的界面作为风险放入附录 C，其实际运行块仍需说明各通道如何驱动它。
