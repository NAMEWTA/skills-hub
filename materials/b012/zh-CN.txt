### 完全自动执行

**你负责裁决，不负责 PR。每个 PR 由一位负责人从构建负责到合并；未写代码的验证群体证明即将落地的代码前，任何东西都不合并。**

一份裁决覆盖一个补丁，绿色 CI 覆盖一个头提交。第 4 步完整群体验证一次，只有重大变化才再跑。`playbooks/shipping.md` 的 patch-id 规则可以延续某通道结果，但每个新头提交都需要自己的绿色 CI。

1. **操作人的门禁优先。** 授权仅覆盖队列事项，操作人指定归自己处理的事项及队列外 PR 停在可合并状态。要求说明计划不等于开始执行。
2. **每个 PR 派一位负责人，让替代者找得到其工作。** 项目一次性确定托管工具。默认 GitHub CLI（`gh`）。若 `command -v origin` 成功且 Origin 能解析仓库，则所有 PR 操作用 `origin pr`。否则继续 `gh`，记录回退。永远不要求 Graphite（`gt`）。每位负责人是 Cursor 云智能体，构建，按 `playbooks/opening-a-pr.md` 打开 PR，在真实产物证明改动，按 `playbooks/babysit.md` 跟进到绿色，步骤 4、5 放行后合并。

   尽早打开 PR，让 CI 和机器人与工作并行。只有执行 `cursor-team-kit` 的 `deslop`（`/deslop`）及 `/no-comments` 后，代码才就绪，以便完整群体验证面对完成代码。之后变基到最新主干，在自证前报告代码就绪头提交，使验证在补丁落地的基线上执行。报告每个后续头提交，自证、CI、跟进完成后报告可合并。修复轮次保持该基线，除非主干冲突、使 CI 失败、或有已知并发改动落在相同文件，因为每次变基都会重启 CI。代码就绪推送前，以及后续需要验证者的推送前，在已提交头上运行仓库对触及路径的检查。

   假定 VM 会死亡。开始后尽快推送，并按 **show-me-your-work** 在根智能体存储（路径见系统提示）开始决策轨迹；每完成一个单元，开始下一个前先推送。谁派子智能体，谁在该存储记录其 ID、状态，以及依据同类过去运行设定的停滞时限，让父级死亡后根仍能探查。只对自己的分支强推，用 `--force-with-lease` 绑定最后一次推送或接管的 SHA；发现任何非自己推送时停止并报告根智能体。
3. **负责人从主干并行工作，不堆叠，** 让每个 PR 独立落地。
4. **群体验证一次。** 完整群体验证在代码就绪头执行一次。只有新行为、重新设计或大规模新差异才再次完整执行。变基、冲突解决、小修复由单一验证者检查新头，纯文字变化无需验证。按 **swarm** 在代码就绪 SHA 扇出独立验证者。他们重跑门禁，通过控制技能，如 `cursor-team-kit` 的 `control-ui` 或 `control-cli`，或指定驱动，在真实界面证明关键行为，并审计差异。没有实际运行通道，或你尚未审计可合并报告凭据时，裁决都不能是干净，因为任何通道都不信未经自身检查的主张。

   只用可展示的问题阻塞 PR：头提交上的失败运行，或 PR 改错的一行文档。基础分支本来就有的问题，无论主干还是堆叠下层 PR，都不阻塞，除非此 PR 复制它或新触达它。只有用户会遇到的缺陷、失败门禁、错误交付文档阻塞，其余放后续事项。
5. **负责人只合并你验证过、且在将落地主干上测过的内容。** 仅绿色 CI 绝不授权合并。群体通道启动后，合并准备变基到最新主干，报告新头，等 CI 绿色。

   合并前立即获取主干，判断其变化会否影响补丁，因为每次主干移动都变基永无止境。即将落地代码从未测试时，需变基并等 CI，如冲突、双方修改同一文件、或 PR 所运行检查变化。双方都改锁文件时，若冻结安装在合并结果上通过，且 PR 修改的包在合并结果解析与头提交相同，无需变基，因为该安装测试了将落地锁文件；安装失败则必须变基修复。主干改动了补丁调用者或依赖，例如它调用的代码或依赖版本，则在合并结果运行补丁检查，通过后合并。其余直接合并。主干在合并准备后若将迫使第三次变基，暂停报告根，由根安排冲突工作的顺序。
6. **运行根层职责。** 任何放松门禁的改动，如提高预算或增加允许列表，都要验证者证据，再由你新签认，因为负责人是希望变绿的一方。授权覆盖批准时，该签认即批准，负责人记录指向你的签认，供通道检查。禁用检查或把检查改为软失败的改动始终撤销，因为这样的检查不再守护任何情形。绝不提供或绕过托管平台强制的批准，没有签认能覆盖它。

   操作人发出开始指令时，用 `/loop 1h` 持续审计直到没有委派工作，因为长任务会漂移、智能体会静默停滞。每周期从主干重读本手册，通过让负责人记录来修正未报告头提交、未登记智能体等漂移，因为漂移是记录缺口，不是停滞。探查每位智能体直至叶子通道，只按实际副作用判断，因为状态文字和摘要会隐藏卡住的子级。错误、无法开始新轮次、超过停滞时限无新活动都算停滞；到首周期既未推送也未写轨迹的负责人也算。等待你或操作人的不算停滞，应回应。立即替换停滞智能体，不等停止生效。本周期有对操作人有意义的变化，按 **ketchup** 更新；没有变化则安静。
7. **操作人要求停止时立即停止。** 暂停作为禁止写入命令传达到每位负责人。各自报告当前位置，保留简报，直到操作人解除。

**回复：** 按 **ketchup** 更新操作人，涵盖每个 PR 状态与裁决、已合并内容、签认及原因、未满足的操作人门禁、搁置后续事项，附每个 PR 与轨迹链接。
