# 测试驱动开发

TDD 就是红 → 绿循环。本技能是一份让这一循环产出值得保留的测试的参考：什么是好测试、测试放在哪里、反模式，以及循环的规则。每节都适用于每次循环：在循环之前与进行中查阅，而不是事后才看。

探索代码库时，阅读 `GLOSSARY.md`（如有），让测试名称与接口词汇符合项目领域语言，并遵守所修改区域的 ADR。

## 什么是好测试

测试通过公共接口验证行为，而不是实现细节。代码可以完全改变，测试不应该因此改变。好测试读起来像规格：“用户可以用有效购物车结账”准确说明存在什么能力；它能够经受重构，因为它不关心内部结构。

示例见 [tests.md](tests.md)，模拟指南见 [mocking.md](mocking.md)。

## 接缝：测试放在哪里

**接缝**是进行测试的公共边界：你通过该接口观察行为，而不伸手探入内部。测试位于接缝处，绝不针对内部实现。

**只在预先约定的接缝处测试。** 编写任何测试前，写下要测试的接缝，并与用户确认。未经确认的接缝不编写测试。你不可能测试一切，因此提前约定接缝，才能让测试工作落在关键路径与复杂逻辑上，而不是每一个边缘情况。

询问：“公共接口是什么，我们应该测试哪些接缝？”给每个建议的接缝附上一行说明：它能捕获什么，又会遗漏什么。

如果接口的形状本身也存在疑问，例如模块有多深、接缝应当位于何处、接口应暴露什么，使用 Skill 工具调用“codebase-design”，获取相应词汇。它是模块、接口、深度、接缝、适配器、效能与局部性术语的共同来源，是供查阅的参考，而不是要运行的一场会话。

## 反模式

- **耦合实现**：模拟内部协作者、测试私有方法，或通过旁路验证，例如查询数据库而不是使用接口。判断信号是：行为没有变化，重构却让测试失败。
- **同义反复**：断言用与代码相同的方式重新计算期望值，例如 `expect(add(a, b)).toBe(a + b)`、以相同方式手工推导的快照，或断言某个常量等于自身，因此测试天然通过，永远无法与代码产生分歧。期望值必须来自独立事实来源：已知正确的字面值、演算过的例子或规格。
- **水平切片**：先写完所有测试，再写完所有实现。批量测试验证的是_想象中的_行为：测试事物的_形状_，而非面向用户的行为；测试对真实变化变得不敏感，并且你在理解实现之前就承诺了测试结构。改用**垂直切片**：一个测试 → 一个实现 → 重复。每个测试都是一发**曳光弹**，回应上一次循环教会你的内容。

## 循环规则

- **先红后绿。** 先写失败测试，再只编写足以让它通过的代码。不要预判未来测试，也不要添加推测性功能。
- **每次一个切片。** 每个循环只处理一个接缝、一个测试、一个最小实现。
- **重构不是这个循环的一部分。** 它属于审查阶段，参见 `code-review` 技能，而不是红 → 绿实现循环。
