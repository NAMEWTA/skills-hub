# 验证指南

按本次改动涉及的契约选择检查，在实际结果中记录版本、环境、命令、退出状态和未覆盖范围。结构、确定性行为、真实工具操作及用户认可各有证据，不能相互替代。

## 准备环境

仓库维护基线为 Node.js 22.14+。在源码根安装锁文件声明的依赖：

```sh
npm ci --ignore-scripts --no-audit --no-fund
```

完整测试会使用 Git 创建临时仓库，npm 包验证需要 npm 及可取得的交互依赖。已有依赖齐全时可使用受控缓存；网络失败或缺少依赖仍属于未完成检查，不是通过。

## 复现入口

| 命令 | 实际检查对象 | 额外前提 |
| --- | --- | --- |
| `npm run check` | 入口预算、包结构、本地链接、持久化路径与来源清单 | 本地源码 |
| `npm run check:full` | 上述内容、递归发现的 Node 隔离测试、有限状态示例与真实故障注入 | 已安装依赖、Git |
| `npm run check:statechart` | 已捕获 TLC 输出的解析、投影、规则和反例回放 | 本地材料夹具；不需新运行 TLC |
| `npm run check:package` | 实际 npm tarball 的清单、完整性、消费端命令、安装和重复安装 | npm 及包依赖可取得 |
| `npm run check:upstream` | 已安装 Archify 的 doctor、中文 locale 图表和完整 finalize | 可启动的 Chrome/Chromium |
| `node scripts/check-skill-quality.mjs --report` | 每个自有技能入口的行数和非空白 Unicode 字符 | 本地源码 |

快速与完整检查的 Node 入口分别是 `node scripts/check.mjs` 和 `node scripts/check.mjs --full`。状态图、打包和上游运行分别由 `scripts/check-statechart-replay.mjs`、`scripts/check-package.mjs` 和 `scripts/check-upstream-runtime.mjs` 执行。`npm test`、`npm run build`、`make check`、`make build` 都使用完整检查。

修改文档或普通技能入口后，先运行快速检查并阅读受影响的全文和引用。修改安装、校验、脚本或运行行为时，运行完整检查及对应专项。发布使用最终版本文件执行所有发布检查，详见[发布指南](release.md)。验证范围由具体风险决定，不靠机械重复同一条命令增加可信度。

## 结构和来源检查

[质量规则](skill-quality.md)定义自有技能的名称、元数据、入口预算、资源可达性，以及独立上游包适用的不同约束。普通检查只读取当前材料快照，不联网更新来源。

材料检查核对父子清单、文件集合、Git blob、SHA-256、执行位、语言和类型规则，以及真实运行映射。显式提供本地来源 Git 对象库时才核对固定提交的完整来源树。目录里出现中文、摘要一致或报告写了完成，都不能证明翻译忠实；仍需阅读原文、对照和运行适配。

## 行为与工具检查

完整检查递归发现 `tests/` 下的 `.test.mjs` 和 `.test.js`，在隔离位置验证安装选择、冲突、备份、失败恢复、命令接口和工具边界。有限状态示例实际修改临时副本、捕获反例后恢复，结论只覆盖示例声明的状态和不变量。

状态图回放先从父清单固定的 statechart corpus 复制全部夹具到临时目录，调用本项目状态图工具。有 `view.mjs` 的用例会通过 `--view` 加载该投影配置；适配器提供已经捕获的输出，不启动真实 Java/TLC。此明确维护入口不扩展为执行任意材料脚本。

回放逐项检查全部捕获用例，包括退出码、规则顺序、图、状态标记和反例。最多并行 4 项，每项 Windows 上限 120 秒，其他平台 45 秒。日志记录用例开始、完成耗时，异常包含用例、耗时、上限及原始错误。超时不会跳过断言，也不把捕获输出回放视为新的 TLC 求解。

npm 包检查先实际打包，再在临时消费者中解析依赖并运行包内命令，按字节核对所选资源和法律文件。它验证发布制品的安装能力，不证明 npm 已公开这个版本。

上游运行检查从已安装的包运行工具。Archify 生成 HTML、静态严格检查和真实浏览器检查分别有结果；缺少浏览器时不能只凭生成文件声称 finalize 全部通过。Google 技能保留上游动态 CLI，静态中文资料检查不能证明最新 CLI 响应为中文，详见[运行前提](../usage/upstream-skills.md#运行前提与中文边界)。

## 技能选择与实际使用

调整 description、路由、读取条件或交接边界时，用真实意图或合成请求检查入口选择，再实际读取所选方法。需要独立观察时使用未参与编写的上下文，记录原始请求和真实产物；不能把执行者自查写成独立评审。

案例覆盖的宿主、工具、版本和任务范围必须明确。一个隔离任务通过不证明所有宿主都会自动发现技能，也不证明生产环境已经操作成功。确认原型还需区分生成完成、浏览器走查和用户对具体版本的认可。

ops 的记录工具、真实隔离 SSH 和自然请求验证见[专项指南](../operations/validation.md)。需要新 TLC 求解、真实远端查询或业务部署时，另行核对该任务的工具与授权，使用实际入口获得证据。

## 提交快照与 CI

工作区检查与被提交的快照可能不同。`--staged` 检查 Git index，`--revision <提交>` 检查指定提交，`--pre-push` 检查实际推送引用的目标树；配置和使用见[hooks 说明](skill-quality.md#提交和推送前检查)。

[验证工作流](../../.github/workflows/validate.yml)覆盖 Linux、Windows、macOS。各平台运行完整检查、状态图回放和实际 npm 包安装；Linux 另运行上游浏览器检查。工作流配置只说明检查安排，具体提交是否通过以对应运行结果为准。

## 记录结果和处理失败

一次验证写入所属 `.agents/dev/changes/<日期-主题>/`，至少保留实际版本或工作区范围、环境、命令、结果、关键证据和限制。先保存失败现象，再根据新证据修复和复验；最终通过不能覆盖曾发生的失败。发布是否完成另写入 `.agents/dev/deploy/`。

区分检查未启动、环境前提缺失、断言失败、超时和远端状态未知。没有现场证据时保留未知，不因为脚本存在、授权已经给出、模型报告成功或 CLI 接受请求就写成任务完成。
