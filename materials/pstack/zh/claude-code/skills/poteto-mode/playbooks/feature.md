### 功能开发

**你负责设计。规划、审查、验证。** 委派实现，自己保持主导。

1. 追踪受影响的子系统。
2. 用 `architect` 确定结构。
3. 把吞吐检查点写成四项待办。确实不适用的维度（单文件、无需扇出）也保留该项，写 `n/a: <reason>`，不要删除：
   - **阻塞性前置步骤。** 在扇出之前完成门禁。
   - **独立工作流。** 不重叠的文件、服务或层可以并行；共享写入必须串行。
   - **共享可变状态。** 默认拆分目标（**separate-before-serializing-shared-state** 原则技能）。只有真实不变量要求时才串行。
   - **最小安全拆分。** 如果一个执行者最好，说明原因。
4. 将代码编写委派给使用已配置 feature 模型的子代理（默认 `claude-opus-5-5-xhigh-fast`），并明确范围（文件路径、按照 **principle-model-the-domain** 命名的数据形状及其组织结构，在编写逻辑前选定：以状态机替代零散布尔值、以表或注册表替代分支、以类型模型替代反复假定的数据形状，以及成功标准）。按照 Subagents 部分，为每个子代理选择适合任务的推理级别。如果实现存在多个有效结构（错误处理、抽象层、测试结构），则改用 **arena** 技能委派，让执行者提出备选方案，并让交叉裁判把关选择。这是强制要求：不得以说明理由为由跳过，Laziness Protocol 也不能覆盖它（收益在于审查职责分离，而不是节省代码行数）。禁止再启动子代理的子代理，应直接负责 diff，同时保持同样的审查分离，以满足要求。不要回复“正在待命”并等待嵌套代理。做精确的小范围编辑；对于源自上游的文件，重新对照原始来源。将共享基础组件的改进移植到所有使用方，并逐一验证。积极提交。
5. 在匹配的界面上验证。“无结论”或在错误界面验证都不算通过，必须指出。
6. 变基为有序的小提交。后续改动堆叠进行。
   使用 **sequence-verifiable-units** 原则技能，在下一个小单元开始前，构建、验证并提交当前单元。
7. 设计有争议时，交付前运行 `interrogate`。
8. 执行 **Opening a PR**。

代码耦合工作（一个功能、一次迁移）交给单一负责人，检查点直接放在其任务中。负责人在阻塞阶段结束后自行扇出。父级扇出用于产出独立成果的切片（审计、跨子系统调查、竞争性实验）。在阶段边界重写检查点。创建新的负责人，不要串联中断。

**回复：** 构建了什么、选择了什么及原因、吞吐检查点、开放决策。设计替代方案用表格。
