# 修改代码之前先理解它

编辑自己不理解的代码，会让隐蔽的回归问题进入交付；这对智能体和你都一样。智能体通常以两种方式失败：误解你的要求，或缺少正确完成工作的背景。[提示词应该包含什么](./02-poteto-mode.md#what-goes-in-a-prompt)处理第一种，本页处理第二种。

pstack 提供四种入口。`/how` 解释当前代码做什么。`/why` 挖掘它为何形成这种形态。`/teach` 把两者融成一份说明。`/recall` 重建你自己围绕某个主题的近期背景。每一种也都让智能体用你能核查的语言解释自己。这就是你监督一个可能比你更了解代码的智能体的方法。

![一位侦探用放大镜研究机器蓝图，机器人取来案卷；她身后的证据板在 /how 和 /why 标签下连接线索。](./images/understanding.jpg)

## 从只读调查开始

原因不清楚时，要求调查发现，不要要求修复：

```text
/poteto-mode 调查为什么后台任务每隔几个小时就超时。告诉我已知事实、用了什么数据，以及你认为最合理的假设。先不要修改代码。
```

“先不要修改代码”会把任务路由到[调查手册](../../skills/poteto-mode/playbooks/investigation.md)。它运行 `/how`，在动机问题上加入 `/why`，返回有引用的解释。面对方案选择时，它返回建议和权衡表。追问“用了什么数据”会让智能体区分证据与猜测。调查发现指向某个修复时，把修复作为新任务启动。

## 用 `/how` 追踪行为

```text
/how 我们怎样对通知去重？查找订阅者时是否存在 n+1？
```

提出你真正想问的问题。[`/how`](../../skills/how/SKILL.md) 阅读代码，像资深工程师带你接手子系统那样回答，讲清运行流程、关键类型和不明显的部分。大型子系统先派出两到四位只读探索者。范围狭窄的问题则直接阅读并解释。

## 用 `/why` 挖掘历史

```text
/why 为什么重试上限设为五次？理由现在仍然成立吗？
```

[`/why`](../../skills/why/SKILL.md) 从源码管理开始，然后并行查询 MCP 提供的各类证据，例如工单跟踪器、长文档、团队聊天、可观测性、错误追踪和分析数据。报告为每项内容提供引用，区分直接证据与推断，记录薄弱时说“看起来”。空结果也会报告，因为“没有人记录原因”本身也是答案。

两种方法可以自然组合。怀疑历史能够解释眼前混乱时，“先做 why，再做 how”是一个好提示。

## 用 `/teach` 真正理解

```text
/teach 给我讲清这个 PR 如何改变重试。说服我它修复的是原因，而非症状。
```

[`/teach`](../../skills/teach/SKILL.md) 用于摘要不足以让你理解的时候。它运行 `/how` 和 `/why`，小改动也许只需要其中一个，然后把发现组织成朴素说明，逐张图建立理解。“说服我”这种表达值得复用，它让解释成为可以检验的论证，而非导览。

它也适用于智能体自己的选择：

```text
/teach 给我讲清为什么你这样实现，而没有使用队列。你做了什么取舍，为什么？
```

教学对智能体和你都有帮助。必须解释工作的智能体需要读代码，并为每个主张提供证据，而非自信地说完就继续。

## 用 `/recall` 重建自己的背景

```text
/recall 帮我回顾上周导出功能的进展
```

[`/recall`](../../skills/recall/SKILL.md) 挖掘你自己的近期聊天，以及共享记录，例如工单、之前的修复和仍在触发的错误，返回当前状态与下一步的简报。旧聊天保存着新智能体缺少的背景，因此在旧主题上开始新工作时，先加载它，再交付新输入：

```text
/recall 回顾我昨天关于虚拟列表的工作，然后读这份缺陷报告。
```

如果要恢复一条指定聊天，使用下方的会话接续手册，而非 `/recall`。

## 用会话接续接手此前工作

另一个智能体，或上周的你，留下了进行中的分支时：

```text
/poteto-mode 接手这个分支。读决策日志，弄清哪些已经完成，然后接着做。不要重做已完成的工作。
```

[会话接续手册](../../skills/poteto-mode/playbooks/session-pickup.md) 把先前轨迹视为权威起点。它重建分支状态与决定，指出恢复点，并对照原始目标验证继承的主张，而非从头推导一遍。

**误区：** 不要因为“智能体反正会读代码”而跳过本页的方法。没有追踪形成的模型就开始编辑，往往会在第一个看起来合理的位置修补症状。先做 `/how`，比再修第二个缺陷便宜。
