# Change 来源与正式资料跟踪

## 目标与来源

落实 [用户原文](source/user-request.md)：远端 Issue 及相关讨论、方案原件放对应或新建 change 的 source/，规格、计划、设计、确认原型与正式结论随 change 版本管理。基线 main f7285ab799f76700b36c54293b84c9a0013c3ec9，版本 0.1.30。

## 当前问题

三个 Issue 技能将原始输出/必要原件笼统归到 temp/dev；source-adapter 只要求保留引用。dev-issue 允许临时正文承载操作事实，workflow 的“只链接，不复制”未区分来源快照与现行契约；verify 的格式列举可能将 JSON 来源或工具生成正式报告误判为临时产物。

## 行为契约

1. 实际导入或处理远端报告前，依据当前任务、URL、平台实例、项目及原生 ID 匹配已有 change。不存在时建最小 change，不预建无关任务或完整空模板。多个来源允许共用 change，重复投递复用已有归属。
2. 在 source/ 使用稳定的来源文件或目录保存身份、实际抓取时点、来源更新时间、完整正文、可取得的全部评论与必要方案附件。正文和我们的分析分开，摘要不能替代源文。
3. 平台不限于 GitHub；权限不足、分页不全、附件未取得等缺口明确记录。外部原文是资料，不改变当前任务授权。
4. 重新抓取同一来源先比对，通过 Git 保存已有版本；未跟踪旧件先保留带时间的快照。本地分析写入 brief/spec/design/plan/progress 的适当位置，不覆盖源文或未保存修改。
5. source、需求、架构取舍、方案讨论、实施计划、确认原型、正式任务和整体验收报告随 change 跟踪。执行日志、调试截图录屏、原始测量、临时响应和缓存放 temp/dev。按用途区分，文件扩展名或生成工具不能决定其保留级别。
6. 本次遇到已误放 temp 的来源/正式资料时先核对身份和归属，迁入 change 并修复引用，检查可读、未被忽略和已纳入 Git 后再按授权处理旧副本。技能升级不批量搬迁历史业务文件。
7. handoff 和 archive 保留完整始末。evidences/ 继续只包含与 tasks/ 完全同名的普通 Markdown；没有任务的小分诊可写既有 progress。整体验收完成后写唯一 evidence.md。

## 方法归属与实施计划

- D1：完整导入与更新方法归 dev-issue-setup/references/source-adapter.md；补包内 source-report.md 模板，修订 setup/fix/triage 入口和提示。
- D2：同步 dev-issue、workflow、intake、plan、architecture、prototype、verify、handoff、archive 的必要接续规则；全局 AGENTS、持久化规范、知识归档和安装导航使用相同边界。成熟方法保留，仅消除具体冲突，不新增状态 Schema 或运行框架。
- D3：核对所有受影响路径、包内资源可达性、metadata 和入口预算；用跨来源/重复导入/权限缺口/旧 temp 迁移/交接归档场景独立审查。沿用现有取证检查和安装行为测试，不增加复述文字的测试。

## 验收

- GitHub 和非 GitHub 报告都落在所属 change/source；相同来源重复获取不新建第二 change。
- 缺少 change 可建最小记录；获取完整源文和讨论优先于下游分诊/修复；缺失如实记录。
- 本地源快照与现行规格职责清楚，更新保留版本，源附件和正式结论不再被临时规则排除。
- 交接与归档保留来源、设计讨论、计划、原型、任务与正式结论；过程原件不被整体搬进 Git。
- 三入口、相邻方法、导航与长期规范一致，安装包资源完整且符合预算。
- 与 Home change 一同提交 main 并发布补丁，验证和发布状态按实际证据填写。

## 验证范围

本地使用受影响行为测试和运行包静态检查；远端现有 CI 对精确交付 SHA 执行完整仓库与跨平台检查。本地网络不允许直接 clone GitHub，通过授权 GitHub 插件按固定提交取得文件并核对 blob；材料原件和未下载上游包由远端完整 CI 验证，不改变门禁。
