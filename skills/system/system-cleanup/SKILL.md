# 磁盘清理

先确认真实主机、目标卷、清理范围和已有决定。体积大、名字包含 cache、容器显示 unused，都不自动意味着可以删除。

## 发现与执行

1. 记录所选卷的空间基线；Linux 也看 inode，Windows/macOS 注意虚拟盘、快照、链接和云占位文件。
2. 从已知的大目录或工具缓存下钻，区分可重建产物、可重新下载依赖、配置/会话、用户数据和业务数据。避免全盘递归扫描。
3. 为候选写清准确路径/对象 ID、所有者、当前是否使用、预计收益、重建代价、删除是否可恢复。可用 [清理记录](assets/cleanup.md)；已经批准的项目保留原决定。
4. 沿用已有的具体授权，直接执行范围内的项目。只有出现新的数据类别、破坏性范围或无法判断的对象才询问；先把证据和具体清单准备好。
5. 删除前再次核对对象和保留项，优先工具自己的清理/卸载方式，小批执行后读回真实空间与重要功能。

按目标读取 [平台方法](references/platforms.md)；涉及容器、包缓存或构建产物再读 [开发缓存与容器](references/development-caches.md)。仅审计/规划的请求不执行清理。

## 保留边界

不清空家目录、卷根、项目根、整个临时目录或未知父目录；不跟随未确认的符号链接/junction。包含未点名子树时保留该父目录，改为逐项处理。

当前 Agent、shell、编辑器、活动运行时、工作树、凭据、未提交文件、数据库、容器卷和备份均需保持可用。旧工具链先验证保留版本；未知共享依赖、锁定文件或系统维护中则停止受影响项，不强制解锁。

删除通常不可逆，清单不等于备份。回收站、快照、数据库、虚拟盘压缩和系统托管存储各有不同后果；普通“清缓存”不能扩大到这些对象。不要为了释放空间关闭安全功能或更改网络。

## 验收与记录

按同一卷计算实际可用空间变化，不把 `du` 的目录总数当作回收量。验证保留的工具、项目和服务仍可用；容器场景核对运行集合与数据挂载。

记录执行、保留、失败、锁定和未验证项。新增运维记录需要持久化时统一放到 `.agents/system/<host>/cleanup-<date>.md`；不要在公共仓库提交私有路径明细、凭据或原始配置。没有执行就交付清单，不宣称已清理。
