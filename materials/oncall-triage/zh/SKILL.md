# 分诊

遵守 `CLAUDE.md` 中的长期规则，尤其是：只建议、不行动（规则 1）；
每个主张都附链接（规则 4）；先数据、后理论（规则 5）；
无需询问就记入 `lessons.md`（规则 8）。

## 步骤

1. **加载上下文。** 从磁盘读取 `ONCALL.md`（策略与路由）、`STACK.md`
   （能力绑定）和 `lessons.md`（已知原因）。以文件为准，而不是记忆
   （规则 7）。

2. **判断症状类别。** 与 `references/` 中的故障类别匹配：

   | 症状看起来像 | 加载 |
   |---|---|
   | 测试失败、不稳定，或悄悄没有运行 | `references/test-failures.md` |
   | PR 卡住、队列深度增长、合并缓慢 | `references/merge-queue.md` |
   | 作业未启动、代理卡住、容量错误 | `references/runner-infra.md` |
   | 部署不良、发布卡住、部署后回归 | `references/deploy-rollout.md` |
   | 以上都不是 | 不加载参考——明确说明这一点，并从基本事实开始调查：先时间线（开始异常前后改变了什么——部署、功能开关、配置），再影响范围，然后缩小范围。 |

   （这些类别是 CI 默认值；你的初始化阶段可能已替换它们。
   上表必须与 `references/` 中实际存在的文件一致；若已经不一致，
   以目录为准并指出这种漂移。）

3. **先查日志。** 在 `lessons.md` 中搜索此类别的 #tag，读取匹配条目；
   绝不载入整个文件，它被设计为会持续增长。匹配的历史事件是第一个
   假设——验证或排除它的成本最低。

3a. **先关联，再分类。** 扫描其他告警频道（及 `incidents` 绑定）
   中相同的时间窗口。五条告警经常其实是一个事件：若这个症状是某个
   已经故障的对象的下游表现——集群问题、共享依赖、另一个团队的事件——
   在诊断中说明（“与 #infra-alerts 中的 X 相关；很可能是一个事件，
   而不是五个”），然后转交上游负责人，不再调查故障的回声。

3b. **告警风暴只做一次分诊，不逐条各做一次。** 若短时间内出现了多条
   告警，或你调查时又有新告警到来，将它们按一批处理：按可能的共同
   原因分组，对每组开展一次调查，并发布一份列出所有已解释告警的诊断
   （“这 14 条告警都指向同一个上游：……”）。若该原因已有打开的事件
   记录，把新告警附到它的讨论串或记录，而不是开启平行调查。
   若这一批看起来是真实事件且尚无记录，按 ONCALL.md 建议声明一个
   事件——由人声明（事件记录不变量）；你绝不声明。
   **批处理只针对共同原因：** 若证据表明这批告警包含确实无关的故障，
   就明确说明并作为不同事件处理——各有独立诊断、独立记录和各自的
   严重度判断。绝不为了整齐而合并。

4. **运行参考中的首轮检查**，使用 `STACK.md` 绑定的能力。
   建立时间线：症状何时开始，在它之前的窗口里改变了什么——
   `deploys`、`flags` 变更历史、配置、合并？

4a. **并行分派（仅限需呼叫值班人员的严重级别；低于此级别默认顺序执行）。**
   若频道所在平台支持启动并行子代理，你就是协调者：参考首检涉及的
   每个已绑定事实来源分别派一个调查者——`metrics`、`logs`、
   `code`/`deploys`、`pager`、`alert-channels`。
   每个调查者恰好收到四项内容：症状句、开始时间窗口、其在
   `STACK.md` 中的绑定行，以及参考针对该来源的首检查询；
   不提供其他内容，使遭污染的讨论串无法引导它（规则 9a 在子代理内
   同样适用）。每个调查者按固定结构返回：

   - **CHECKED（已检查）：** 运行的查询，附链接。
   - **FOUND（发现）：** 带时间戳的观测——只写观测，绝不写根因。
   - **NOT FOUND（未发现）：** 查找过但没有找到的内容；只有运行/
     时间窗口完整时，“不存在”才算证据。
   - **CANNOT ACCESS（无法访问）：** 所有 403 或超时项；在诊断中
     显示为缺口，绝不能悄悄省掉。

   综合只由你负责：关联、排除冲突（两个调查者给出不同开始时间本身
   就是一项发现），写成一份诊断。并行分派会成倍增加 token 成本；
   对需要呼叫值班人员的事件值得，对晨间日志事项不值得。

5. **应用参考的关联表。** 观测匹配某一行时，得到一个候选根因；
   将它提升为结论前，要用时间线验证（规则 5）。

5a. **用“现在是否仍在发生”交叉检查归因**（CLAUDE.md 规则 5a）。
   归因判断——二分定位、回退通知、“那个 PR 搞坏了它”——指出的是
   *让故障开始*的变更；在把它称为当前原因前，确认症状在最近一次
   **已完成**的运行/窗口内仍出现。出现总能确认红灯；未出现只有在
   已完成的运行中才能确认绿灯。

6. **在讨论串内按此格式发布诊断：**

   > **正在发生什么：** 一句话，并通过新读者理解检查。
   > **根因（置信度高/中/低）：** 故障机制，每个主张都链接到证据。
   > **影响范围：** 谁/什么受到影响，附链接。
   > **建议修复：** 动作、为何安全，以及之后观察什么。
   > **已排除：** 检查过的替代解释，以及排除它们的证据。
   > **什么会改变我的判断：** 能改变判断的那一项观测。

6a. **长时间事件的更新。** 首次诊断超过 30 分钟后发布的任何更新，
   开头都用 2–4 句话讲清*截至目前的经过*，使刚加入的人无需背景也
   能理解：何时开始、哪里坏了 → 对原因的**当前最佳理解**
   （不是最初猜测）→ 已经尝试了什么 → 当前处于何种状态，
   用一句话收住。然后写新增变化。已排除的假设，除非仍支撑当前
   判断，否则不再出现。**绝不发布“没有变化”的更新**；
   保持安静是一种有效状态，噪声会让读者养成跳过更新的习惯。

7. **路由。** 如果 `ONCALL.md` 的路由树为该类别指定了负责人，
   就提及他们。否则不提及任何人（规则 12）。

8. **面对人的问题或质疑**（“会不会其实是 schema 改动？”）：
   把它作为一个假设，用数据检查，再带证据报告支持或反对结果。
   不为诊断辩护；重新推导它。

9. **修复已部署后**（由人，或允许且通过关卡的动作执行）：
   观察它实际生效，但限定次数。在参考的预期恢复窗口检查受影响
   指标（半个窗口检查一次、完整窗口一次、两倍窗口一次——
   共三次检查，不是轮询循环），回到基线时发布结果，超过窗口则按
   路由树升级。不要标记已解决（规则 2）。如果人希望更密切观察，
   他们可以提出要求；持续轮询绝不是默认行为。通过故障原来进入的
   同一入口验证：重跑原先失败的路径，或复查最初发现事件的精确信号，
   绝不用替代指标。“合并又流动起来了”只能证明合并路径，
   不能证明整个提供方正常；若检查看不到原始症状，说明验证是部分的，
   并指出它看不到什么。

10. **事后**，按条目格式把事件追加到 `lessons.md`（规则 8）。
    如果事件暴露了某份参考文件的缺口，提出一个修订 PR（规则 9）——
    修正运行手册，而不只处理事件。还要问告警问题：
    **一条规则能否更早发现它？** 如果是人发现或发现晚了，
    在复盘中提出规则——按 `ONCALL.md` 指定格式给出可直接粘贴的内容，
    以本事件为来源。按 ONCALL.md 的安装模式处理：
    默认由人粘贴；若启用 alert-editor 扩展，可在频道得到明确批准后
    自行创建（只新增，并记入 lessons.md——CLAUDE.md 规则 1a）。
