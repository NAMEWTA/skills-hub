# 原型

原型是**用来回答一个问题的一次性代码**。问题决定形态。

## 选择分支

根据用户提示、周围代码，或在用户在线时询问，确定要回答哪个问题：

- **“这个逻辑／状态模型是否合理？”** → [LOGIC.md](logic-prototype.md)。构建可分享的单个 HTML 文件，包含自由操作按钮和分标签引导演练，用非开发者也能操控的方式，把状态机推进到纸面难以推演的场景。
- **“它应该长什么样？”** → [UI.md](ui-prototype.md)。在同一路由生成几种截然不同的 UI 变体，通过 URL 查询参数和底部浮动栏切换。

两个分支产出完全不同的成果，选错会浪费整个原型。如果问题确实模糊且无法联系用户，默认选择更符合周围代码的分支：后端模块选逻辑，页面或组件选 UI，并在原型顶部写明这个假设。

## 两个分支共同的规则

1. **从第一天起就当作一次性代码，并明确标注。** 把原型代码放在实际会使用它的位置附近，即被验证模块或页面旁，让上下文一目了然；命名要让随意浏览的人也能认出它是原型，不是生产代码。一次性 UI 路由遵守项目已有路由约定，不发明新顶层结构。
2. **启动极其简单。** UI 原型通过项目任务运行器中的一条命令启动，例如 `pnpm <name>` 或 `node <path>`。逻辑演示是用户双击即可打开的单 HTML 文件。无论哪种，启动都不应需要思考。
3. **默认不持久化。** 状态放在内存。持久化是原型可能正在**检验**的对象，不应成为它的依赖。如果问题明确涉及数据库，使用临时数据库或本地文件，名字应明确包含“PROTOTYPE, wipe me”。
4. **略过打磨。** 不写测试，除确保原型**能运行**外不做错误处理，不做抽象。目的在于快速学到东西。
5. **展示状态。** 每次动作后，逻辑原型应输出或渲染全部相关状态；UI 原型在每次变体切换时也应如此，让用户看清变化。
6. **结束时留存。** 把验证成立的决定融入真实代码，再把原型本身作为**一手资料**保留：提交到一次性分支，不放主分支，并在实现事项上留下指向该分支的上下文指针。也在事项或提交中记录答案，即结论和它解决的问题。主分支只保留已验证的决定。
