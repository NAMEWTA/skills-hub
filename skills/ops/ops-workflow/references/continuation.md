# 接续与结果收束

## 进展询问

从当前 run 和实际返回结果汇报：已经完成、现在执行什么、观察到什么、哪些信息仍缺少、下一步由谁负责。查询进展不创建另一套任务，不把旧摘要当作新的现场观测。回答后继续原有授权工作，除非用户明确要求停止或改变目标。

## 恢复旧任务

1. 确认用户要继续哪个任务，利用已有 run ID 或 history 找到原记录。发现同名多任务时先消除歧义。
2. 阅读原请求、目标快照、步骤和最新总结。原始步骤与后端记录优先于派生索引；区分过去观测与现在事实。
3. 把未知执行、尚运行的 job/session、原 writer 与冲突范围交给 execute 核实。原命令失败、会话退出或锁超时不证明远端没有发生动作。
4. 由原任务 owner 判定剩余步骤的前提是否仍成立。环境或部署版本变化时重新核验相关步骤，已证实且未受影响的工作不重复执行。
5. 沿用原 run，必要重试关联新的 attempt；独立会话使用关联子 run。写入者变更按 execute 的交接方法完成。

这里只协调恢复点。远端任务核实、写入者交接和安全重试的完整方法归 execute，不在此复制。

## 明确暂停或取消

停止尚未开始的后续动作，保留进度与未完成项。对正在执行的动作，交 execute 依据实际后端能力判断能否安全暂停/取消；发出取消请求不等于远端已停止，不在未知状态下释放共享操作范围。只要求“保存一下”时保留上下文后继续当前授权工作。

## 项目交接

发现必须修改应用、升级中间件、切换制品/部署配置或执行 migration 时，在本 run 中整理：真实项目/环境、服务/实例/资源、症状、已确认事实、尝试过的动作、当前状态、共享消费者、需要项目处理的事项与运维复验条件。

该材料由用户或上层交给项目自己的流程。ops 不执行发布、不修改项目发布记录、不自动安装其他 domain。已有的项目后续授权可以由上层接续，交接本身不增加重复审批，也不改变方法归属。

## 最终结果

逐项核对最初完成条件，分别说明：

- 实际完成的操作与对象，真实使用的方法和证据。
- 执行状态、现场结果和记录状态；多目标的差异与缺口。
- 原失败路径、服务就绪和相关消费者的验证覆盖。
- 临时缓解、运行恢复、根因确认分别是否成立。
- 未完成事项、原因、责任归属与下一步所需条件。

使用[结果模板](../assets/result.md)把汇总交给同一 run 的写入者。新知识需要沉淀时交 runbook；不将所有聊天内容复制成长期指令，不把一次暂时恢复晋升为通用规则。
