# 实现改动并清理差异

各实现手册共用一条纪律：说清你观察到什么，让手册要求所需的证据。本页说明常见实现任务的提示词应包含什么，再介绍使差异便于审查的清理习惯。

## 用已知事实提示每种实现手册

缺陷提示说明症状，并要求先复现：

```text
使用本技能 这个命令重试后输出两条记录。先复现，再修复并验证。
```

功能提示说明行为，以及哪些内容必须保持不变：

```text
使用本技能 添加 --json 标志。文本输出保持逐字节一致。验证两种形式。
```

重构提示在移动结构之前固定行为：

```text
使用本技能 把解析移到一个模块，行为完全不变。先记录当前输出，再证明改动后没有变化。
```

性能提示陈述测量，而非印象：

```text
使用本技能 在这个夹具上启动需要 1.8 秒。追踪它，修复测得的原因，展示前后对比。
```

每种请求路由到对应手册：[缺陷修复](bug-repair.md)、[功能](feature-delivery.md)、[重构](behavior-preserving-refactor.md)、[性能问题](perf-issue.md)。手册补充你没打出来的步骤：修复前复现，实现前明确数据形状，重组前固定行为，优化前做性能分析。

持续改进一个数字时，使用[爬坡优化手册](hillclimb.md)。给出指标、目标和尝试次数下限，它会冻结测量框架，每次检验一个假设。保留有效改进，撤回其他改动。

两份性能手册都会对数字运行 [测量检查](measurement-checklist.md)。性能问题手册核验基线及之后的每个数字，爬坡优化手册在冻结框架之前核验它。[验证并交付](measurement-checklist.md)说明何时应自己明确调用。

有时你希望先知道原因，再决定是否修复。泄漏、空闲 CPU 忙转、视觉故障等现场症状，使用[运行时取证手册](runtime-forensics.md)检测正在运行的进程。已有捕获的性能分析文件时，[轨迹取证手册](trace-forensics.md)读取制品，把热点帧映射到源码。两者都返回诊断，不返回修复：

```text
使用本技能 这是慢启动的 cpuprofile。告诉我时间花在哪里，哪些源码行负责这些耗时。先不要修复。
```

## 用测试驱动方法先写失败测试

缺陷具有低成本的本地测试路径，且上下文明确时，可以直接简短要求：

```text
使用测试驱动方法实现当前切片
```

有上下文时，这就够了。[测试驱动方法](bug-regression-tdd.md) 先写因预期原因失败的最小测试，再修复，再重新运行测试。如果测试需要大范围搭建框架或脆弱的模拟，技能会说明情况，并使用最接近目标的可执行检查。真实命令能够提供更强证据时，不要强行测试。

## 按名称加载 TypeScript 规则

[TypeScript 方法](typescript-method.md) 把类型系统原则落实为具体规则：可辨识联合、边界处的 `unknown`、穷尽变体、从 Schema 推导的类型。任务触及 `.ts` 或 `.tsx` 文件时，按当前问题读取本包完整 TypeScript 方法和模式，不要求额外安装技能。

## 提交之前清理

[发起 PR 手册](pull-request-procedure.md) 在每次提交之前对差异运行 代码差异清理，并用 [文字清理](clear-writing.md) 处理 PR 描述和提交正文。代码差异清理按本包交付方法完成，不需要外部插件。用普通语言要求具体结果：删除逐行叙述的注释、没有依据的防护、失效兼容路径和无关编辑。

对于文字，文字清理 接受目标和你额外指定的规则：

```text
文字清理 清理 README 的改动，不要长破折号
```

你会逐渐形成自己的简短说法。技能可以从“清理那个，再收紧些”这样的简短提示中理解意图。

## 用 注释审查 清理注释

用户要求或项目策略采用注释清理时，让注释得到独立审查，优先由未写它的人检查。作者会维护自己的注释，就像你维护自己的注释一样。因此审查之前，让新视角来检查：

```text
注释审查 检查差异
```

[注释审查](comment-review.md) 按实际能力派出[独立注释审查者](comment-reviewer.md)，一位只读审查者，保留清单很短：许可头、公共 API 文档注释、解释代码无法表达内容的链接，以及无法重塑的外部依赖强制要求的行为。在项目选择的严格清理模式中，其余注释逐项审查并移除已证实冗余的内容。真实且尚未由结构保证的理由与约束继续保留。自己代码里的意外情况没有这种豁免。这类注释会以重构信号返回，注释审查 从根因修复它认可的信号。注释宣称“不要删除”等约束时，技能会提出把该主张编码为类型、测试或 lint。只有约束已经被等价机制保证或说明已无必要时，才移除注释；尚未落实或无法确认的约束仍保留。

这几者的分工应保持清楚。代码差异清理 清理代码中的冗余，文字清理 清理文字中的冗余，注释审查 把注释交给不是原作者的审查者。

**误区：** 清理不是可有可无的润色。包含叙述性注释和防御性冗余的差异，在审查者看来仍未完成；多余代码也是下一个缺陷的藏身处。差异看起来膨胀时，应在提交之前说“清理它”，而非等审查指出之后再做。
