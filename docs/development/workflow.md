# 开发流程与衔接

## 目标

从任意来源的需求出发，把目标、规格、可视化确认、垂直切片、实现、UI、审查、部署与知识沉淀连起来。每一步有自己的用途与输出，但不建立必须逐关通过的状态机。

先决定要交付的行为及边界，再选择适合的开发与验证方法。规格可以是一段话，不等于长 PRD。行为契约稳定时可以采用 TDD 的红、绿、重构短循环；探索性任务可以先做可丢弃原型；状态与并发风险高时结合状态图和形式化分析。无论采用哪一种，都核实最终代码、实际制品与真实运行结果。

每次任务先确定一个当前负责人，其他技能按需提供局部结果后返回。一个变更沿用一份权威行为契约，可在已有 brief 或 spec 中逐步完善；每个决定也只在一个位置维护，其他资料引用它。已有结果充分时直接继续，仍适用于当前代码、环境和范围的验证证据直接复用。

## 日常入口与完整方法

先在目标项目安装所需 dev 技能，具体选择、更新及领域导航见[安装契约](../usage/installation.md)。`dev-setup` 核验项目运行要求、当前宿主和用户指定的执行主机，在 `.agents/dev/context/environment.md` 记录资源快照、任务峰值预算和已有预留。跨阶段任务用 `dev-workflow` 加目标和验收；已有明确阶段时直接选择对应入口，例如按已有规格与有效体验基线实施用 `dev-build`，把完整文档转成可交互 HTML 让用户确认用 `dev-prototype`。`dev-help` 包含完整使用指南、场景配方和能力选择，但不内嵌执行包。方法归属与安装协作见[方法归属](method-ownership.md)。

总入口按[协作路由](../../skills/dev/dev-workflow/references/method-handoffs.md)协调完整流程，方法按职责分布在对应技能中，包括调查、缺陷、性能优化、单指标迭代、运行与轨迹取证、新功能、重构、原型、视觉对齐、技能编写、盲测评估、PR 跟进、验证落地、自主运行、跨日协调、独立 PR 队列、堆叠 PR 队列、任务接手、安全暂停、多阶段计划、工作树清理和创建 PR。保存交接、任务接手与明确暂停由 `dev-handoff` 维护，也可独立使用。采用哪一条取决于用户目标，步骤与原则按需读入；没有复杂状态引擎或准入网关。

完整工程原则及注释审查方法只在 `dev-guardrails` 保存，委派角色由 `dev-workflow` 保存，其他技能按需调用。角色含义来自任务职责；多模型仅在工具确实支持时使用，没有并行能力就如实串行，不伪造独立复核。

## 多个已有 Change 一起交付

用 `dev-program` 加上成员清单或已有批次文档。只要编排时交付顺序和 Goal 文本；在 Goal 中要求实施时，按当前产物直接推进到约定终点。单份规格内的切片继续使用 `dev-plan`。见[批次入口与示例](../../skills/dev/dev-program/SKILL.md)。

## 一次需求怎样推进

| 阶段 | 消除的不确定性 | 最小有用产物 |
| --- | --- | --- |
| `dev-issue` Issue 撰写与维护 | 开发者能否据现有材料直接认领，远端内容是否准确 | 含需求、证据、计划与验收的 Issue，或增量评论；发布动作有回读结果 |
| `dev-intake` 需求整理 | 多个来源究竟要求改变什么 | 有来源的目标、事实、范围、已有决定和缺口 |
| `dev-grill` 决策访谈 | 哪些产品取舍必须由用户决定 | 指定记录中的已确认决定与剩余分歧 |
| `dev-spec` 行为规格 | 现有约定还缺什么才能独立实施和验收 | 原有权威契约中补全的行为、验收、边界与约束 |
| Architecture / UI | 什么结构或体验支持这些行为 | 必要的取舍、接口/所有权、交互与设计约束 |
| Prototype | 文字共识是否与用户看到、操作到的最终效果一致 | 沿项目风格的完整交互 HTML、实际走查及具体版本的真实用户确认 |
| `dev-plan` 实施规划 | 每一片交付什么，哪些前置产物决定顺序 | 一票一份 Markdown，再以 `plan.md` 汇总票据 DAG、共享上下文、接续点和整合验收 |
| Build / Debug | 实际实现能否满足行为 | 可运行改动、根因修复与当前版本证据 |
| Review / Verify | 实现是否符合行为契约、工程规范，真实入口是否有效 | 有证据的缺陷、补充验证或残余风险；没有 spec 文件仍审明确用户要求 |
| `dev-deploy` PR 交付 | PR 是否达到用户要求的创建、可合并或已合并状态 | PR 地址、当前 CI 与审查证据、实际合并结果 |
| `dev-deploy` 环境部署 | 指定环境是否真正运行此版本 | 当前制品、实际入口、业务验证与发布记录 |
| Archive | 哪些认识能帮助下一次开发 | 更新后的少量长期知识与干净的历史记录 |

`dev-workflow` 按真实缺口选择需要的阶段。需求整理后只有未决产品取舍才调用 `dev-grill`，只有契约不足才调用 `dev-spec`；表格不是必经顺序。实施遇到故障调用 `dev-debug`，需要测试先行调用 `dev-tdd`，完成后返回原切片。工具缺失时按实际能力完成可做部分并说明缺口，不伪装调用成功。

显式要求实施计划时，单个切片也保存本地票据和单节点计划。明确的单项实施可直接交给 `dev-build`。接手票据计划时，按票内的产物依赖判断开工条件，进展沿用原票或现有 `progress.md`。

只要求编写或维护 Issue 时，以 `dev-issue` 为负责人，不自动创建整套本地计划。没有既有规格时，Issue 正文可以承担权威行为契约；已有规格、票据与计划时，正文包含接手必需的内容和可访问来源版本，本地任务与直接依赖仍在原处维护。远端新决定应按授权同步原记录，无法同步时明确待同步；详细用法见[Issue 撰写与维护](issues.md)。

涉及新的可见布局、交互或用户明确要求可视化对齐时，文档收敛后先形成确认原型，再实施依赖该体验的部分。`dev-prototype` 默认产生同一 change 下的 `prototype/index.html`、必要资源和 `prototype-review.md`；已确认原型规定其覆盖的可见效果，规格解释业务与不可见约束，任务安排工作。确认必须对应实际资源版本或内容指纹；已有同内容同范围确认直接复用，资源改变后只复核受影响范围，不能由 Agent 代签。完整用法与边界见[可视化意图确认](prototype.md)。

## 按问题组合小技能

| 需要解决的问题 | 可以插入的能力 | 与主流程的衔接 |
| --- | --- | --- |
| 工作进行中需要快速知道目前发生了什么 | `dev-status` | 对照最新代码和执行记录给简报；回答状态问题后继续原目标，除非用户明确暂停 |
| 保存开发上下文、交给新会话、接手具体旧任务或明确暂停 | `dev-handoff` | 引用同一规格、计划与证据，返回交接文档或已核对的恢复点；仅保存不停止执行 |
| 编写或修改项目技能 | `dev-personalize` | 使用通用技能编写分支，明确触发与成果并核对真实场景；无需先提供个人历史 |
| 多次重复工作希望形成自己的稳定方法 | `dev-personalize` | 只分析允许访问的历史，把真正重复的偏好写入项目技能，不把一次纠正提升为普遍规则 |
| 想改写请求的表达、目标、材料与验证方式 | `dev-sharpen` | 交付可使用的请求；只要求改写时不启动开发，真实产品取舍交决策访谈 |
| 不理解过去为何这样设计 | `dev-why` | 在学习、重构和删改历史约束前查找理由，并区分证据和推断 |
| 已选择并行覆盖独立工作，或需要比较不同实现 | `dev-parallel` | 先明确范围、评分与隔离方式，再集成；没有并行工具就如实串行 |
| 用户指定测试先行，或当前实现已选择 TDD | `dev-tdd` | 每个垂直切片内逐个红、绿、重构；已有正确行为补测试不自动进入实现循环 |
| 已有或明确需要 TLA+ 模型，要展示 TLC 检查结果 | `dev-statechart` | 不变量生成最短图路径，时序属性保留反例循环，回到代码重放；普通讲解图由当前学习或设计任务直接完成 |
| 关键不变量、并发或恢复属性值得更严格分析 | `dev-formal-verify` | 从明确属性建模，检查反例，回到真实实现验证；只有 TLA+/TLC 模型交 statechart，JS 模型使用兼容展示 |
| 已知错误反复出现，单靠提醒不足 | `dev-guardrails` | 核对可机械判断性、收益、误报及维护成本，再选择类型、结构或已有检查；依赖判断的经验保留文字与案例 |
| 需要证明真实入口和副作用可用 | `dev-verify` | 实施、审查与发布时驱动真实对象，必要时建立项目专用验证方法 |
| 优化需要量化比较，或要判断指标是否可信 | `dev-benchmark` | 固定负载、版本和测量条件，运行比较；预算取自本项目目标 |
| 需要让文档、PR 与交接表达准确易读 | `dev-writing` | 根据读者任务选择文档类型，解释行为、取舍和证据，减少空泛措辞 |

结构约束、经验验证与形式化分析互相补充。模型检查覆盖的是声明的模型与属性，定理证明也受所证明命题和前提限制，有界检查则受边界限制；任何一种都不能替人判断规范是否表达了正确需求。需要明确写出实际执行了什么、未检查什么，并把反例和结论映射回真实代码。

开发资料保存在 `.agents/dev/`。Change 的 `evidences/` 只含与 `tasks/` 完全同名的 Markdown，失败与复验更新原报告；完成整体验收才写根 `evidence.md`。生成图、轨迹、原始测量和日志留目标项目根 `temp/dev/`。长期知识归 notes，开发环境与任务上下文归 context，环境操作和发布归 deploy，可重复的模型与验证代码留项目真实源码或验证位置。结果归档、分类命名和退役知识按[知识与归档](../reference/knowledge.md)处理；活跃任务继续留在原 change。

## Issue 自动化怎样接入

Issue、聊天或日志只是输入来源，先按预期产出选择技能。把想法、Bug、性能或重构诉求写成可认领 Issue，更新正文或追加评论用 `dev-issue`；整理成开发请求用 `dev-intake`；报告分类、查重与分流用 `dev-issue-triage`。要求复现、定位和修复功能缺陷用 `dev-debug`，要求测量与优化性能用 `dev-benchmark`。只要完整 Issue 时，缺陷或性能描述决定需要补充的证据，不自动触发代码修复。

手动撰写 Issue 不要求初始化监控或配置后台任务。`dev-issue` 核对实际目标仓库、已有正文、评论和相关实现，复用来源与决定；按当前授权发布并回读。只要求草稿时交付草稿。单条手工材料也能分诊，配置适配器不是区分 intake、triage 与 Issue 撰写的依据。

`dev-issue-setup` 将报告来源、问题追踪器、仓库路由、可信身份、UI 控制与触发器分别配置；聊天、工单、邮件、监控告警与手工材料按实际可用适配器接入；没有后台能力时交付真实可用的手动方法或配置，不把文件写好说成自动化已启用。`dev-issue-triage` 读取已有证据、追踪原因、去重和分流，不在该阶段复现或修复。`dev-issue-fix` 在可信分诊和控制条件齐备后查已有修复，按本次目标仅复现、仅验证已有补丁，或执行授权内修复并以同路径证据交付草稿 PR。

可信标记是任务路由依据，不是给 Issue 正文提升权限。发消息、创建平台自动化、发布或合并都遵守本次已经明确的目标与范围；已经授权的动作无需重复确认。失败重试和交接沿用业务票及其同名报告，原件留 `temp/dev/`。长期有效的配置理由进入 notes，环境运行方法进入 deploy。

## 相似请求怎样区分

| 请求中的主要目标 | 主入口 |
| --- | --- |
| 写可认领 Issue、补全已有正文、给 Issue 追加方案评论 | `dev-issue`；发布与否按本次授权 |
| 把聊天、Issue 或截图整理成目标、事实、范围和缺口 | `dev-intake`（需求整理） |
| 产品规则尚未确定，需要按依赖逐层决定 | `dev-grill`（决策访谈） |
| 共识已明确，补齐独立实施和验收的行为约定 | `dev-spec`（行为规格） |
| 判断报告类别、重复性与处理去向 | `dev-issue-triage` |
| 按已有规格与有效体验基线实施 | `dev-build` |
| 文档已齐备，需要直观看到并操作整个 change 的最终效果 | `dev-prototype`（默认确认模式） |
| 尚未决定布局或逻辑，需要比较可运行候选 | `dev-prototype`（探索分支） |
| 从想法持续推进到上线，或接续后阶段不明的任务 | `dev-workflow` |
| 保存上下文、准备交接、接续具体旧任务或明确暂停 | `dev-handoff` |
| 改写待执行请求与验收表达 | `dev-sharpen`（请求改写） |
| 创建 PR、跟进 CI/审查或合并已验证改动 | `dev-deploy` 的 PR 交付分支 |
| 将指定制品发布到指定环境 | `dev-deploy` 的环境部署分支 |
| 编写项目技能 / 提炼个人工作偏好 | `dev-personalize` 的技能编写分支 / 偏好提炼分支 |
| 查当前机制并讲清楚 | `dev-learn` |
| 独立查当时的设计理由 | `dev-why` |
| 复述理解中的目标 / 把上一条解释讲通俗 | `dev-intake` / `dev-learn` |
| 功能不正确 / 性能指标需要改善 | `dev-debug` / `dev-benchmark` |
| 项目知识收尾 / 个人方式 / 结构防错 | `dev-archive` / `dev-personalize` / `dev-guardrails` |
| 进展简报或报告视频 / 构建可操作的状态应用 | `dev-status` / `dev-build` |
| 普通流程图 / TLA+ 结果图 / 属性检查与模型维护 | 当前学习或设计任务 / `dev-statechart` / `dev-formal-verify` |

完整任务复用同一规格、基线和记录。通用决策审计由 workflow 的决策证据方法负责，性能技能只负责其测量范围。UI 的设计系统、语义 token 与组件规范统一在 `dev-ui-design`，无需 Figma。

## 一个贯通示例

用户说：“账户页面增加邀请成员，参考这张截图，上线到预发。”

**接收。** 将聊天、截图与可能的 Issue 记录为同一需求来源。查看当前“账户”的代码概念和界面：它可能是个人账号，也可能是组织租户。不能仅因中文近似就把两个模型合并。

**澄清。** 从代码回答已有角色、邀请接口和存储位置。向用户询问无法从代码决定的产品规则，例如是否允许无账号邮箱接收邀请、哪个角色可邀请；如果早已决定则直接沿用。

**规格。** 在选定的权威契约中补齐发起邀请、接收邀请、重复/过期/权限不足的行为与成功条件；已有完整约定直接沿用。需求目标与当前代码分开表述。UI 补充空态、加载、错误、成功反馈、键盘操作和窄屏行为。不会因为参考源偏营销页就给后台强加 Hero 与 CTA。

**可视化确认。** 沿用现有账户页的导航、字体、颜色和组件，把发起、接收、重复、过期与权限不足做成可操作的 HTML。模拟发送不真正发邮件，提供失败恢复和重置；实际走查后交给用户体验。将用户真实确认绑定完整资源版本与范围；不能把“文档写完”或 Agent 点过按钮当成确认。

**架构与切片。** 确认身份与组织归属边界，优先复用现有能力。第一片跑通一个合法邀请的完整链路；后续增加幂等、防滥用、状态展示等独立可验收场景。不能把“先写所有表，再写全部接口，最后做全部页面”当作垂直切片。

**实施和审查。** 每个相关任务引用确认原型的页面、状态及结构/样式/交互定位，以相同视口、主题与场景核对实际界面；另验真实邮件、权限与持久化。按契约和风险选择测试先行、实现后验证或二者结合，并验证完整场景。审查一条线看规格是否完整实现，另一条线看接口、状态所有权、错误处理和复杂度。缺陷根据真实证据修复；不用修改规格来隐藏未满足的要求。

**部署。** 核对预发目标、精确制品、环境配置及数据迁移。执行后从实际入口验证邀请流程，记录实际版本。生产未授权就不发布生产；用户明确授权预发后不再重复询问每个可逆准备步骤。

**归档。** “账户”在本项目中确实指组织租户的，写入带范围和代码引用的 glossary；若与个人账号不同，显式保留边界。邀请状态持久化的取舍若会影响未来开发，写 ADR。一次临时重试留在发布记录，只有可能复发的原因才进入 errors。确认原型及其资源、版本和反馈随 change 保留，现役设计仍能找到它；核对并修正旧导读中已移动的文件引用。

## 不同规模和来源

- **两行文案修正**：简短规格、修改、实际界面检查；不强制架构文档、分片和 ADR。
- **已要求实施且有完整 Issue/spec**：核实版本、当前实现及适用的体验确认；已有有效基线直接进入计划或实施，需要确认的范围交 `dev-prototype`，不重新采访已解决的问题。只要求维护 Issue 时继续由 `dev-issue` 负责。
- **陌生项目二次开发**：先沿用户目标运行 `dev-learn`，建立相关垂直链路，再做变化；不默认通读全仓。
- **行为保持型重构**：记录需保持的不变量，必要时按调用链分波迁移；大范围机械替换可用脚本，不强求每片新增用户功能。
- **生产缺陷**：先定位和控制影响，在授权内修复或恢复；补齐可复用错误经验，不把紧急工作变成表单流程。
- **仅设计或调研**：以可评估的设计或有证据的解释为终点，不擅自部署。要求交互原型时保留实际交付与用户确认的区别，尚未确认就如实说明。
- **API/CLI/后台流程的可视化对齐**：用户明确要求时，用 HTML 模拟输入、状态、输出和错误恢复，说明它不是新增产品 UI，也不证明真实服务已完成。

## 中断、并行和变更

长期任务在 `.agents/dev/changes/<日期-主题>/` 保留规格、最新进展、当前分支/制品、证据与下一步。`dev-handoff` 按需在同一目录写 `handoff.md`，引用已有产物，保留下次重点和建议技能；接续时重新核对代码和用户最新指令，旧进度不是当前事实。只有明确暂停才执行安全暂停，保存或宿主压缩不等于停止工作。完整用法与边界见[开发上下文交接](handoff.md)。

有确认原型时，交接一并携带资源入口、固定版本/指纹、确认来源与覆盖范围；接续核对资源漂移，不把临时预览 URL 或旧报告当成有效确认。

运行资源交接引用同一环境记录，并列出未退出进程的主机、归属和可核对身份。恢复时按 `dev-setup` 更新当前资源与预留，不把前任的可用名额视为当前事实。已完成检出的清理由 `dev-worktree` 负责，确认退出与释放后再归还预算。

交接只负责开发任务的上下文，不承担宿主编排。接续后回到原执行技能，阶段不明时由 `dev-workflow` 选择下一步；无需安装其他领域技能。已有业务记录保留真实位置，技能资源迁移不搬动它们。

只在真正独立的文件或研究范围上并行，分配所有权并由主代理集成。可开工项由真实依赖决定，实际启动数还受各主机资源预算与工具上限约束；同一资源池的多个 Change、会话和嵌套执行者共用预留。资源暂时不足时排队，不为此伪造任务依赖。不要并发写同一全局索引。子代理报告不是验收本身，集成后的制品仍需验证。

需要 Git 检出隔离时按 [工作树技能](../../skills/dev/dev-worktree/SKILL.md) 创建或接手。当前批次交付后逐个合并到直接父分支，用双亲提交保留顺序和原提交。遇到在途冲突时按 [Git 冲突处理](../../skills/dev/dev-merge-conflict/SKILL.md) 恢复组合行为。

新增要求如果修正既有意图，就更新对应规格并找出受影响切片；如果是独立后续任务，单独记录来源和范围。保留被替代决定的理由，不积累互相矛盾的多个“最终版”。

需求来源与监控初始化的完整边界见[报告来源与监控配置](issue-sources.md)。`dev-setup` 负责开发环境与主机资源，`dev-issue-setup` 负责来源接入和实际触发；文件配置完成不等于监控已经启用。
