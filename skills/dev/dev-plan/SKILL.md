# 垂直切片与实施计划

使用**曳光弹式垂直切片**：每个切片贯穿完成该行为所需的层，交付一件可以演示或验证的事情。计划服务于实施，不建立额外的工作流状态机。

每个切片说明目标行为、真实依赖与验收方式；可以采用 TDD 短循环、实现后行为验证或适合该切片的其他方式。

## 先读取当前分支的完整方法

| 当前任务 | 开始前读取 | 产物 |
| --- | --- | --- |
| 大需求的终点或路线还不清楚 | [决策地图](references/uncertainty-map.md) | 已决定事项、明确的问题与尚未明确部分 |
| 已有规格，需要拆分交付行为 | [完整切片方法](references/vertical-slicing.md) | 垂直切片、验收与真实阻塞 |
| 已有切片，需要跨阶段或多 PR 安排 | [多阶段计划](references/multiphase-plan.md) | 每个交付单元的构建、可见结果、验证与交付安排 |

按当前缺口选择，不把三行当成必经阶段。已有决定、规格和切片直接沿用；明确的小改动使用[最小计划](references/plan-template.md#最小计划)，不加载完整多阶段模板。核对已有计划时读取它对应的方法，不重新从需求访谈开始。

## 从完整上下文开始

读取规格、相关讨论和已有计划。用户提供 issue / PR 时读取正文、评论和当前改动。用领域词汇描述任务，遵守本次已经确认的约束与授权。

定位当前代码和可复用实现。确有结构阻碍时先安排小范围前置调整；不要把泛化重构、工具换代或技术债清理偷偷加入本次范围。

小而明确的改动可只有一个切片。不要为了有计划而拆成多个文件或人为增加审批阶段。

## 切成可交付的行为

每个切片应当：

- 贯穿所需的数据、业务、接口、UI 与验证层，而非“先做数据库，再做全部 API，最后做全部 UI”。
- 完成后可独立演示或给出行为证据。
- 尺度适合一个实施者在可控上下文内完成；超出时按用户行为继续拆分。
- 有独立验收条件与清楚的边界，不依赖实施者猜测“做到什么算完”。

先做能尽早暴露关键假设的最小完整路径，再扩展场景。若一项只是调查或原型，它的交付是一个决定或事实，不伪装成已完成的产品功能。

为每个切片记录**真实阻塞**：只有前项的产物、决定或共享不变量确实是开工前提时才连接依赖。无阻塞切片可以同时推进；“看起来顺序更整齐”不是依赖。

## 对复杂重构使用诚实的整合边界

跨全仓库的机械改动可能无法按功能切片单独保持可运行。此时明确一条整合分支及最终统一验证边界。

若项目确实要求迁移期间持续兼容，可采用“扩展 → 分批迁移调用者 → 删除旧接口”；只有这种约束存在时才保留过渡层。用户已经允许直接替换时，规划一次完成全部调用者迁移及旧实现清理，不凭空引入兼容包袱。

说明哪些中间提交允许暂时不可运行，以及哪个整合点必须完整通过验证。中间状态不能被标记为可部署交付。

对于尚不明确的大需求，把“问题已清楚、答案待调查”与“还无法定义的问题”分开记录。只拆当前能说清的工作，完成调查后再展开后续切片。

## 写计划与任务

使用 [计划与切片模板](references/plan-template.md)。已授权的 tracker 继续按实际能力使用；新增本地计划与切片资料统一放在 `.agents/dev/changes/`，已有计划按真实位置引用：

- `.agents/dev/changes/<YYYY-MM-DD-slug>/plan.md` 保存目标、切片索引、依赖与执行顺序。
- 内容足够大或需要分工时使用 `tasks/<NN>-<slug>.md`，每个文件描述一个切片；已有任务保留其标识和引用。
- 当前进度只在选定的任务文件或 `progress.md` 维护，包含证据入口和下一步，其他位置链接它。计划中的目标与执行结果分开，具体记录见[本地工作记录](references/local-work-records.md)。

任务正文写交付行为和验收，不写逐行修改教程。交给新会话或独立实施者时，使用[单个切片](references/plan-template.md#单个切片)补足来源与必要背景、本项规格范围、已定约束、前置产物和验证入口；已有任务原处补足，不另建一份正文。资料指针必须能被接手者实际读取，不能共享时提供必要原文。

代码导航与行为契约分开，区分已有入口与拟新增文件，实施时复核；跨阶段安排才使用完整多阶段模板。验收写条件、动作与可观察结果，按真实风险覆盖正常、失败和回归；每项都能找到验证动作与通过判据，不用“测试通过”代替行为判断。信息密度可参考[任务示例与反例](references/task-examples.md)。

对适合并行的工作明确唯一写入者与文件/模块边界，同时核对共享 API、数据模型、迁移序列和测试资源；不同文件不等于互不冲突。先稳定共享契约，再推进独立消费者；不让多个代理同时覆盖同一分支或同一共享文件。

## 交付前核对

按[计划核对](references/plan-review.md)检查粒度、阻塞、交付与验收，并从规格反查是否有遗漏、重复责任或未承接的消费者。多切片按需使用[规格覆盖表](references/plan-template.md#规格覆盖)，保留用户明确的数量与交付边界，不把票数当成交付数量。

前置产物可用后，本项应能完成自己的验收；跨任务的整合验收另有明确归属，不把未来工作藏进早期任务的完成条件。全部任务勾完仍需核对原始目标和整合结果，规划中的预期证据不代表已经通过。

## 进入执行

如果用户要求先审方案，交付计划后停在所要求的位置。如果已经要求持续实施，说明计划并按授权继续；只为影响目标、不可逆操作或确实缺失的产品决定寻求补充。

发布 issue / sub-issue 需要已有授权。按阻塞项在前的顺序创建，使用真实链接建立依赖；不要编造未来编号，不自动关闭父 issue。

实施时工作前沿是“所有阻塞已满足的切片”。完成一项就更新依赖事实，继续推进可开始的下一项。不用预设状态枚举或复杂 Schema。

本技能交付一张可执行的工作图。实施授权已明确时调用 `dev-build`，传递目标、规格与计划指针、所需前置产物、写入边界、验收与证据入口、当前进度和授权终点。持续协调、恢复与暂停由 `dev-workflow` 负责，交付操作由 `dev-deploy` 负责，沿用同一记录。
