# 在当前部署兼容范围内恢复数据

数据恢复会改变业务状态。使用现有经过核验的项目/数据运行手册，不能提供“一条命令恢复任意数据库”的通用配方。

## 1. 明确数据目标与损失窗口

记录项目环境、稳定数据库/存储服务、实际实例、逻辑数据库/schema/卷或对象范围、希望恢复到的时间及原因。

核对用户已有授权是否覆盖该对象和可能丢失的当前写入。已有明确授权持续有效；若只说“修复服务”而没有授权覆盖生产数据，不把它解释为可以覆盖整库。先完成备份检查、兼容分析和计划，再说明缺少的具体决定。

共享服务的某个逻辑库恢复，与整个实例恢复有不同影响。一个项目的请求不自动覆盖同实例其他项目数据。

## 2. 验证恢复材料

| 方面 | 必须核对 |
| --- | --- |
| 备份身份 | 来源 job、源对象、创建完成时间、实际保存位置和链条 |
| 完整性 | 工具支持的校验、增量链/日志链、加密密钥可用性引用 |
| 数据一致性 | 快照/事务条件、跨服务数据边界、当时写入情况 |
| 恢复点 | 可真正到达的时间；时间戳与时区；日志重放终点 |
| 版本与格式 | 数据引擎、备份工具、存储格式及当前运行版本兼容性 |
| schema | 与当前应用/中间件部署的兼容性；是否会触发转换或迁移 |
| 验证依据 | 既有恢复演练及其实际版本、环境、覆盖与未验证项 |

文件存在、备份任务成功、相同数据库大版本，都不足以单独证明可恢复。密钥不存在、链条断裂或版本条件未知时，报告缺口，不能对生产目标试错。

## 3. 决定是否仍属于运维

符合当前部署、当前应用/中间件版本与 schema 契约的数据恢复，可以按既有方法运维；仍需明确数据损失和验证。

下列情况交项目协同处理：

- 需要换到旧应用或数据库/中间件版本才能读取数据。
- 需要回退/升级 schema、执行应用 migration 或发布配套转换。
- 需要修改项目持久拓扑、创建新生产资源、切换部署配置。
- 恢复要求改变多个项目未授权的业务数据。
- 不存在适用于当前版本与数据范围的已验证恢复方法。

ops 保存当前事实、备份证据、损失窗口与建议协同事项，不执行版本回退来强行让旧备份可用。

## 4. 准备与执行

1. 确认当下写入状态、现有任务和恢复冲突，复用已有业务暂停/隔离方法。是否需要暂停写入由真实恢复程序决定，不能自行推导。
2. 保存必要的当前状态及其恢复证据；做新的备份也要说明时间、空间和写入影响，不能无限延迟既有紧急目标。
3. 使用已有隔离验证结果或明确授权的测试目标核对方法；不为认证技能在生产演练。
4. 记录有限步骤、恢复点、数据损失、就绪规则、停止条件和验证。
5. 通过 ops-execute 调用现有恢复入口。开始前保留目标与授权，执行中保留后端任务 ID 和逐步结果。
6. 原任务未确认停止、远端结果未知或记录能力不足时，不重复启动另一次恢复。

恢复过程不是普通可逆重启。执行失败可能已覆盖部分数据；不得把非零退出码当成未修改，也不能无条件重跑。

## 5. 验证实际业务结果

验证恢复点、数据完整性与当前应用可用性三个不同问题。按现有方法检查数据一致性、关键对象、原失败路径、相关消费者及写入恢复后的行为。

恢复完成后的新写入与恢复点前数据分开描述。对可能丢失的数据窗口、跨服务不一致和未覆盖消费者据实报告，不能只凭“数据库启动成功”宣布恢复全部业务。

共享实例恢复要覆盖全部已知受影响项目，或者逐项写明验证缺口。若结果部分成功，保留每个目标的执行、现场和记录状态，不把后续项目发布任务计作已完成。

## 6. 保留事实与方法边界

本次记录保存实际恢复对象、时间点、工具/手册版本、结果、验证和剩余未知。秘密、全量数据和原始备份不写进通用技能或报告。

需要更新手册时把经过核验的方法与反例交 ops-runbook；当前地址、版本、数据量留在事实来源，不固化成跨项目通用参数。
