# 分诊参考：合并队列（完整示例）

> 本工具包 webshop-CI 场景中的虚构示例内容。
> 你的 `oncall-setup` Mine 阶段会从自己的事件历史，
> 按以下结构起草真实版本：症状 · 首轮检查 · 关联表
> （每行都有来源）· 已知原因 · 升级处理。
> 如果你的值班工作没有此类故障，请删除本文件。

## 症状

- PR 卡在队列中；队列深度持续增长
- 队列在推进，但很慢（等待时间升高，吞吐量大体正常）
- 队列为空，但合并仍没有进入目标分支
- 一个 PR 反复循环：不断被移出又重新入队

## 首轮检查（按顺序；时间线已能解释症状时停止）

1. **深度与吞吐量。** 深度增长而吞吐量正常，是一波到达高峰；
   深度增长且吞吐量下降，才是真实停滞。
   `(query: {{metrics}} → mq.depth, mq.merges_per_hour, last 6h vs yesterday)`
2. **队首是否卡住？** 队列按顺序处理；一个无法合并的队首 PR
   看起来就像系统性停滞。检查队首 PR 自身状态，
   以及它占据队首多久了。
3. **时间线。** 窗口内改变了什么：流水线定义合并、
   CI 基础设施部署、功能开关逐步放量、runner 容量事件。
   `(sources: {{deploys}}, {{flags}}, {{code}})`
4. **合并高峰检查。** 每小时提交数高，而最新主干构建已完成且为
   绿灯，这是高峰，不是事件——说明这一点并停止。
   如果该构建仍在运行，你还不知道：未完成构建上没有失败，
   什么也不能证明。

## 关联表

| 如果看到 | 同时 | 通常意味着 | 那么 |
|---|---|---|---|
| 深度增长，吞吐量接近零 | 队首 PR 反复在同一个必需检查失败 | 队首卡住——一个 PR 伪装成系统性停滞 | 建议移出队首 PR（由人行动）；深度应按平常速率下降 *（出现 3 次：INC-104、INC-116、INC-126）* |
| 所有等待时间都升高 | runner 队列年龄也升高 | 容量问题，而非队列问题——转给 runner-infra | 加载 `runner-infra.md`；不要调队列 *（出现 2 次：INC-109、INC-121）* |
| 队列已排空，但目标分支没有推进 | 合并后流水线（不是队列）失败 | 队列已经完成职责；卡在下游 | 将目标分支流水线作为独立事件调查 *（出现 1 次：INC-130）* |
| 一个 PR 反复被移出 | 它的基线正在与高合并率窗口竞争 | rebase 反复变动，PR 在处理过程中不断过期 | 建议作者在较安静的窗口合并；不作为基础设施事件 *（出现 1 次，未验证：INC-119）* |

## 已知原因

提出理论前，检查 `lessons.md` 中标有 `#merge-queue` 的条目。

## 升级处理

- 队列完全停滞且深度上升 → 按 `ONCALL.md` 属于需呼叫值班人员的级别
- 明显合并高峰期间等待升高 → 记晨间日志，不呼叫值班人员
- 移出卡住的队首后，预期恢复窗口是一个队列周期（约 15 min）。
  若深度没有开始下降，队首就不是原因——回到首轮检查，
  把容量列为调查对象。
