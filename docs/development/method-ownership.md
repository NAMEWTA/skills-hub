# 开发技能的方法归属

每份完整方法由一个技能负责，每个当前任务也有一个明确负责人。`dev-workflow` 协调跨阶段任务，`dev-help` 帮助选择，阶段明确时由专门技能直接负责；按目标调用其他方法，完成局部工作后回到原任务。

## 原因与目标

单一归属让方法修改只发生在一处，调用者通过明确的输入、产物和返回条件协作。它保留完整知识，也避免帮助、工作流和各阶段各持一份稍有差别的副本。共享方法仍归某个实际技能，不另建公共方法库或依赖注册表。

## 方法归属

| 负责技能 | 完整职责 | 协作方式 |
| --- | --- | --- |
| `dev-help` | 能力地图、使用指南、提示词与场景配方 | 提供选择与用法，不内嵌执行包 |
| `dev-setup` | 宿主、角色模型、预算、工具和验证配置 | 记录真实环境；目录导航归安装器 |
| `dev-workflow` | 任务路由、工程执行、自主队列、跨日协调和决策证据 | 推进同一任务，集成阶段结果 |
| `dev-handoff` | 开发上下文交接、会话接续、安全暂停 | 保存或核对恢复点后返回原阶段；仅保存不暂停 |
| `dev-intake` | 需求整理：来源、事实、目标、范围、已有决定和缺口 | 输出开发请求；有未决产品选择才调用 grill，契约不足才调用 spec |
| `dev-grill` | 决策访谈：按依赖解决尚未确定的产品取舍 | 沿用调用方指定的决策记录，解决后返回；不重复访谈 |
| `dev-spec` | 行为规格与完整实施简报：独立实施、审查和验收所需契约 | 补全同一份 brief 或 spec；已有契约充分时直接复用 |
| `dev-plan` | 垂直切片、复杂决策地图和多阶段计划 | 维护实施顺序与依赖，决定只写在对应权威记录中 |
| `dev-sharpen` | 请求改写：检查目标、材料、方法与验收表达 | 返回可使用的提示词；只要求改写时不启动实现 |
| `dev-architecture` | 架构、模块深度、依赖与候选方案 | 接受行为契约，返回接口、取舍及理由 |
| `dev-ui-design` | 设计系统、语义 token、组件与交互规则 | 沿用项目设计约束，不要求 Figma |
| `dev-prototype` | 确认原型、设计证据、版本指纹及探索原型 | 用可操作 HTML 固定体验依据，确认绑定具体版本与范围 |
| `dev-build` | 功能实施、任务图、行为保持重构和界面交付 | 读取规格与适用原型，调用诊断、TDD 或探索方法 |
| `dev-debug` | 缺陷回归、科学诊断与人工复现 | 返回根因、修复和原失败场景证据 |
| `dev-tdd` | 缺陷红绿回归、逐切片测试先行和替身设计 | 按当前任务选择适用方法，不重复两套同目的流程 |
| `dev-benchmark` | 测量、性能修复、单指标迭代和轨迹取证 | 固定负载、版本与基线比较 |
| `dev-guardrails` | 工程原则、类型、注释审查和结构化防错 | 调用方保留适用条件，按风险、可判断性、收益和维护成本选择约束 |
| `dev-review` | 契约与工程审查、对抗审查、盲测和意见分诊 | 没有 spec 文件仍检查明确用户要求；复用有效证据，返回缺陷与残余风险 |
| `dev-verify` | 真实入口验证、项目验证方法、功能图和视觉对照 | 检查实际对象，必要时调用专门验证工具 |
| `dev-formal-verify` | 属性选择、检查工具、模型与代码映射维护 | 仅 TLA+/TLC 模型交 statechart；其他模型使用兼容展示，生成 `dev-formal-verify-<area>` |
| `dev-statechart` | TLA+/TLC 结果图、规则标记和反例回放 | 接受兼容模型和结果，区分状态不变量与时序属性 |
| `dev-deploy` | PR 交付与环境部署两个分支；PR 准备、跟进、落地及工作树审计 | 只要求 PR 时不执行部署；指定环境发布时核对制品、入口和业务结果 |
| `dev-learn`、`dev-why` | 当前机制讲解；历史理由调查 | 区分现在如何工作与当时为何决定 |
| `dev-archive`、`dev-writing` | 知识维护与 change 收尾；技术和 Agent 文档 | 分别维护归档方法和写作规则 |
| `dev-issue-setup` | 报告来源配置与共同协议 | 配置实际接入和触发能力，不复制执行方法 |
| `dev-issue-triage` | 报告分类、查重与分流 | 来源适配器或单条材料均可；只使用已有证据，不自动复现或修复 |
| `dev-issue-fix` | 可信交接后的 UI 复现、补丁验证与受限修复 | 先满足报告流程和控制前提，再按具体目标执行 |
| `dev-personalize` | 通用技能编写与稳定个人偏好提炼两个分支 | 写项目技能无需个人历史；提炼偏好只使用授权材料 |
| `dev-parallel`、`dev-status` | 并行协作；进展报告 | 在当前负责人任务内提供所需结果 |

具体条件和返回结果见[工作流协作路由](../../skills/dev/dev-workflow/references/method-handoffs.md)。这里描述职责，不替代完整方法或当前目录发现；可运行 `node install.mjs list --domain dev` 查看实际入口。

## 追踪与变体处理

[资料父清单](../../materials/manifest.tsv)导航到逐文件子清单。`runtime_paths` 指向实际采用方法，`runtime_reviewed_blob` 记录最后核对的来源对象。来源、完整对照与运行适配分开维护，当前材料不等于运行版已经更新。

去重前按来源路径、blob、正文和适用条件比较。保留专门方法的授权、宿主、持久化、证据和失败条件；同一来源在同一技能内拆成方法与模板可以有多个映射。来源删除、移出范围、拆分或合并时，先保留旧映射的影响分析，不自动删除运行方法。

历史资源迁移表作为[回归夹具](../../tests/fixtures/dev-resource-moves.tsv)保留。它记录过去移除位置及保留资源，用于回归检查；当前归属以运行文件和材料映射为准，新增改动在自己的 change 记录路径变化。

## 安装与执行

安装器按显式选择复制完整包，不自动解析兄弟依赖。完整开发套件可按 dev 领域安装，部分安装在缺少必要方法时说明具体缺口。已有 handoff、prototype 或旧 UI 包的升级步骤见[安装迁移](../usage/installation.md#开发交接入口迁移)。

调用者传递目标、阶段、权威行为契约、各决定的记录位置、已有产物、代码版本、证据、授权、返回条件，以及适用原型的资源版本和确认范围。被调用者补充指定记录后返回原任务；同一未决问题不能在没有新证据时反复转交。没有宿主调用 API 时直接读取实际安装入口，不声称启动了不存在的子代理。

一个变更只有一份权威行为契约，可在既有 brief 或 spec 中逐步完善；每个决定也只在一个位置维护，其他资料引用它。已确认原型及资源独立保存，作为其覆盖范围内的可见效果与交互依据。对当前代码、环境和范围仍有效的验证证据直接复用，缺口或条件变化才触发补验。

生成的应用操作验证技能使用 `dev-verify-<app>`，形式属性验证技能使用 `dev-formal-verify-<area>`。创建前检查已有目录和职责，更新对应包，避免相同 app 与 area 名称覆盖彼此。

项目中的规格、原型和交接文件保留真实位置，技能资源归属改变不搬动业务记录。

## 防止再次膨胀

材料检查拒绝同一开发来源映射到多个负责技能。包装检查识别长篇完全重复资源，以及仅改 Markdown 目标或空白的复制；回归检查核对方法唯一归属、历史迁移目标和帮助不内嵌执行包。

这些检查不能证明译文忠实或识别所有近义改写。修改后还需对照完整原件和唯一运行正文，核对调用者与返回条件。来源与改造说明统一见[第三方声明](../../THIRD_PARTY_NOTICES.md)。
