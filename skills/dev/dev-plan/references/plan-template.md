# 计划与切片模板

本文件连接[完整切片方法](vertical-slicing.md)的行为任务与[多阶段计划](multiphase-plan.md)的实施清单。已有任务模板可直接沿用；只有需要实施导航时补充相应信息，不要求维护两份任务正文。

## 最小计划

```markdown
# <需求名称>实施计划

目标：<与规格一致的可检查结果>
规格：<链接>
交付点：<本地完成 / 推送 / PR / 指定环境上线，依据用户授权>

| 切片 | 完成后的行为 | 真正依赖 | 所有者与边界 | 验证方式与通过判据 |
| --- | --- | --- | --- | --- |
| 01 <名称> | <可演示结果> | 无 | <模块或文件> | <命令或场景 → 预期结果> |
| 02 <名称> | <可演示结果> | 01 的 <产物> | <模块或文件> | <命令或场景 → 预期结果> |

## 顺序与并行
<哪些可以并行，哪个共享契约需要先确定，谁负责整合>

## 未定部分
<还需要调查什么，以及它只阻塞哪些切片>

## 完成边界
<最终整合验证、交付状态、已知限制>
```

只有切片足够大或需要分工时才建立独立任务文件。

## 单个切片

```markdown
# <NN> <切片名称>

规格：<相关行为的链接；标明本项承担的验收范围>
交付：<从用户或调用者视角描述的完整结果>
依赖：<真实阻塞项及所需产物；无则写无>
边界：<唯一所有者、涉及模块、明确不做>
当前代码指针：<已核实的路径 / 符号 / 观察版本；拟新增文件另行标注，实施时复核>

## 实施要点（需要时）
<沿用已定接口与设计；只列必要的修改和顺序，不逐行预写实现。多阶段工作使用完整计划中的构建块。>

## 验收
- [ ] <可观察条件及对应验证入口>
- [ ] <重要边界及对应验证入口>

## 完成证据
<运行命令或操作场景 → 预期结果 → 证据位置；注明所需环境、基线和必要的失败证据。拟新增测试应写明创建任务，不冒充已经可运行。实际结果由执行者记录，不预填“通过”。>
```

## 垂直与横向

“数据库表全部建好”“全部 API 完成”“全部页面完成”不能让用户体验一个完整能力，通常不是独立功能切片。

“用户创建一条任务，退出重开后还能看到它”贯穿输入、业务、存储与展示，是一个垂直切片。后续可分别扩展“编辑任务”“完成与撤销”“筛选任务”。

公共依赖不一定要单独出一项。若基础调整很小、只有一个调用者，可以并入第一个完整切片。只有实际阻塞多个切片且可独立交付的工作才单列，写清调用者、契约与独立验证入口。

工作包可用于组织多个切片，但工作包名称不代替每片的交付和验收。例如“导出与导入”若由两个独立行为组成，可分别验收；不能只检查导出成功就把两者都标为完成。

## 任务图与工作前沿

假设 A 交付领域契约，B 和 C 各自依赖 A，D 依赖 B 与 C：

- 起初只有 A 可执行。
- A 完成后 B、C 可以并行，且各有独立写入边界。
- B 先完成时，不必让负责 C 的代理停下来等汇报；D 仍等待 C。
- 两者真实产物整合后，D 执行完整场景验证。

“代理说完成”不自动解除依赖；以实际可读的产物和验证为依据。

## 跨仓库机械重构

先说明为什么不存在能独立落地的垂直切片。按实际约束选择：

- 要求逐批可运行：提供有期限的迁移桥接，迁完全部消费者后删除。
- 允许整体替换：在整合分支完成所有消费者迁移，一次验证新契约。

对于后一种，不把临时无法运行的中间点标为已交付，也不为了表面上每一步通过而长期保存两套接口。

## 持久化最小集

规格与计划说明目标；进度说明已经发生什么；证据说明如何知道结果。按[本地工作记录](local-work-records.md)选择当前进度的权威位置，用链接连接它们。不要复制同一段验收条件到多个互相独立的真相源，不建立强制状态迁移图。交付前按[计划核对](plan-review.md)检查，规划中的预期证据不等于实际完成证据。
