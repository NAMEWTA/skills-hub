# 意图与路由

## 先确定本次结果

从用户输入和已允许读取的资料取得目标、环境、时间、对象与期望结果。把“看看”“解释”“查历史”“制定计划”和“执行维护/恢复”区分开；能力说明不构成现场变更授权。用户已经指定范围和动作时沿用，不再次要求填写相同信息。

同名项目存在 prod/staging 时，先查真实映射与现有会话，不猜生产。尚不能唯一定位对象时可分析已提供日志、整理候选和影响，只有相关现场动作被阻塞。

如果输入包含多个诉求，先区分是否同一目标的步骤。例如“查出为什么超时并恢复当前服务”可在一个主 run 内诊断和恢复；“另外查上周另一项目的费用”是独立目标，建立关联新任务。不把所有未来运维放进一个永久 run。

## 最小路由

| 例子 | 入口 | 何时需要追加其他方法 |
| --- | --- | --- |
| “把这台主机登记为 `01`” | inventory | 按用户给出的别名写入登记；不因此取得现场操作授权 |
| “host-b 上有哪些服务” | inventory | 已有登记与现场有冲突时继续核验来源；没有变更动作 |
| “检查 `01`” | inspect | inventory 先按当前工作根解析主别名；解析失败不猜主机或连接 |
| “检查 shop/prod” | inspect | 组成不明时补 inventory；用户要求调查异常时交 diagnose |
| “shop API 超时，定位并处理” | diagnose | 需要背景时 history；边界内已授权的具体处置交 maintain/recover |
| “更新 host-b 的指定内核包” | maintain | inventory 提供共机影响，专门方法核对包集合与重启要求 |
| “启动已经退出的 worker” | recover | 专门方法核验当前制品、配置、数据和真实启动副作用 |
| “昨天 shop 做过什么” | history | 仅为消除对象歧义补关系资料，不自动连接现场 |
| “从已有记录形成 shop 技能” | runbook | 证据缺口先标明，不为凑足样本自动生产变更 |
| “升级共享数据库” | 项目交接 | ops 列出当前消费者、证据与复验条件；不执行升级 |

专门技能的结果可能改变下一步。健康检查发现异常不等于自动获准恢复；故障处理的既有授权足够且实际处置仍在范围内时，继续完成，不每个步骤重新审批。

## 执行与记录是共同契约

创建或接续 run、记录内部调用、检查真实操作入口和核实未知结果都使用 `ops-execute`。workflow 不维护另一套记录器。history 查询开始时固定时间截点，其本次轻量记录不递归影响所查历史。新记录缺少可靠保存能力时，按执行 owner 的规则处理，不能声称已记录。

## 方法缺失

按实际安装情况查找所需入口。完整领域包含全部九个技能；安装器不解析域内依赖。只安装 workflow 并不提供其余八种方法，只安装专门技能也不强制安装 workflow。

缺少所需 owner 时，完成已有材料可支持的解释与计划，指出缺少哪个方法、会阻塞什么。不要伪造调用成功、偷偷安装其他领域、临时编写执行器或跳过记录去操作。

## 反例

- 历史问题被扩大为全网巡检：回到用户时间与对象范围。
- 模糊的“处理一下”被解释为生产重启：先确定真实期望和必要授权。
- 同一 tag 被当作同一部署：由恢复/执行方法核对 digest、配置和启动行为。
- 项目发布缺少入口便在 ops 加发布步骤：保留能力缺口，形成项目交接。
- 为了“完成流程”而自动生成项目技能：知识沉淀由用户目标或已授权知识维护任务触发。
