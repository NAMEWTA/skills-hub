# 按规格实现

以规格定义结果，以代码实现结果，再取得风险相称的行为证据。保留 Matt Pocock 的 **任务前沿、上下文指针和独立实施者**，以及 pstack 的 **可验证小单元、明确所有权、同一交付面验证**。

**禁止 TDD、测试先行和 red-green-refactor。** 先明确行为契约和关键设计，再完成实现，最后补充有价值的回归检查并验证。已有测试可以帮助观察现状与验证结果；不以编写失败测试驱动实现。

## 开始或恢复

读取规格、计划、进度和影响本次代码的项目规范。复核最新代码、分支和未提交改动；保留用户与其他任务的工作。恢复会话时，以当前工作树、远端记录和实际产物复核旧进度，不盲信“已完成”。

没有正式 spec 的小任务，先在现有记录中写清目标行为、范围和验收即可。缺失会改变产品目标或数据语义的决定时，只阻塞相关部分，不擅自猜成定案。

采用项目已有记录位置。无约定时使用 `.agents/changes/<YYYY-MM-DD-slug>/`，按需维护 `spec.md`、`plan.md`、`progress.md` 与 `evidence.md`。这些是项目工作记录，不属于技能安装目录。

## 从前沿推进

把计划看成带真实阻塞关系的任务图。每次选所有前置产物已经可用的切片；完成一个就重新计算前沿。切片交付完整行为，不把各层的半成品当成已完成。

有可独立推进的工作时并行处理；有共享状态、共享文件或紧密接口耦合时先确定唯一所有者。优先消除不必要共享，再考虑串行。小任务由一个实施者完成即可。

需要代理协作时，按 [委派与整合](references/delegation.md) 提供目标、契约、可写边界、依赖和完成证据。优先给文件与提交指针，不复制整段上下文。不同任务可用独立上下文和工作树；工具不可用时顺序完成同样的工作，不把工具依赖变成阻塞。

## 实现一个可验证单元

1. 确认切片的输入、行为、数据形状和成功条件。
2. 按现有约定修改代码。非平凡设计先确定接口与所有权；已有设计足够时直接实现。
3. 保持范围清楚。新发现若阻塞本次目标，纳入并说明；无关改进记为后续项。
4. 完成实现后，选择能证明该行为的最便宜充分检查。重要回归可以添加自动检查；低影响修改不为数量添加测试。
5. 记录实际结果、产物和仍未验证的部分，再推进下一单元。

验证入口必须匹配交付物：UI 打开页面并操作相关状态，CLI 实际执行，服务调用接口，存储检查写入后重载。类型检查、构建和静态审查各自有价值，但不能证明它们没有观察的行为。

遇到失败时依证据排查。被证据否定的试探性修补应撤回，不留下“可能有用”的代码。复杂故障可选用 `dev-debug`；未安装时继续完成复现、假设验证、修复和同路径复核。

## 整合与复核

先阅读实际 diff 和行为产物，再接受实施者的完成报告。整合依赖更新后，复核受影响的接口；发生冲突按契约解决，不能通过保留两个互相矛盾的实现来消除冲突标记。

分开审查两件事：实现是否满足规格，是否符合项目规范。较大工作可用独立审查者；也可在新一轮上下文中自行审查。可选 `dev-review`，不把安装另一个技能作为完成条件。

检查结果绑定具体工作树或提交。代码后来变化时，判断原证据是否还覆盖当前交付；受影响的验证重跑。不要重复已经充分证明且未受影响的检查。

## 持续到授权的交付点

按照用户要求和项目流程提交、推送、创建 PR 或继续部署。外部动作只在已有授权覆盖时执行；用户已经授权的步骤直接完成，不反复问是否继续。没有被要求的 PR 评论、issue 关闭或团队通知不自动发送。

达到完成点时明确：

- 哪些规格行为已实现，证据在哪里。
- 哪些验证已运行，哪些因环境限制尚未完成。
- 实际提交、远端、PR 或部署状态；排队、配置成功和执行成功分开。
- 下一步是否属于本次授权范围。

若本次目标包括部署，代码完成只代表进入部署阶段，可选 `dev-deploy`。完整需求完成后将可复用知识交给 `dev-archive`，或自行按代码证据更新项目记录；单独安装本技能也能完成开发交付。
