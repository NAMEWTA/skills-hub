# 开发环境、资源与团队配置

需要集中核验环境或评估当前项目容量时，可单独使用 `dev-setup`。报告先给包含主会话的建议 Agent 总数、当前可新增数、同时运行的重任务及其内部 worker，再给 worktree 保留量、硬件和证据。完整方法和模板由[技能入口](../../skills/dev/dev-setup/SKILL.md)维护。

开发任务需要环境信息时，直接复用 `.agents/dev/context/environment.md` 或已有权威位置中仍有效的内容；记录缺失、过期或执行主机变化时，按本次任务补查实际运行条件。创建环境文档和调用 `dev-setup` 都不是其他阶段的前置步骤。

## 选择这次需要的评估

| 当前需要 | 使用方式 |
| --- | --- |
| 初次接入项目、切换主机，或想知道当前能安排多少并发 | 用 `dev-setup` 只读核对执行环境，复用已有负载样本并更新报告。 |
| 缺少指定负载的样本，且已授权运行该任务或测量并发容量 | 优先观测本来就要运行的任务；需要额外校准时，限定并发、时长或轮次及停止条件。 |
| 按已有规格继续开发、评审或验证 | 直接复用有效记录，启动前核对实时余量和预留，按会话与重任务预算分批执行。 |

## 只读核对当前环境

```text
使用 dev-setup 只读核对本项目的运行要求和当前执行环境。
我指定的远端 host-a 也用于执行构建，请通过现有连接核验。
先给包含主会话的建议会话总数和当前可新增量，
再给重任务并发、每项内部 worker，以及指定状态的 worktree 保留量。
区分实测、估算和未知，缺少样本时给出最小补测方法。
```

默认只读调查项目与执行环境，并按请求写入报告。普通评估不自动安装依赖、构建、运行测试、批量启动 Agent、创建 worktree 或执行删除，也不修改全局 CLI 参数和系统服务。

只观测到当前执行器时，报告就写“当前执行器”，不能称为用户电脑。只指定本机时不发现其他主机。远端仅核对用户指定且已有连接能力的目标；不可达就记录未知，不把假定容量加入本机。每台机器分别给结论，共享父宿主、配额和存储另列共同约束。

需要保存环境记录时，默认使用 `.agents/dev/context/environment.md`。已有等价权威记录原地维护，各工作树、Change 与执行者引用同一位置；存在原生调度器时引用其预算入口。记录包括：

- 实际执行主机、容器/虚拟机边界、版本要求与核对结果。
- CPU 有效配额、可用内存与压力、真实卷剩余空间，以及适用的 PID/inode 等限制。
- 主机、父配额与共享存储的对应关系，采样时间与未知项。
- 项目版本、负载类别、内部 worker 设置与已有样本的适用条件。
- 当前负载的峰值估计、系统保护量、已经兑现和未兑现的预留。
- 会话、重任务、保留 worktree 的建议总量和当前可新增量，排队原因及刷新条件。

## 用报告中的数字安排工作

先看报告开头的执行建议、容量表、当前瓶颈与待补测项，再按需要查看硬件和测量细节。按以下口径使用数字：

| 报告项目 | 如何安排 |
| --- | --- |
| Agent 会话 | 建议总数包含主会话，当前数量包含仍在运行或等待的会话；当前可新增量单列。task 数量、Git 分支和历史会话不直接换算为运行会话数。 |
| 重任务 | 安装、构建、测试、浏览器验证等按实际负载分别给并发，每项还要注明内部 jobs 或 workers。一个会话名额不附带一个重任务名额。 |
| 保留 worktree | 指明纯源码、依赖已初始化或保留产物等状态，按实际卷计算磁盘增量。在这些树中同时运行重任务的数量另受重任务预算限制。 |

三项共用同一份资源预算，必须按报告给出的组合安排，不能分别用满每一行。原生 subagent 若共享宿主进程，逻辑会话数与进程数分别记录，共享服务和宿主占用只计算一次。物理机总内存不能突破容器及可见祖先配额；远端空闲内存不能给本地任务提供额度。

以下仅说明报告格式，数字不是默认配置，也不是用户宿主机的实测结果：

> 建议同时保持 5 个 Agent 会话，包含 1 个主会话和 4 个 worker。其中最多 2 个会话同时执行已测量的重任务，每项使用已验证的 2 个内部 worker。当前已有 3 个会话，可再增加 2 个。磁盘还可保留 3 个已初始化 worktree，但不增加重任务名额。具体依据见负载样本与预算，实际硬件极限未知。

报告中的“已验证运行规模”表示某个环境、负载、参数和观测窗口中成功运行过的组合。“建议并发上限”是当前操作建议，“资源估算容量”依赖写明的假设；两者都不自动成为运行时硬限制。产品限制要按实际版本及作用域单列，注明是否包含主会话。API 额度尚未核实时，保留有依据的硬件建议，同时说明端到端可用容量仍有缺口。

| 观测或证据 | 应采用的结论与行动 |
| --- | --- |
| 只确认 1 个主会话，缺少新增会话成本 | 写“实际并发上限未知，暂无可确认的新增名额”。可新增记为 `0` 时注明证据不足，不能写成本机最多只能运行 1 个 Agent；复用适用样本，或在余量允许且已授权时补测一个代表会话。 |
| 5 个会话在指定组合下成功运行 | 写“已验证运行规模为 5”，保留负载和窗口；这不能证明第 6 个必定失败，也不能写成“实测最大上限为 5”。 |
| 当前已有 5 个会话，重算后建议总数为 3 | 同时保留当前数与建议数，可新增为 `0`。停止扩张，按压力情况排队和收敛，不抬高建议值，也不因生成报告而自动结束已有会话。 |

## 按需校准指定负载

缺少样本时，先给未知项和最小补测路径。用户已经授权运行任务或测量并发容量时，优先观测正常开发中本来就要执行的工作，无需重复确认同一授权。

```text
观察本次已经要运行的项目构建，沿用当前 jobs 设置，
记录完整进程树的资源峰值、完成时长、退出结果和残留占用。
如果还需要并发校准，先按当前余量确定最大试运行并发、
总时长或轮次、停止条件及可用停止入口，再更新原环境报告。
```

校准选择可停止的代表负载，先观察一个会话或一项任务，再在有证据支持的余量内逐步增加同类负载。明确每项内部 worker，不同时放大多个未知类别。样本应记录项目版本、执行资源池、命令与参数、冷暖缓存、观测窗口和采样方法；未覆盖关键峰值就保留缺口。

触发保护线、出现持续换页或 I/O 压力、任务失败，或可比任务的吞吐不再改善时停止扩张，回到已验证的稳定组合。没有可比样本时，只给资源估算，不声称已找到性能最优点。校准不通过耗尽资源或故意触发 OOM 寻找极限。

## 复用报告分批执行

```text
复用 .agents/dev/context/environment.md 中仍有效的预算执行本次任务。
优先让现有 worker 接续多个 task；重任务按可用名额排队，
每项使用报告中的 jobs 或 workers 设置。
启动前检查实时余量和已有预留，缺失或过期的部分按实际主机补查。
```

规划、派发和实施继续按各自职责消费同一份记录：

| 阶段 | 责任 |
| --- | --- |
| `dev-setup` | 维护完整评估方法与环境记录；默认只读，需要时按已授权范围校准 |
| `dev-plan`、`dev-program` | 复用已有预算或按实际主机核对，区分依赖就绪与资源排队；跨 Change 共用预留 |
| `dev-parallel`、`dev-build`、`dev-review` | 启动前复测并取得预留，控制嵌套 Agent、构建与测试 worker |
| `dev-worktree` | 创建和初始化前核对容量；集成树也计入；按唯一清理方法回收 |
| `dev-pr`、`dev-deploy` | PR 的本地/CI 验证与目标环境的部署负载各按实际执行位置核验 |
| `dev-handoff` | 传递预算位置和未退出实例，恢复前重新采样 |
| `dev-archive` | 核实剩余占用，将已结束检出交回清理方法 |

同一资源池由一个主会话或已有调度器安排准入。多个 Change、仓库和 worktree 共享已占用资源及预留，不各自复制一份全机预算；子代理继续分工时使用父任务分配的额度。优先由同一会话接续多个 task，切换 task 或压缩上下文不自动创建新会话，也不释放其常驻占用。

资源不足时保留任务范围，停止新增和重试，排队重任务并减少可控 workers。允许新增量为 `0`，不伪造 DAG 依赖，也不因等待超时而扩大预算或强行启动。必要时按已有授权有序停止本任务可恢复的进程，不擅自终止其他会话。恢复前重新采样，按报告中有来源的窗口与恢复条件逐步放行。

换机、升级 CLI 或依赖、改变 worker 设置、恢复旧会话、首次运行新的重任务，以及回收后，都要核对相关结论是否仍有效。会话退出后仍保留的服务和 worktree 继续计入对应占用。

技能使用实际可用的系统观测、CLI 并发参数和运行时能力，不新增调度服务。建议预算与已经生效的系统硬限额分别记录；Markdown 约定本身不提供 OS 级资源隔离。

## 资源如何释放

普通只读报告不触发清理。确有回收任务时，继续使用已有工作树生命周期方法。

沿用 `dev-worktree` 的审计与清理入口，检查任务已经结束、写入者已交回、最新提交落在实际直接父分支，以及文件、会话和保留状态。再核实本任务残留进程的主机、会话、PID、启动时间和停止入口，有序退出后删除符合条件的检出。

删除后的卷空间与进程状态要重新读取。停止请求已发送、目录预计大小或 `git worktree prune` 成功都不等于资源已释放。部分回收成功只归还相应部分，用户固定、手工锁定或归属不明的对象保留。

## 多套团队配置

普通环境评估不创建团队文件。用户明确要求保存时，按团队主题分别存放：

```text
.agents/dev/context/team/capture-annotations.md
.agents/dev/context/team/release-review.md
```

用户给定名称或文件时沿用；没有名称时从 topic 生成单段名称，并检查重名。每份只保存这个团队实际使用的角色、模型/推理意图、成本与协作约定，具体参数必须由当前宿主能力证实。

使用时明确引用，例如：

```text
本次按 .agents/dev/context/team/capture-annotations.md 协作，
实现当前已确认的截图批注规格。
```

团队文件不设项目默认，不因存在而自动加载，也不写入根 `AGENTS.md` 的自动读取指令。`dev-build` 等阶段不主动选择模型规则。未被点名的团队保留供以后使用，文件里的角色数量表示覆盖需求，实际并发仍使用环境预算。

本版不自动搬迁目标项目已有的角色文件。需要整理时明确指定文件和主题，由 `dev-setup` 保留内容、核对引用后迁移。历史文件中的自动加载导航若要移除，也应在该次整理范围内处理。

## 方法来源

资源保留、按负载测量、准入和工作树生命周期参考的官方资料与固定上游地址集中见[第三方声明](../../THIRD_PARTY_NOTICES.md#开发环境与资源准入)。本项目把这些机制适配为现有技能之间的协作约定，没有引入 Kubernetes、特定 CLI 或额外常驻服务作为必需依赖。
