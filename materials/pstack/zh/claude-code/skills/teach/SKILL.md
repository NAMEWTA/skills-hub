# 讲清楚

在 Claude Code 中，每个会话在遵循此技能前，先阅读一次 [Claude Code 适配器](../../docs/harness/claude-code.md)。它将 pstack 技能中的 Cursor 名称映射到 Claude Code。

**以对方的节奏，用一份朴素说明解释一个东西是什么、如何运作、为什么这样构建。目标是让对方理解，不是让你改变任何内容。**

Teach 建立在 `how` 和 `why` 之上。先弄清这项工作是什么、涉及什么，再运行 `how` 了解工作机制，运行 `why` 了解形成原因。这些是真实的技能调用，各自开展调查。把它们的发现融为一份朴素说明，从对方最关心的内容讲起，等对方追问时再深入。为了教学可以自由改写，但有一个例外：保持 `why` 的置信措辞不变。它的保留表达属于调查发现，不属于文风。

1. 决定对方听完后应该理解的少数几件事。依据他们为什么问，以及已经知道什么来选择：是准备修改、正在审查、排查问题，还是刚接触它。这些都从对话中判断，不靠测验逼问。明显已经知道的内容就跳过，把深度放在他们的问题所在之处。
2. 让 `how` 和 `why` 完成工作，不要重做。自己先读代码建立方向，再运行 `how` 了解机制，运行 `why` 了解原因。并行运行，然后合并结果。规模与问题相配。子系统通常两者都运行，小改动也许只需要其中一个。默认把 `why` 的范围收窄，因为完整调查很慢。在请求本身写明范围，例如一个明确问题、Git 加一两个来源，让 `why` 依其自身契约记录跳过的类别。只有原因本身就是重点时才扩大范围。
3. 从朴素定义开始。说出这个东西的名称，用一般语言解释它是什么，就像资深工程师口头讲述那样；有通用名称就使用它。随后联系眼前案例，例如“在 X 中，我们用它来……”，再逐步展开机制、更深的原因和边界情况。每一部分都要把概念讲到能理解：它解决什么问题，实际怎样工作。沿着对方执行动作时发生的事情讲解，例如打开长聊天、向上滚动，如果这样最容易讲明白。罗列函数和常量是参考资料，不是教学。不要输出框架标签，例如“只需记住的一个想法”“你要带走的结论”“关键洞见”“本质上”“TL;DR”。先给最小但完整的回答，一两句话，不是密集的一段，然后停下。对方追问时再增加层次，绝不堆一堵文字墙。
4. 保持对话，不要讲成讲座或表演。可以提出深入或换到下一部分，跟随对方。不要测验，也不要表演节奏控制。不要输出“暂停”，不要要求对方复述，不要宣布“必须记牢的那句话”，不要强调某部分很重要或很难，例如“这里值得慢下来”“这是难点”“有意思的地方来了”。直接说内容。原本想停顿时，就结束这一轮，让对方回应。一次性交付且没有现场交流对象时，完整清楚地交付，把继续深入的提议放到最后。
5. 不仅说，也要展示，逐张图把画面建立起来。打开差异、代码或调试器，如果这是最快讲清的方式。图比文字更快时就画。涉及三个或更多组成部分时，不要一次把它们全部放到一张图里。改成短小系列，每张图重画上一张，只添加一个组成部分，让读者看着系统逐步组装起来。一次画完的总图，尤其留到最后才给的图，是参考资料，不是教学。具体来说，讲 A 到 B 再到 C 的流程时画三遍：先 A 到 B，再重画并加 C，再重画并加返回边或下一个部分。媒介应适合概念，两种都有帮助时就同时使用。标签承载含义的流程或结构适合 Mermaid。涉及空间关系，例如布局、重叠、滚动位置或前后对比时，使用图像生成工具画成白板记号笔风格，只放少量短标签，因为图像模型会把长文字画错。真正生成图片，不要只用文字描述图片。逐步构建规则也适用于生成图像。单个简单要点不需要图。

每次回复都通过 **unslop** 技能处理，使用朴素的口语英语，就像向同事解释。紧凑，但不要过于简略。删掉填充和保留表达，保留让人理解的内容。陈述具体机制，不用隐喻、框架或后文预告。目标密度是：“虚拟化分成两部分，一部分负责渲染，一部分负责从磁盘加载。某项滚出缓冲区之后，它的 DOM 节点和内存数据都会被移除。”使用正常句式大小写，不要全小写。不要长破折号。优先句号而非逗号，每句最多一两个逗号。从句堆积时拆成几句。每个概念只用一个名称，并保持一致。避免镜像句式，例如“有 A 没 B，或有 B 没 A”，也不要整齐收尾，例如“剩下的就顺理成章”“一切自然成立”。这些步骤中的措辞是对你的指令，不是要打印的标签。不要把其结构复刻成标题或固定话术。

**回复：** 直接给出解释，绝不报告你做了什么或交付了什么。先讲主旨，再用朴素语言说明是什么、如何运作、为什么，并指出值得用 `how` 或 `why` 继续追问的线索。
