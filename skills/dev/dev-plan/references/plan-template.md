## 最小计划

```markdown
# <需求名称>实施计划

目标：<与规格一致的可检查结果>
规格：<链接>
交付点：<本地完成 / 推送 / PR / 指定环境上线，依据用户授权>

| 切片 | 完成后的行为 | 真正依赖 | 所有者与边界 | 验证方式与通过判据 |
| --- | --- | --- | --- | --- |
| 01 <名称> | <可演示结果> | 无 | <模块或文件> | <命令或场景 → 预期结果> |
| 02 <名称> | <可演示结果> | 01 的 <产物> | <模块或文件> | <命令或场景 → 预期结果> |

## 顺序与并行
<哪些可以并行，哪个共享契约需要先确定，谁负责整合>

## 未定部分
<还需要调查什么，以及它只阻塞哪些切片>

## 完成边界
<最终整合验证、交付状态、已知限制>
```

只有切片足够大或需要独立交接时才建立任务文件。明确的一项小改动可以只用一句行为说明、范围和验证办法；表格只保留真实切片，不为填满模板增加任务或标题。

## 单个切片

```markdown
# <NN> <切片名称>

规格：<相关行为与来源的链接；标明本项承担的验收范围，必要时简述背景及已确认决定>
交付：<从用户或调用者视角描述的完整结果>
依赖：<真实阻塞项及所需产物、读取位置；无则写无>
边界：<唯一所有者、涉及模块、明确不做和不能自行改变的契约>
当前代码指针：<已核实的项目相对路径 / 符号 / 观察版本，必要时说明入口关系；拟新增文件另行标注，实施时复核>

## 实施要点（需要时）
<沿用已定接口与设计；只列必要的修改和影响安全或正确性的顺序，不逐行预写实现。实际风险需要的恢复、停止条件在此说明或链接；多阶段工作使用完整计划中的构建块。>

## 验收
- [ ] <条件 / 动作 → 可观察结果；对应验证入口>
- [ ] <重要失败或回归风险的条件与结果；对应验证入口>

## 完成证据
<运行位置与命令或操作场景 → 通过判据 → 证据位置；注明必要环境、测试输入和基线。拟新增测试或命令明确列为创建工作，不冒充已经可运行。实际结果由执行者记录，不预填“通过”。>
```

## 独立接手与按风险补充

用少量背景连接来源、现状差距和本项结果，说明接手者无法从代码自行推断的决定与理由。项目特有术语就近解释或指向实际定义；相关事实用精确指针，不复述整个仓库。接手者应只凭任务、可读来源和当前代码就能开始，不依赖聊天记忆或其他代理的隐藏上下文。

只展开适用内容，不新增固定深度字段，也不要求空栏目逐项写“不适用”：

| 实际情况 | 在原任务需要补足的信息 |
| --- | --- |
| 局部、可逆、沿用既有模式 | 现有目标、边界和验收足够；实现者决定局部代码组织，不预写全部步骤 |
| 跨模块或共享接口 | 稳定输入输出、不变量、接口两端和生产消费者；配置、示例、文档及回归由谁承接。依赖解除以真实产物为准 |
| UI 有已确认设计或原型 | 采用版本、本项页面与状态、对应设计章节及适用组件/HTML、样式和交互源码定位；约定同状态、视口的真实验证入口，不只链接原型首页。缺失会改变体验的设计决定交给 `dev-ui-design` 补齐 |
| 数据迁移、权限、不可逆写入或兼容风险 | 关键安全顺序、失败或部分完成后的核对与恢复、停止条件及已有批准边界；重试前确认是否已经生效，兼容收缩要有可验证退出条件 |
| 性能目标或模型/工具可见接口改变 | 性能引用 `dev-benchmark` 的有效基线与判据；提示、工具参数和返回/错误行为指定真实调用入口，不以格式合法代替行为正确 |

用户、项目安全规则或验收要求的必需方法在原约束中说明来源、使用条件和产物；普通可选方法无需事前全量枚举。实现细节若遵循现有惯例即可决定，就留给实施者。

验收按真实风险选择正常、失败和回归场景，不强制固定条数或测试层级。写清什么证据只能证明静态结构、什么需要真实用户或调用入口；缺少必需环境时记录缺口和可继续范围，不把未运行或替代性低层检查写成行为通过。不同场景可用表格连接动作、判据与证据，但不另建一套验收正文。

会改变外部调用方式、持久数据、安全权限、兼容策略、范围或验收的未决决定，不是局部代码组织。规划者也不能把推荐默认值写成已确认契约；先查可发现事实，仍需用户选择时列出选项、建议、受影响切片和解除条件，只暂停相关部分。低影响可逆假设说明适用范围和核实办法。实现者发现来源、接口或假设冲突时先核对事实，修订受影响计划，不自行换目标、放宽验收或重复有副作用的操作。填写密度见[任务示例与反例](task-examples.md)。

## 规格覆盖

从规格逐项反查实现与验证归属，不能只检查已列出的任务。小需求直接对照原文；多切片、多人协作或有遗漏风险时，在原计划使用下面的短表，沿用已有标题或标识，不强制为所有要求新编号。

| 规格要求或明确产物 | 实现归属 | 验证归属与入口 |
| --- | --- | --- |
| <行为或明确数量要求的来源> | <负责切片及其范围> | <负责验证的切片与场景> |
| <跨切片组合行为> | <参与切片> | <整合责任与完整入口> |

本表只做导航，不复制验收正文或维护另一份进度。一个要求可由多个切片共同实现，但本项验证与最终整合责任应明确。检查未覆盖项、重复责任、漏接的调用方与文档，以及用户明确要求的实际数量；已同意延期的部分保留依据和后续归属。票据数量不能证明交付数量，全部任务完成仍需按原始目标检查整体结果。不为每条要求或每种检查机械新增一票。

## 垂直与横向

“数据库表全部建好”“全部 API 完成”“全部页面完成”不能让用户体验一个完整能力，通常不是独立功能切片。

“用户创建一条任务，退出重开后还能看到它”贯穿输入、业务、存储与展示，是一个垂直切片。后续可分别扩展“编辑任务”“完成与撤销”“筛选任务”。

公共依赖不一定要单独出一项。若基础调整很小、只有一个调用者，可以并入第一个完整切片。只有实际阻塞多个切片且可独立交付的工作才单列，写清调用者、契约与独立验证入口。

工作包可用于组织多个切片，但工作包名称不代替每片的交付和验收。例如“导出与导入”若由两个独立行为组成，可分别验收；不能只检查导出成功就把两者都标为完成。

## 任务图与工作前沿

假设 A 交付领域契约，B 和 C 各自依赖 A，D 依赖 B 与 C：

- 起初只有 A 可执行。
- A 完成后 B、C 可以并行，且各有独立写入边界。
- B 先完成时，不必让负责 C 的代理停下来等汇报；D 仍等待 C。
- 两者真实产物整合后，D 执行完整场景验证。

“代理说完成”不自动解除依赖；以实际可读的产物和验证为依据。

可并行还要求没有未解决的共享写入与语义冲突。不同文件可能改变同一 API、表结构、迁移序列、全局注册或测试数据；明确共享对象的唯一负责人及必要顺序。小的共享调整可并入首个切片，不为所有公共文件单独造票；独立工作区也不能替代共享契约协调。

## 跨仓库机械重构

先说明为什么不存在能独立落地的垂直切片。按实际约束选择：

- 要求逐批可运行：提供有期限的迁移桥接，迁完全部消费者后删除。
- 允许整体替换：在整合分支完成所有消费者迁移，一次验证新契约。

对于后一种，不把临时无法运行的中间点标为已交付，也不为了表面上每一步通过而长期保存两套接口。

## 持久化最小集

规格与计划说明目标；进度说明已经发生什么；证据说明如何知道结果。按[本地工作记录](local-work-records.md)选择当前进度的权威位置，用链接连接它们。不要复制同一段验收条件到多个互相独立的真相源，不建立强制状态迁移图。交付前按[计划核对](plan-review.md)检查，规划中的预期证据不等于实际完成证据。

来源决定、代码基线、设计版本、接口、配置或验证输入改变时，只重估受影响的任务、依赖和证据；保留仍有效的结果及历史理由，不重启整套阶段。实际证据对应具体工作树或提交、环境和输入，不能沿用已失效的完成结论。
