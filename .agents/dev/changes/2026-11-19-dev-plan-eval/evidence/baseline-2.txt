# `.agents/dev/changes/2026-11-19-mail-draft-delivery/plan.md`

## 邮件草稿、附件恢复与投递实施计划

**目标。** 用户断网后能保存并续写带附件的草稿。发送后，即使只接受了部分收件人，或在确认前断线，用户也能在重启后的发件箱查到每次尝试、各收件人的结果，以及哪些地址可以安全重试。

**依据与交付点。** 行为以 `mail.md` 的 M-05～M-07、「发信」「只读与离线」「新格式备份与恢复」「统一能力」为准。S6b 沿用既有的 Huhu 新格式邮件子集恢复职责。本轮交付同一会话接续使用的计划，文件为模拟写入。当前仅核对了所给文本，代码、原型确认范围及运行结果均待实施时核实。

## 切片与验收

| 切片 | 完成后的行为与写入边界 | 真正依赖 | 验收动作与通过判据 |
|---|---|---|---|
| 01 离线关闭并续写草稿 | 在可写 Vault 保存归属原账号的草稿版本，包含富文本、主题、To/Cc/Bcc 和适用的回复引用。工作台与已开放的 CLI/MCP 共用草稿读写 handler。 | 无 | 断网并使 Mail 密钥暂不可用，从原账号回复，写入内容后关闭、重启并续编，逐项比对字段与账号。注入保存失败，编辑器和未保存内容仍在；主动丢弃后才放弃编辑。只读打开原 Vault 可读已有草稿，尝试保存时原数据不变。 |
| 02 重开草稿并找回附件 | 草稿持有受管附件引用。添加、去重、移除和转发时区分附件元数据与实际字节。大附件通过受限句柄流式读写。 | 01 的草稿版本和保存接口 | 添加同一附件两次，关闭编辑器、移走原文件、重启，读回一份内容一致的受管副本。移除后重开，引用已消失，其他草稿仍能读取其共享副本。转发只有文件名的收件附件时，界面显示缺字节；重新绑定后校验读回内容。外部入口传任意 Engine 主机路径时拒绝读取。 |
| 03 同一草稿版本只发起一次投递 | 按 Vault、账号、草稿及版本识别业务操作。先持久登记操作和本次收件人，再进入 SMTP 提交边界。各入口用同一 handler 提交和查询。发件箱可打开本次尝试。 | 01 的版本化草稿。以无附件邮件独立验收 | UI 双击并由已开放的 CLI/MCP 并发提交同一版，所有入口查到同一操作，模拟 SMTP 只收到一次提交。正文或收件人改变后形成新版本，旧尝试仍可查询。只读入口和接收专用账号发送前即返回原因，SMTP 调用数为零。 |
| 04 在发件箱修复部分成功与未知结果 | 持久保存逐次尝试、逐收件人的 SMTP 事实，由同一结果驱动详情、核对入口和重试范围。恢复上次选择，支持续编及删除本地记录，区分本机记录与服务器 Drafts/Sent。 | 03 的操作标识、提交边界和查询入口 | 按下表注入故障，重启后由 UI 和外部查询逐项比对。显式重试产生可追溯的新尝试，SMTP 信封只含可证明未提交的地址。密送地址只出现在相应私有记录；删除本地记录时，远端邮箱及其他账号记录不变。 |
| 05 通过 S6b 恢复草稿、附件与投递历史 | 接入带类型和版本的 Mail 子集包。在目标 Vault 预检后提交，恢复草稿、已发记录、操作及尝试历史和受管附件。缺失字节列为待重绑。恢复过程不调度投递。 | 02 的附件引用与重绑能力、04 的持久投递结果，以及 S6b 的实际包读写和预检接口 | 导出一份带附件草稿和含混合结果的发件记录，分别用完整包和缺字节包恢复。核对完整包的字节、两份包的收件人结果及历史；缺字节项可定位、重绑并续编。预检不改目标，只读提交被拒。恢复、重启和重连前后 SMTP 提交计数相同。 |

## SMTP 故障判据

以模拟 SMTP 会话记录、持久操作记录和发件箱详情三方核对。`RCPT TO` 获准只表明地址进入本次信封，最终接受须有正文提交后的明确成功响应。稳定的 Message-ID 用于关联核对，不能单独证明唯一投递。

| 受控场景 | 发件箱可见事实 | 再次操作的判据 |
|---|---|---|
| A、B 在收件人阶段获准，C 被拒，随后正文获得最终成功响应 | A、B 已接受，C 显示拒绝原因，操作显示部分成功 | 修复并显式重试时只向 C 提交；第一次尝试保留 |
| A、B 获准，C 被拒，正文可能已交付但最终响应丢失 | A、B 显示「结果未知」及核对入口；C 仍显示已知拒绝 | A、B 排除在常规重试之外。C 可单独处理；核对入口展示账号、时间、相关收件人和 Message-ID |
| 连接在提交前失败，持久证据足以证明未提交 | 受影响地址显示未提交及原因 | 用户可显式重试；关闭、重启或重连均不触发重投 |
| SMTP 可能已接受，进程在结果持久化前退出 | 重启后，缺少确定结果的相关地址显示「结果未知」；已持久确认的地址沿用原结果 | 重开详情、重复提交同一版本及恢复备份均不增加 SMTP 提交次数 |

## 接续顺序与整体验收

同一会话先做 01。其版本接口可用后，02 和 03 均可开始；建议先用 03 的无附件路径验证并发与崩溃边界，再完成 04 和 02。05 负责组合验收。共享 schema、迁移顺序及 handler 注册由同一实施者维护。S6b 的接口尚待核实，其就绪情况只约束恢复接入。

实施前从 `mail.md` 引用的 `plan.md`、`design.md` 定位既有切片、存储入口与在途发送约定。对照 `prototype/index.html` 和 `prototype-review.md` 核实编辑器保存失败、附件待重绑、部分成功及未知结果各自的确认版本与范围。只将已确认场景用于桌面和 Web 的同状态、主题及视口比对；其余可先验证 handler、持久化和模拟 SMTP 行为。

最终在两个模拟账号中走通“离线写信并添加附件 → 重启续编 → 跨入口并发发送 → 查看逐人结果 → 仅重试可证明未提交者 → 导出并恢复”。另用最终响应丢失的故障重复后半程。切换 Vault 或停用 Mail 后，迟到响应不得写入当前账号或 Vault；清缓存及重建索引后，草稿、唯一附件字节与投递历史仍可读取。干净安装时外部工具默认关闭，开启指定能力后再对照工作台结果。

实施时把工作树版本、故障注入点、SMTP 信封与提交次数、重启前后查询结果及界面截图记入本变更的 `evidence/`。本次离线计划使用模拟账号、附件和 SMTP 结果；真实邮箱验收仍按原规格单独采证。
