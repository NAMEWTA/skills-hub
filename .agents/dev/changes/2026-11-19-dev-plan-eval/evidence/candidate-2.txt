# `.agents/dev/changes/2026-11-19-mail-durability/plan.md`

# Mail 离线草稿、附件恢复与投递实施计划

本计划按 `dev-plan` 拆为五个可独立验收的垂直切片。目标是让用户离线保存并恢复写信内容，重启后查询同一投递操作，并在部分成功或结果未知时安全处理剩余收件人。计划正文保留在这一份文件中，供同一会话后续实施。

**依据**为 `mail.md` 的 M-06、M-07，以及「网络事实、发送与持久数据」中的发信、只读与离线、新格式恢复和统一能力条款。本轮交付计划正文。代码入口、现有测试命令、`design.md`、已有 `plan.md`、原型及确认记录均待核实，以下使用行为入口和模块边界安排工作。

## 切片与实施顺序

| 切片 | 用户可独立验证的结果 | 开工所需产物 | 唯一写入责任 |
| --- | --- | --- | --- |
| 01 离线保存并续编草稿 | 断网写信，关闭并重启后从发件箱续编 | 无功能切片前置 | 草稿版本、编辑器保存与续编、草稿共享能力 |
| 02 恢复草稿附件 | 重启后恢复附件字节，缺字节时识别并重绑 | 01 的草稿版本、附件引用边界和续编入口 | 受管附件、附件界面、恢复与重绑 |
| 03 提交并查询一次投递 | 并发提交同一版本只产生一个业务操作，重启后可查明确接受结果 | 01 的不可变草稿版本和共享写入边界 | 投递操作、SMTP 回执、尝试记录、发件箱查询 |
| 04 处理部分成功 | 发件箱逐收件人展示结果，只重试可证明未提交且允许重试的收件人 | 03 的操作、尝试与回执契约 | 逐收件人结果和重试入口 |
| 05 核对未知结果 | 回执丢失后仍显示未知，恢复生命周期时提交次数保持不变 | 03 的持久化提交边界。与 04 的共享写入安排见下文 | 未知判定细化、核对入口及整合验收 |

01 之后，02 和 03 可在附件引用边界稳定后独立推进。03 首先用纯文本或无附件富文本完成验收。带附件发信的整合验证消费 02 的真实附件解析能力。04 和 05 都消费 03 的记录契约，并会修改投递结果处理和发件箱。由同一实施者顺序整合，先 04 后 05。03 必须先具备保守的未知处理，04 才能安全开放重试。工作台、CLI 和 MCP 共用 Engine schema、handler 和错误语义。各切片更新自己新增的能力声明和适用的调用方，沿用 #6 的目录、配置和传输。

## 01 离线保存并续编草稿

贯通写信浮层、草稿存储、共享保存及读取能力、发件箱续编。持久化发件账号、To/Cc/Bcc、主题、富文本和附件引用边界。正文或收件人变更时产生新版本，已交给投递的版本保持可查询。草稿存入所属 Vault，保存和打开已有草稿可在离线或 Mail 密钥暂不可用时完成。含内容的编辑器在关闭前等待保存，主动丢弃走显式动作。

- [ ] 在可写 Vault 断网写入多地址、主题和带链接的富文本，关闭编辑器并结束进程。重启后，从发件箱选中原草稿，核对账号、各地址栏、主题、正文及可恢复的选择。编辑正文或收件人并保存，读取结果显示新版本。
- [ ] 注入持久化失败后关闭含内容的编辑器，观察错误和仍可编辑的原内容。恢复写入后重试保存，再重启核对。验证主动丢弃可放弃当前编辑。
- [ ] 在只读 Vault 打开已有草稿，从工作台和已开放的外部入口尝试保存或丢弃持久记录，观察一致拒绝及原 Vault 数据不变。切换 Vault 或停用插件时递送迟到的保存响应，核对当前界面和数据归属保持正确。

## 02 恢复草稿附件

贯通编辑器添加、去重和移除、Engine 受管存储、版本引用、恢复和重绑。草稿提交成功时，其已持久化附件应可读取。保存或重绑中断时，保留上一次成功保存的草稿及其有效引用。清理依据持久引用，覆盖草稿、发送快照和本地发件记录。外部调用经受限句柄和流传输，Engine 拒绝调用方传入的任意主机路径。

- [ ] 添加同一文件两次，再添加同名异内容文件。核对重复项合并、独立文件保留。保存并重启，从原草稿逐个读取，核对原始字节。移除附件并保存，再重启核对移除结果及其他版本引用的字节。
- [ ] 在隔离恢复夹具中缺失一个附件的字节，打开草稿后看到名称及待重绑状态。用正确文件重绑并重启，核对字节可读取。注入重绑写入失败，观察缺失状态保留且其他附件仍可读。带缺字节的版本须在 SMTP 提交前返回可修复错误。
- [ ] 从已开放外部入口用受限流添加大附件，再以主机路径作为输入重试，核对前者恢复后内容完整，后者被拒绝。验证清缓存与重建索引后仍可读取唯一受管副本。
- [ ] 本片用恢复夹具验证引用和缺字节行为。真实新格式 Mail 子集包的预检、提交及恢复由规格中的 S6b 承接，跨切片验收复用本片的附件契约。

## 03 提交并查询一次投递

贯通工作台发送、已开放工具提交、Engine 投递记录、SMTP 和发件箱查询。Engine 以 Vault、发件账号、草稿标识及版本约束业务操作的唯一性，原子地创建或读取已有操作。先持久化操作、冻结的发送内容及尝试，再进入网络副作用。重启后无法证明是否越过提交边界的尝试按可能已接受处理。稳定 Message-ID 用于关联操作与邮箱记录。每次显式提交或查询返回可关联的操作标识，尝试记录供发件箱读取。

SMTP 逐收件人响应记录信封阶段事实。只有完成消息提交后收到明确的最终接受回执，才可把该事务内的适用收件人标为已接受。断线、超时或进程崩溃留下的模糊窗口须持久呈现为未知，且没有常规重试资格。服务器 Drafts/Sent 和本机记录分别展示。

- [ ] 在隔离 Vault 用工作台双击发送，同时用已开放 CLI/MCP 提交同一版本。受控 SMTP 返回最终接受。三个入口关联同一操作，SMTP 只收到一次消息提交。重启后，发件箱恢复选择并显示本地回执及尝试记录。
- [ ] 注入记录持久化失败，观察发送失败且 SMTP 提交计数为零。再注入本地记录已落盘、远端接受后结果未落盘的崩溃，重启查询可见未知且计数不增。
- [ ] 修改正文或收件人后显式提交，得到新版本对应的新操作，旧记录仍可查询。在只读 Vault、插件停用或接收专用账号下从适用入口发起发送，观察明确原因及零投递。关闭外部工具后核对工作台能力仍可用。
- [ ] 发件箱能查询每次尝试和删除本地记录。测试本地删除不触及服务器邮箱，并验证删除、随后查询或重复提交同版均不会绕过投递去重与重启保护。实施前核对 `design.md` 中账号删除与在途发送的规定，再接入对应删除路径。

## 04 从部分成功中重试可安全投递的收件人

由 Engine 按收件人保存回执和重试资格，工作台与外部入口使用同一判定。重试沿用原操作和冻结版本，追加可查询的尝试。重试请求提交前重新校验目标资格，并防止并发重试重复投递。发件箱展示已接受、明确未提交和未知等结果；Bcc 详情仅在相应私有发件记录可见。

- [ ] 在受控 SMTP 中让 A 通过信封阶段并收到最终接受，让 B 在信封阶段被临时拒绝。发件箱显示部分成功及各自结果。通过 UI 与已开放工具并发重试，服务器记录只新增一次尝试且信封仅含 B，A 的尝试数保持不变。重启后可查两次尝试和各自回执。
- [ ] 在同一夹具覆盖明确永久拒绝和最终回执丢失。永久拒绝显示对应原因和可用修复入口，未知收件人无常规重试资格。直接通过 handler 请求重试已接受或未知收件人，核对拒绝且 SMTP 计数不变。
- [ ] 用含 Bcc 的夹具核对私有详情与公开会话。私有发件记录显示对应 Bcc 回执，公开参与者和会话数据保持原有边界。

## 05 核对未知结果并完成整合验收

在发件箱和已开放查询入口提供结果与核对所需上下文，包括来源账号、尝试时间、受影响收件人和稳定 Message-ID。通过来源账号的真实可用查询路径提供核对入口。核对线索不足时保留未知。实现前核对 `design.md` 与确认原型对核对入口及结果变化的定义。若资料未定义何种额外证据可改写未知，先交付保留未知的只读核对，涉及状态改写的部分待证据规则明确。

- [ ] 分别在消息可能已提交、且最终回执尚未收到时断线、超时或终止进程。通过工作台和已开放查询入口观察相同的逐收件人未知结果及核对信息。关闭编辑器、重启、重连、切换 Vault 后返回，核对 SMTP 提交计数都保持不变。使用同一 Message-ID 找到相关记录时界面提供关联线索。
- [ ] 从离线写信和附件恢复开始，重启后提交。让同次操作含明确未提交的收件人和结果未知的收件人。核对显式重试只覆盖符合资格的子集，未知记录持续可查。检查停用、Vault 切换及迟到响应不会改写其他 Vault 或账号的发件箱。
- [ ] 用带草稿、附件引用和未知操作的隔离恢复夹具验证加载后无自动投递。与 S6b 整合时，用 Huhu 新格式 Mail 子集包在目标 Vault 预检并提交，再核对草稿、附件字节或待重绑状态、逐收件人结果和尝试历史。恢复流程和随后重连期间 SMTP 计数保持原值。整 Vault 包恢复到新空目录的实际验收使用同一判据，待对应恢复入口可用后执行。

## 开工核实与证据

- 授权实施后，先核实 `AGENTS.md`、当前检出和上游差异、已有切片编号与计划，以及写信、草稿存储、附件、SMTP、发件箱、恢复和 #6 注册的实际入口。优先复用现有路径和测试设施。沿用已有任务标识与共享迁移顺序，在验证入口确定后补入真实命令。
- 对照 `prototype/index.html` 与 `prototype-review.md`，记录确认版本或内容指纹、确认范围及相应结构、样式和交互位置。场景包括关闭保存失败、续编、附件缺失及重绑、发件箱恢复选择、部分成功和未知核对。体验确认缺失或版本漂移时，先推进不依赖布局或交互决定的服务与受控验证。适用的实现通过桌面和 Web 的实际入口，在对应状态、主题与视口取证。
- 用隔离 Vault、模拟账号和可记录 SMTP 会话的受控夹具验证协议边界。为每个切片保留工作树或提交、启动和操作方式、夹具输入、通过判据及实际输出。工作台变化保存截图或短录像，投递故障保存脱敏协议记录和提交计数，CLI/MCP 保存真实调用输出。证据拟放在本变更目录的 `evidence/<切片>/<场景>/`。实现后的真实测试邮箱证据按 `mail.md` 的关闭条件单列，需有对应环境。受控故障证据证明协议与恢复行为。
- 在主干与待交付版本分别运行可用的同一场景，优先选离线保存、重启续编及正常发送。主干缺少入口时记录实际基线，并以待交付版本的端到端结果验收相应新增行为。

## 范围与完成条件

M-06、M-07 的离线保存与续编由 01 验收，受管附件与缺字节重绑由 02 验收，版本去重与操作查询由 03 验收，部分成功及重试边界由 04 验收，未知核对与跨切片恢复由 05 验收。S6b 保留 Huhu 新格式 Mail 子集恢复的交付归属。真实旧格式迁入和远端 Sent APPEND 沿用规格边界。
