## 测量设计与交付要求

### 1. 固定环境和计时边界

记录硬件、系统、Node.js 小版本、进程启动参数、电源模式、背景负载，以及数据读取是否计入。

首先测量可从快照直接执行的模块场景：数据已经载入内存，从调用 `listNotes(notes, query)` 前开始，到函数返回完整结果数组时停止，包含标题处理、过滤和排序。数据生成、文件加载、日志输出及结果正确性校验放在这段计时之外。

另外单独测量 `loadNotes` 的文件读取与解析，以及 `loadNotes → listNotes` 的组合过程。冷文件读取与操作系统缓存后的读取需区分；未控制缓存时如实记录限制。三种边界分别报告，不能混为一个“搜索耗时”。界面延迟暂无法测量，因为快照不含界面或调用链。

### 2. 固定数据与查询集

优先取得能够公开描述的真实负载特征；在没有用户数据时，使用标准库编写确定性合成数据生成器，记录条数、种子、字段长度与字符分布、归档比例、时间分布、是否预排序和校验值。合成参数是调查假设，不代表用户真实数据。

查询集至少覆盖以下独立场景，并为每个场景记录实际匹配数：

| 场景 | 需要验证的行为与成本 |
| --- | --- |
| 空查询 | 返回所有未归档笔记，包含大结果集排序成本。 |
| 无匹配查询 | 扫描完成但不排序非空结果，帮助隔离扫描成本。 |
| 少量命中查询 | 观察扫描为主的负载及结果正确性。 |
| 大量命中查询 | 观察扫描加排序的负载，避免只用低命中率查询得出结论。 |
| 相同文本的大小写变体 | 命中结果一致，确认大小写规则未被候选优化改变。 |
| 代表性长标题、非 ASCII 标题及含空格查询 | 暴露数据分布和既有字符串语义的影响；不新增分词、去空格或区域性大小写规则。 |

单个同步调用为首个可复现场景。若用户的输入频率、并发或数据修改方式不同，再追加对应负载，并说明来源；不得把单次调用结果当作未知并发下的保证。

### 3. 采样、剖析与比较

拟新增基准脚本使用 `node:perf_hooks` 的单调计时或 `process.hrtime.bigint()`；记录冷启动/首次查询，暖机与正式样本分开。脚本公开重复次数、暖机次数、查询执行次序和独立进程轮数。

可先做短预采样，以观察 JIT、垃圾回收与调度抖动，再确定正式采样窗口。正式报告须保留所有原始样本、样本数、p50、p95 和最大观测值；这些统计量用于描述分布，**不表示已把用户的“不超过 80ms”改成 p95 ≤80ms**。若结果不稳定，扩充采样并解释原因，不能只挑最好的一次。

使用 Node.js 自带 CPU profile 获取同一负载的热点，必要时拆分扫描与排序成本；剖析结果与无 profiler 的计时分开，因为剖析会影响耗时。按需要在计时区间外记录 `process.memoryUsage()`，用于比较候选方案的构建成本和内存代价。

候选方案前后对照必须使用同一设备、运行时、数据、查询、计时边界与采样方法。结果先做正确性对照，再谈耗时；缓存或预处理的初始化时间、首次查询、稳态查询及更新代价分别报告。

## 复用与候选方案

先复用 `listNotes` 作为行为基准和 `loadNotes` 作为存储入口，不添加依赖。具体优化由数据决定：

| 候选方向，尚未采纳 | 需要先证明什么 | 必须验证的代价或风险 |
| --- | --- | --- |
| 预计算或缓存小写标题 | 标题转换占主要时间，且查询间有可复用数据。 | 内存增加；编辑、删除、归档、导入及文件重读后失效。当前接口允许调用者传入新数组或修改记录，不能默认缓存会自动保持正确。 |
| 维护预排序视图或调整筛选/排序安排 | 大结果集排序是主要成本。 | 是否保留所有结果与相同次序、同时间的稳定性，以及更新/重建成本。 |
| 减少重复加载与解析 | 实际调用链确实在搜索时重复加载文件。 | 新鲜度、调用者生命周期和错误传播；快照没有证明存在重复加载。 |
| 维持现有实现并调整后续范围 | 基线已满足约定的模块目标，或真正瓶颈在快照之外。 | 明确未覆盖的完整流程，取得调用链后再定位，不能把局部达标写成用户问题解决。 |
