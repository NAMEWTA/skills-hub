# 改进代码库架构

揭示架构阻力，提出**深化机会**：把浅模块变成深模块的重构。目标是可测试性，以及便于 AI 导航。

此命令以项目领域模型为参考，以共享设计术语为基础：

- 用 "codebase-design" 调用 Skill 工具，获取架构术语（**module**、**interface**、**depth**、**seam**、**adapter**、**leverage**、**locality**）及原则（删除测试、“接口就是测试面”、“一个适配器 = 假想接缝，两个 = 真实接缝”）。每条建议都准确使用这些术语，不要漂移到 “component”“service”“API” 或 “boundary”。
- `GLOSSARY.md` 中的领域语言为好的接缝命名；`docs/adr/` 中的 ADR 记录本命令不应重新争论的决策。

## 过程

### 1. 探索

**扫描之前先定范围：YAGNI。** 深化模块的回报在于让未来修改更容易，因此要更加重视代码库中近期变动的部分。先决定*看哪里*，再开始看：

- 如果用户指出方向（模块、子系统、痛点），按该方向进行，跳过下面的推断。
- 否则，回看足够长的一段提交历史（`git log --oneline`），找出代码库热点：反复出现的文件和区域，让这些路径优先吸引你的注意。如果变更分散、没有明确热点，再扩大范围。

先读取项目领域术语表（`GLOSSARY.md`），以及即将涉及区域的 ADR。

然后启动一个拥有全新上下文窗口的子代理来浏览代码库。不要遵循僵硬启发式，自然探索，并记下遇到阻力的地方：

- 理解一个概念时，哪里需要在许多小模块间来回跳转？
- 哪些模块很**浅**，接口几乎和实现一样复杂？
- 哪里为了可测试性提取了纯函数，但真正的缺陷隐藏在调用方式中（没有 **locality**）？
- 紧耦合模块在哪里跨接缝泄漏？
- 代码库哪些部分没有测试，或难以通过当前接口测试？

对任何疑似浅模块应用**删除测试**：删除它会集中复杂度，还是只会转移复杂度？“是，会集中复杂度”就是你要找的信号。

### 2. 用 HTML 报告呈现候选项

把自包含 HTML 文件写入操作系统临时目录，避免向仓库落文件。由 `$TMPDIR` 解析临时目录，回退到 `/tmp`（Windows 上为 `%TEMP%`），写到 `<tmpdir>/architecture-review-<timestamp>.html`，保证每次运行生成新文件。为用户打开它（Linux 用 `xdg-open <path>`，macOS 用 `open <path>`，Windows 用 `start <path>`），告知绝对路径。

报告通过 **CDN 加载 Tailwind** 实现布局和样式；当图、流程、时序能可靠传达结构时，通过 **CDN 加载 Mermaid**。将 Mermaid 和手工 CSS/SVG 视觉元素结合：关系呈图结构（调用图、依赖、时序）时用 Mermaid；想要更具编辑设计感的表现（面积图、剖面图、收拢动画）时用手工 div/SVG。每个候选项都有**前后对照可视化**。重视视觉表达。

为每个候选项渲染一张卡片，包含：

- **文件**：涉及哪些文件/模块
- **问题**：当前架构为什么造成阻力
- **方案**：用朴素英语描述会改变什么
- **收益**：用 locality 和 leverage 说明，以及测试如何改善
- **前后对照图**：并排、定制绘制，展示浅结构与深化效果
- **推荐强度**：`Strong`、`Worth exploring`、`Speculative` 三选一，渲染为徽章

报告以**首选建议**部分结尾：先处理哪个候选项，为什么。

**领域概念使用 GLOSSARY.md 的术语，架构概念使用 `/codebase-design` 的术语。** 如果 `GLOSSARY.md` 定义了 “Order”，就说 “Order intake module”，不要说 “FooBarHandler”，也不要说 “Order service”。

**ADR 冲突**：如果候选项与现有 ADR 矛盾，仅当实际阻力足以支持重审 ADR 时才提出。在卡片中明确标记（例如警告框：_“与 ADR-0007 冲突，但值得重新讨论，因为……”_）。不要列出 ADR 禁止的每一种理论重构。

完整 HTML 骨架、图形模式与样式指导见 [HTML-REPORT.md](HTML-REPORT.md)。

此时不要提出接口。写完文件后询问用户：“你想探索其中哪一项？”

### 3. 深入追问循环

用户选择候选项后，用 "grilling" 调用 Skill 工具，与用户一起走过决策树：约束、依赖、深化模块的形状、接缝后面放什么、哪些测试保留。

决策逐渐明确时，同步产生必要变更；用 "domain-modeling" 调用 Skill 工具，在过程中保持领域模型最新：

- **要用 `GLOSSARY.md` 中没有的概念给深化模块命名？** 将术语加入 `GLOSSARY.md`。文件不存在时才按需创建。
- **对话中正在厘清模糊术语？** 当场更新 `GLOSSARY.md`。
- **用户基于关键理由拒绝候选项？** 提议 ADR，措辞为：_“要我把它记成 ADR，以免未来的架构审查再次建议同样的事吗？”_ 只有未来探索者确实需要此理由才能避免重复建议时才提议；跳过临时理由（“现在不值得”）及不言自明的理由。
- **想探索深化模块的不同接口？** 用 "codebase-design" 调用 Skill 工具，采用其“设计两次”的并行子代理模式。
