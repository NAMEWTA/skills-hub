# 商店条目技巧与常见拒绝原因

## 撰写有效描述

### 简短描述（最多 132 个字符）

它出现在搜索结果和分类页面，是你的简明介绍。规则如下：

- 以动词或扩展功能开头：“拦截所有网站的广告”，而不是“广告拦截器”
- 具体明确：“将选中的文本翻译成 50 多种语言”，而不是“翻译工具”
- 自然包含主要关键词
- 不要浪费字符说“Chrome 扩展”，用户已经知道

**好的示例：**
- “一键保存文章，稍后阅读。离线也可用。”
- “将新标签页替换为显示天气和任务的简洁仪表盘”
- “高亮并标注任意网页中的文本。将笔记导出为 Markdown。”

**不好的示例：**
- “Chrome 最好的生产力工具！”（含糊、营销话术）
- “帮你把事情做得更好的扩展”（没有说明任何内容）
- “全新！惊艳的 Chrome 浏览器标签页管理扩展工具应用”（关键词堆砌）

### 详细描述（最多 16,000 个字符）

CWS 会移除所有 Markdown 格式。使用带换行的纯文本，结构如下：

模板保留上游英文占位符。依次填写：一句话功能概述、后续操作步骤、数据类型、具体功能、触发操作、联系邮箱、支持 URL、版本号和最新版本的简短更新日志。

```
[One sentence: what does this extension do?]

功能
• 功能 1 — 简短说明
• 功能 2 — 简短说明
• 功能 3 — 简短说明

使用方式
1. 点击工具栏中的扩展图标
2. [Next step]
3. [Next step]

隐私
本扩展不收集任何个人数据。你的 [data type] 仅存储在本地设备，
绝不传输到任何服务器。

权限
• “读取和更改你访问网站的数据” — 用于 [specific feature]。
  扩展仅在你 [trigger action] 时激活。

支持
发现问题或有建议？请发送邮件至 [email]，或在 [URL] 提交 issue。

版本 [X.Y.Z] — [Brief changelog for latest version]
```

### 实现细节规则

**绝不要描述扩展如何构建。** 潜在用户不是在评估技术栈的开发者，他们希望知道扩展能为自己做什么。

从所有文案中删去以下内容：

- Web API 名称：`MutationObserver`、`IntersectionObserver`、`Service Worker`、`Shadow DOM`、`IndexedDB`、`WebSockets`
- Chrome API 名称：`chrome.storage`、`declarativeNetRequest`、`chrome.scripting`、`offscreen document`
- 框架/库名称：React、自定义元素、Lit、Webpack、TypeScript
- 架构描述：“后台处理”“事件驱动”“声明式”

**将每句实现描述改写为用户收益：**

| 改写前（实现） | 改写后（用户收益） |
|-------------------------|----------------------|
| “使用 MutationObserver 检测页面变化” | “浏览时自动检测新内容” |
| “使用自定义元素和 Shadow DOM 构建” | “无缝工作，不影响页面样式” |
| “由 service worker 驱动” | “在后台安静运行” |
| “通过 chrome.storage.sync 同步设置” | “设置可在所有设备间同步” |
| “实现 declarativeNetRequest 过滤” | “拦截广告和跟踪器，无需读取页面内容” |

### 为什么这种结构有效

1. **一句话开场**：审核者和用户都会扫读第一行，充分利用它。
2. **功能清单**：用户会快速查找能力，纯文本项目符号（•）显示效果好。
3. **使用方式**：减少支持请求，并说明扩展确实能工作。
4. **隐私章节**：提前回应用户的权限顾虑，建立信任。
5. **权限解释**：用户安装时会看到权限警告；在描述中解释后，他们更不容易中止安装。
6. **支持信息**：CWS 政策要求提供“有意义的客户支持”。
7. **最新版本说明**：显示扩展正在积极维护。

### 单一用途声明

它填写在开发者控制台中，不向用户展示。审核团队会仔细阅读。必须用一句话说明扩展范围明确的用途。

**获批示例：**
- “将网页中的高亮文本保存到本地阅读列表”
- “将新标签页替换为可自定义的仪表盘”
- “拦截网站上的 cookie 同意横幅”

**被拒示例：**
- “改善浏览体验”（过于含糊）
- “生产力和组织工具”（范围过大）
- “高亮文本、保存书签、管理标签页并拦截广告”（不是单一用途）

如果扩展有多项功能，重点说明主要功能。次要功能可以在详细描述中介绍。

## 常见拒绝原因

### 1. 权限过多

**表现：**“你的扩展申请的权限超过实际需要。”

**修复：**
- 用具体主机模式替换 `<all_urls>`
- 如果只在点击时需要当前标签页，将 `tabs` 替换为 `activeTab`
- 移除未使用的权限
- 确保每项权限都有明确理由

### 2. 缺少或不合格的单一用途

**表现：**“你的条目没有单一、明确的用途。”

**修复：**
- 重写单一用途字段，使其范围明确且具体
- 如果扩展确实承担过多不相关功能，考虑拆分

### 3. 误导性描述或功能

**表现：**“你的扩展没有提供描述中的功能。”

**修复：**
- 确保描述列出的每项功能确实可用
- 移除尚未实现功能的声称
- 除非能够验证，不要使用“最好”“最快”等最高级表达

### 4. 隐私政策问题

**表现：**“你的扩展需要隐私政策。”或“你的隐私政策 URL 无法访问。”

**修复：**
- 将隐私政策托管在稳定、公开的 URL
- 确保无需登录即可访问
- 确保覆盖扩展实际收集的所有数据
- 使隐私政策与数据披露表一致

### 5. 商标侵权

**表现：**“你的扩展未经授权使用了商标内容。”

**修复：**
- 不要在扩展名称中使用其他公司的名称（例如“YouTube Downloader”）
- 不要使用暗示关联关系的 logo 或品牌配色
- 使用通用词：“Video Downloader for [site]”可能可以，但应检查站点条款

### 6. 代码可读性

**表现：**“你的扩展包含混淆代码。”

**修复：**
- 允许压缩，不允许混淆
- 使用构建工具（webpack、rollup、vite）时，确保不包含 source map，产物只是压缩而非混淆
- 不要使用字符串编码技巧掩盖代码意图

### 7. 远程代码执行

**表现：**“你的扩展执行了远程托管代码。”

**修复：**
- 将所有 JavaScript 打包进扩展
- 运行时不从 CDN 加载脚本
- 不对远程内容使用 `eval()` 或 `new Function()`
- 从 API 获取 JSON 数据可以；获取并执行 JS 不可以

### 8. 用户数据披露不一致

**表现：**“你的扩展数据使用情况与披露不一致。”

**修复：**
- 审查每个 `fetch()`、`XMLHttpRequest` 和 `chrome.storage.sync` 调用
- 记住 `chrome.storage.sync` 会将数据传到 Google 服务器
- 使用任何分析库（即使自托管）都应声明
- 向外部服务记录错误时也应声明

## 被拒之后

扩展被拒时：

1. 仔细阅读拒绝邮件，其中会指出违反的政策
2. 在 CHROMEWEBSTORE.md 记录拒绝原因与修复
3. 对扩展代码或条目作出所需修改
4. 按发布前清单重新检查
5. 通过开发者控制台重新提交
6. 注意：反复违反政策可能导致账号停用

## 审核时间

- 首次提交：通常 1–3 个工作日，也可能更久
- 现有扩展更新：通常更快，往往在 24 小时内
- 加急审核：官方未提供；保持良好记录有所帮助
- 延后发布：审核通过后可以选择手动发布，以控制时间。必须在获批后 30 天内发布。
