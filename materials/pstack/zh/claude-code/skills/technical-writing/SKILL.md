# 技术写作

在 Claude Code 中，每个会话在遵循此技能前，先阅读一次 [Claude Code 适配器](../../docs/harness/claude-code.md)。它将 pstack 技能中的 Cursor 名称映射到 Claude Code。

写得让疲惫的工程师也能一遍读懂。

- 删除每个没有发挥作用的词。
- 使用简短、日常的词：用“use”，而不是“utilize”。
- 如果某条规则让句子变差，就换一种方式修改，或保持原样。
- 写出真正的符号、文件、标志或命令名称，不用其同义词或描述替代。
- 不要发明术语。使用开发者会在口头表达中使用的词。第一次提到某种有名称的模式时，说明其含义。

## 让节奏有变化

- 长短句交错。承载两个意思的句子应拆开；承载一个意思的长句可以保留。
- 解释类文字可以有观点，参考类文字保持客观平实。
- 表达具体。不写“模式变更可能导致问题”，而写“重命名列会让构建失败”。

## 先选择模式（Diátaxis）

一份文档只采用一种模式。不要混用；应拆开并互相链接。

- **教程：边做边学。** 说明学习者将构建什么。每一步都产生可见结果，并说明应当看到什么。解释只占一个分句，并附上链接。
- **操作指南：通往目标的步骤。** 解决读者的问题。假设读者具备相应能力。只写行动。允许分支。以任务为指南命名。
- **参考：供查阅的事实。** 只作描述。客观平实、完整、确定。结构应与所描述的对象对应。
- **解释：理解与原因。** 聚焦一个边界清晰的主题。给出背景：设计决策、历史、约束和备选方案。只有这里允许表达观点。

## 面向读者写句子（Google 开发者风格）

- 以“你”称呼读者，使用现在时。
- 说明谁做什么。只有行为主体未知或无关紧要时，才使用被动语态。
- 用命令句写指令。先说条件，再说指令；先写常见情况。
- 不用流行空话、比喻或“请”；流程说明中绝不写“只需”“简单”或“快速”。
- 不预先宣告将要说什么，也不要连续以同一个短语开头。
- 链接文字应说明链接通向哪里。
- 标题表达要点，使用句首大写。每页只有一个 h1，不跳过标题级别。
- 顺序使用编号列表，其他内容使用项目列表。用完整句子引出列表，条目保持并列结构。
- 代码使用代码字体。UI 元素使用粗体。使用列举逗号。删除“etc.”。

## 让每次陈述只承载一项内容（STE 规则）

- 每个句子只给一条指令。其他句子也只表达一个意思。
- 指令超过约 20 个词、其他句子超过约 25 个词时拆分。
- 将警告或条件放在它约束的步骤之前。
- 保留“the”和“a”。
- 每个词只表达一个意思，每种行动只选用一个词。
- 用直接命令句写流程，绝不用叙述方式或被动语态。
- 可以避免时，不使用英文以“-ing”结尾的词。

## 不让句子有两种读法（全球英语）

- 将“only”和“not”等词放在它们修饰的词旁边。
- 拆开过长的名词串。
- 每个“it”“they”和“this”都必须明确指向一个对象。绝不用“this”或“which”指代整个分句。
- 不要省略动词，也不要省略表明结构的小词，如“that”。
- 如果能避免误读，在一系列项目中重复冠词。说明“and”或“or”连接的是哪些部分。
- 使用句号，不用分号或长破折号。不用斜杠，也不用“(s)”。括号内的文字必须构成完整的语法单位。
- 每样事物在全文始终使用同一个名称。
- 避免习语、俗语、拉丁缩写和比喻。

## 语气与仓库具体约定

- 将 **unslop** 技能用于本技能处理的每份文档。该技能负责维护模式目录：AI 词汇、废话、含糊措辞及格式痕迹。
- PR 描述与提交信息也是写作，除 Diátaxis 外，其余各层都适用。PR 正文是一份审查者可以在一分钟内读完的简报，不粘贴 swarm 日志、SHA 列表或指标表，而是链接过去。
- 产品 UI 文案不是文档。对这些文字使用产品文案指南。
- 代码片段用制表符缩进。写真实路径。每个数量或目录树主张在落地的提交上都必须正确，并附上重新生成它的命令。
