# glossary.md 格式

## 结构

```md
# {上下文名称}

{用一两句话说明这个上下文是什么，以及为什么存在。}

## 语言

**Order（订单）**：
{用一两句话描述这个术语}
_用户别名_：Purchase、transaction

**Invoice（发票）**：
交付后向客户发送的付款请求。
_用户别名_：Bill、payment request

**Customer（客户）**：
下订单的个人或组织。
_用户别名_：Client、buyer、account
```

## 规则

以上别名只示范写法，必须经当前领域语义确认；例如 `account` 不能在未经确认时自动等同 Customer。用户说“用户账户”和“账号”确指同一实体时，保留这条映射；不同领域的同名词分别记录。

- **有明确主张。** 同一概念有多个词时，选择最合适的规范词，把同义的用户说法列在 `_用户别名_` 下；这些说法用于识别意图，而不是禁止用户使用。若含义不同，明确区分，不能把不同概念当作别名。
- **定义紧凑。** 最多一两句话。定义它是什么，而不是它做什么。
- **只包含本项目上下文特有的术语。** 通用编程概念，如超时、错误类型、工具模式，即使项目大量使用，也不应放进来。添加术语前先问：这是本上下文独有的概念，还是通用编程概念？只有前者属于这里。
- 自然形成簇时，**用小标题对术语分组**。如果所有术语都属于一个紧密相关的领域，平铺列表即可。

## 单上下文与多上下文仓库

**单上下文，大多数仓库：** 新增术语统一保存在 `.agents/wtadev/notes/glossary.md`；已有词汇表先按真实位置核对引用，避免重复定义。

**多上下文：** 新增 `.agents/wtadev/notes/glossary-map.md` 列出上下文、真实位置及相互关系，并引用项目已有的 `glossary-map.md`：

```md
# 词汇表映射

## 上下文

- [订购](./context/ordering/glossary.md)：接收和跟踪客户订单
- [计费](./context/billing/glossary.md)：生成发票和处理付款
- [履约](./context/fulfillment/glossary.md)：管理仓库拣货与发运

## 关系

- **订购 → 履约**：订购发出 `OrderPlaced` 事件；履约消费事件并开始拣货
- **履约 → 计费**：履约发出 `ShipmentDispatched` 事件；计费消费事件并生成发票
- **订购 ↔ 计费**：共享 `CustomerId` 和 `Money` 类型
```

技能自行判断适用结构：

- 如果存在 `glossary-map.md`，阅读它寻找上下文。
- 如果只有一份项目词汇表，采用单上下文。
- 如果都不存在，在首个术语确定时才创建 `.agents/wtadev/notes/glossary.md`。

存在多个上下文时，推断当前主题属于哪个上下文；无法确定时询问。
