# 技能编写指南

维护目标、允许的适配与同步顺序见[关键开发约束](development-constraints.md)。保留成熟完整方法；本文只规定如何让本项目入口可选择、资料可发现。

## 一个技能解决一个可识别的任务

名称使用 `领域-动作`，与目录名称一致。`description` 写用户什么时候会需要它、它处理什么任务以及容易混淆的边界。描述必须能帮助模型选择技能，不要把描述写成完整执行流程。正文采用中文；保留真实 API 名、文件名、命令和配置键，不能为翻译而破坏可执行内容。

先写具体任务和产物，再写容易混淆的必要前提。不要因为某方法适用于代码，就把“任何开发、设计或审查”都写成触发条件。普通报告、已配置来源与触发器的自动化、普通绘图和 TLA+ 结果可视化分别具有不同的实际前提。主入口负责当前结果，其他方法补充它，不重复建立计划或记录。

`SKILL.md` 只保留 `name` 和 `description` 两个简单 frontmatter 字段。不要为普通任务增加状态字段、强制模型、环境变量合同或复杂输入 schema。界面名称与默认提示放在 `agents/openai.yaml`；默认提示点名本技能。

## 定义成果与判断方式

先说明完成后用户能看到什么，再写影响成败的判断、边界与执行方式。对于模型已熟悉的通用操作，无需机械列出每次点击或每个思考步骤。保留容易出错的具体规则、项目约束、完整参考实例和必要模板。

不要把单个成功案例固化成所有任务必须遵循的路线。小任务可以只有简短规格与实施验证；复杂任务才需要需求目录、垂直切片、设计决定和多轮集成。已解决的问题沿用已有决定，已授权的工作继续推进。

## 完整内容与按需加载

入口保持聚焦，长篇方法放在 `references/`，复制后要填写的产物放在 `assets/`。参考文件较长时提供目录和清晰标题，入口说明“什么情况下读哪一份”。每份 Markdown 资源必须能从 `SKILL.md` 沿本地链接找到，但不要求每次任务读取全部资料。

主分支尽量由入口直接链接完整方法；支撑例子可按主题索引查找，避免多层导航后才发现真正步骤。同一包内同一方法只保留一份完整正文。不要把详细资料复制进入口，也不要为了扁平化把全部参考目录塞进入口。

本项目将官方编写建议落实为可复核预算：`SKILL.md` 正文最多 500 物理行和 12000 个非空白 Unicode 字符；frontmatter 的 description 最多 1024 字符。字符预算为本项目约定，不是官方 token 限制。超限先拆独立细节、补链接和读取条件，再压缩重复说明；完整内容仍保留在本包。口径、官方来源和命令见[质量门禁](skill-quality.md)。

每个技能独立安装后仍须成立。内部链接只能指向自己的包，不链接兄弟技能、仓库根目录、全文对照库或外部站点。交接到其他技能时说明这是可选能力，并保留当前技能能独立完成的必要方法。命令示例只能引用已提供的脚本或宿主实际拥有的工具，不能写不存在的专用 API。

技能运行产生的项目资料统一使用 `.agents/dev/` 为根目录，按 changes、notes、deploy、archive、project、context、system 的职责按需保存。技能入口和模板都应使用一致的路径；项目资料不写入 `.agents/skills/` 安装包。已有外部文档引用真实位置，迁移资料后核对导航与入链。

有确定性、重复而且容易出错的步骤时才增加脚本。依赖和输出要明确；普通推理不必包成脚本。模板提供最小有用结构，允许根据任务裁剪，不要求填写没有事实支持的字段。

## 中文整合规则

参考内容完整复制并逐份翻译为中文，保留判断标准、步骤、反例、表格、数值和代码含义。译文底稿用于核对完整性；实际运行资源再统一到本项目。

运行版必须逐处处理不兼容指令：保留适用的工程方法与验证顺序；改成本地资源路径；将来源专用技能调用和模型绑定改为当前工具能力；把复杂状态引擎换成必要的 Markdown 记录；尊重用户已经给出的授权。不能只在开头写一句“以本项目为准”，却让下文继续要求相反的动作。

技能内不出现来源项目名、作者名、致谢、来源 URL 或“请去某项目查看”的指令。集中致谢在仓库 README，完整法律声明保存在配套许可目录。字面译文与运行适配的区别记录在仓库维护资料中，不能把适配后的行为宣称为未经修改的原文。

## 工程实践与分层验证

先理解用户目标与可观察行为，再按任务选择规格驱动、TDD、原型、行为回归或形式化分析。保留成熟方法的具体机制，不能因为偏好某个范式就删去其他有效方法。类型、lint、接口设计形成结构约束；测试、评测和实际使用提供经验验证；形式化方法用于明确的高价值属性，并记录假设、边界和模型漂移。

验证围绕尚未解决的实际风险，不为形式完整而重复。技能包装检查证明文件可安装、链接可解析；行为验证说明具体场景能否执行；内容审查检验方法是否完整、冲突是否解决。三者用途不同，不相互冒充。

## 项目记忆

技能告诉 Agent 如何做事；项目笔记保存某个项目已经确认的事实、用户语义和决定。不要把本次任务的临时进度、账号秘密或项目实现细节写回通用技能。代码能解释的事实直接引用源码，文档重点保存意图、理由、边界和查找入口。

## 修改后的检查

运行 `node scripts/check.mjs` 检查预算、包装、自包含和资料映射；用 `node scripts/check-skill-quality.mjs --report` 查看各入口占用。修改安装器、门禁或验证器行为后执行 `node scripts/check.mjs --full`。再按实际改动阅读完整资料，路由与执行条件变化时使用不提供预期答案的独立任务检查；包装通过不表示选择行为已经得到验证。

## 领域持久化路径

运行技能写入长期项目资料时，路径必须来自自身领域：`skills/dev/` 对应 `.agents/dev/`，`skills/system/` 对应 `.agents/system/`；后续领域依此类推。技能安装目录 `.agents/skills/` 不承载项目记录。旧 `.agents/wtadev/` 只能作为迁移输入，详见[领域持久化](persistence-roots.md)。
