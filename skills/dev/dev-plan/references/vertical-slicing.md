把计划、规格或对话拆成一组**任务**：曳光弹式垂直切片，每项声明哪些任务**阻塞**自己。

使用已有跟踪器或[本地工作记录](local-work-records.md)，没有外部平台也能完成计划。

## 流程

### 1. 收集上下文

从对话已有上下文开始。如果用户在参数中传入引用，例如规格路径、事项编号或 URL，就获取并阅读完整正文和评论。沿用已有目标、非目标和决定，保留用户明确的交付数量与边界。需要独立接手的任务保留相关来源与必要背景，不要求接手者记得本次对话。

### 2. 探索代码库，可选

如果尚未探索，先了解代码当前状态，定位行为入口、可复用实现、真实调用方与已有验证接缝。任务标题和描述使用项目领域词汇表，尊重涉及区域已有的 ADR。能从代码、配置和测试查明的事实先自行查明；会改变产品行为或数据语义的未决决定只阻塞相关切片，不包装成实施假设。

寻找预重构机会，让实现更容易。“先让变更容易，再完成容易的变更。”

### 3. 起草垂直切片

把工作拆成**曳光弹**任务。

<vertical-slice-rules>

- 每个切片贯穿所有相关层，例如数据结构、API、UI、测试，路径窄但**完整**；它是垂直切片，不是单层的水平切片。
- 完成的切片能独立演示或验证。
- 每个切片的大小适合单个全新上下文窗口。
- 确有必要的预重构先于依赖它的切片进行；范围只包含让本次变更可实施的调整。

</vertical-slice-rules>

为每个任务声明**阻塞依赖**，即它开始前必须先完成的其他任务，并说明需要它的什么产物。没有阻塞者的任务可以立即开始。前置产物可用后，本项应能完成自己的验收；若验收还需要后续切片，调整任务边界或明确交给整合任务，不提前声称完整场景通过。

每片同时交付该行为所需的验证。先完成最小完整路径，再扩展其他场景；最终整合不是第一次检查早期切片是否可用。公共能力可以单列，但应有明确调用者、输入输出或不变量，以及独立验证入口。

包含多个可分别验收的行为、不同高影响决定或过宽写入范围时继续拆分；若只是技术层切割、没有独立价值，或必须反复加载同一不可分割上下文和验证，则合并。文档、失败处理与回归放入拥有该行为的切片，不为每种检查单独造票。

**广泛重构是垂直切片的例外。** **广泛重构**是一次机械变化，例如列重命名或共享符号重新定型，其**影响范围**扇出到整个代码库，一次修改可能同时破坏数千调用点，任何垂直切片都无法独立保持检查通过。不要强行做成曳光弹。若迁移期间必须保持兼容，可按**扩展—收缩**编排；若已允许整体替换，则一次迁移全部调用者并在整合点验证，不额外保留兼容层。下面说明需要持续兼容时的完整方式。先扩展：在旧形式旁加入新形式，保持兼容；再按影响范围分批迁移调用点，例如按包、按目录，每批一个任务，依赖扩展任务，旧形式仍在，因此批与批之间 CI 持续通过；最后收缩：没有调用方后删除旧形式，该任务依赖所有迁移批次。如果连批次也无法独立通过，保留顺序，但共享一个集成分支，让所有批次都阻塞最后的集成验证任务；只在最后那里承诺检查通过。

### 4. 向用户核对

以编号列表展示建议拆分。每个任务展示：

- **标题**：简短、描述性的名称。
- **被谁阻塞**：哪些任务必须先完成；没有则说明。
- **交付什么**：这个任务让哪项端到端行为工作。

先围绕以下问题核对拆分；用户要求审阅计划或存在实际粒度分歧时，再向用户核对：

- 粒度是否合适，太粗还是太细？
- 阻塞依赖是否正确：每项任务是否只依赖真正限制它开始的任务？
- 是否有任务应合并或继续拆分？

按[计划核对](plan-review.md)检查交付、依赖和验收是否对应，并从规格反查全部要求及明确数量的承接，修复漏项、重复责任和未声明的整合前提。并行候选同时检查文件与共享接口、数据、迁移和测试资源，不能只凭路径不同就认定独立。用户要求先审计划时等待意见并迭代；已要求持续实施时先展示计划，在既有授权内推进，只对实质不确定的产品决定提问。

### 5. 发布到配置的跟踪器

保存已确定的任务。**如何保存**取决于项目已有跟踪方式；任务本身相同，只是阻塞依赖的表达形态不同。外部发布、建立子事项和改标签必须已有相应授权：

- **本地文件** → 较大或需要独立交接的任务各写一个文件，位于 `.agents/dev/changes/<YYYY-MM-DD-slug>/tasks/<NN>-<slug>.md`，从 `01` 开始按依赖顺序编号，阻塞者在前。每个文件的“被谁阻塞”列出依赖编号或标题。小需求可将同样信息放在 plan.md 的一张表中，不强制拆文件。
- **外部事项跟踪器** → 按依赖顺序发布，每个任务一个事项，阻塞者在前，让依赖能引用真实标识。平台有原生阻塞关系时使用它，否则把阻塞事项列入“被谁阻塞”。如果来源是已有事项，把各任务设为其子事项，遵循跟踪器文档中的操作。除非另有要求，复用已有的就绪描述或标签，无需创建 `ready-for-agent`；这些任务设计出来就可由智能体接手。

推进**前沿**：任何所有阻塞者均已完成的任务。纯线性链就是从上到下。

创建切片本身不授权关闭或修改父事项；只有用户明确要求时才更新父事项。

下面两类模板保留紧凑的行为契约，适用于本地与外部跟踪器。交给新会话或独立实施者时，按[单个切片](plan-template.md#单个切片)在原任务补足等价信息或链接到它，不同时维护两份任务正文；不能把“构建什么 + 测试通过”当作完整交接。只有同一上下文的小任务才直接保留最简条目。

## 实施导航

无论哪种形态，行为契约不依赖具体文件路径或行号；独立接手或需要实施安排时，按[计划与切片模板](plan-template.md)单列必要背景、已定约束与当前代码指针，跨阶段或多 PR 工作再使用[多阶段模板](multiphase-plan.md)的文件、构建、可见结果与验证块。已有入口实施时复核，新增文件明确标注创建；每项验收应能沿链接找到运行位置、必要环境、验证动作和通过判据，不复制整份规格。

用户、项目安全规则或验收明确要求的方法随任务传递；普通可选知识按需发现，不要求预扫描全部技能。UI 的设计版本与状态、迁移的恢复和停止条件等仅在实际涉及时补充，见[按风险补充](plan-template.md#独立接手与按风险补充)。局部实现仍由实施者决定。

例外：原型片段比文字更准确地表达决定时，例如状态机、reducer、数据结构或类型形状，可以内联并简短注明来自原型。裁剪为富含决定的部分，不放完整可运行演示，只放关键部分。

各切片围绕完整行为交付，测试先行与实现后验证均可使用；按风险选择验证深度，避免只覆盖内部实现细节。若需要大型需求探路，阅读[决策地图](uncertainty-map.md)。
