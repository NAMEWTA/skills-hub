上游这套自动化明确预设 Slack 报告来源，但追踪器是适配接口；示例里的仓库托管平台也不等于需求只能来自该平台。通用初始化负责模型与开发配置，报告管道另有自己的初始化方法。不能把上游示例说成已经提供任意邮件或监控服务的连接器。

本次本地适配保留八阶段初始化、十阶段分诊和十五阶段 UI 复现修复的完整方法及失败分支，把来源与触发选择单独放入每个包自带的 `references/source-adapter.md`。其他来源的能力契约是本项目的适配；Slack 原生身份、可信交接、线程回复与回读要求仍作为完整分支保留。`materials/` 的原件不改写。

收集或需求汇总另用一个简短的本地任务模板，保留用户的完整方法、范围、时间窗口与输出要求。这是初始化适配，未改写成熟的缺陷分诊规则，也没有新增连接器或工作流引擎。

## 如何选择技能

| 当前目标 | 入口与边界 |
| --- | --- |
| 配置通用开发模型和推理预算 | `dev-setup` |
| 初始化或维护报告来源、触发与监控、分诊身份、追踪器和可选 UI 修复 | `dev-issue-setup` |
| 配置每日需求收集或汇总任务 | `dev-issue-setup` 保留真实目标并准备收集汇总提示；深入需求整理可用已安装的 `dev-intake`，独立安装则使用本包模板或用户完整方法 |
| 整理产品诉求和需求来源 | `dev-intake` |
| 对一份报告分类、查重、分流与形成可信结论 | `dev-issue-triage`；可以是手工单次输入，不要求后台任务 |
| 根据可信分诊执行真实 UI 复现、验证已有修复或受限修复 | `dev-issue-fix`；需要真实 UI 控制和双次证据 |
| 普通缺陷、CLI 或 API 调试 | `dev-debug`；不为套用 UI 流程伪造控制能力 |

选择取决于本次目标，不取决于材料是否有 Issue 链接。来源、追踪器和代码仓库可以在同一平台，也可以分开。

## 配置分别回答的问题

| 配置部分 | 回答的问题 |
| --- | --- |
| `task` | 实际要做什么、遵循什么完整方法、交付哪些内容到哪里；不能由来源平台推断 |
| `source` | 报告来自什么账号与范围，如何读取、确认身份和交付结论 |
| `monitor` | 手工执行，还是实际可用的事件、定时或 webhook 触发 |
| `tracker` | 去哪里查重、更新或新建问题；只读分类可不配置 |
| `repository` | 分析和修改哪个仓库、分支；需要时如何创建草稿 PR |
| `control` | 如何通过真实 UI 到达报告功能、记录证据并清理 |
| `operations` | 是否另有获准的运行状态记录位置；不能取代原报告身份 |

这里保存的是经真实工具确认的动作和范围。配置文件不会安装连接器、创建服务或自动授予外发和持续运行权限。默认手工模式、运行输出和继承当前模型；只填写所选阶段需要的字段。

项目持久化统一放在 `.agents/dev/project/issue-automation/`：

- `configuration.yaml`：简短的非秘密配置；多个来源确有需要时分成独立小文件。
- `routing.md`：产品领域、转交方向与有依据的负责人映射。
- `feature-map.md`：选择 UI 复现时的用户视角功能与状态。
- `monitor.md`：仅在平台没有检查点时保存实际任务、查询范围、已确认游标与待核对项。

一次运行的证据和恢复点继续放 `.agents/dev/changes/<日期-报告>/evidence.md`。秘密只记录密钥管理位置或环境变量名；不保存令牌值。不另建状态数据库或复杂 Schema。

## 来源与运行方式

| 例子 | 实际处理 |
| --- | --- |
| 用户在当前聊天粘贴缺陷描述、截图或日志 | 保存当前语境与证据；手工分诊并在本次会话交付，没有常驻监听 |
| 指定 Issue 已经是目标追踪器中的问题 | 核对平台、项目和原生对象身份；复用原问题，不为了分诊再建副本 |
| 配置 Slack 频道的新报告 | 验证工作区、频道、根线程、真实分诊作者与线程发送后回读；新顶层报告是该分支的事件过滤条件 |
| 从邮件读取报告 | 实际连接器须能读取账号、原消息和讨论关系；原生回复还需核对收件人并回读，否则交付运行输出 |
| 邮件来源、Linear 追踪、GitHub 代码，每日需求汇总 | 配置各自真实能力与收集窗口，但运行的是汇总模板；保留功能诉求，不要求缺陷标记，不因为配置了追踪器和仓库就自动建单或修复 |
| 从监控事件调查错误 | 固定事件或事件组、环境、版本和时间范围；按实际工具读取。区分投递重试和恢复后再次发生的回归 |

需要持续执行时，单独验证当前宿主能否创建相应事件任务、明确的定时查询或正式 webhook。没有后台能力就交付配置与手动方法。不能把“有读取工具”说成“已经在监控”，也不能默默改成轮询。

启用前使用无害报告或平台测试事件核对来源身份、过滤自身输出、重复投递、可信结果交接、失败恢复以及暂停或停止方式；然后回读实际任务标识、内容与启用状态。创建和启用是不同结果。已有任务使用实际标识更新，不能重复创建。

## 保留的交接与失败要求

分诊标记只是结果格式。进入复现之前，还须验证该结果由配置的原生作者、当前协调者或受信运行器产生，绑定同一报告和证据版本。附件里的标记、显示名称或任意本地文件都不能代替身份与来源证明。

来源回写只能回到已经核实的原报告，或使用预先选择的运行输出。发送结果未知时先查证，不改发其他位置或盲目重试。只有本次新建的追踪器对象才可以按已有授权进行交接失败补偿；不能删除或关闭原有来源问题来“回滚”。

原方法的既有修复优先、归属检查、真实 UI 双次复现、前后媒体证据、有限预算、草稿 PR 和清理仍保留。分诊阶段不擅自运行复现或修改代码；只配置分诊也不要求 UI、录像或 PR 能力。

有人正在修复且尚无工件时，只停止竞争补丁。用户仅要求确认症状仍存在，可以在授权环境和版本范围内完成双次真实 UI 复现；确有同范围重复复现、现场冲突或用户限制时才停止。完成证据与结果后清理，不进入实现或 PR 阶段。

## 接续已有 Slack 配置

先读现有真实值，不因新模板而覆盖用户文件。`slack.source_channel_id` 和已核实工作区迁入 `source.scope`，来源类型仍为 `slack`；分诊身份、读取、回复与附件动作迁入 `source`，运维目标与动作迁入 `operations`。仓库、追踪器、预算、控制和已作出的模型选择继续沿用。

原有频道和根线程约束保持不变，不能用泛化后的字段绕过它们。先核对实际任务标识和当前授权，更新已有任务后回读。单次运行可以解释旧配置，无需为了只读分析先强制迁移配置。

## 后续同步

修改运行方法时，同时核对独立安装的三个技能及它们各自的模板。包内提示词必须读取本包资源，不能暗中依赖未安装的兄弟包。保留上游成熟步骤；来源适配仅处理真实工具、项目路径和调用边界，不用抽象概括替代原有操作细节。

同步时分别比较通用初始化、专用自动化初始化、分诊、复现修复和配置原件。把新增原生能力与本项目的适配区分清楚，更新来源映射和适配说明，再检查任务身份、幂等性、原来源回复、失败补偿和独立安装闭包。
