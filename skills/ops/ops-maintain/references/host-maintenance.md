# OS、内核与主机重启

## 首次维护前提

取得稳定资源身份、真实 SSH/平台连接入口、操作系统与包管理器、当前内核、启动方式、挂载和全部已知服务。确认控制台或既有恢复入口是否可用，不能假定 SSH 断开后会自动恢复。

先用 ops-inspect 采集相关基线。登记同机项目、共享中间件、未知对象与原有维护任务；只维护一个项目不自动授权整台机器重启。

## 审查实际包集合

1. 读取当前已安装包和候选版本，确认来源与当前变更目标。
2. 使用该发行版支持的模拟/预览，完整阅读安装、升级、删除、依赖及重启集合。
3. 分开主机基础组件与项目组成服务。数据库、缓存、代理等即使由系统包管理器安装，也不自动成为允许升级的 OS 组件。
4. 检查安装脚本、服务自动重启、内核/引导变化、配置文件冲突和依赖传递。不能只批准顶层包而忽略其实际变化。
5. 明确包版本与目标在执行前是否仍相同。仓库索引刷新会改变候选集合，不能沿用过期预览。
6. 按实际窗口与已确认命令执行，逐项记录结果。出现额外服务升级或新影响，分离可做部分并形成项目交接。

### 既有命令入口示例

以下示例由 ops-execute 通过真实工具执行，不是通用升级脚本。名称、版本和平台必须来自本次核查。

| 平台/目的 | 入口示例 | 注意 |
| --- | --- | --- |
| 当前内核 | uname -r | 运行内核与已安装待启动内核分开 |
| Debian 系列包身份 | dpkg-query -W 已核验包名 | 只读取必要包，不保存无关清单 |
| Debian 系列候选 | apt-cache policy 已核验包名 | 记录索引时间与候选来源 |
| Debian 系列模拟 | apt-get --simulate install --only-upgrade 已核验包名=已核验版本 | 仍需审查依赖、配置和重启副作用；模拟并非真实验证 |
| RPM 系列 | 既有管理平台或包管理器的实际预览能力 | 不伪造跨发行版等价参数 |
| 当前启动标识 | 读取 /proc/sys/kernel/random/boot_id | 只在适用平台记录启动观测，不代替稳定主机身份 |

不得以 apt upgrade、dist-upgrade 或类似全量操作作为“只升级 OS”的保证。不使用自动接受全部配置冲突的参数掩盖真实选择。

## 主机重启与滚动维护

明确本次重启的理由、范围和窗口；核对在该主机上运行的所有已知服务及共享消费者。必要摘流或停止步骤来自已有验证过的运行方法，不从通用依赖图自动推导。

逐机维护只有在以下条件真实成立时使用：剩余实例确实健康；流量/任务能转移；共享存储或单实例数据库不会随之一并中断；实际容量能承受；回到下一台前的就绪条件明确。

通过 ops-execute 记录重启被实际接受的证据，然后以有界方式核查：

- 连接恢复到相同稳定资源，host key 或身份变化不能盲目忽略。
- 启动标识和运行内核与本次目标一致。
- 挂载、存储、网络和时间正常。
- 既有服务按其真实运行规则就绪。
- 原项目与共享消费者路径验证完成或明确缺口。

SSH 在重启时断开是预期可能现象，但不证明命令成功或主机已重启。先查询既有平台任务、连接与现场状态，不能再次无条件发送 reboot。连接长期未恢复时使用已知控制台/责任方，不能擅自重建机器。

## 失败与恢复边界

包执行失败可能已经部分修改系统，保存实际集合、配置状态、日志与尚未开始步骤。不要将失败退出码解释为“没有变化”。

主机基础组件的恢复应使用本次已核验方法；需要更换项目服务制品、回退应用/中间件版本或改部署定义时交项目处理。恢复已有服务运行状态交 ops-recover，不在维护包复制启动/恢复引擎。

维护成功要同时说明主机目标与项目影响；“新内核已运行，某消费者未验证”应据实报告，不能合并成全部正常。
