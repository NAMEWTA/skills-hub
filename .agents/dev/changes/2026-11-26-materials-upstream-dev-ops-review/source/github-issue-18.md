完善现有 `dev-setup`，让用户在项目接入、切换执行主机或准备并行开发时，得到一份**先给并发结论、再给硬件与测量依据**的 `.agents/dev/context/environment.md`。

1. 当前主机上，这个项目建议同时运行多少个 Agent 会话，是否包含 Lead，目前还能增加几个？

## 3. 核心定义与计数规则

| 对象 | 本 Issue 中的含义 | 资源归属 |
| --- | --- | --- |
| task | 一份待完成的工作，可以由同一会话依次完成多个 task | task 数量不直接转换为进程数或会话数 |
| Agent 会话 | 实际运行的 Lead、worker、subagent 或独立 CLI 会话；注明运行中、等待模型、等待重任务等状态 | 按真实执行位置和共享关系计算常驻成本，保存的历史会话不算正在运行 |
| 重任务 | 一次安装、编译、测试、浏览器验证、索引或必要服务启动 | 在会话常驻成本之外增加 CPU、内存、I/O、线程和磁盘峰值 |
| 内部 worker | 构建 jobs、单元测试或浏览器测试 worker 等内部并行单位 | 受所在重任务额度约束；一个 worker 可以派生多个进程，worker 名额不等于 PID 名额 |
| worktree | 源码检出与该目录中的依赖、产物和缓存 | 保留时主要占磁盘；在其中运行的任务另外占执行资源 |
| Git 分支 | Git 引用 | 分支数量不能用来推导活跃 Agent 数或构建数量 |

必须保留以下关系：

- task 与执行会话解耦，遵守已合并的 [Issue #15](https://github.com/NAMEWTA/skills-hub/issues/15) / [PR #16](https://github.com/NAMEWTA/skills-hub/pull/16)。换 task 或上下文压缩不自动创建新会话；handoff 沿用原规则。
- 单独创建纯源码 worktree 不增加 Agent 数量。读取、审查类 Agent 可以不新建 worktree；需要隔离写入时再由现有方法处理。
- 等待远端模型响应的本地 CLI 仍可能保留内存、连接、MCP 和 LSP。不能只统计当时 CPU 忙碌的进程。
- 原生 subagent 可能共享一个宿主进程，也可能另启进程。逻辑 Agent 个数与 OS 进程个数分别记录，不按人数重复计算同一个宿主 RSS。
- 云端任务、SSH 远端执行和本地模型按实际执行资源池分别计量。远端模型推理不意味着本地加载模型权重；本地工具与代理转发的实际开销仍须计入。

## 4. 本轮范围与职责

完整环境评估方法仍由 `dev-setup` 持有，输出仍为 `.agents/dev/context/environment.md`，已有等价权威记录原地维护。

本轮实施包括默认只读检查、结果优先模板、负载与证据语义、可选校准、推荐组合计算、执行时复核及使用示例。工作树创建、初始化、集成和回收继续由 `dev-worktree` 负责；派遣继续由实际 Lead 或已有调度器负责。

保持现有轻量边界：不新增同职责 skill、常驻守护进程、资源数据库、流程 JSON、跨机器调度平台或第二套清理器。不以安装 Python、psutil、Kubernetes 或额外监控服务作为技能使用前提。本轮沿用现有系统观测命令、宿主接口和既有工具，不新增独立的全平台主机探测工具包。

团队文件只按用户明确请求维护，普通评估不创建默认团队、不选模型、不改全局 CLI 参数、不向根 `AGENTS.md` 注入新的自动加载步骤。

## 5. 默认执行流程：先只读评估

### 5.1 确认评估的是哪台机器

记录项目、检出位置、采样时间与时区、实际执行位置，以及物理机、容器、VM、WSL、SSH 或云端执行器的边界。只能观测当前执行器时，明确写“当前执行器”，不能称为用户电脑。

远端仅检查用户指定且已有连接能力的目标；不可达主机不计入可用容量。多台机器分别给结论，共享父宿主、NAS 或配额另列共同约束。

### 5.2 读取硬件、有效约束与当前负载

沿用 `host-resources.md` 的平台观测表，补齐“每项数据用于哪一个决定”，不把所有命令强制用于所有机器。

| 信息 | 必要内容与判读 |
| --- | --- |
| CPU | 型号、架构、物理与逻辑核数按可见性记录；用于计算的是 affinity、cpuset、适用 CPU quota 共同限定的有效容量。小数核保留，不能将 1.5 核向上当 2 核保证。 |
| 内存 | 总量用于说明设备；预算使用当前可用量、容器及可见祖先剩余量、压缩或换页压力。`memory.high` 是操作压力边界，`memory.max` 是硬限制，两者分开。 |
| 磁盘与 I/O | 仓库、worktree、包缓存、构建和临时目录的真实卷、剩余空间、适用 quota/inode、可见 I/O 压力。相同卷不能多次相加；NAS、慢盘和 tmpfs 标明约束。 |
| 现存负载 | 现有会话、安装/构建/测试、浏览器、LSP、MCP、开发服务、容器及其他后台工作；报告归属和必要摘要，不保存完整命令行或秘密。 |
| 适用限制 | PID/线程、文件描述符、文件监视器等已存在限制或异常；需要本地推理或 GPU 任务时才增加显存画像。 |
| 项目条件 | 清单、锁文件、运行时、构建与测试入口、worker 设置、浏览器与服务需求、主检出和新 worktree 的初始化差异。 |

操作系统接口缺失、权限不足或祖先配额不可见时写明边界。Node 的 `os.availableParallelism()` 只是程序建议并行度，不能直接等于 Agent 数；`process.constrainedMemory()` 的 `0` 不能直接解释成 0 RAM 或无限容量。相关接口只能作为观测来源，需结合实际平台限制解释。来源见第 10 节 R9、R10。

默认复用已有样本和必要的轻量观测。**不为出报告而自动安装依赖、构建项目、跑全量测试、创建一批 worktree、启动一批 Agent 或执行删除。** 默认的“只读”指对宿主与业务环境的调查，按请求写入环境报告属于正常交付。

### 5.3 根据现有证据给结论

有同项目、同执行环境、相近版本及相同 worker 设置的可靠样本时，给出带依据的推荐组合。没有样本时先给当前占用、可确认新增量、未知项以及最小补测方法，避免无限期只写“未知”却不给下一步。

只读评估不是证明系统绝对稳定的压测；单次快照也不代表未来整机容量永久不变。

## 6. 项目负载画像与按需校准

### 6.1 画像保持少量且与项目相关

至少区分“会话常驻/轻量工作”与“附加重任务”。项目实际使用浏览器或多种构建方式时再细分，不要求每个项目维护全部类别。

| 画像 | 测量范围 |
| --- | --- |
| 会话常驻与轻量工作 | 实际 CLI/宿主版本、常见上下文规模、读写搜索、必要 MCP/LSP；区分独立 CLI 与共享进程 subagent 的增量 |
| 依赖初始化 | 新 worktree 中的安装、解包、编译依赖、冷缓存峰值和最终磁盘增量 |
| 构建或单元测试 | 真实命令、项目规模、jobs/workers、完整进程树峰值、CPU 需求、时长、缓存条件 |
| 浏览器或集成验证 | 测试 runner、浏览器及其子进程、开发服务器、数据库或容器、截图与追踪产物 |
| 合并后的最终验证（如项目需要） | 仅当负载或运行环境与前述画像不同才单列；否则复用已有画像，只说明最终验证与必要集成树的预留，避免重复计费 |

每份样本记录项目 revision/锁文件或等价版本依据、主机及资源池、命令与参数、冷/热状态、开始和结束时间、样本窗口、采样方法、观测峰值、退出结果、残留占用及适用边界。样本未覆盖关键阶段时不能标为完整峰值；少量样本不能伪装成有统计意义的 P95。

优先使用现有监控、任务/cgroup 聚合统计；使用进程树 RSS 求和时说明共享页可能重复计算，单个 CLI 父进程 RSS 不能冒充整体开销。短时任务可能逃过轮询，缺少样本不等于零成本。

### 6.2 校准只在实际需要且已经授权时运行

优先在正常开发中观测本来就要执行的任务；用户明确要求测量并发容量，或当前已授权任务需要验证该组合时，可以执行有界校准，无需再增加重复确认。

开始前根据当前余量与任务范围，记录本轮最大试运行并发、总时长或轮次边界、停止条件及可用停止入口；缺少支持下一档并发的依据时不继续递增。这些边界由已授权任务和现有资源信息确定，不另设固定审批步骤。

1. 先读取最新余量、已有预留和运行时限制，选定一个可代表真实工作、可停止且有时长或范围边界的样本。
2. 先观察一个会话或一项任务。已有 Lead 的稳定运行只能作为该 Lead 的样本，不能直接证明新 worker 或新 CLI 的增量开销。
3. 在已知余量内逐步增加同类任务，明确每项内部 worker，不同时放大多个未知类别。
4. 覆盖真实构建、测试和浏览器峰值；比较相同工作量的完成时长/吞吐、失败情况、内存余量与压力。没有可比较的任务或样本时，只报告资源估算，不声称已经找到性能最优点。
5. 资源保护线触发、明显换页/回收、任务失败或收益不再改善时停止扩张；回到已验证的稳定组合。不能通过故意触发 OOM 来寻找极限。
6. 记录本轮成功运行的组合与未测范围，并更新原环境报告。退出后仍有服务或 worktree 时继续计入相应占用。

这里的“最优”指**在明确负载与响应要求下，兼顾稳定吞吐、交互余量和任务独立性的推荐组合**。它不是“最多能创建多少会话”，也不是“把 RAM 或 CPU 使用率推到 100%”。只读阶段通常给资源可行建议；经过可比校准后才可说明哪一档更合适。

## 7. 容量计算：保留现有算法，输出联合可执行组合

以下是本项目的工程方法，不是任何厂商给出的通用 Agent 硬件公式。沿用现有增量预算，不再建立第二套算法。

### 7.1 有效预算

对内存、磁盘、inode、线程等使用当前剩余量的维度：

```text
可新增预算 = max(0,
  当前有效剩余量
  - 额外保护余量
  - 已准入但尚未启动的需求
  - 运行中任务尚未兑现的峰值增长)
```

当前剩余量已反映现有进程和文件，不能再次扣除它们全部的占用。保护余量优先沿用用户/平台的已有策略，其次依据当前服务和背景波动；采用保守假设时必须写出数值、来源与理由，不能把固定“每 Agent 几 GB”或统一百分比冒充官方标准。

CPU 按有效容量减去系统预留与正在运行、待启动任务的承诺量计算，不从瞬时空闲率推导可重复预留的核数。不同资源池分别计算，不能用远端空闲 RAM 为本地构建提供额度。

### 7.2 联合需求与内层并发

每个资源维度都须满足：

```text
新增会话数 × 会话增量成本
+ 新增构建数 × 构建附加成本
+ 新增浏览器/测试数 × 对应附加成本
≤ 可新增预算
```

只对有依据且大于零的需求做除法。未知不能当零，明确不消耗的维度才可略去。共享服务计一次，会话画像已经包含的附加进程不能再次全额计入。

Agent 会话、重任务和 worktree 三列共用资源，不是可以各自同时用满的独立额度。除资源约束外，再核对实际 CLI 限制、已知 API/账户额度、用户上限及任务可并行性；作用域不同的限制必须先对应到实际会话树、进程和任务，不能直接把所有数字相加或取最小值。

API RPM/TPM 与同时运行的会话数不是同一种单位。只有具备调用速率、延迟和请求成本依据时才转换成并发建议；配额未知时单独注明，保留有依据的硬件建议，但不声称端到端可用容量已经确认。

必须限制嵌套并发。例如多个 worktree 各自启用“全部 CPU”的测试默认值，即使 Agent 总数不多也可能超配。按实际工具版本映射 jobs/workers，并验证参数是否真的生效。Playwright 的 worker 会启动自己的浏览器，`--workers` 是可复用的原生控制入口。来源见第 10 节 R11。

### 7.3 worktree 分三种成本

- 纯源码检出的磁盘增量。
- 完成依赖初始化并保留产物后的磁盘增量。
- 在该树中启动构建/测试时的执行成本和临时磁盘峰值。

保留数按实际卷、容量预留和指定状态估算；正在运行重任务的工作树数按重任务预算限制。共享 Git 历史/缓存只计一次，hardlink/CoW 不等于未来增长免费，tmpfs 同时受内存预算约束。必要集成树和最终验证容量先留出。

## 8. environment.md 的输出契约

### 8.1 首屏先给能用的结论

开头固定包含：评估对象与时间、一句执行建议、主要容量表、当前瓶颈及待补测项。用户不需要翻过工具链、进程与清理细表才能找到结论。

主要表格包含：

| 项目 | 当前数量 | 建议总并发/保留量 | 当前可确认新增 | 证据与适用条件 |
| --- | --- | --- | --- | --- |
| 本资源池运行中的 Agent，会话口径包含 Lead | 实际观测 | 具体数字或未知 | 具体数字或暂无可确认名额 | CLI/模式、负载组合与来源 |
| 同时运行的重任务 | 实际运行 | 按本项目相关类别列出 | 按组合计算 | 每项内部 workers/jobs |
| 保留 worktree | Git 登记与可见目录 | 指定初始化状态下的磁盘建议 | 实际剩余能支持的增量 | 同卷、共享缓存、集成树条件 |

随后按需要展开有效资源、负载样本、计算依据、运行时限制、当前预留、失效条件与未覆盖范围。没有校准、回收或远端操作时不创建空表，更不能用模板占位符表示已完成。

报告明确区分：

| 结果类型 | 正确含义 |
| --- | --- |
| 当前观测 | 采样时正在运行的数量和占用 |
| 已验证运行规模 | 指定环境、负载、参数与窗口中成功运行过的组合 |
| 建议并发上限 | 基于成本、预留和实际限制得出的当前操作建议 |
| 资源估算容量 | 模型在明确假设下得出的可行范围，未必已实跑 |
| 运行时硬限制 | 当前版本/配置/套餐实际约束的范围，注明是否包含 Lead |
| 实际极限未知 | 尚未证明更高并发可行或不可行，不伪造精确硬件极限 |

“5 个并发验证通过”应写“已验证运行规模为 5”，不能写“已验证最大上限为 5”。验证过的规模不能证明更高规模必定失败。

### 8.2 已有样本时的报告示例

以下为**格式示意，不是用户宿主机实测结果，也不是默认值**：

> 当前项目建议同时保持 5 个 Agent 会话，包含 1 个 Lead 和 4 个 worker。其中最多 2 个会话同时执行已测量的重任务，每项按已验证参数使用 2 个内部 worker；其余会话继续读代码、编码或审查，进入重任务阶段时排队。当前已有 3 个会话，可再增加 2 个。磁盘还可容纳 3 个已初始化 worktree，但这不增加重任务名额。本组合基于报告所列样本推算，实际硬件极限未知。

真实报告必须在后文提供支持上述数字的预算与样本；不能复制示例数字填表。

### 8.3 只有 1 个 Lead、没有新增样本时

> 当前确认 1 个 Lead 正在运行，新增会话的成本尚未校准，实际并发上限未知。目前暂无可确认的新增名额；这不表示本机最多只能运行 1 个 Agent。下一步可复用同环境的已有样本，或在余量允许且任务已授权时，先观察缺少成本样本的代表会话。需要评估重任务容量且缺少对应样本时，再观察一项项目构建或测试，更新相应推荐组合。

若内部准入需要数字，可以将“已确认可新增”记为 `0`，同时注明原因是证据不足。不得把它重写成“机器容量为 0”或“硬件上限为 1”。也不能通过 `max(1, capacity)` 强制放行未确认可容纳的工作。

当新建议上限低于当前运行数量时，如实列出两者，可新增量为 `0`。不能为消除表格差异把建议值抬高到当前数量，也不因重算报告而自动结束已有会话；按排队与压力处理规则逐步收敛。

## 9. 执行时如何消费结论

1. 各阶段直接复用仍有效的环境记录；缺失或过期时按实际主机补查。本轮不引入必须先运行某个初始化 skill 的依赖。
2. 同一主机/共享池由一个 Lead 或已有调度器协调。多个 Change、多个仓库和嵌套 Agent 共用剩余容量；子级只获得父级分配的预算。
3. 新会话、worktree 初始化与重任务启动前，检查实时余量及已承诺增长。名额不足时排队，任务范围和 DAG 依赖保持原定义。
4. 优先复用当前会话接续 task。会话名额允许继续工作，并不自动授权该会话再启动一项重任务。
5. 实际可用时使用原生会话上限、jobs/workers 或已配置 OS 限制；报告“建议值”和“已经生效的限制”分别记录。CLI 参数要按已安装版本核对，不从文档示例猜测。
6. 保护线被突破、出现持续内存/I/O 压力或限制事件时，先停止新增和重试，再排队重任务、减少可控 workers；必要时有序停止本任务可恢复的进程。持续压力不会因为等待超时而自动获得启动许可。
7. 恢复前重新采样，并在压力持续恢复正常后逐步放行，避免在一个阈值附近反复扩张与收缩。采用的阈值、窗口及恢复条件必须写明来源；没有全平台通用的 PSI 安全常数。来源见第 10 节 R9。
8. 会话退出、换机、CLI/依赖/worker 设置变化、恢复旧会话、重任务首次运行和回收后刷新。工作树或后台服务实际释放后才归还相应资源。

普通报告不执行清理。确需回收时调用已有 `dev-worktree` 审计与清理方法，继续保护活动、锁定、归属不明和有未保存成果的对象。文档与单 Lead 约定覆盖受其管理的任务，不能宣称强制限制了所有外部进程。

## 12. 验收矩阵

以下行为契约已完成本轮实现与验收。勾选表示技能方法及相应证据通过，不表示所有平台、厂商 CLI 和真实最大并发均已运行；合成场景、实际只读使用、独立语义审查和仓库 CI 的范围逐项见上述验收映射。

- [x] **默认只读**：仅要求评估当前项目与环境时，只读观测并更新报告；不安装、构建、测试、批量创建会话/工作树或执行删除。
- [x] **结论可发现**：报告首屏和聊天交付先给推荐会话、重任务/内部 worker、可新增量及一句依据，详细硬件和工具链在后。
- [x] **未测新增会话**：仅确认 1 个 Lead 时写“实际并发上限未知、暂无可确认新增名额”，不写“最多 1 个 Agent”；给最小补测路径。
- [x] **已验证不冒充极限**：并发 5 个成功时记录已验证组合、负载和窗口，不推断第 6 个必定失败。
- [x] **真实执行位置**：只连接到云端执行器时不把它作为用户电脑；远端构建单列资源池，不与本地空闲 RAM 相加。
- [x] **容器约束**：物理机 64 GiB、当前容器限制 8 GiB 时按适用限额及当前占用计算；可见祖先限制更紧时继续收紧。
- [x] **小数与未知值**：1.5 核配额不向上取整；不可见配额、缺失接口与 `constrainedMemory()=0` 不被误写成已确认无限或零容量。
- [x] **会话与工作树分离**：20 个闲置 worktree、2 个运行会话时分别统计；新增纯源码 worktree 不增加 Agent 数量。
- [x] **task 与会话分离**：多个顺序 task 能交给同一 worker，压缩上下文不凭空产生新实例或释放其常驻占用。
- [x] **共享进程与进程树**：subagent 共用宿主时不重复计算整个 RSS；浏览器、LSP、MCP、构建子进程按实际归属纳入。
- [x] **嵌套并发**：10 个 Agent 同时到达构建阶段、预算仅允许 2 项时，其余重任务排队；每项 jobs/workers 的限制实际生效。
- [x] **增量预算**：有效剩余内存 10 GiB，额外保护 2 GiB，未兑现增长/预留 2 GiB，则可新增内存预算为 6 GiB。新会话 1 GiB、构建附加 3 GiB 时，“2 个新会话 + 1 个构建”使用 5 GiB，“2 个新会话 + 2 个构建”使用 8 GiB 不可准入；其他维度另检，已有占用不重复扣。
- [x] **共享磁盘**：多个 worktree 在同卷时不重复相加余量，依赖/产物增量与共享缓存分开；为集成树和临时峰值保留空间。
- [x] **多项目共享主机**：两个 Lead 不能各自使用同一份完整快照；没有公共协调能力时说明覆盖边界并保守安排新增。
- [x] **运行时与 API 边界**：Codex/Claude/Grok/Copilot 等限制按实际版本和作用域记录；API 额度未知时不当无限，也不把硬件估算自动降为“机器只能 1 个”。
- [x] **校准不放大未知**：只校准已经授权、可停止、有范围边界的代表任务；没有样本、任务过早退出或漏过关键峰值时不产出虚假的零成本。
- [x] **压力退让**：余量低于保护线或持续压力时允许可新增为 0，停止新派发及重试风暴；等待超时不能强制启动。
- [x] **现有数量超出新建议**：当前 5 个会话、重算后建议 3 个时，同时保留这两个事实并报告可新增 0；不抬高建议，不因生成报告直接结束会话。
- [x] **实际回收**：会话退出但 worktree/后台服务保留时，只归还确认释放的部分；普通只读报告不触发清理。
- [x] **刷新与持久化**：换主机、升级依赖、改变 worker、恢复旧任务或完成回收后重新核对；沿用权威报告，不在每个 worktree 复制全机预算。
