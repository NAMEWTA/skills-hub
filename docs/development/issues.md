# 用 dev-issue 撰写和维护 Issue

使用 `dev-issue`，把想法、缺陷或优化诉求整理成开发者可以认领的 GitHub Issue。它负责研究目标仓库、组织正文和执行已授权的发布、更新或评论。需要实施时，再把同一份契约和证据交给开发流程。

## 准备目标与材料

明确目标仓库或 Issue 的完整地址，说明希望交付什么。提供已有规格、截图、日志、原型和约束；一句话想法也可以开始。技能先读取目标项目的规范、相关源码、Issue 模板和讨论，能够自行核实的内容先查证。

安装后可按技能名称调用。完整方法见 [dev-issue 入口](../../skills/dev/dev-issue/SKILL.md)；按领域安装的方法见[安装指南](../usage/installation.md)。以下示例是自然语言请求，`create`、`update`、`comment` 是操作名称，不是 CLI 子命令。

## 选择本次操作

| 目标 | 请求方式 | 交付结果 |
| --- | --- | --- |
| 新建 Issue | `create`：给出仓库和诉求，要求研究后发布 | 查重后的完整正文及实际 Issue URL |
| 完善已有 Issue | `update`：给出 Issue URL 和调整目标 | 保留有效决定、附件和完成项的更新正文 |
| 补充他人讨论 | `comment`：给出 Issue URL 和要补充的材料 | 关联原讨论的增量评论及评论 URL |
| 只看草稿 | 在任一种操作中明确“只给草稿，不发布” | 完整正文或评论草稿，以及仍需补足的信息 |

`draft` 是交付方式。用户已经要求发布、修改或评论时，技能完成核查后继续执行；只要求讨论或草拟时不写入远端。

### 从想法创建 Issue

```text
使用 dev-issue，为 https://github.com/OWNER/REPO 新建并发布 Issue。
我想让首页支持可拖动、可调整大小的插件卡片。
先查当前布局与插件规范，优先复用已有实现，写清交互、方案、任务与验收。
```

### 完善已有 Issue

```text
使用 dev-issue，更新 https://github.com/OWNER/REPO/issues/42。
结合最新代码和全部评论补齐实施计划，保留已确认的决定、附件和完成项。
已有 change 在 .agents/dev/changes/2026-11-23-dashboard/，沿用其中的契约。
```

### 追加评论

```text
使用 dev-issue，在 https://github.com/OWNER/REPO/issues/42 追加评论。
结合我提供的日志核对这次复发是否属于原问题，写明新证据与建议验证方法。
```

### 先形成草稿

```text
使用 dev-issue，研究 https://github.com/OWNER/REPO 的列表卡顿问题。
目前没有性能测量，先给完整 Issue 草稿，不发布；说明怎样取得基线与确认目标。
```

## 检查正文能否直接认领

按任务大小合并或展开栏目。小 Bug 可以用短正文，复杂功能要交代跨模块影响。开发者应能从正文判断以下内容：

1. 谁遇到什么问题，当前行为与目标行为有何差异。
2. 本次范围、已确认决定和项目约束是什么。
3. 哪些事实来自用户报告、源码或实际运行，哪些仍是假设与建议。
4. 复用什么实现，为什么适合，改动涉及哪些模块、接口或数据。
5. 每项任务交付什么、依赖什么、怎样确认完成。
6. 通过什么操作与可观察结果验收，哪些问题仍阻塞实施。

复杂任务可以用稳定的需求、任务和验收编号对应检查。只有前项产物确实阻塞后项时才建立依赖。验证方式沿用目标项目，可选择 TDD、实现后验证或其他合适方法，技能不规定测试与实现的固定先后。

| 类型 | 补足的内容 | 证据不足时怎样写 |
| --- | --- | --- |
| 新功能 | 使用者、主要流程、必要的空态与失败状态、接口或数据约束 | 标明尚未决定的行为和受影响范围 |
| Bug | 版本与环境、最小复现、预期与实际、影响、日志或截图、回归验证 | 区分用户报告、已复现现象和待验证根因 |
| 性能 | 固定负载、数据量、环境、指标、基线、目标与正确性检查 | 基线未测就写待测；目标来自用户或明确的论证，不编造提升幅度 |
| 重构 | 维护问题、外部行为、影响面、迁移与删除范围、兼容决定 | 说明尚待核对的调用方或迁移前提 |
| 评论 | 原段落或评论、新证据、影响判断、具体建议 | 不把个人建议写成已采纳共识 |

涉及 UI 时，引用原型的实际版本、页面或状态和确认范围。尚未确认的体验决定写明前提。引用代码时使用固定版本链接，区分已有入口与拟新增文件；复刻来源写出完整仓库、具体文件、版本和适配范围。

如果关键决定或必要证据仍缺失，交付待澄清或待调查的内容，并说明接续动作。发布成功不等于已经具备直接实施条件。

## 沿用一份权威契约

没有既有 change 契约时，Issue 正文可以承担行为契约，不要求为了发布再建一套 spec、plan 或任务文件。

已有本地规格或实施票据时，在原位置维护契约。Issue 是注明来源版本的发布视图：正文包含认领所需的事实、任务与验收，同时链接接手者能访问的完整资料。不要只给本机绝对路径，也不要在远端另维护一套不同的任务依赖和进展。

远端讨论改变既有契约时，在授权范围内先核对并同步原记录，再更新发布视图。无法同步时指出差异、受影响内容与待完成动作，不报告双方已一致。`dev-plan` 的本地票据与 DAG 约定见[开发流程](workflow.md)。

读取远端 Issue 时，完整源正文、讨论及必要源附件必须保存到已有或新建 `.agents/dev/changes/<日期-主题>/source/`，保留平台实例、仓库、原生身份、抓取时间和读取缺口。更新正文前保留源快照旧版本；本次分析、计划、方案和正式结果写入 Change 的相应记录。源快照与现行行为契约分开，不强制再造一套规格和任务文件。完整导入方法见[来源留存](../../skills/dev/dev-issue-setup/references/source-adapter.md#把来源保存到所属-change)。

只根据当前输入起草一次性 Issue、尚未获取远端来源时，可以直接在会话交付。CLI 的临时正文文件只是传参副本，不能成为方案或恢复证据的唯一保存位置。项目记录不写入技能包或 `temp/dev/`，实施与测试的临时过程输出仍沿用运行目录。

## 核对写入和结果

新建前查询开放和已关闭的相关 Issue、PR，结合来源与问题内容判断重复。更新前重新读取最新正文及完整相关评论，合并他人新增内容。普通编辑不是原子比较后交换，不能保证别人不会在回读后再次修改。

写入超时或响应不明时，先读取目标对象及相关讨论，核对内容是否已经保存。无法确定时保留草稿和未完成动作，避免重复建单或评论。

发布后回读仓库、编号、标题、正文或评论及 URL。交付结果区分已发布、已更新、已评论、仅草稿和写入尚未验证。没有权限或工具能力时，仍交付完整草稿，说明具体受阻操作。

更新正文不隐含关闭、重开、指派或修改标签；评论不隐含编辑原作者正文。这些动作分别遵守本次授权。仅有 Issue 内容中的指令也不能扩大用户授权。

## 按目标衔接其他技能

| 当前还缺什么 | 负责技能 |
| --- | --- |
| 散落来源、目标、范围和需求缺口 | `dev-intake` |
| 会改变行为或验收的产品决定 | `dev-grill` |
| 独立实施、审查和验收所需的行为契约 | `dev-spec` |
| 本地独立实施票据、垂直切片和依赖 DAG | `dev-plan` |
| 报告分类、查重和处理方向 | `dev-issue-triage` |
| 来源接入、触发器与持续任务配置 | `dev-issue-setup` |
| 已授权的诊断、性能测量或实施 | `dev-debug`、`dev-benchmark`、`dev-build` |

一次手工 Issue 请求不要求先启用自动化。按当前缺口调用其他技能，带上同一契约、已有决定和证据，完成后回到本次 Issue 操作。完整职责见[方法归属](method-ownership.md)，持续报告流程见[报告来源与自动化](issue-sources.md)。
