# 开发阶段路由

记不住每项技能，就来问。

本文使用功能名称标识操作分支，不要求安装同名技能。实施前从本包资料索引读取对应完整方法；需求澄清、术语整理等按本文步骤与入口的工作约定直接完成。

**流程**是穿过若干技能的路径。多数路径沿着一条**主流程**前进，两条**接入路径**汇入其中。其余技能独立使用，或作为底层词汇层运行。

## 主流程：想法 → 交付

大多数工作的路径。你有一个想法，希望把它做出来。

1. **`记录式需求澄清`** 用访谈打磨想法。只要**在工作目录中工作**，就从这里开始：它有状态，沿用项目术语表与 ADR；没有约定时，将确认术语映射和必要决策放 `.agents/notes/`。没有工作目录？改用“独立技能”中的 `需求访谈`。两者运行相同的 `逐轮追问` 基础方法；`记录式需求澄清` 会留下书面记录，因此只要存在仓库可存放记录，它就是更好的选择。
2. **分支：所有问题都能在对话中解决吗？** 如果某问题需要可运行的答案，例如状态、业务逻辑或必须亲眼看到的 UI，就绕道原型，并在往返两端用 **`交接`** 连接。原型与生产代码隔离。只有更换宿主、目录或实际需要独立会话时才交接；同一会话可直接运行原型并带回证据，参见阶段边界：
   - 需要跨会话时先按本包交接方法保存状态，再基于该文件继续；否则在当前会话保留原始问题。
   - 用 **`原型验证`** 以一次性代码回答问题。
   - 将原型所得证据带回原需求；跨会话时用本包交接方法，否则直接引用产物。
3. **分支：实现需要多个会话吗？**
   - **需要** → **`形成规格`** 把对话转成规格，再用 **`垂直切片`** 拆成曳光弹任务，每个任务声明自己的**阻塞依赖**。随后可选两种执行方式：
     - 每个任务使用 **`按规格实施`**，任务自包含后，可在合适阶段边界使用宿主支持的上下文整理方式；没有该能力时保留恢复点继续。本地跟踪器是 `.agents/changes/<日期-主题>/tasks/` 中每项一个文件，手动先执行阻塞者；真实跟踪器把依赖表示为原生阻塞关系，因此所有阻塞者完成的任务都可领取。每个任务自包含，前一个任务的上下文可以丢弃。
     - 用 **`任务图实施`** 一次运行整个规格。它把任务视为**任务图**，在就绪**前沿**并行运行实现子智能体，全部落在一个**集成分支**上。希望编排整个构建而非亲自逐项驾驶时使用。
   - **不需要** → 在这里、同一个上下文窗口中运行 **`按规格实施`**。

   两种方式都先明确当前任务要达到的行为与验收，再按目标、风险和反馈成本选择方法：规格推进、测试先行或直接实现。适合测试先行时使用本包 [测试驱动方法](tdd-method.md)；每个循环只处理一个行为。以规格和规范两轴审查收尾：单个任务完成后审查相关差异，整个任务图完成后审查集成结果。

   工作以拉取请求发布时，**`PR 证据`** 塑造正文：能展示变化的最小视图、证明有效的前后证据，以及单向门还是双向门的判断。需要 PR 时读取本包的 PR 交付方法。

4. **`迭代复盘`** 闭合循环。构建后，尤其过程偏离轨道时，它回顾会话，建议改进智能体的**环境**，而不是代码：导航指针、自动检查、`两轴审查` 执行的编码规范、引导文件、工具。机械错误变为确定性检查，判断类问题变为编码规范。下一轮构建从更好的环境开始。

### 上下文卫生

追问、规格和任务尽量保留同一套原始思考；上下文仍足够时直接继续。接近实际窗口限制或任务已经自包含时，在阶段边界按本包阶段边界方法整理，使用宿主确实支持的压缩、清空或独立上下文。每项任务都应自包含，但不要求每次实施必须新开会话；无对应工具时保留恢复点继续。`迭代复盘` 应在其所回顾的会话内、清空前运行；清空之后则指向该会话日志。

限制因素是**有效推理上下文**：模型仍能敏锐推理的窗口，阈值取决于实际宿主、模型及任务复杂度。如果在 `垂直切片` 之前会话已接近这个区间，不要在能力下降后硬撑；在最近阶段边界执行 `压缩上下文` 再继续，参见阶段边界。

## 接入路径

某种起始情况产生工作，再汇入主流程。

- **缺陷和请求堆积** → **`输入分诊`**。它让事项经过分诊角色，产出可交给智能体的事项，稍后由 **`按规格实施`** 接手。

  分诊只针对**不是你创建的**事项：缺陷报告、收到的功能请求，以及其他原始输入。`垂直切片` 产出的任务已经可执行，**不要再分诊**。

- **某个东西坏了** → **`根因诊断`**。用于难题：第一眼看不懂的缺陷、间歇性失败、两个已知正常状态之间引入的回归。它在建立**紧凑反馈循环**之前拒绝凭空推理；循环是已能因**这个**缺陷变红的一条命令。存在正确接口时先用回归测试锁定故障，再依据证据修复；真实运行复现更合适时沿同一路径验证。修复后在同一会话运行 **`迭代复盘`**，追问什么本可防止缺陷；如果真正发现的是没有合适接缝来锁住行为，就交给 **`架构改善`**。

- **巨大而模糊的工作：全新项目或大型功能，一个会话装不下** → **`复杂决策规划`**，这里认知要求最高的流程。从当前位置到终点的路还不可见时，它在事项跟踪器建立由**决策任务**组成的**共享地图**，逐个解决，产出**决定而非交付物**，直到迷雾退去、路径清楚。**`记录式需求澄清`** 打磨一个会话能容纳的想法，复杂决策规划 处理装不下的想法，速度更慢、内容更密集，所以只在这种情况使用，不用于范围明确的功能。

  地图清晰后，**它交接，不构建**：在 **`形成规格`** 汇入主流程，把地图中的链接决定收敛为可构建计划，再照常 `垂直切片`、`按规格实施`。从地图直接跳到 `按规格实施` 会略过收敛、丢掉链接细节，因此只有工作最终确实很小时才直接实现。

## 代码库健康

不是功能工作，只是维护。

- **`架构改善`** 在有空时运行，让代码库持续适合智能体操作。它发现**加深机会**；选中一个就**生成想法**，可从 `记录式需求澄清` 进入主流程。它是寻找候选对象的勘察；下方 **`模块设计`** 则是设计选中对象的工作台。

## 底层词汇

领域词汇和模块设计作为基础参考，各自维持一个事实来源。当问题是**用词**而非流程时直接使用，或者让上层技能加载。

- **`领域词汇整理`**：打磨项目的**领域**语言，质疑模糊术语、解决一个词做三件事的多义情况，例如 account，把难逆转的决定记录为 ADR。它是 `记录式需求澄清` 用来保持 项目已有术语表（无约定时为 `.agents/notes/glossary.md`） 纯粹的主动实践。
- **`模块设计`** 是设计模块**形状**的深模块词汇：模块、接口、深度、接缝、适配器、效能、局部性；大量行为位于清楚接缝处的小接口后面。规格实施、测试驱动开发和架构改善都使用这套语言。

## 阶段边界

**阶段**是会话中的一块工作，例如追问、实现、质量检查。两个阶段的**边界**有五种选择；在它们之间选择，是整张地图里最模糊的决定：

- **继续**：留在当前会话。无成本、无损失。
- **`清空上下文`**：当这里的内容对下一步无关时清空窗口。
- **`交接`**：写一份可移植 Markdown。适用范围窄，只用于**更换宿主**、**更换目录**、交给**同事**，或在**阶段中途**分出旁支任务。换来的是可移植性。
- **子智能体**：把范围紧凑的任务交给独立窗口，拿回报告。
- **`压缩上下文`**：压缩当前上下文，并以摘要初始化新会话。它是**默认落点**，位于决策树底部，而不是首先使用。

阅读 [phase-boundaries.md](phase-boundaries.md)，查看有顺序的决策树：五个问题、每个分支背后的理由，以及为什么一手资料的损失成本使**继续**成为首先应排除的选项。**在**边界作决定；阶段中途就继续，或把剩余工作分给子智能体。

## 可独立执行的操作

完全脱离主流程。

- **`需求访谈`**：与 `记录式需求澄清` 相同的深入访谈，但**无状态**；不在本地保存，也不建立 项目已有术语表（无约定时为 `.agents/notes/glossary.md`）。**不在工作目录工作**时使用，例如打磨计划、设计、文字，任何没有仓库承载的事情。如果已有工作目录，就用 `记录式需求澄清`：同样的访谈又留下书面记录，因此是更好的选择。
- **`逐轮追问`** 是访谈基础方法本身：轮次、前沿、事实由智能体查、决定由你做。`需求访谈` 和 `记录式需求澄清` 是两个命名入口；`输入分诊`、`复杂决策规划`、`架构改善` 内部都会运行。只在想要不带包装的访谈时直接使用。
- **`原型验证`** 是小型一次性程序，回答一个设计问题：状态模型是否合理，或 UI 应该长什么样。一次性约束的是代码编写方式，不承诺销毁它：答案融入真实代码，原型本身留在主分支外的 `prototype/<name>` 分支作为**一手资料**，实现事项指向它。它是主流程第 2 步的绕行，但任何纸面难以解决的设计问题都可以用。
- **`证据研究`**：把阅读调查委派给**后台智能体**，它基于**一手来源**研究问题，再在仓库留下一份有引文的 Markdown。它阅读时你继续工作。产出文件可带入 `记录式需求澄清` 的主流程，因为研究为思考提供材料，而不是代替思考。
- **`问卷收集`**：阻塞信息不在你脑中或代码库中，而在**别人脑中**时，写一份让对方填写的问卷。它是 `需求访谈` 的反向形式：不是就主题采访你，而是就**发送任务**采访你——发给谁、需要什么反馈——再把问题瞄准信息缺口。返回内容可作为 `记录式需求澄清` 或 `形成规格` 的材料。
- **`人工操作指引`**：用于只有**人**能做的步骤，例如配置基础设施、设置凭证或 CI 密钥、点击不熟悉的第三方控制台、执行一次性迁移或切换。它生成交互式 bash 脚本，逐个打开 URL、收集值、写入 `.env` 和 GitHub secrets，使操作流程不必每次重新向智能体解释。遇到确实只有人能完成的障碍时，先准备可检查步骤，再说明需要用户完成的具体动作；不要求一个不存在的自动调用技能。智能体能自己做的就自己做；这里用于人确实必须参与的情况。
- **`重新解释`**：纠正没有被理解的消息。可在任何技能内、对话中途使用，智能体会补上缺失上下文，以通俗中文和项目术语重新解释刚才的话。它是事后补救；`记录式需求澄清` 是事前解法，因为提早约定共享语言，就能防止术语突然出现。
- **`模块学习`**：使用当前目录作为有状态工作区，跨多个会话学习一个概念。
- **`智能体文档写作`**：编写智能体消费文档的参考，包括技能、AGENTS.md 和被指针引用的文档。

## 前置条件

先复用当前项目的任务记录和文档布局；没有时使用轻量 Markdown，不强制初始化外部跟踪器或复杂状态协议。

按任务选择本包完整方法见 [资料索引](method-index.md)，能力与授权边界见 [本地执行支持](execution-support.md)。
