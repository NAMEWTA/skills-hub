# 复现并修复问题

等待来源线程中可信的分诊标记。通过目标应用的真实 UI 复现精确症状。存在已有修复时，验证它。只有确认复现后，才尝试范围受限的修复。

加载自动化提供的外部 Benny 配置。如果配置、所需动作、控制适配器或填写完整的功能映射缺失，则停止，不执行后续动作。

## 不可违反的安全规则

- 在开展任何工作之前，固定来源频道和根线程坐标。
- 绝不在来源频道发布根消息。
- 每次向来源线程发帖之前，都检查来源父消息。
- 协调者是唯一可以向 Slack 发帖的执行者。
- 委派的分析工作者只能读取，并返回发现或媒体说明。
- 修复阶段的代码工作者只有在其环境可以证明不包含 Slack 凭据和任何 Slack 写入动作时才能编辑。否则由协调者编辑。
- 每个子任务提示都必须明确禁止 `SendSlackMessage`、`PostToSlack`、`chat.postMessage` 和所有其他 Slack 写入。
- 绝不给子工作者 Slack 令牌、发帖指令、用于发帖的来源坐标或向外报告的许可。
- 如果子工作者需要 Slack 写权限才能运行，不要启动它。
- 工具机器人是证据来源。除非有人明确把修复委派给它们，否则它们不拥有修复任务。
- 能区分正确与错误的精确症状，必须通过真实 UI 交互出现两次。
- 状态检查可以确认观察结果，但不能注入或强行制造症状。
- 没有确认复现，就不编写修复。
- 已有拉取请求或提交会使运行切换到验证模式。不要在其上另写修复。
- 使用 `github.com` 拉取请求链接。
- 不要把截屏、录像、日志和令牌纳入源码版本控制。
- 对委派分析使用 pstack 的 `principle-guard-the-context-window`。
- 在复现、修复和验证过程中应用 pstack 的 `principle-sequence-verifiable-units`、`principle-fix-root-causes` 和 `principle-prove-it-works`。

## 1. 固定来源坐标

在制作工作清单或委派之前：

1. 要求触发频道等于已配置的来源频道。
2. 如果存在 `trigger.thread_ts`，将 `SOURCE_THREAD_TS` 设为该值；否则使用 `trigger.ts`。
3. 要求 `SOURCE_THREAD_TS` 非空。
4. 将 `SOURCE_CHANNEL_ID` 和 `SOURCE_THREAD_TS` 保存为不可变值。
5. 读取来源线程，并验证其根消息恰好具有这些坐标。
6. 获取来源永久链接。

绝不把这些值替换为回复时间戳、运维时间戳或状态消息时间戳。

每次向来源频道发帖之前：

1. 使用不可变坐标读取线程。
2. 确认父消息存在、未被删除，而且仍属于来源频道。
3. 只能使用 `channel=SOURCE_CHANNEL_ID` 和 `thread_ts=SOURCE_THREAD_TS` 发送。
4. 再次读取线程，验证新消息是一条回复。

如果任何检查失败，不发布任何消息。绝不改在根层级或后备频道重试。

## 2. 等待分诊契约

在配置的结论等待预算内观察来源线程。等待期间保持安静。

只有以下条件成立时才接受结论：

- 作者与 `slack.triage_identity_user_id` 匹配。
- 它是 `SOURCE_THREAD_TS` 之下的一条回复。
- 它恰好包含一个已配置的标记。

公开标记形式：

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

只有 `bug` 或 `performance` 才继续。记录可选的追踪器 URL。遇到 `other`、没有结论、不可信作者、冲突标记或超时，安静地停止。

此标记替代了私有机器人身份和自由格式的结论匹配。

## 3. 检查任务归属和修复工件

在开始工作前立即重读线程。

### 有人明确正在修复

当某人明确认领修复、给出具体实现计划，或要求另一智能体实现、打补丁、修复或打开拉取请求时，停止。

不要把以下情况视为修复归属：

- 机器人总结证据。
- 工具查找日志或工单。
- 有人要求机器人诊断、解释、检查或复现。
- 机器人发布原因假设，但没有同意实现修复。

判断请求的动作，而不是看是否出现机器人。

### 已有修复工件

如果开放的拉取请求或已经合入的提交可能修复这份报告，切换到 `references/verify-existing-fix.md`。

工件可能来自线程、追踪器问题、仓库历史或拉取请求搜索。没有提交或拉取请求的口头声称不是修复工件。

如果有人拥有这项工作，但还没有产出工件，则停止。不要与其竞速。

## 4. 开启可选的运维线程

如果配置了 `slack.operations_channel_id`，协调者可以在那里创建一条根状态消息。这是复现流程中唯一允许的根消息。

将其坐标保存为 `OPERATIONS_CHANNEL_ID` 和 `OPERATIONS_THREAD_TS`。绝不把它们与来源坐标混淆。

使用配置中的普通 Unicode 状态字符串。保持状态文本简短：

- 正在复现
- 未能复现
- 受阻
- 已复现
- 正在验证已有修复
- 正在尝试范围受限的修复
- 已打开草稿拉取请求
- 修复未能交付

优先使用配置的 Cursor Slack 动作。只有当用户为狭窄的缺失能力配置了 `BENNY_SLACK_BOT_TOKEN` 时才使用它，例如只编辑这一条状态消息。绝不把令牌暴露给工作者。

如果没有配置运维频道，把详细状态保留在自动化运行输出中。不要改在来源频道发布根消息。

## 5. 加载并检查控制适配器

阅读 `references/control-adapter.md` 和位于 `control.feature_map_path` 的完整映射，然后调用 `control.skill_name` 指定的技能。

找到与报告中的用户路径匹配的功能映射章节。在操作应用之前先阅读它。如果没有章节覆盖该功能，将运行标记为受阻，而不要编造路径或选择器。

要求具备全部七种能力：

1. 启动配置的目标应用和测试环境。
2. 导航到映射的功能，并操作其记录的状态。
3. 通过点击、输入、按键、滚动、拖动、调整大小或导航操作真实 UI。
4. 检查状态但不修改它。
5. 捕获截图。
6. 开始和停止屏幕录像。
7. 清理进程、会话、配置文件和临时数据。

如果适配器不存在，或任一所需能力缺失，将运维状态标记为受阻并停止。不要把截图、单元测试、状态修改或源码阅读冒充为 UI 复现。

## 6. 研究报告

阅读完整来源线程，以及存在的追踪器问题。

收集：

- 精确的操作路径
- 预期行为
- 观察到的行为
- 两者分歧处可以区分结果的状态
- 发生频率
- 版本、环境和平台
- 附件和错误特征
- 候选代码领域

检查截图和视频。有帮助时，使用只读并行工作者研究代码历史、测试思路、影响范围和媒体。给每个工作者一个聚焦的问题，并禁止它向 Slack 写入。

使用 pstack 的 `how` 技能在仓库中追踪操作。对回归历史和防御性代码使用 `why`。形成互相竞争的原因假设，并找出可以区分它们的证据。

## 7. 复现

通过控制适配器启动目标应用。

操作前，确认应用、工作区、账户、数据集和功能状态都正确。使用稳定的应用标识。不要只依赖窗口顺序或熟悉的标题。

通过真实 UI 操作执行报告中的路径。

在宣称已复现之前：

1. 说清正确的最终状态。
2. 说清错误的最终状态。
3. 到达两者分歧的位置。
4. 观察错误状态。
5. 重置足够的状态，使第二次尝试独立。
6. 重复相同路径，再次观察到相同错误状态。
7. 可能时，用真实状态值交叉核对。

预期的对话框、加载状态或设置步骤并不是缺陷。捕获能够区分正确行为与错误行为的最终状态。

使用配置的复现预算。如果症状未在预算内复现，报告明确的“未能复现”结果。如果环境无法提供某项所需能力，报告“受阻”，并说明缺失了什么。

## 8. 捕获并审阅证据

对于成功的复现：

- 记录出现症状的完整路径。
- 截取错误最终状态的截图。
- 保存一条简短说明，记录精确步骤和观察到的状态。
- 将工件保存在配置的临时工件目录。

让只读媒体审阅者回答一个问题：证据是否可见地展示了能区分错误的最终状态？

如果答案是否或不确定，复现就尚未确认。捕获更好的证据，或使用“未能复现”。

只有配置了运维线程时，才把详细证据发布到该线程。来源更新保持简短。

## 9. 报告复现结果

先更新运维状态。

对于“未能复现”或“受阻”，不在来源线程发布任何内容。由运维线程或运行输出承载结果。

对于确认的复现，执行来源预检，并最多主动发布一条来源回复：

- 说明问题已复现。
- 存在运维证据线程时链接它。
- 最多包含三条简短发现。
- 存在追踪器问题时链接它。
- 默认不提醒负责人。

只有当配置的 Slack 动作能使附件保留在同一个来源线程中，且组织保留策略允许时，才附上证据。

等待配置的异议窗口。如果有人证明设置或解释有误，更正复现一次。在窗口结束且没有有效异议之前，不开始修复阶段。

## 10. 验证已有修复

存在修复工件时，遵循 `references/verify-existing-fix.md`。

验证必须展示基线上存在症状，而修补后的构建上不存在。两条路径都通过真实 UI 各执行两次。

不要编辑已有修复、添加竞争补丁，或打开替代拉取请求。

## 11. 判断能否进行范围受限的修复

只有以下条件全部成立时才尝试修复：

- 结果是明确确认的复现。
- 媒体审阅确认了错误最终状态。
- 没有出现已有修复工件。
- 在异议窗口内没有人认领修复。
- 运行时证据识别出了根因。
- 可能的变更符合配置的修复预算和仓库范围。
- 控制适配器能够运行基线和修补后的构建。

如果任一条件不成立，保留复现报告，停止且不创建拉取请求。

通过门槛时，将运维状态更新为“正在尝试范围受限的修复”。

## 12. 定位根因并实现

协调者负责每次 Slack 发帖、最终差异审查、提交和拉取请求。

只读工作者可以：

- 追踪代码和历史
- 提出测试方案
- 绘制影响范围
- 审查差异
- 审阅媒体

它们不编辑、不执行外部写入、不发布状态，也不拥有修复。

只有当工具隔离从工作者环境中移除了 Slack 凭据和所有 Slack 写入动作时，才可以在这个阶段委派范围严格限定的代码编辑。提示仍必须明确禁止 Slack 写入。协调者审查编辑，并执行或核验所需测试。如果工具隔离不确定，编辑由协调者完成。

通过运行时证据确认机制。在编辑之前排除竞争假设。

用最小的、有理由支持的变更修复根因。

- 存在成本低的本地测试目标时，调用 pstack 的 `tdd` 技能，在修复之前编写失败测试。
- 当路径昂贵、不清楚或高度依赖集成时，说明跳过 TDD 的原因。
- 排除无关清理。
- 如果变更超出配置的工作量或风险预算，停止。

## 13. 证明修复

保留原始基线证据。

在修补后的构建上：

1. 执行相同的真实 UI 路径。
2. 重复两次。
3. 展示错误状态已经消失。
4. 展示预期状态已取而代之。
5. 捕获修复后的录像和截图。
6. 交叉核对基线所使用的同一个真实状态值。

编译、单元测试、代码审查或看起来合理的差异，都不是修复后的证据。

先运行聚焦测试，再对变更行为周围的影响范围做冒烟验证。覆盖变更可能影响的相邻状态、输入、权限、平台和失败路径。如果仍有回归，则停止，不创建拉取请求。

## 14. 打开草稿拉取请求

只有具备修复前后证据后才执行：

- 审查最终差异，检查无关变更和秘密信息。
- 运行仓库要求的检查。
- 仓库工作流允许时，创建按顺序排列的小提交。
- 打开草稿拉取请求。绝不从本工作流合并或部署。
- 使用追踪器支持的拉取请求语法，链接配置的追踪器问题。
- 使用配置的公开 URL 形式，通常为 `https://github.com/{owner}/{repo}/pull/{number}`。
- 包含复现步骤、根因、测试结果、修复前后证据和影响范围检查。
- 对拉取请求文本和所有 Slack 更新使用 pstack 的 `unslop` 技能。

如果创建拉取请求失败，不要宣称成功。将提交或分支状态保留在运行输出中，并将运维状态标记为“修复未能交付”。

成功时，将运维状态标记为“已打开草稿拉取请求”，在运维线程中发布一条带拉取请求链接的简短回复。不要创建第二条来源频道根消息，也不要主动追加来源回复。

## 15. 后续处理与清理

在一个后续窗口内观察已配置的运维线程。

- 使用已收集的证据回答直接问题。
- 如果一项具体更正使原设置失效，应用该更正，并重新复现一次。
- 不参与人工协调和旁支闲聊。
- 被要求停止时停止。

始终调用控制适配器的清理能力。工件的保留时间不得超过配置的保留策略。
