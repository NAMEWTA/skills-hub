# 检查示例与反例

所有名称均为演示，不代表已发现的真实资产。

## 一个项目跨两台机器

shop/prod 的 API 在 host-a、worker 在 host-b，共享 redis-main 也在 host-b。用户问“项目是否正常”：

1. 沿用项目已有组成与消费范围；不将同机的 billing-worker 自动归入 shop。
2. API 就绪正常；worker 进程运行，但最近十分钟消费数为零且积压增长；Redis PING 正常。
3. 报告“项目异步消费路径异常，API 与 Redis 的已检查路径正常”，并保留时间窗与队列证据。不能汇总成“两个服务绿色，因此项目正常”。
4. 已授权继续排查时，把原路径及证据交给 ops-diagnose；不直接重启 worker。

## 没有指标不等于健康

主机查询成功，应用指标超时，采集器状态未知。结果是主机已检查、应用数据缺失；不能将空数组当零错误，也不能仅凭采集器失败宣布应用故障。

## 声明与现场不一致

手册写 image: api:stable，现场容器 image ID 与前次观测不同。保留本次 image ID、声明来源与采集时间。该检查没有证明是否经过项目正常发布，也不授权换回旧镜像。

## 访问失败与日志秘密

某主机 journal 权限不足：保存命令范围、时间和拒绝结果，不通过自动 sudo 扩权。另一主机日志包含连接串：只保留经脱敏的错误类型和时间/关联 ID，原文留在有权限控制的来源。
