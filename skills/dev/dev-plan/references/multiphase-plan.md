**本分支先形成实施计划，由负责人按计划执行，以证据核对进展。** 用户只要求计划时，计划就是交付物；用户已要求持续实施时，计划完成后继续已授权工作。

## 规划步骤

1. 改动只有一两个文件且方案明显时，用简短行为说明代替多阶段计划，并按当前授权继续。
2. 写作前先解决影响计划的开放问题：能用现有代码或一手资料查明的，沿用或补齐事实；需要可运行答案的使用 `dev-build`（原型方法）。在附录 A 保留原型的实际位置、版本和适用的截图或运行证据。只有任何运行都无法解决的产品或偏好问题才询问操作人。给出选项，其他已明确部分继续推进；尚不能明确的问题按[决策地图](uncertainty-map.md)记录，不假定已有答案。
3. 可用时用独立子智能体探索相关模块，没有时自行按范围调查。返回文件指针、约定、已有验证命令和入口点，避免把整段源码复制进计划。按实际能力与任务复杂度分工，不依赖指定模型或宿主。
4. 把下方骨架复制进计划文件，保留适用标题与子块的顺序，填完保留部分的占位符。除非用户本次明确指定其他路径，否则统一写入 `.agents/dev/changes/<YYYY-MM-DD-slug>/plan.md`。没有 PR、并行或人审的工作不生成这些操作；不适用的验证维度说明原因，不为凑栏目虚构工作。每个实际交付单元一节；使用 PR 时，一个 PR 就是一个拥有独立证据的改动，在这个边界产出可核对结果。在**如何阅读**中指出执行方式：本地交付、已授权自动合并、交给用户合并的堆叠 PR，或持续项目的分阶段交付；并明确终点与授权。实施由 `dev-build` 负责，持续协调由 `dev-workflow` 负责，PR 与合并操作由 `dev-deploy` 负责。已有切片直接沿用，需要拆分时先用[完整切片方法](vertical-slicing.md)。
5. 正文写成可执行操作指南，解释与参考放附录。每个标题说明任务或发现；使用具体动词、证据与清楚依赖，删掉套话，不建立额外写作工具依赖。
6. 按[计划核对](plan-review.md)对照下方模板：每项有交付、真实依赖、唯一负责人和证据；已有文件与命令已在当前项目核实，拟新增的文件、测试和命令明确标注创建，不冒充已存在。检查构建、可见结果与验证逐项对应，再从规格及用户明确数量反查覆盖与整合归属，修正悬空占位符或无依据的通过结论。独立交接按[单个切片及风险说明](plan-template.md#独立接手与按风险补充)补足必要背景与约束，不要求每个交付单元另建任务文件。项目已有计划检查命令时运行它并修复实际问题；没有时如实报告内容核对，不虚构脚本结果。
7. 给出计划位置、核对结果与剩余决定。用户只要求计划时在这里交付；已有实施授权时按计划继续，不重复要求开始指令。

## 验证选择

**验证。** 验证覆盖本次真实风险；记录适用的静态或单元检查、实际行为及性能证据，不适用的维度说明理由。这句话就是验证规则，每个验证块说明该维度实际证明什么。行为变更需要实际运行证据；纯文字等低风险变更可以直接检查。按风险选择独立验证场景，在实际头提交上操作对应入口；模板保留十个可选场景槽位，生成计划只填写实际选中的场景，其他槽位移除，覆盖需要时可增加，不强制十个智能体。每条场景记录动作、适当证据和通过判据。其中一条是**对照主干的回归通道。** 它在主干和头提交上运行同一个关键场景。若主干没有此功能，通道记录这一事实，并以差异新增的行为及用户等待的最终状态为门禁，不编造主干结果。涉及性能目标或风险时，性能比较必须双侧：主干与头提交都必须产出指定指标。若主干没有此功能，还要隔离差异新增的工作，为该工作和用户等待的端到端状态设置绝对预算。不要对不相同的场景宣称比率。性能块要写清指标、交错执行的探针、先测量的主干基线，以及带有失败数值的规则。交互改变时保存截图或视频；用户明确要求预先审查的，合并前交其审查，否则在持续授权内验证后推进。无需额外人审的 PR 写 `**审查门禁。** 无。<PR id> 无额外人审，按已有授权交付。`，其下不放人审复选框；交互证据仍保留在实际运行块中。

**操作入口。** 按界面选择当前可用的工具：Web 或桌面网页使用浏览器或现有 UI 驱动，CLI／TUI 使用终端，原生移动端使用项目已有模拟器。触及两个界面时验证两者。缺少操作能力时在附录 C 记录真实限制与可行替代，不把无法执行记为通过。
